# 安全发现分诊方法(Triage Finding)

## 目标

针对**已经存在的安全发现**,用静态代码证据对照当前仓库逐条研判。每条输入发现只给一个有证据支撑的结论:

- `confirmed`(成立)
- `not_actionable`(不需处置)
- `needs_review`(需进一步核实)

对 `confirmed` 和 `needs_review` 的发现,还要在各自队列里给一个离散的**可利用性优先级**。

这套方法是为"消化积压的安全发现"服务的。它的起点是用户**已经拿到**的东西:扫描器报告、CVE/漏洞通告、漏洞赏金报告片段、安全工单、或一段自由文本的漏洞声称。它**不是**:对整仓做漏洞扫描、做动态验证、写修复、做看板或队列管理。

## 范围:这是"积压消化",不是"逐个孤立分诊"

当用户一次给来多条发现时,把它们当成**一个整体的积压消化问题**,而不是一堆互不相干的单次分诊。目标是:把嘈杂的现成发现源,变成一份**带证据、可排序的处置队列**;同时为了可审计、可呈现,**每条输入保留一条独立结论**。

把工作按"流水线"组织起来:

- **先把整批输入归一化成分诊条目清单,再开始判定。** 这里"归一化"指:给每条发现分配一个分诊条目 ID,保留原始来源 ID 和引用,抽取下文「输入抽取」里列的字段,并把缺失字段**如实记成证据缺口**——绝不为了凑齐字段而**编造**扫描器名、严重度、修复建议等信息。
- 每条归一化条目用静态证据研判,**一条输入对应一条结论**。
- 把 `confirmed` 和 `needs_review` 的结论排成处置队列。
- **本方法不做去重。** 如果输入里有看起来重复的条目,仍然每条输入保留一条结论;去重属于另一套独立流程。

工作量很大、发现很多时,这正是**派子代理**的合适场景:可以用 `create_subagents` 创建多个不同分工,由宿主自动并行做"逐条深研"。但若当前环境不具备派子代理的能力,就**老实说明这个限制**,不要据此声称"已对全部发现穷尽研判"。

## 静态评估的复用准则

研判每条发现时,核心都是同一套静态取证工作:**污点源 → 控制 → 汇聚点(sink)的链路追踪、找最小够用的证据集、可达性分析、边界输入、反向证据(counterevidence)、证据缺口、静态置信度**。把这套取证当成可复用的底座,每条发现都按它来做。

本方法在此之上,额外负责:**外部发现的接入与归一化、积压分诊的三类结论、首轮"不跑运行时"的约束、以及输出契约**。

## 缺输入时怎么办

如果用户没有给任何发现,就**不要**去翻仓库、**不要**下结论、**不要**输出结论清单。

直接请用户提供要分诊的发现,并说明支持的形态:扫描结果、CVE/漏洞通告或漏洞描述、安全工单、漏洞赏金报告片段、任务系统里的安全工单链接或检索条件、或一段自由文本的漏洞声称。顺带可以一并问清楚仓库路径或受影响的文件/组件。

## 输入抽取

开始研判前,先把下面这些信息抽出来:

- 仓库路径,或当前工作仓库
- 输入 ID、扫描器 ID、规则/结果 ID、CVE/漏洞编号、工单 ID 等,有就记
- 标题或简短声称
- 来源类型:`scanner_result`(扫描结果)、`cve`、`advisory`(漏洞通告)、`scanner_ticket`(安全工单)、`bug_bounty`(漏洞赏金)、`freeform`(自由文本)、或 `unknown`
- 被指为脆弱的组件、包、API、文件、路由、类、函数或服务
- 声称的"攻击者可控的污点源"
- 声称的"汇聚点 / 被绕过的安全控制"
- 受影响的版本、路径、配置或部署面
- 必需的前置条件,以及声称的影响
- 用户已提供的现成代码引用、证据、反向证据
- 来源系统的溯源信息:工单/告警链接、告警编号、状态、所属项目、标签、组件、优先级、报告人、时间戳、引入查询等

**只有当仓库路径或漏洞声称含糊到无法去看代码时,才追问一句。** 否则直接去翻仓库,把缺失字段保留为证据缺口。

## 任务系统接入(若发现来自任务系统)

如果发现是从 my-agent 任务系统里来的(用户给了任务链接、任务 ID,或要求"把某批安全工单拉进来分诊"):

- **先把任务正文内容取到,再归一化。** 先从当前 capability registry 确认是否真的接入了对应工单/任务系统工具；有就使用该工具按用户给的链接、ID 或查询条件逐条读取，没有就请用户提供导出内容，绝不编造不存在的任务工具调用。
- 把任务里的漏洞工单归一化为 `source_type: "scanner_ticket"`——除非正文明显属于更具体的输入类型(如 `bug_bounty`、`advisory`、`cve`)。
- **保留来源溯源**:任务 ID、状态、标签、优先级、报告人、时间戳、以及你用来拉取的检索条件,都写进 `input_id`、`references` 和证据/缺口文本里。
- **默认只读接入。** 不要去改任务状态、加评论、转派负责人或改标签,**除非用户明确要求回写**。如果用户确实要回写,**先把所有静态结论做完**,再汇总"计划要做的任务变更",并把"改任务"这一步和"取证分析"严格分开。
- 对来自任务系统的批量接入,最后的简明总结要说清楚:**拉了多少条、用的什么检索条件/任务集合、完整结果写在哪、有没有动过任务**。默认状态是:**未对任务做任何改动**。

## 仓库安全策略闸(研判前必做)

在做静态取证之前,先看目标仓库根目录(或其上层)有没有 `SECURITY.md` 一类的**安全策略文件**。有的话,在追踪污点源/控制/汇聚点/可达性、下结论**之前**先读它。

把安全策略文件当成"本地最权威的依据":它定义了**受支持的安全边界、可信输入、受支持版本、披露范围、加固控制、以及明确不在范围内的面**。用它来判断:一条可达的代码路径,到底有没有跨过项目**声明支持的**安全边界——只有跨过了,才有资格往 `confirmed` 推。如果仓库里没有安全策略文件,就把"无策略文件"这件事记成一个证据缺口,改用次优的本地策略证据(产品文档、威胁模型、披露策略、就近的代码注释等)继续。

## 工作流程

1. 若发现来自任务系统,按上面「任务系统接入」处理:先取正文,保留溯源,归一化到既有来源类型,默认不回写。
2. 把每条发现归一化成分诊条目:
   - 给 `triage_item_id` 赋值,如 `triage-001`。
   - 在 `input_id` 里保留外部来源 ID。
   - **不要**为了凑齐某个字段而编造扫描器字段、严重度或修复建议。
3. 解析出仓库路径和代码版本(有的话)。
4. 跑「仓库安全策略闸」:
   - 在追踪污点源/控制/汇聚点、做可达性分析**之前**,先找安全策略文件。
   - 有就读它,记下相关策略依据(受支持的安全边界、可信输入、受支持版本、加固控制、不在范围内的面)。
   - 没有就把"缺失"记成证据缺口,改用现有产品文档、威胁模型、披露策略、本地注释继续。
   - 如果安全策略文件和可得的本地证据**都没能确定**目标产品面、不可信输入边界、或可信的运维/开发者输入,而这个答案又会**实质影响结论**,就先问几个有针对性的上下文问题,再下结论。
5. 按那套静态取证底座,审最小相关的证据集,记录:污点源、控制、汇聚点、可达性、边界输入、反向证据、证据缺口、静态置信度。
6. **判定产品面和信任边界**:
   - 识别这条路径属于哪种面:命令行工具、库 API、对外服务、本地开发者界面、工具/插件扩展面、示例/演示、测试/夹具、文档、生成代码、外部引入(vendored)代码,还是无法判定。
   - 当包清单、导出、可执行入口、部署文件、产品文档、安全策略、披露策略、威胁模型、就近注释属于"标准做法"或"与本声称就近相关"时,去查它们。
   - 记录:声称的污点源在**预期的产品模型里**到底是"不可信输入",还是"可信的运维/开发者配置"。
7. **追踪声称的污点源、控制、汇聚点、以及可达路径**:
   - 把扫描器/通告的描述当成**声称**,不是证据。
   - 从被引用的代码、清单、版本范围、或用户提供的证据起步。
   - `confirmed` 本就要求可达性。当你主张"可达"时,要记下**可达性锚点证据**:具体的调用方、入口、路由、命令、包导出、部署路径、依赖边,或其它能证明"脆弱条件确实连到了产品面"的仓库事实。
   - 记录支撑证据。
   - 记录会削弱或推翻该声称的**反向证据**。
   - 把没解决的证据缺口**如实记下来**,不要抹平。
8. 套用「判定规则」。
9. 给 `confirmed` 和 `needs_review` 的发现分配可利用性优先级。
10. 对 `confirmed` 的发现,在判定之后,当本地归属证据容易得出时,补一个负责人线索。
11. 汇总成一份输出结果(见「输出契约」),每条输入对应一条结果,保持输入顺序。

## 产品面与信任边界闸(给 `confirmed` 把关)

在判 `confirmed` 之前,先把这条发现的**预期产品面**和**信任边界**分类清楚。

审查**最小够用的证据**,看它落在哪一类:

- **已发布/运行时的面**:包清单、导出、可执行入口、服务路由、部署配置、容器/构建文件、对外 API 文档、产品文档。
- **非产品面 / 可信面**:示例、测试、夹具、文档片段、仅本地的开发者工具、生成/外部引入代码、内部测试脚手架、命令行工具配置、插件/测试工具、或"刻意允许执行代码"的扩展点。
- **仓库安全策略 / 威胁模型**:安全策略文件、安全文档、受支持版本说明、披露策略、威胁模型,或定义"可信输入与受支持边界"的注释。

**只有数据流可达是不够的。** `confirmed` 要求同时满足两条:

1. 在声称的前置条件下,脆弱条件**静态可达**;
2. 污点源跨过了项目**看起来支持**的一道安全边界。

如果这段代码**只能**经由"可信配置、本地开发者界面、示例、测试、夹具、演示应用"触达,就**不要**判 `confirmed`——除非静态证据表明这个面确实是**已发布、已部署、对不可信用户开放、或绕过了一道有文档依据的加固/鉴权边界**。

当边界归类**取决于策略、或本身就不清楚**时,优先判 `needs_review`,并把这份模糊性写进证据缺口。

## 判定规则

**`confirmed`(成立)**:仅当静态证据把脆弱条件连到了"在声称前置条件下可达的代码",且污点源跨过了一道"面向已发布/已部署/有文档依据的产品面"的预期安全边界。**仅仅依赖项里存在某个脆弱组件,不够。**

**`not_actionable`(不需处置)**:仅当静态证据**正面推翻**了这条发现。例如:

- 脆弱的包或功能根本不存在;
- 锁定版本不在受影响范围内;
- 声称的代码路径在本仓库配置下不可达;
- 危险汇聚点被一道相关的校验闸 / 校验器 / 净化器 / 鉴权控制保护住了;
- 扫描器声称指向的是死代码、仅测试、生成、外部引入或未使用的代码,且仓库证据支持这个结论;
- 相关代码仅在示例 / 夹具 / 文档 / 本地 中存在,不随受影响产物发布;
- 污点源是可信配置、命令行参数、仅本地工具的输入,或本仓库安全模型下"刻意允许执行代码"的扩展点。

**`needs_review`(需核实)**:当证据不足、模糊、只能靠运行时确认、取决于策略、取决于环境、或因缺仓库上下文而卡住时。**宁可判 `needs_review`,也不要给一个臆测的 `confirmed` 或 `not_actionable`。**

## 可利用性优先级排序

判定之后,**分别**给 `confirmed` 和 `needs_review` 两个队列各自分配离散的可利用性优先级。

- `confirmed` 的发现走 `confirmed` 优先级队列,标 `P0`、`P1`、`P2`……`P0` 是本批结果里**最可利用**的成立发现。
- `needs_review` 的发现走 `needs_review` 优先级队列,同样用 `P0`、`P1`、`P2`……`P0` 是**最该优先去核实**的未决发现。
- 优先级标号**本身不编码所属队列**。用"所属队列"字段去区分"成立的优先级"和"待核实的优先级"。
- `not_actionable` 的发现**不排序**,所属队列和优先级都置空。

**按可利用性排,而不是只按扫描器给的严重度排。** 优先排:攻击者可达性更清晰、所需权限更低、前置条件更少、污点源到汇聚点的控制更直接、校验闸更弱或没有、且静态证据更可靠地表明"这条利用路径真能跑通"的发现。声称的影响 / 扫描器严重度,只在可利用性其它方面打平时,当**最后的破平依据**。

**结果保持输入顺序**,用优先级字段来体现处置先后,**不要靠重排结果来表示优先级**。

## 负责人线索(仅 `confirmed`)

只对 `confirmed` 的发现,在判定并排好优先级之后,当本地归属证据**容易得出**时,补一条简短的负责人线索。

优先用代码归属文件(如 CODEOWNERS / OWNERS)里的证据。如果归属不清楚,就**宁可不写,也不要瞎猜**。负责人线索只是路由用的附加信息:**绝不能用归属去影响判定、置信度、边界评估或可利用性优先级**。把负责人线索文本放进输出的相应位置(理由、证据或"建议下一步"里),当它有用时。

## 输出契约

最终结果应当包含(每条发现):

- 标题或输入 ID
- 判定结论与置信度
- 简短理由
- 受影响位置(若有)
- 已确立的可达路径(若有)
- **边界评估**:产品面、污点源可信级别、策略依据、以及"有没有跨过一道受支持的安全边界"
- `confirmed` / `needs_review` 的可利用性优先级
- 支撑证据
- 反向证据
- 证据缺口
- 负责人线索(`confirmed` 且可得时)
- 建议的下一步
- 当判定为 `confirmed` 时,给出"转入修复"的交接说明

整批结果的结构化部分,**每条发现都必须带**:

- 来源类型 `source_type`(用上文列的输入来源类型之一);
- 边界评估 `boundary_assessment`(即使某些字段未知也要在);
- 可利用性优先级 `exploitability_stack_rank`;
- 一条输入对应一条结果,保持输入顺序。

## 转入修复的交接说明

对 `confirmed` 的发现,给出一段"可直接拿去修复"的简洁交接说明,包含:

- 脆弱的污点源、汇聚点、或被绕过的控制;
- 攻击者可控的输入,以及前置条件;
- 确切的代码引用;
- 必须维持的安全不变量;
- 建议的修复边界;
- 修复时应当**保留或验证**的证据缺口。

**不要**自己擅自进入修复——只有用户明确要求"继续进入修复"时,才用 `task_progress(action=update)` 把修复步骤加入当前任务清单,或派子代理去修。

## 任务系统接线(贯穿全程)

这可能是一项很长的工作,要让任务系统看得见进度、并守住"不漏研判、不谎称"的承诺:

- 开工时用 **`task_progress(action=update)`** 把分诊步骤登记进当前任务清单,目标写清楚:"在每条输入发现都有一条带证据的结论、`confirmed`/`needs_review` 都排好优先级、整批结果已写出 之前,分诊不结束";
- 过程中用 **`task_progress`** 持续记录进度（研判到第几条、各结论计数、卡在哪）；需要人介入时（如出现高可利用性的 `confirmed`，或环境缺上下文导致无法判定），在当前回复里列明证据和所需决定；子代理状态由宿主自动递给父级；
- 全部完成才用 **`task_progress(action=update)`** 把对应 items 标为 `done` 并附证据;若用户要求把结果交付验收,直接给出最终回复。

## 收口前自检(声称完成 / 交付验收前自己过一遍)

- [ ] 用户确实提供了发现;没有就停在"请提供发现",没有去翻仓库、也没下结论。
- [ ] 每条输入发现都归一化成了分诊条目,保留了来源 ID 和溯源,**没有编造**扫描器字段/严重度/修复建议。
- [ ] 研判前跑过「仓库安全策略闸」:读了安全策略文件,或如实把"无策略"记成证据缺口。
- [ ] 每条发现都做了"产品面 + 信任边界"分类;没有仅凭"污点数据到了危险汇聚点"就判 `confirmed`。
- [ ] 每个 `confirmed` 都同时满足"静态可达 + 跨过受支持安全边界"两条。
