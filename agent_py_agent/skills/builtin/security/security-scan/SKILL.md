# 安全扫描方法

当用户要审计一整个仓库、或某个指定路径/包/目录/子模块的安全漏洞时用这套方法。核心纪律只有一句:**五个阶段必须分开、按线性顺序跑,每个阶段都做到该阶段要求的深度再进下一个**;最后用一份覆盖台账证明"确实扫全了",而不是靠"看了几个高危点"就声称扫完。最终产出一份结构化的安全发现报告。

## 阶段序列(必须线性、不许合并)

把这五步当成一条单行道,逐个完成:

1. **威胁建模**:这个系统的攻击面、信任边界、高价值资产、入口与特权边界在哪。
2. **发现**:在已建模的威胁上下文里,把仓库/指定路径里的运行时攻击面排序成一张工作清单(worklist),逐行排查候选漏洞。
3. **验证**:对发现阶段产出的每个候选项、以及每条仍未关闭的高危/根控制台账行,确认它到底是真漏洞、还是可抑制/不适用。
4. **攻击路径分析**:对验证后仍站得住的发现,分析可达性、攻击链、影响面与严重级别。
5. **生成最终报告**:把验证过的证据汇成结构化报告。

每个阶段内部都按这个小循环走:**只加载该阶段需要的输入 → 完成该阶段的工作和检查表 → 关闭该阶段产物 → 才进下一阶段**。不要提前预读后面阶段的内容,也不要把精力"摊薄"到各阶段——当前阶段没做到位就往后跑,等于没扫。

## 门函数:开扫前的前置校验(preflight)

进入实质性扫描工作前,先做一次能力/环境前置校验,确认这次扫描跑得起来(能读到目标代码、能派子代理、必要工具到位)。校验有三种结果,照着处理:

| 结果 | 处理方式 |
| --- | --- |
| **就绪(ready)** | 继续。如果有非阻断的告警/建议(warn/suggest),把它对扫描覆盖度的实际影响如实说清,再继续。 |
| **不完整(incomplete)** | 把缺什么、需要补什么的确切原因列给用户,问是否补齐,**停下等回答**,不要擅自跳过或硬扫。 |
| **阻断(blocked)** | 同上先列原因、问是否补救。补救被拒绝、补救不可用、或重试仍不就绪,都**不要自动判定扫描失败**——先保住已在跑的进度,在还能恢复时重试或交接。只有当所有可恢复手段都用尽、确认阻塞不可解,或用户明确取消,才判定本次扫描失败。 |

注意:某个配置值跟"建议值"不一样,不等于告警——只有当能力要求本身没被满足时才算问题。

## 收尾目标:什么时候才算"扫完了"

前置校验返回就绪后,给这次扫描立一个明确的收尾目标(若任务系统支持就用 TaskCreate 建任务并 task_progress 记录推进;不支持就把同样的收尾标准写进第一条可见的扫描进度里)。目标措辞应当是:

> 对 `<已解析的目标>` 做仓库级/指定路径安全扫描;在范围内每个文件/工作清单行都拿到完成回执或显式延期关闭、每个候选项都集齐台账回执、最终报告已写出之前,**不停**。

**没满足下面三条之前,不许把这个目标标记完成**:

- 解析出的范围内,**每个文件或工作清单行**都有一条完成回执,或者一条带确切理由的显式关闭(`deferred` 延期 / `not_applicable` 不适用 / `suppressed` 已抑制)。
- **每个进入发现阶段的候选项**都集齐了发现、验证、攻击路径三种台账回执,或者对缺失的证明有显式的延期理由。
- 最终的安全发现报告已经写出来了。

## 覆盖台账:扫描的真凭实据

仓库级和指定路径扫描的灵魂是一张**覆盖台账(coverage ledger)**——它不只是"发现列表",而是"我排查过哪些攻击面"的证据。台账的每一行是一个运行时攻击面/分片(shard),状态只能是这四个之一:

- `reportable`(可上报,确认是发现)
- `suppressed`(已抑制,有反证)
- `not_applicable`(不适用)
- `deferred`(延期,带明确理由)

**只要某个攻击面在范围内,就必须在台账里有一行并被关闭**——哪怕结论是"不适用"。候选项 id 只是台账行到具体发现的可选链接;一行被标 `not_applicable`/`suppressed`/`deferred` 时,这一行本身仍是必须存在的。

## 派子代理:穷尽式扫描的并行分工

用户显式发起这套穷尽式扫描,就视为**授权你派子代理**来跑(create_subagents / dispatch_subagents / schedule_child_subagents)。如果当前环境派不了子代理,**不要声称做到了穷尽覆盖**,把这个限制如实说清,只在仍能诚实满足请求范围的前提下,退而提供"仅主代理"的更窄路径。

分工必须**显式归属、各管一摊**:

| 角色 | 拥有什么 | 产出什么 |
| --- | --- | --- |
| **排序子代理** | 一个生成出来的排序分片(最多 5 行) | 只写它对应的那份本地输出 |
| **文件审查子代理** | 一个被评估的文件、或一个极小分片 | 整文件回执 + 去重前的发现对象(含本地验证证据和攻击路径事实) |
| **验证子代理** | 一个需要验证关闭的候选项或台账行 | 该项的验证报告更新 + 验证回执 |
| **攻击路径子代理** | 一个已验证的候选项或验证关闭行 | 攻击路径事实、严重级别/策略分析、攻击路径回执 |
| **父代理(你自己)** | 有界的子代理编排、台账对账、聚合、跨文件去重、最终关闭 | 把上面所有产物收拢成最终报告 |

派子代理时务必把它该拥有的那一份(候选项/台账行 + 发现证据 + 各产物路径)交代清楚,让它写回或返回对应回执——别让子代理自己去扩大或缩小扫描范围。

## 范围解析

开扫前先把审计范围解析清楚:

- **仓库级**:整个检出的仓库都在范围内。
- **指定路径**:用户指定的路径/包/目录/子模块边界,连同"看懂具体发现所必需的直接相关文件",一起在范围内。

阶段划分:
- **阶段 1(威胁建模)默认仓库级**,除非用户显式要求更窄、或已提供权威威胁模型/足够具体的仓库级安全指引。
- **阶段 2 起(发现/验证/攻击路径)守在解析出的仓库或指定路径内**,既不无故扩大也不无故缩小用户要的范围。

## 产物路径与默认位置

本方法里提到的产物(工作清单、覆盖台账、原始候选、各发现的候选台账、去重后候选、各阶段报告、最终报告)都按一套统一的"每次扫描一个目录"的布局落盘。如果用户为某个必需输入/输出显式指定了别的路径,**用用户给的路径**。如果某个必需输入仍然缺失,**停下来问用户**再继续。

## 检查点:别让一次中断毁掉全部进度

大仓库扫描里,在深入排查 sink 或验证之前,**先把排好序的运行时攻击面工作清单和初始覆盖台账落盘**。一次扫描如果在"画完攻击面边界"之后被打断,也应该在磁盘上留下可复核的覆盖产物。验证过程中,各发现的验证报告要保持足够新,让 `reportable`/`suppressed`/`not_applicable`/`deferred` 这些关闭行能挺过中断或后续的阶段性摘要——包括记下确切的根控制 `文件:行号` 和种子锚点 `文件:行号`(两者不同则都记)。

## 铁律(逐条照做,这些是这套方法的命根子)

- **声称完成 / 交付验收前,先立目标、后扫描、再收尾**:前置校验返回就绪后才立扫描收尾目标,且在满足上面"什么时候才算扫完了"的三条关闭标准之前,绝不把目标标记完成,绝不声称"已扫完"。
- **不许把 sink 数量等同于覆盖完成**:覆盖台账必须把每个适用的高危分片行关闭成 `reportable` / `suppressed` / `not_applicable` / `deferred`。"扫了很多 sink"不等于"扫全了"。
- **每个候选发现都要有候选级覆盖**:一个候选发现没拿到针对它本身的发现、验证、攻击路径三种回执(或对缺失证明的显式延期理由)之前,不许把它定稿。
- **候选发现覆盖 ≠ 文件覆盖**:一个原始候选发现没拿到它本身的本地验证回执和本地攻击路径回执(或显式延期理由)之前,不许去重、不许定稿。
- **工作清单必须先于"发现完成"存在**,而且覆盖台账必须明显比"被提升的候选列表"更宽——台账窄到只剩几个发现,说明根本没扫开。
- **有外部漏洞标识(CVE/安全公告/缺陷单/版本号等)时,种子调研必须先于"发现完成"存在**:记下查过哪些权威来源、命中的候选文件/函数/类/代码块、以及失败的查找尝试。缺种子调研 = 由公告牵引的发现不完整(除非扫描显式声明当时没有任何可用的网络/本地历史来源)。
- **大型单仓(monorepo)里,按文件数或部署重要性排在前面的产品/运行时区域**,要么作为台账分片出现、要么用仓库证据显式排除;全局 sink 计数和"没冒出头号候选"都不能关闭覆盖。
- **种子化的包/类族/漏洞族保持开放**,直到那一行确切的种子行被关闭成 `reportable`/`suppressed`/`not_applicable`/`deferred`。隔壁同族的另一个发现**不能**替它关闭。
- **大型仓库级扫描里,先对所有适用的高危分片做一遍可达性扫描,再去长时间验证任何单个分片**。一行只有在拿到具体入口或特权边界、最近的相关控制、sink 或被破坏的控制、以及合理影响之后,才升级为验证候选。
- **某分片已经有一个被提升的发现,但还有未关闭的同胞包/具体实现/可复用根控制行(它们可能各自独立可被攻击)时,发现阶段就还没完成**。把这些行关掉、或显式标延期,再做最终报告。
- **最终汇报必须从"可上报的验证关闭行"和"幸存的候选"出发**。不要因为攻击路径分析或发现阶段在"隔壁同族发现"上写了更多文字,就把一条可上报的种子/根控制行丢掉。
- **保留独立可达的同胞实例直到最终报告**:重复出现的脆弱模板、查询构造器、解析器操作、鉴权/对象端点、共享 helper 的各个调用方,都需要各自独立的发现条目、受影响行号和处置;归并放进摘要文字里,且只能在各个实例已经单独列出之后再归并。
- **查询/解析注入,不要仅因为后面有个业务检查看起来限制了影响就抑制语法控制证据**。把注入候选一直带到验证阶段,直到验证证明那个确切的查询 API + 查询后防护确实挡住了该实例的语义篡改。
- **最终报告不完整的情形**:一个被提升的高危发现,其受影响行号里漏掉了发现/种子阶段查到的具体根控制 `文件:行号`(比如某个编解码器、转换器、解析器特性开关、类过滤器、资源路径控制、协议状态迁移、自助更新守卫)。把根控制受影响行补上,或带确切反证显式抑制/延期它,再定稿。
- **大型仓库范围被迫延期时**,最终报告要明确写出:哪些已部署/特权区域、哪些漏洞族被延期了。

## 写出最终报告

最后一步才动手汇总报告。把所有发现语义(清单、各发现、覆盖度)填进结构化产物,从"可上报的验证关闭行"和幸存候选出发组织内容。报告里每个发现给到:确切的 `文件:行号`、攻击路径、影响、严重级别、处置(可上报/已抑制/不适用/延期)及理由。需要把发现升级成系统任务跟进时,用 TaskCreate 建任务、raise_event 抛事件;这次扫描的收尾用 submit_for_acceptance 提交验收。
