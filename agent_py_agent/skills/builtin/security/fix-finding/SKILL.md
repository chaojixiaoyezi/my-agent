# 安全发现修复方法

把一条安全发现处理到位,意味着:**问题还在,就做一个最小且经过验证的代码改动;问题其实已经修好,就用聚焦验证把这一点证实出来、并如实报告无需改代码。**

一份合格的修复成果应当包含:确有需要时的修复本身、聚焦的回归测试(或另一种可重复的验证手段)、正常行为仍然工作的证据、以及原始问题不再复现的证据。

## 铁律(先记住这几条)

- **改完代码和原始脆弱路径都查过,才能说"修好了"**:不要在没复核改后代码、也没复核"原始污点源 → 汇聚点(sink) / 被破坏的控制"路径之前,就声称问题已修复。
- **能动手验证就别只靠读代码**:只要聚焦测试或复现器是可行的,就不要停在代码审查上下结论。
- **别在第一个报错就放弃运行时验证**:缺依赖、缺生成文件、环境没装好,都先当成"可修复的中间阻塞"去定向排查,做有边界、有证据的修复努力,而不是立刻退回纯代码审查。
- **慢 ≠ 失败**:构建或测试跑得慢,在没有硬性失败证据前不要judgment为失败;进度不明时,先用定向的状态/日志/产物/资源检查去区分"在跑"和"卡死",再判定是否受阻。
- **不扩散范围**:不要借机做无关清理、无关重构。
- **不动用户改动**:不要删除或覆盖用户的本地改动和无关修改。
- **不为了让测试通过而削弱安全**:绝不通过削弱认证、授权、租户隔离、输入校验、沙箱、日志记录来让测试变绿。
- **不藏证据缺口(诚实优先)**:环境挡住了验证,就**明确说出是哪条命令 / 哪步环境失败了、还缺哪些证据**,绝不在结论里谎称"已验证 / 已修复"。

## 输入(先把发现的细节抠出来)

开工先尽量抽取这条发现的已知信息:

- 标题、受影响的组件
- 脆弱的污点源 / 汇聚点 / 被破坏的控制
- 攻击者可控的输入
- 期望成立的安全不变式(security invariant)
- 影响、以及触发所需的前置条件
- 已有的 PoC / 复现器 / 测试 / 验证证据
- 涉及的文件与行号

某个关键字段缺失时,先去代码里实地勘察、用代码证据补齐。只有当"不问就只能去猜某条业务策略或安全不变式"时,才回头问用户。

## 运行时验证须知(复现 / 跑测试 / 验证修复时都适用)

下面这套要求,在复现发现、跑测试、验证修复的任何环节都适用:

- **尽最大努力让运行时验证先跑起来**,再考虑退回到代码审查。
- 先查项目自身的说明:仓库内的项目说明文件(如 README、安装文档、测试文档、构建文件、包管理元数据)里写的必要前置条件。
- 缺依赖、缺生成文件、缺服务、本地没装好时,用项目已记录的安装方式 / 包管理器 / 构建系统 / 现成测试命令去装好或生成出来。
- 把安装报错当成"要定向排查并修复的中间阻塞",用针对性命令去解决,而不是把它当成立刻放弃运行时验证的理由。
- 一条命令只要还有输出、还在占资源、还在产出产物、或有其他"在推进"的迹象,且没有硬性失败证据,就不要只因为它耗时就放弃这次复现 / 构建 / 测试 / 验证。
- 长任务看着没结论时,先用定向检查(进程状态 / 最近日志 / 输出文件时间戳 / 资源占用 / 测试运行器状态)区分"在推进"和"卡死",再决定是否停下或弱化验证。

> 这是一项可能很长的工作,长任务可以用 `run_command` 的后台运行能力把构建/测试挂起来跑,再周期性回看进度,别让它阻塞主线。

## 工作流程(按序推进)

1. **锁定修复范围(scope)。**
   - 审受影响的文件,以及"理解这条脆弱路径所必需"的最小支撑文件集合。
   - 动手改之前,先确立:在当前检出的代码里,这个被报告的弱点是**具体可达的**。笼统的弱点标签、文件锚点、看着可疑的代码,都不算证据。
   - 如果做了有边界的勘察后,仍无法证实"同一个被破坏的安全边界确实存在",就不要去补一个相邻弱点、也不要堆叠臆测性的纵深防御。证据表明该路径已经安全 → 收成 `无需改动`;否则收成 `受阻`,并说清缺哪份证据。
   - 找出"安全不变式应当被强制成立"的那个**最窄代码边界**。
   - 在新写校验/控制之前,先查有没有现成的辅助函数、校验器、权限检查、消毒函数、策略对象、测试模式可复用。
2. **可行时,先复现 / 先把问题编码下来,再动手修。**
   - 优先做一个会失败的回归测试(单测 / 集成测试 / 属性测试 / 贴近真实接口的复现)。
   - 在判定"运行时复现不可行"之前,先按上面的《运行时验证须知》努力一遍。
   - 运行时复现确实不可行时,退而求其次,做一个尽可能强、有边界的静态或 harness 验证产物,并把证据缺口写清楚。
   - 不要保留一个会触发不安全行为的测试,除非它是安全、确定性、且适合放进本项目的。
   - 如果还没改任何代码、问题就已经无法复现,就去查清楚它是不是早已被修好,并把这份验证证据保留下来。
3. **生成修复。**
   - 做**能让不变式成立的最小行为改动**。
   - 避免大范围重构;优先用局部的、已确立的现成抽象,除非"让安全不变式成立"本身就要求更大的改动。
   - 保留现有 API,除非"改这个 API"恰恰就是安全修复本身。
   - 显式处理错误路径,不要默默接受不安全输入。
   - 若项目证据 + 验证都表明这条发现已被修好,就跳过代码改动。
4. **加上可重复的验证。**
   - 加聚焦的回归覆盖:它在脆弱行为下会失败、在修复后会通过。
   - 同时给"合法行为仍应正常工作"加上正向覆盖。
   - 在"能证明不变式成立"的最低层级加测试;当脆弱路径可从外部触达且可行时,再补一个接口层级的测试。
5. **验证修复确实生效。**
   - 跑覆盖到改动代码的那批聚焦测试。
   - 若有原始 PoC / 复现器,把它再跑一遍,确认它不再得手。
   - 在退回代码审查之前,先按《运行时验证须知》努力一遍。
   - 在修复后的代码里,把"原始污点源 → 汇聚点 / 被破坏的控制"路径重新走一遍。
   - 搜一搜附近的调用点和变体,看有没有能绕过新控制的路子。
   - 条件允许时,确认"把修复去掉,这个回归测试就会失败"。
   - 把改动文件按惯例该过的检查跑一遍:相关单测、集成测试、格式化、lint、类型检查、该包特定的依赖检查,以及项目对受影响文件通常要求的其他检查。
6. **报告结论**:带上确切命令、运行结果、改动文件、残余风险。

## 同模式的"兄弟实例"也要顾(别只修一个代表)

这是修复里最常见的漏网点:**一个有代表性的路由/汇聚点修好了,却放过了同一处根因牵连的其他脆弱兄弟实例。** 当这条发现的根因是一个共享辅助函数 / 校验闸 / 模板模式 / 序列化反序列化点 / 查询构造器时,确认:

- 要么修复落在了**共享根部**、一并覆盖所有兄弟;
- 要么逐个兄弟实例都各自被复核、各自被验证;
- 别用"代表性那一个已修好"替换掉对其他兄弟的检查。

把这一步并进上面的第 1、5 步:锁范围时识别兄弟家族,验证时回头确认它们都被覆盖。

## 任务系统接线(贯穿全程)

让任务系统看得见进度、并守住"修到位 + 验证到位"的承诺:

- 开工时用 **`TaskCreate`** 建一个修复任务,目标写清楚:"在 → 原始脆弱路径已被复现或证伪、修复(或'已修好'结论)已就位、回归/验证产物已加、正常行为仍工作、原始问题不再复现 都满足之前,任务不结束"。
- 过程中用 **`task_progress`** 持续报进度(范围锁到哪、复现成功没、修复改了哪些文件、验证跑到第几步),用 **`raise_event`** 抛出需要人介入的关键事件(如发现严重度比报告更高、或环境缺工具导致无法验证)。
- 全部完成才用 **`TaskUpdate`** 把任务标完成。

工作量大、文件多、或需要并行深审多个兄弟实例时,这正是**派子代理**的合适场景:可以用 `create_subagents` / `dispatch_subagents` / `schedule_child_subagents` 把"逐文件验证 / 多实例复现"分摊出去。

当一个修复阶段被派给子代理执行时,**子代理拥有这个阶段直到它给出终态结论**;父代理保持编排者角色,不要重复子代理已经做过的改动,也不要把子代理的一句聊天回复当成"已完成"。

## 修复阶段(可分阶段交接时的阶段边界)

当修复被拆成可交接的阶段时,阶段边界规定的是"什么时候可以写代码",但它**不削弱上面任何验证要求**:

- **生成(Generate)**:保持选定的目标检出不变。需要改动来开发或测试修复时,在隔离的工作树或临时副本里改。把"完整的源码改动 + 回归测试改动"写成**一份规范的统一 diff**,然后用约定的标识记录 `已生成` 或 `失败`。
- **应用(Apply)**:先核对基线版本与补丁摘要,再把**恰好那一份补丁**应用到选定的工作区,不夹带无关改动。记录 `已应用` 或 `失败`。本阶段**不做验证、不关闭发现**。
- **验证(Verify)**:**不改源码**。把原始复现器(或现有最强的利用检查)、聚焦回归覆盖、合法行为检查、附近绕过检查、相关项目检查全部重跑一遍。只有当原始问题确实不再复现时,才记 `已验证`,并把确切命令与结果保留在验证小结里;否则记 `失败` 并说清证据缺口。本阶段同样**不擅自关闭发现**。

## 完成检查表(声称修好之前逐条过)

- [ ] 原始发现已用具体的 污点源 / 汇聚点 / 控制 措辞复述清楚。
- [ ] 修复落在了正确的边界上、让安全不变式成立。
- [ ] 有一个聚焦的回归测试(或验证产物)覆盖到了利用条件。
- [ ] 合法行为仍被覆盖、仍能工作。
- [ ] 原始 PoC / 失败测试 / 复现,在修复后不再得手。
- [ ] 修复后,那批聚焦测试通过。
- [ ] 运行时验证遵循了《运行时验证须知》——该装的装了、该修的环境修了、长任务该查状态的查了。
- [ ] 若没有改任何代码,有证据表明问题早已被修好、或在当前代码里无法复现。
- [ ] 该跑的相关单测、集成测试、格式化、lint、类型检查、依赖检查及项目要求的其他检查都跑了。
- [ ] 附近的绕过路径、等价调用路径都查过了。
- [ ] 任何尚未验证的论断,都被**明确标注为证据缺口**,没有混在"已验证"里。

## 出报告 / 交付验收(放最后)

**在声称完成 / 调用 `submit_for_acceptance` 交付验收 / 标记任务完成之前,最终报告里必须包含:**

- 修复的小结;
- 改动了哪些文件;
- 新增了哪些测试 / 验证产物;
- 跑了哪些命令、各自通过还是失败;
- **明确说明"原始问题是如何被证实为不再复现的"**;
- 究竟是做了代码改动,还是问题本就已被修好;
- 残余的不确定性、或被跳过的验证(若有)。

上面任何一条不满足,就**不算修复完成**,不要标记任务完成、也不要声称"已验证 / 已修复"。
