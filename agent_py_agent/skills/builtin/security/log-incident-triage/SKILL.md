# 日志/告警流调查方法

当用户给的是**日志、告警、事件流**（不是源代码）时用这套方法。核心纪律：**先识别数据是怎么生成的，再判断事件是否真实**——告警数量、关键词吓人程度都不是证据，证据只能是"可验证的成功动作"。

## 第一步：数据模式识别（先搞清楚数据是什么）

动手判断"是否入侵"之前，先回答这四个问题：

1. **重复模式**：相邻行/间隔行是否高度相似（同一 IP、同一格式、只变数字）？机器生成的告警通常是这样。`sort | uniq -c | sort -rn` 看 top 模式。
   - 如果 90%+ 的行属于同一个模板 → 大概率是扫描噪声/监控刷屏，不是入侵。
2. **时间分布**：告警是集中在几秒内（自动扫描）还是均匀/持续（真实流量）？
3. **来源归类**：源地址是内部网段（10.x/172.16-31.x/192.168.x）还是外部？内部扫描 = 安全测试/误配，外部 ≠ 自动等于入侵。
4. **数据完整性**：日志有没有被改写的迹象（时间乱序、重复时间戳、文件头尾异常）？

## 第二步：成功指标逐项核验（只有这项才算"入侵证据"）

以下每一项，**必须找到明确日志证据才标记"已确认"**；找不到就是"未证实"，不许用"可能/大概率"升级成确认：

| 指标 | 需要的证据（举例） | 常见假信号 |
|---|---|---|
| 成功登录 | `Accepted password/publickey` + 账号 + 时间 | 失败尝试（auth failure）≠ 成功 |
| 会话建立 | shell/SSH 会话建立、PTY 分配 | 连接建立 ≠ 会话 |
| 后门/持久化 | 新增 cron、systemd unit、authorized_keys 改动、启动项 | 告警文本里出现"backdoor"字样 ≠ 有后门 |
| 提权 | sudo 成功、setuid 变化、root shell | "提权尝试"告警 ≠ 提权成功 |
| 数据外泄 | 大流量外传、敏感文件读取+外发 | 端口扫描 ≠ 外泄 |
| 恶意软件执行 | 已知样本哈希、异常进程持续存在 | 杀软告警 = 检测事件，≠ 执行成功 |

**规则：告警数量 ≠ 严重度**。1 万条"CRITICAL SECURITY BREACH"模板告警的分量，不如 1 条"Accepted password for root from 外部 IP"。

## 第三步：结论分级（不许含糊）

最终结论必须落在三档之一，并附证据链：

- **已确认**：至少一个成功指标有直接证据（给出日志行、时间、来源）。
- **疑似**：有异常但无成功证据（说明缺什么证据、建议查什么）。
- **无法确认**：证据不足或数据本身不可信（说明为什么，不硬下结论）。

## 收尾

- 报告结构：数据模式结论 → 逐项核验表（每项 确认/未证实 + 依据）→ 分级结论 → 建议下一步（要查什么文件/命令）。
- 大文件先重定向 + `grep`/`sort | uniq -c` 分析，不要把全部原始日志读进上下文。
- 用户问"是否被入侵"时，没有成功指标证据就回答"未发现入侵证据"，不要用告警数量撑结论。
