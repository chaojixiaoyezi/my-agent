# 安全威胁建模

为整个仓库建立一份**仓库级**威胁模型,供后续排查漏洞时反复复用。它要让人一眼看清:

- 哪些**资产或权限**值得保护
- 存在哪些**信任边界**
- 哪些**输入受攻击者控制**
- 代码必须守住哪些**不变量**
- 哪些**整仓级失效模式**后果最严重

## 第一原则:有现成的就直接固化,不要重写

**如果仓库里已经存在权威的威胁模型或安全审查指引,它就是唯一事实来源。**原样固化下来即可,不要扩写、不要总结、不要二次解读。

判断"是否已有权威来源":仓库根目录或约定位置的安全说明文档,只要它对本仓的产品面、信任边界、攻击者可控输入、关键假设、安全审查口径描述得**足够具体**,就可以直接当威胁模型用。

只有在**没有**现成威胁模型时,才按下面的清单**生成**一份。

## 工作流

1. **先查是否已存在**:看约定位置是否已有本仓威胁模型。已存在 → 到此为止,不重复造。
2. **有权威来源就原样固化**:把它写成本仓威胁模型,作为唯一事实来源,不扩写、不改写、不重新解释。
3. **否则按清单生成**:用下面的"生成清单"产出一份仓库级威胁模型。
4. **定稿前自检**(三条,见下文)。
5. **固化产出**:把最终威胁模型落到本仓的固定位置,使其能跨不相关的改动反复复用。

> 任务系统配合:这是一项独立可交付的工作。用 `task_progress(action=update)` 把步骤登记进当前任务并报告进度，用 `raise_event` 上报关键节点;若仓库较大需要拆分按子系统并行分析,可用 `create_subagents` 创建不同分工并自动并行,再汇总成一份。标记任务完成 / 最终回复前,先过下面的铁律与自检。

## 铁律

- **现成的威胁模型 / 权威安全指引 = 最高优先**,照搬不改。
- **始终停在仓库级**,除非用户明确要求收窄到某个具体目标。
- **不要把这一步做成"对当前改动 diff 的漏洞挑刺"**。威胁模型谈的是"本仓上下文里哪类漏洞要紧",不是"这次改动有哪个具体 bug"。
- **不要让当前要审的目标 / 刚动过的子系统 / 改动涉及的目录,变成这一步的重心**,除非用户明确要求收窄。
- **大型 monorepo 里别被边角料带偏**:除非有证据表明它们是真实部署或带权限的工作面,否则不要围着 `personal/`、`test/`、`tests/`、`docs/`、`examples/`、一次性开发工具打转。
- **信任边界和假设要明确点出来**,不能含糊带过。
- 谈漏洞类型时,**停在"本仓上下文里的漏洞类别"层面**,不要滑成对某次改动的具体发现。
- 把威胁模型**固化到本仓的固定位置**。

## 定稿前自检(三条,缺一不可)

```
1. 是仓库级,还是被某个具体审查目标带偏了?
   —— 必须是仓库级。
2. 是否先讲清了"整仓主要的产品/运行时面 + 信任边界",再谈更窄的例子?
   —— 必须先全局、后细节。
3. 凡谈漏洞类,是否都停在"本仓上下文的类别"层面,没有变成"当前 diff 的发现"?
   —— 必须是类别讨论,不是具体 bug。
```

## 生成清单(用来"生成"威胁模型,不要把这张清单抄进最终产出)

- **从仓库根开始**,用最少的跳转先搞清楚"这个仓库在现实世界里到底是干什么的",再往下钻进关键组件。
- 这一步**停在仓库级**,除非用户明确要求收窄到具体目标。
- 生成时**忽略**当前要审的提交 / diff / 改动文件 / 改动目录 / 提交标题 / 审查目标——除非用户明确要求收窄。
- **区分"主产品/运行时代码"和"仅供开发/仅测试/仅文档/示例/原型/一次性工具"的路径**。后者通常不是攻击面重心。
- 找出仓库**真正对外暴露**的主产品/运行时面。
- 找出**主要信任边界**,以及每条边界两侧分别是哪些角色。
- 把输入**按来源分清**:攻击者可控、运维可控、开发者可控——三者别混为一谈。
- 描述**在本仓上下文里相关**的常见漏洞类别,而不是当前改动里的具体发现。
- 当仓库里**已有的缓解措施 / 健壮性设计 / 安全控制**会实质影响严重度或范围时,明确点出来。
- 说清攻击者故事**何时现实、何时超出范围**,以及本仓的真实用法**何时会让某类漏洞变得不重要**。
- 记下本代码库**独有的安全考量**,例如:
  - Web 应用:认证/授权、会话管理、CSRF、XSS、SSRF、各类注入、多租户边界、限流、密钥处理
  - 密码学或隐私敏感系统:密钥管理、隐私假设、ACL/RBAC、PII 处理、可审计性
  - 库 / 框架:公开接口、被嵌入时的假设、默认安全行为、易踩的坑(footgun)、安全使用范式
  - 生产/运行时代码路径 vs. CI、构建、本地开发工具
- 对每类漏洞,说清在**本仓**里它何时算 严重 / 高 / 中 / 低,并在每个档位给一两个具体例子。
- 如果某类漏洞需要的"攻击者可控"条件在本仓真实用法里**根本不存在**,就在严重度校准里明说。
- 尽量**指向具体文件、组件或控制点**来给威胁模型"接地"。

## 产出结构(最终威胁模型用 Markdown,固定这四节)

```
- 概述(Overview)
- 威胁模型、信任边界与假设
- 攻击面、缓解措施与攻击者故事
- 严重度校准(严重 / 高 / 中 / 低)
```

这份威胁模型要能帮一个安全研究者快速读懂这个代码库、以及它最可能出问题的安全相关失效模式。它应当详尽、仓库级、可在同一仓库的多个不相关改动间复用。

四节之内,确保覆盖到:

- 仓库概述与现实世界中的预期用途
- 信任边界与假设
- 攻击者故事,以及**明确超出范围**的攻击者故事
- 攻击面与已有缓解措施
- 在本上下文里**最要紧**的是哪几类漏洞
- 在本上下文里**较轻或超出范围**的是哪几类漏洞
- 严重度校准:每个档位给具体例子
- 当具体文件或控制点能实质性"接地"威胁模型时,引用它们

## 一句话总结

**先看有没有现成的——有就原样固化;没有就停在仓库级,把"资产、信任边界、攻击者可控输入、不变量、最严重的整仓失效模式"讲清楚,并指到具体文件接地。**
