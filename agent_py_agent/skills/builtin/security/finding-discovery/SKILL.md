# 安全漏洞发现

## 这个阶段要干什么

以威胁模型为背景,审查待评审的代码(或代码改动),找出**技术上说得通**的候选安全漏洞。

发现阶段只负责**列出候选、保全证据**;它**不负责最终的严重度定级,也不负责完整的攻击路径论证**——那是后续阶段的事。本阶段的产物是一份"每条都能指到具体文件、具体污点源/汇聚点(sink)、具体证据"的候选清单。

## 先确定要审的范围

开扫之前,先把"这次发现要覆盖的代码到底是哪一段"锁死。常见两类:

### 只盯改动(diff-scoped)

扫描目标是一组改动(任务收尾的整体改动 / 单次提交交付 / 分支区间 / 工作区补丁)时:

- 先从"被改动的源码类文件"出发,把这批文件作为发现对象。**改动扫描不对改动文件做排序或剔除**——每个被改的文件都进深审。
- 只有当仓库里确有证据表明"必须看它才能理解这次改动的安全行为"时,才把直接支撑文件纳进来。**不要**借此散成与改动无关的全库枚举。
- 对每个发现对象做深审,遵守本阶段的检查表。
- 始终锚定在**改动的代码 + 直接支撑文件**上。未改动的兄弟文件是上下文或反向对照(negative control),除非 diff 新触达了它们、削弱了它们共享的控制、或改了它们依赖的共享汇聚点/辅助函数。
- 当 diff 太大、单靠一个父代理一遍审不可信时,**派子代理**分摊逐文件深审(`create_subagents` / `dispatch_subagents` / `schedule_child_subagents`),仍遵守相同的深审规则。若当前环境不具备派子代理的能力,就**如实说明这个限制**,不要据此声称"已对全 diff 穷尽覆盖"。

### 整库 / 限定路径(repository-wide / scoped-path)

扫描目标是整个仓库或某条限定路径时,把"已解析出来的审计范围"当作 in-scope,逐文件枚举推进;此时**不受 diff 重叠的限制**。维护一份**覆盖台账**(哪些文件/家族审了、状态如何),靠它推进,而不是靠零散的全文本搜索。

## 发现检查表

这份检查表用来让发现保持**具体**,同时**不越界**变成验证或攻击路径分析。逐条对照:

- 下结论之前,先用工具实看被改文件、以及它们依赖的最小支撑文件。
- 把提交标题/说明当成"可能不完整甚至误导";相信真实代码路径,而不是叙述。
- 把被改的代码链跟到"足以看清这次改动如何影响授权、信任边界、危险汇聚点或安全控制"为止。
- **只在根因不同时**才拆成多个独立的"漏洞家族";不要把同一个问题拆成换皮变体,但**独立可达的实例要各自单列**为候选。
- 当 diff 改了某个共享辅助 / 校验闸(guard)/ 路由模式 / 模板模式 / 汇聚点包装层时,扩展到"被改代码直接影响到的兄弟调用点",并保住每个脆弱实例可定位。
- 寻找由改动**引入或新变可达**的:攻击者可控输入、被破坏的强制校验、危险汇聚点。
- 始终锚定在 diff 及其依赖的支撑文件上,别飘到无关的全库扫描去。
- 整库 / 限定路径扫描时,锚定在工作清单、运行时清单、覆盖台账上,别飘到随意文本搜索去。
- 当有外部安全通告/漏洞情报作为种子线索时:把通告给出的确切文件、行、污点源、汇聚点、被破坏的控制等**线索全部保留在候选台账里可见**。一个相邻的同类(同 CWE)发现可以是**额外**候选,但它**不能替种子行结题**,除非它覆盖的是同一个脆弱控制和同一种效果。
- 不要把多个脆弱文件塞进一个候选——只要这些文件各有"行级别"的污点源/汇聚点/控制证据,就分开列。
- 当一个危险汇聚点有多个调用点时,**逐个调用点列出**各自的污点源和最近的控制。
- 当重复出现的模板、查询构造器、解析操作、认证/对象端点、共享辅助调用方各自独立可达时,**每个脆弱文件和汇聚点/控制行各成一个候选实例**——哪怕最终报告之后会把相关条目合并叙述。
- 当污点源/汇聚点证据"穿过一层包装"进入共享汇聚点/控制辅助时,候选里要**同时**包含两处位置,使验证既能测可达性、又不丢失根部脆弱行。
- 当某个具体的"操作 / 策略 / 转换器 / 校验器 / 处理器子类"选定了攻击者可控的操作语义、并委托进共享的被破坏控制或汇聚点时:把那个**子类方法或构造器**作为受影响候选位置,与共享辅助**并列**——不要只留抽象基类或共享辅助。
- 如果某条候选断言说"某共享解析器 / 加载器 / 求值器 / 认证闸 / 操作家族影响**所有/每一个/任意**具体实现",就**把让这句话成立的具体实现逐个枚举出来**;不要把具体脆弱类只留在叙述文字里。
- 当一个宽泛的候选桶命名了"整个操作家族"(例如"所有 SQL 触发器变体""所有反序列化变体""所有路径穿越辅助""所有 SSRF 模式""所有未鉴权变更端点"),把它**展开成子候选**,以"具体导出函数 / 路由分支 / 汇聚点语句 / API 模式 / 解析器变体 / 受保护动作"为键,再交给验证。
- 如果同一个路由或辅助在同一家族里暴露了多个危险操作(如 `execute`/`executemany`/`executescript`,`pickle.load`/`pickle.loads`/`yaml.load`/`yaml.load_all`,各自独立的路径/文件辅助方法,insert/select/delete/update 查询构造器,或无鉴权的 create/delete/reset/admin/job 动作),只要攻击者能独立触发它们,就把这些操作各自列为候选实例。
- 把共享或自动生成的包装层当作**可达性证据**,而不是"折叠子汇聚点变体"的理由。包装层可以是一个共享的受影响位置,但每个独立的汇聚点、控制、受保护动作仍需各自的候选 id。
- 当扫描上下文或证据指向某个特定的边界包、类家族或漏洞家族时,**让那个种子行一直开着,直到那个确切的包/类家族被关闭**。附近一个同家族发现是支撑上下文,不是种子根控制的替代品。
- 当提供了漏洞编号 / 通告 / 版本 / 发布 / 工单 / 包版本等上下文时,把任何"通告种子调研"产物当作发现输入。把种子调研出的文件/函数/类/代码块作为台账行保留,直到本地代码证据把它们关成:可报告、已压制、不适用、或暂缓。
- 当通告类目泛泛或没用时,**不要直接退回到宽泛的热点发现**。先从"修复 / 发布 / 安全测试"等来源推导一份种子短名单;若拿不到,就对项目特有的协议、解析器、校验器、工具类、版本/比较辅助跑一遍"本地回归种子"排查,再叠加通告关键词。
- 如果发现过程打开或搜过某个种子目标文件/类/包/代码块,就**为它建一条显式的结题行**。别让确切种子只留在工具输出、背景上下文、或"被压制候选"的叙述里。若有更宽的兄弟发现共享同一证据三元组,就把种子锚点文件/行留作受影响位置;否则把种子行单独结题。
- 对"通告主导"的行,**不要**因为相邻问题更好打/更好验证,就用相邻热点替换掉确切的种子构造。让种子行一直开着,直到本地仓库证据独立支持或证伪"同一污点源 + 同一被破坏控制 + 同一影响"的三元组。
- 对共享的反序列化、类解析、模板、认证控制:当下游传输或调用方证明可达时,把"解析器 / 过滤器 / 允许名单 / 拒绝名单 / 校验闸"那一行当作候选位置。不要只锚定那个更戏剧化的传输,而漏掉可复用的被破坏控制。
- 对反序列化和对象构造家族:把解析器或序列化配置注册的具体编解码器、反序列化器、转换器、容器处理器逐个枚举,包括数组、集合、映射、bean、枚举、throwable、通用对象处理器。一个顶层解析器/配置发现**不能**关掉某个具体编解码器行——只要该编解码器会对攻击者可控数据**递归地**触发解析、类型解析、转换或对象构造。
- 对文件格式对象模型:把"转换或遍历攻击者可控文档结构"的原始/容器辅助方法逐个枚举,包括 `to*Array`、`get*`、`getObject`、数值转换、`parse*`、迭代器、`size`、未检查的强制类型转换、分配循环。当畸形文档可能触发类型混淆、异常、无界遍历、或内存/CPU 耗尽时,把这些辅助当作候选根控制。
- 如果工作清单或覆盖台账标出了某个"针对不可信格式的核心对象模型包",在关掉解析器家族之前,先把该包的数组、字典、节点、集合、原始转换辅助纳入发现行。相邻包里的某个解析器/过滤器/编解码器发现,**不能**关掉核心对象模型里那些未检查的转换辅助。
- 对象模型辅助的扫荡先产生**必须存在的发现行**,而不是自动变成可报告发现。只有当畸形/对抗性输入可信地到达该辅助、且缺失的"类型/尺寸/形状/递归/数值/转换"校验会造成崩溃、拒绝服务、解析器混淆、授权绕过或别的具体安全影响时,才把它升格。
- 当不可信的远程、协议、文档、归档或包输入能到达缺失的校验、并能让一个服务/请求工作线程/解析流水线/安全协商中止时,**不要**把确定性的解析器/辅助崩溃当成"健壮性问题"压制掉。压制需要确切的"包含证据",例如调用方一侧有恢复、有等价于缺失校验的输入预校验、或这是个非安全边界。
- 对结构化的补丁/编辑/应用类 API(如 JSON Patch、图补丁、文档编辑、配置变更),把请求选定的具体操作逐个枚举,如 add、remove、replace、move、copy、test。当它们喂进共享求值器或绑定器时,保住操作特定的路径变换、数组追加处理、通配选择、对象绑定行的候选可见性。
- 在具体操作类里,检查专门的辅助方法,而**不是只看**顶层的 `perform`/`handle`/`apply` 重写。如果操作特定的辅助在委托给共享求值器/绑定器之前,对攻击者可控路径做了切分、过滤、规范化或重建,就把那个辅助行当作候选根控制。
- 当某具体操作有特殊分支(如 append、wildcard、fallback、copy/move 的 `from`、默认值、类型解析路径),只要它们绕过或收窄了共享校验器,就把分支判定式和分支局部变换行当作受影响位置。一个共享辅助发现**不能**关掉分支特定的根控制。
- 当类过滤、允许/拒绝/黑/白名单或解析逻辑在 core、server、client、远程、插件、导入等多个包里重复时,只要它们实现的是同一个被破坏控制,就把运行时/导出的等价物当作候选位置。某个传输调用点证明可达,但它**不能**替换可复用的解析器实现。
- 在框架或库扫描里:存储的客户端、租户、应用、身份提供方、异常、或导入的配置值,当它们之后被渲染、求值、解析、或用于授权,且该实例有一条来自应用/租户/身份提供方/导入或别的边界的可信运行时路径时,就是**跨边界输入**。不要仅因为"写入方在当前仓库之外"就压制它——除非仓库证据证明该值在正常部署里只可能可信。
- 对 SQL/NoSQL/LDAP/XPath 等查询类 API:**不要**仅因为"端点本来就接受用户可控数据""操作是 insert/update""或之后有一个业务检查看起来限制了最终应用效果"就压制候选。只要攻击者可控输入经一条可信运行时路径到达查询语法或选择器操作符,就把候选带进验证,并把那个后置检查记为"可能的反证"。
- **不要**仅因为多个高影响证据三元组共享一个路由或辅助,就把它们折叠成一个候选。当汇聚点、最近控制或影响不同,就把命令执行、SSRF、路径/文件影响、XML/解析器行为、XSS/模板执行、授权/状态变更影响**分开**。
- 对出站请求面(如下载器、URL 导入器、webhook/回调客户端、预览/渲染抓取器、跟随重定向的 HTTP 客户端),把每个攻击者可控的目的地源、以及它最近的"允许/拒绝/过滤/重定向"控制逐个枚举。**不要**因为"抓取/回调是预期功能""过滤器可选或默认为空""或兄弟路由发现了更响的文件/路径问题"就压制 SSRF;只要用户输入能选定目的地、且硬边界不完整/靠运维配置/或只在请求前生效,就保住这条网络行。
- 在 XML/解析器/反序列化面,把默认解析器工厂、转换器、校验器、转换流程、unmarshal/parse 调用、处理器入口各自独立枚举。一个安全的兄弟解析路径,只是那个兄弟的反向对照,**不是**另一个默认工厂或转换器的压制证据。
- 对命令/动作执行器,在关掉命令注入覆盖之前,把每种攻击者可控的参数类型和执行模式逐个枚举。把类型安全映射、不安全类型拒绝名单、模板替换、shell 包装、直接 exec 分支、webhook/API 参数摄入、前端专属的控件约束当作**各自独立**的控制。一个覆盖了 `raw`/`url`/`email` 的拒绝名单,**不能**关掉 `password`、`checkbox`、`confirmation`、choice 等"类型检查为空/无操作"、却仍可能渲染进 shell 命令的分支。
- 对 XML 解析器和转换器候选,当加固是"尽力而为/失败即放行/不完整"时,把特性设置行和解析行纳入。仅有"安全处理"特性开关、被吞掉/只记日志的设置失败、或一个安全的默认解析器,**不能**压制掉那些"用不可信数据创建 SAX/DOM/StAX/Transformer 源"的、调用方提供的解析器工厂/读取器或转换器路径。
- 对资源服务和静态文件路径,把"决定攻击者所选路径是否被允许"的允许名单、匹配器、规范化、URL 解码、资源选择行纳入。不要用一个更安全的兄弟处理器替换掉脆弱的遗留/旧 API 处理器。对 restore/import/export、备份、admin、login 命名的路由,还要先核实确切的全局中间件和装饰器语义,再假定"需要鉴权";当启用鉴权的配置缺失时,可选/条件的登录包装会让这条路由仍然是匿名的。
- 对路径敏感的文件系统家族,把 restore/import/export、备份/恢复、归档解压、文件 copy/move、download/open、key/config 抓取等具体导出操作逐个枚举。对每个独立可达的操作,保住 decode、join、normalize、canonicalize、strip-prefix、扩展名检查、目的地选择行的候选可见性。
- 对归档解压和 restore/import 流程,保住归档成员名、目的地拼接、包含性检查、extract/write 调用作为候选根控制的可见性。**不要**用之后的 copy、import、UUID/清单闸、或顶层文件选择步骤替换掉它们——如果解压或文件系统写入已经先发生了。"标准库辅助会规范化路径"这种泛泛说法不够;让这条行一直开着,直到代码显示出"解压/写入前确有逐条目的包含性检查",包括任何可能把攻击者可控内容之后提升进被导入子树的 symlink、hardlink、元数据、递归 copy 路径。**不要求**写入逃出整个应用/数据根;覆写可信配置、对等对象目录、共享根、或该根内被导入的子树,**仍然算**文件影响。
- 当上传/归档成员行有"精确的污点源 → 解码/过滤后的成员名 → 目的地拼接/写入"三元组时,即便运行时无法复现、或置信度只是中等,也要保留它们作为候选。同仓库里一个更干净的 download/open 穿越或鉴权问题,**不是**丢掉归档成员行的理由;以校准过的严重度/置信度报告它,或保留一条带"缺失证据"说明的显式暂缓台账行。
- 当同一产品区域还有鉴权、密钥或配置 bug 时,让路径/文件候选一直开着,直到它自己的证据三元组被关闭。**不要**用那个更响的相邻问题替换它。
- 在框架或库扫描里,**不要**仅因为受影响 API 已弃用、需显式开启、或文档标注危险就压制一个高影响候选。把这点写成前置条件;只要发布的运行时代码里、在受限或正常用法路径上含有可绕过的控制、且该实例有一条可信的跨边界源和运行时/部署路径,就保住候选。
- 在认证/授权面,把"读取受保护对象、触发构建/任务、或变更受保护状态"的公开 webhook、status、callback、API 端点,从相邻的凭据或配置 bug 中**独立**枚举出来。
- 对有状态的认证协议,把"在预认证、TLS 升级、重定向、断言、或身份提供方切换之后,安装或复用主体/凭据/令牌/签发方/协议状态"的那一行纳入。缺失的重绑定/重认证、或"已校验对象 vs 实际消费对象"不一致,当它们可能认证成错误身份时,就是候选控制。
- 在 SSO/SAML/联合身份包里,把"响应/断言校验器"与"通用声明授权器"和"服务方法授权"区分开。把断言选择、列表索引、取 DOM、克隆节点、签名对象查找、subject 确认、recipient、audience、destination、ACS URL、issuer 绑定行纳入——当它们决定"哪个断言被信任或被返回"时。
- 在认证/令牌/断言校验器里,留意"一个校验循环或'已找到有效项'标志,之后却跟着一个独立的固定索引、首/末元素、克隆、序列化、或返回路径"。把那条后置的对象选择行当作被破坏控制,直到确切反证证明"被校验对象和被消费对象完全相同、且绑定一致"。
- 对 realm/认证器包,在升格一个相邻的通用 HTTP 认证发现之前,先把 LDAP、Kerberos、PAM、SAML、OAuth/OIDC 或自定义 realm 类等具体实现逐个枚举。在 TLS 升级或多步绑定里,保住绑定/重绑定和主体/凭据安装行的候选可见性。
- 在协议密集的仓库里,即便最显眼的候选是 REST/上传/admin 热点,也要检查底层的版本、能力、特性、协商工具类。搜 `Version`、`versionCompare`、`versionMatch`、`Capability`、`Feature`、`Negotiation`、`parseInt`、`split`、`matches`、比较器方法等辅助名,然后把成对的校验器/解析器行显式结题。
- 对自助更新路由,把"将请求对象与持久化对象比对"的校验闸或判定方法纳入。当它们能改变身份、信任状态、租户成员、角色、组、或账户恢复属性时,把"安全敏感标量字段和集合别名上缺失的检查"当作候选位置。
- 当某个模板或配置模式反复出现时,把每个受影响的文件/行枚举出来,并标注附近不该被报告的安全控制。
- 对只盯改动的扫描,**只在** bug 与 diff 重叠、且那些行确实与问题相关时,才包含 `相关行(relevant_lines)`。
- 对递归占位符或模板类发现,把"启用递归展开或表达式求值"的辅助/解析器设置行,连同解析/求值/渲染行一起纳入。
- 已知时带上 CWE 编号;类别不清时用空列表。

## 候选门槛(Finding Bar)

优先列那些技术上说得通的候选,例如:

- 授权绕过(authz bypass)
- 混淆代理(confused deputy)
- SSRF
- 路径穿越(path traversal)
- 有真实汇聚点的注入(injection with a real sink)
- 跨租户数据泄露
- 缺少正确强制校验的敏感状态变更
- 沙箱或信任边界逃逸

发现阶段识别"说得通的候选"并保全其证据;它**不拥有**最终严重度校准。可报告性和严重度的标准,留到攻击路径分析阶段去判。

避免列这些:

- 泛泛的"需要更多校验"评论,且给不出利用路径
- 可维护性 / 代码风格抱怨
- 同一根因的换皮重复

## 输出契约

如果没有任何说得通的候选,返回"未发现"结果即可。

否则,每条候选都要包含:

- 候选 id
- 标题
- 受影响位置;当不止一处适用时打上标签:`入口/包装层(entrypoint/wrapper)`、`根控制(root_control)`、`汇聚点(sink)`、`具体实现(concrete_implementation)`
- 整库 / 限定路径扫描的实例键,格式 `<家族>:<文件>:<行>`
- 整库 / 限定路径扫描里"种子/根控制"行的台账行 id(若有)
- 通告/来源引用(若是由外部通告作种子的行)
- 攻击者可控的污点源
- 脆弱汇聚点或被破坏的控制
- 影响
- 为什么从当前代码看这个问题说得通
- 最近的表面控制、以及它为何缺失/被绕过/作用域错配/不完整
- 是否建议进入验证
- 只盯改动扫描的 `相关行(relevant_lines)`——当 bug 与 diff 重叠、且那些行与 bug 相关时
- 分类(已知时带 CWE 编号)
- 足够的证据,让后续评审者在验证之前就能看懂"这条候选为什么技术上说得通"

每产出一批候选,就把它登进**候选台账**:一条候选对应一条发现记录(receipt),写清候选标识、扫描范围、发现状态、受影响位置、以及产出它的证据。这样后续验证和攻击路径分析才能为这条确切的发现证明覆盖。

## 铁律(必须守住)

- **下结论前先用工具实看仓库文件。**
- **盯真实改动,不盯提交说明。**
- 只盯改动的扫描:锚定在 diff 及其依赖文件上。整库 / 限定路径扫描:把已解析出的审计范围当作 in-scope,受影响位置不受 diff 重叠限制。
- 候选发现说的是**说得通(plausibility)**,不是最终严重度。
- **不许产出"没台账的候选"。** 每条候选发现都要有稳定的候选 id 和一条发现记录登进候选台账,后续验证和攻击路径分析才能为这条确切发现证明覆盖。
- 没有 bug 就**不要**加 `相关行`。只盯改动的扫描里,只有 bug 与 diff 重叠、且那些行相关时才加。
- **不要**把发现做成完整验证或完整严重度校准。
- 一直审到**没有新的、独立的、说得通的候选**为止。
- 最后把一份可见的发现报告写出来(收口产物),让结果可审计、可被下一阶段接手。

## 任务系统接线(贯穿全程)

这可能是一项很长的工作,要让任务系统看得见进度、并守住"不漏审"的承诺:

- 用 **`TaskCreate`** 建发现任务,目标写清"在'每个发现对象都审查闭环、每条候选都有发现记录、最终发现报告已写出'之前不结束"。
- 过程中用 **`task_progress`** 持续报进度(审到第几个文件、出了几条候选、卡在哪),用 **`raise_event`** 抛出需要人介入的关键事件(例如疑似高危候选、或环境缺工具导致某些文件审不到)。
- 全部完成才用 **`TaskUpdate`** 把任务标完成。

## 诚实优先于覆盖度

跑不动工具、或环境缺工具导致某些文件审不到、或没能派成子代理时,**如实说明哪些没覆盖**,绝不在结论里声称"已穷尽审查 / 已对全 diff 穷尽覆盖"。宁可深审一半并标清未覆盖,也不要全部浅审。这一点在**声称完成 / 调用 `submit_for_acceptance` 交付验收 / 标记任务完成之前**尤其要守住。

## 收口前自检(交付前自己过一遍)

- [ ] 要审的范围已锁定(只盯改动 / 整库 / 限定路径),类型清楚。
- [ ] 每个发现对象都被实际审过——能逐个点名,没有"大概扫了扫"。
- [ ] 同模式的兄弟实例查过了,确认没有"一个代表性汇聚点掩盖了其他脆弱兄弟"。
- [ ] 每条候选都有:稳定 id + 发现记录登进候选台账;受影响位置、污点源、最近控制、汇聚点、影响、证据齐全。
- [ ] 没有把发现做成完整验证或最终定级——越界的部分留给了后续阶段。
- [ ] 最终发现报告已写出。
- [ ] 环境缺工具 / 没派成子代理 / 某些文件没审到的情况,已如实写进报告,没有谎称"已穷尽"。
