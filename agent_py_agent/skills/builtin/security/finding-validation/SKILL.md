# 安全发现验证

## 目标

把发现阶段交上来的候选问题,逐条做出**你能拿出的最强、有证据支撑的验证结论**。

能跑就跑:优先用有针对性、非交互的复现或证伪;当动态执行被卡住(缺服务、缺基础设施、为这一条搭环境的代价明显失衡)时,改用聚焦的代码追踪。

**核心原则:置信度来自验证方法和证据,而不是"这个漏洞听起来多吓人"。**

## 工作流

1. **先立标尺**:动手前,给这条候选定一份验证评分表(最多五条判据),想清楚"看到什么才算坐实、看到什么才算推翻"。
2. **拆三元组**:对每条候选,先明确——攻击者的输入从哪进、危险的落点(sink)在哪、要满足哪些前置条件。
3. **选验证路径**(按"现实可用的最强方法"从强到弱挑):
   - **崩溃 PoC**:崩溃、内存破坏、解析器混淆、拒绝服务这类候选,若工程能在有限代价内构建,尝试编一个 debug 变体并造出能触发崩溃的 PoC。
   - **内存检测工具**:内存安全/崩溃类候选若没能立刻复现、而构建又支持,接着上 valgrind / ASan 之类工具。
   - **调试器追踪**:有运行时环境但链路不清时,用非交互方式跑调试器(gdb / lldb),把"源到落点"的路径打出来。
   - **单测 / 集成测试**:危险路径已被现有测试覆盖到,就加一个或改一个**最小的聚焦用例**,让它走到漏洞代码并断言出危险行为。
   - **真实接口复现**:代码暴露了用户能真正触达的接口(HTTP、CLI、文件解析器、RPC、消息队列、插件钩子、对外 API),用精心构造、能打到可疑落点的输入,做一次最小的端到端复现。
   - **代码理解(静态追踪)**:有限次尝试后动态复现仍不可行或不划算,就退回静态评估——把"源 → 控制流 → 落点 → 可达性 → 边界证据 → 反证 → 证明缺口"逐项追清楚(本 skill 末尾附了静态追踪要点)。
   - **大型内部仓库模式**:对整仓或限定路径的扫描,若运行时复现要靠拿不到的内部服务、密钥、云账号、服务网格或线上数据,在候选已凑齐"源/控制流/落点/影响"完整四元组后,用静态追踪 + 现有测试 + 部署/配置证据来定论。**注意:缺内部运行时环境不等于"这条是误报"的证据。**
4. **非编译型技术栈**:尽量造出 PoC 或有针对性的命令,实际走一遍危险路径、触发漏洞。
5. **编译型技术栈**:只要搭环境代价有界,优先做动态验证——构建 debug 变体或搭一个聚焦测试,用小 PoC 复现危险行为;当 valgrind / ASan / 非交互调试追踪能实质提升置信度时再上。
6. **留证据**:把 PoC 文件、输入样本、日志,统一放进**当前任务的工作区**(随任务走,别散落在临时目录或只留在终端回滚里)。
7. **跑不动也要交代清楚**:如果验证不可行,写明试过什么、还剩哪些不确定、**确切的证明缺口在哪**。
8. **逐条出结论**:给每条候选一个清晰、基于证据的验证判定,连同证明缺口和残余不确定性一并写出。
9. **同步任务系统**:验证结论要落进任务进展,用 `task_progress` / `TaskUpdate` 把"哪条发现、用了什么方法、证据/缺口、最终处置"写清楚;需要任务发起方拍板的(比如要不要立项修复、影响面有争议),用 `raise_event` 显式抛出来。
10. **留验证回执**:每条候选都要留一份回执,记录:**验证方法、证据或确切证明缺口、处置结论、证据文件/报告位置**。哪怕结果是"压制/不确定/暂缓",也必须留回执——不能让某条候选"悄无声息地没了下文"。

## 使用要点

- 验证命令一律走 `run_command`,要**短、有界、非交互**(git、在改动目录内的 grep -nI、构建/测试 gate、最小 PoC)。
- 避开交互式编辑器、整仓长时间扫描、非必要的网络访问。
- 必须用调试器时,以非交互方式调用(gdb:`-q -batch -ex run -ex bt -ex quit`;lldb:`-b -o run -o bt -o quit`)。
- 造 PoC 验证时,**直接打真实的应用/库本身**,理想情况是还原"攻击者会怎么触发这个 bug"。

## 验证准则(保留实例 + 检查表 + 置信度)

### 保留实例
- 一条候选对应一个具体的"实例"(同一类问题在不同位置出现就是不同实例)。验证、压制、暂缓都**针对具体实例**做,不要用一个代表性证明去笼统替所有同类位置下结论。

### 验证检查表(每条候选过一遍)
- [ ] 攻击者输入的源点已落到 `文件:行`
- [ ] 危险落点(sink)已落到 `文件:行`
- [ ] 源 → 落点的控制流/数据流路径连得起来,中间没有"被忽略的拦截"
- [ ] 触发所需的前置条件已写明,且在现实中可被满足
- [ ] 已主动找过**反证**(校验、转义、白名单、权限闸、不可达分支),并说明它为什么挡不住 / 为什么不存在
- [ ] 证据要么来自真实复现,要么来自连贯的静态追踪——不是"凭感觉"
- [ ] 残余不确定性和**确切证明缺口**已写出来

### 置信度怎么定
- **高**:有真实复现(崩溃 PoC / 通过的聚焦用例 / 端到端触发),或静态链路完整且反证已被逐一排除。
- **中**:静态链路基本连得上,但有一两处可达性/前置条件未坐实,或复现被环境卡住但代码证据有力。
- **低**:只有可疑落点,路径或可达性大段缺失,反证尚未检查。
- 置信度**只跟"方法 + 证据"挂钩**,与漏洞类别听起来多严重无关。

## 静态追踪要点(退回代码理解时用)

当动态复现跑不动、或对大型内部仓库而言静态证据已足够时,按这套追:

- **源(Source)**:不可信输入从哪进系统(请求参数、文件、环境变量、上游服务返回……)。
- **控制流 / 数据流(Control)**:输入怎么流到落点,中途经过哪些函数、有没有被改写/拼接/解码。
- **落点(Sink)**:真正产生危害的那行(命令执行、SQL 拼接、反序列化、路径拼接、越权读写……)。
- **可达性(Reachability)**:这条路径在真实调用中走得到吗?有没有前置鉴权、feature 开关、不可达分支把它挡死。
- **边界证据(Boundary)**:数据跨信任边界的那一刻有没有校验/转义/编码,强度够不够。
- **反证(Counterevidence)**:任何能证伪这条发现的东西——存在有效校验、落点参数其实可控范围有限、调用方已做约束。**没有确切反证,就不能把一条有完整四元组的候选判成"不成立"。**
- **证明缺口(Proof gap)**:还差哪一块证据才能从"疑似"变"坐实",把它精确写出来,而不是含糊带过。

## 输出契约

对每条候选发现,至少给出:

- 发现标题
- 候选 id / 实例标识 / 台账行号(若上游提供)
- 根因控制点 `文件:行` 与受影响位置标签(若发现阶段提供)
- 来源参考与种子锚点 `文件:行`(若有,尤其当它与根因控制点不在同一行)
- 置信度
- 用了哪种验证方法(或建议用哪种)
- 评分表勾选清单(`- [x]` / `- [ ]`)
- 观察到的证据
- 简洁说明测了什么
- 残余不确定性
- 还需更多证据时的**最小下一步**
- 产生了验证文件/日志时的存放位置
- 信息量要够:后来读的人不用另看一个状态标签,也能判断"这条发现到底有没有挺过验证"

对整仓 / 限定路径的扫描,额外给一张**验证收口表**,列:

| 列 | 含义 |
|----|------|
| 台账行号 | 对应候选在台账里的行 |
| 实例标识 | 唯一定位这一处实例 |
| 来源参考 | 有就填 |
| 种子锚点 `文件:行` | 与根因控制点不同时填 |
| 根因控制点 `文件:行` | 真正的问题源头 |
| 入口/源 | 攻击者输入从哪进 |
| 落点/控制 | 危险落点 |
| 处置 | `可上报` / `已压制` / `不适用` / `暂缓` |
| 反证或证明缺口 | 为什么这么判 |
| 是否挺过 | `是` / `否` / `不确定` |

## 铁律

- **没真验证,就不许暗示验证过了。**
- **不许让候选的覆盖情况变成"隐含"。** 每条进入验证的候选都必须留下回执,哪怕结果是压制、不确定或暂缓。
- 优先走"贴近真实的本地复现",别为了出结果搭一堆牵强的假环境。
- 一条发现如果依赖某个"缺失的产品前提",就把问题**清清楚楚地问出来**,绝不编一个答案填上去。
- 命令保持短、有界、非交互。
- 在技术栈和扫描范围允许时,先尝试更强的方法(崩溃 PoC、valgrind、ASan、调试追踪、聚焦用例、真实接口复现),再退回纯代码理解。
- 置信度从"验证方法 + 证据"来定,不从"这个 bug 类别听着多危险"来定。
- 验证产物和最终可见结论都随任务工作区走,让整次扫描的材料聚在一起、可被后续复核。
- 当运行时验证会**实质改变"是否可上报 / 置信度 / 严重度"**时,要认真地、在有界代价内把它跑通:翻一翻仓库里的指引(README、构建文件、测试文档、依赖元数据),搞清楚要哪些依赖、生成物、服务和步骤。
- 对"不许改动目标代码树"的扫描:在任务工作区下另开一个一次性副本或生成物目录,用来构建、生成客户端、打补丁的测试桩、放 PoC。**"不改原树"不等于"连只读的构建副本都不许有"。**
- 对整仓 / 限定路径扫描:每决定一行(可上报/已压制/不适用/暂缓)就更新一次验证报告和收口表。**别把已验证的行只留在临时笔记或终端日志里**——扫描一旦中断,后续要能从已存的报告里重建"挺过验证的发现"。
- 对大型整仓扫描:搭环境/构建/调试的投入要与"这条候选 + 剩余高影响覆盖"成比例。别把全部预算耗在死磕复现某一个内部服务上——静态追踪 + 现有测试 + 部署/配置证据已经够定论时,就收手。
- 同一类高影响模式里,一旦有一条候选拿到强证据四元组,就切去台账里的兄弟候选,用"同样的源、最近的控制点、落点、影响"逐条核;只有当更深的运行时验证会实质改变结论时才继续往深跑。
- 一个分片里若已有一条"同族已坐实"的发现,外加若干未决的种子/根因行,先把这些兄弟行收口(可上报/已压制/暂缓),**再去碰旁边那条更抓眼球的新发现**。代表性证明能提升置信,但不能在没有确切反证的情况下替兄弟根因点结案。
- 工程或代码**编不过 / 构建不起来**时,先把失败诊断到"能判断还能不能用有针对性的构建、现有测试、对外 API 测试桩或一次性副本去走原始代码"。优先验证原目标,而不是另写一个复刻版。
- **别把搭环境报错、编译错误、缺依赖当成即时反证。** 先记下"是什么挡住了运行时证明",当继续搭环境变得不划算时,改用静态追踪 + 现有测试/配置/部署证据。
- **别因为一条命令"跑得久"就放弃它**——只要还有输出、资源占用、生成物或其它进展迹象,且没有确凿的失败证据。长命令看着没结论时,先查进程状态、近期日志、输出文件时间戳、资源占用或测试 runner 状态,再决定是否停止或降级验证。

## 一句话总结

**先坐实,再下结论;坐实不了,就把缺口说清楚。**

证据决定置信度,吓不吓人不决定。
