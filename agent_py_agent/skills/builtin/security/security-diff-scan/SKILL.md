# 改动安全扫描方法

当一组改动准备收尾交付时,要审查它有没有引入**安全回归**。核心原则只有一句:**扫描范围跟着改动走,不要散成全仓枚举**;同时把各阶段分开做,别一锅烩。

一份有价值的安全扫描,是"真的逐个看过改动文件、跑过验证"才得出的——每个结论都能指到具体文件、具体污点源/汇聚点(sink)、具体证据,而不是凭印象拍。

## 铁律(先记住这几条)

- **只盯改动**:从改动的文件出发,只向"理解这次改动的安全行为所必需"的支撑文件外扩。改动没碰到、也没被改动影响的代码,不是本次扫描对象。
- **逐文件实看**:本次改动涉及的每个源码类文件都必须被实际审过。"我大概扫了一遍"不算覆盖;没看完就别声称"已完成扫描"。
- **阶段分开、按序推进**:威胁建模 → 漏洞发现 → 验证 → 攻击路径分析 → 出报告,严格线性,不要把阶段揉到一起,也不要"匀着劲儿"每个阶段都浅做。
- **诚实优先于覆盖度**:跑不动验证、或环境缺工具导致某些文件审不到时,**如实说明哪些没覆盖**,绝不在结论里声称"已穷尽审查"。宁可深审一半并标清未覆盖,也不要全部浅审。

## 先确定扫描目标(改动到底是哪一段)

开扫之前,先把"要审的改动"精确锁定。常见几种目标类型:

| 目标类型 | 取 diff 的方式 |
|---|---|
| 任务收尾的整体改动 | 任务起点基线 ↔ 当前状态 的全部改动 |
| 单次提交交付 | 该提交 ↔ 其父基线(或指定基线) |
| 分支区间 | 合并基点(merge-base)↔ 分支头 的区间 |
| 工作区补丁 | 暂存 + 未暂存的工作区改动 ↔ 指定基线 |

目标类型不同,但**收尾出报告的口径一致**——都是"改动安全扫描",用同一套阶段和铁律。

## 阶段序列(分开做,按序推进)

把下面四个阶段当成各自独立的工作,做完一个再开下一个,出报告放最后:

1. **威胁建模(threat-model)**
2. **漏洞发现(finding-discovery)**
3. **验证(validation)**
4. **攻击路径分析(attack-path-analysis)**
5. **产出最终报告**

每个阶段的做法:
1. 先想清楚这个阶段要解决什么问题,只装入这个阶段需要的输入。
2. 把这个阶段的流程和检查表做到位。
3. 做完当前阶段,再进入下一阶段——不要提前"偷看"后面阶段、抢着干后面的活。

工作量很大、文件很多时,这正是**派子代理**的合适场景:可以用 `create_subagents` / `dispatch_subagents` / `schedule_child_subagents` 把"逐文件深审"分摊出去并行做。但若当前环境不具备派子代理的能力,就**老实说明这个限制**,不要据此声称"已对全 diff 穷尽覆盖"。

## 范围的不对称(这是有意设计)

- **威胁建模(阶段一)默认是项目级**:除非用户明确要求更窄范围、或已提供权威威胁模型/足够项目特定的安全指引,否则别让"这次改动碰的那个子系统"绑架整个项目的威胁模型。
- **阶段二之后(发现 / 验证 / 攻击路径)是改动聚焦的**:跟着改动的代码和它的直接支撑文件走。

把这种不对称当成刻意为之:

- 用 diff 来**定位**后续阶段要审的目标位置;
- 但**别让 diff 偏置阶段一的威胁建模**;
- 别因为"这次只改了某个子系统"就把整个项目威胁模型缩成那个子系统——除非用户明确要这个更窄范围。

## 只盯改动的发现(Diff-Scoped Discovery)

发现阶段应当:

- 从改动的源码类文件出发,逐个深审;
- 只在"项目里有证据表明、确实需要它才能理解这次改动的安全行为"时,才把直接支撑文件纳进来;
- 始终锚定在**改动的代码 + 直接支撑文件**上,不要散成与本次改动无关的全仓枚举。

## 同模式的"兄弟实例"也要覆盖(关键,别漏)

只盯改动的同时,要保住"由同一段改动模式所新建或影响的、重复出现的脆弱实例"——这是最常见的漏网失败模式:**一个代表性的路由/汇聚点,掩盖了同一补丁引入的其他脆弱兄弟**。

发现阶段应当:

- 从改动的文件、以及理解改动行为所需的支撑文件起步;
- 从一个被改动的**路由 / 处理器 / 共享辅助函数 / 校验闸(guard) / 模板模式 / 查询构造器 / 序列化反序列化 / 文件或网络汇聚点 / 配置块 / 包装层**,扩展到那些"diff 也改动了、或经由同一被改的共享依赖被新触达/被影响"的兄弟实例;
- 当 diff **新增、移除或改写**了某个已存在的(解析器 / 反序列化器 / 表达式求值 / 文件路径辅助 / 归档工具 / 认证授权辅助)周围的校验闸时:把相邻的、原有的汇聚点/控制作为**支撑上下文**;候选项仍锚定在"被改的校验闸"或"被新暴露的路径"上——除非用户明确要更大范围的实例扩展;
- 当被改的包装层/校验闸/API 委托给某个共享的(解析 / 反序列化 / 路径 / 归档 / 认证)辅助时:**包装层调用点和底层共享汇聚点/控制行都要可定位**;不要用"只有包装层"的证据替换掉根部汇聚点/控制的证据;
- 每个脆弱兄弟实例都带上自己的:受影响位置、污点源、最近的控制、汇聚点、影响、以及"为什么压制/不压制"的证据,一路带过发现和验证;
- 把**未改动的兄弟**当作上下文和反向对照(negative control)——只有当 diff 让它们**新变脆弱**、或改了它们依赖的共享控制/汇聚点时,才把它们写进报告;
- 当这一"由改动牵连的模式家族"穷尽后就**收手**,不要继续散成全仓枚举。

## 各阶段要点

**威胁建模**:产出/采用本次扫描的威胁模型(默认项目级)。把它当成后续阶段的"事实来源",原样保留以便审计追溯。

**漏洞发现**:对照威胁模型,在 diff 范围内逐文件审,产出"技术上站得住"的候选漏洞清单。**若发现阶段没产出任何技术上可信的候选,就在此停住**——跳过验证和攻击路径,直接把结论收成"未发现"并完成扫描。

**验证**:对发现阶段出来的每个候选逐一验证。验证要"保留或压制已给定的实例",**不要自己把审查扩成全仓扫描**。每个候选在进入验证前要有发现记录,验证完要有验证记录,才能往出报告推进。**这里务必动手核实**——用 `run_command` 跑命令/跑测试 gate 去印证猜想,而不是停在"我觉得这里有问题"。

**攻击路径分析**:对验证后仍需判定"可报告性 / 攻击路径 / 严重度"的发现做分析。每个走到这一步的候选都要有攻击路径记录——**即便最终判定是"忽略 / 压制 / 暂缓"也要记**,保证可追溯。

## 任务系统接线(贯穿全程)

这是一项可能很长的工作,要让任务系统看得见进度、并守住"不漏审"的承诺:

- 开扫时用 **`task_progress(action=update)`** 把扫描步骤登记进当前任务清单,目标写清楚:"在 diff 范围内的每个文件都有审查闭环(完成 / 明确暂缓 / 不适用 / 已压制 并附确切理由)、每个候选都有发现+验证+攻击路径记录、最终报告已写出 之前,扫描不结束";
- 过程中用 **`task_progress`** 持续报进度(覆盖到第几个文件、发现了几个候选、卡在哪),用 **`raise_event`** 抛出需要人介入的关键事件(如发现高危、或环境缺工具导致无法验证);
- 全部完成才用 **`task_progress(action=update)`** 把对应 items 标为 `done`，并附上验证证据。

## 出报告 / 交付验收(放最后)

把所有结论汇总成一份最终报告(结构化清单:每条发现的受影响位置、污点源、控制、汇聚点、影响、严重度、处置建议),再做交付。

**在声称完成 / 给出最终回复 / 标记任务完成之前,必须满足下面的收口条件**:

- diff 范围内的**每个文件**都有审查闭环——要么完成,要么带确切理由的 `暂缓 / 不适用 / 已压制`;
- **每个走到发现阶段的候选**都有发现、验证、攻击路径三类记录,或对缺失证据给出明确的暂缓理由;
- **最终报告已经写出**。

不满足上面任何一条,就**不算扫描完成**,不要标记任务完成、也不要声称"已穷尽 diff 覆盖"。

## 收口前自检(交付验收前自己过一遍)

- [ ] 扫描目标(哪段 diff)已精确锁定,目标类型清楚。
- [ ] 威胁建模按项目级做了(除非用户明确要更窄),没被本次改动的子系统绑架。
- [ ] diff 范围内每个源码类文件都被实际审过——能逐个点名,没有"大概扫了扫"。
- [ ] 同模式的兄弟实例查过了,确认没有"一个代表性汇聚点掩盖了其他脆弱兄弟"。
- [ ] 每个候选都跑过验证(动手用 `run_command` 印证,而非空想),有发现/验证/攻击路径记录。
- [ ] 最终报告已写出,每条发现都带得到证据。
- [ ] 环境缺工具/没派成子代理/某些文件没审到的情况,已如实写进报告,没有谎称"已穷尽"。
