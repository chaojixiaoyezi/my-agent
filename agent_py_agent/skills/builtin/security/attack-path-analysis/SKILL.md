# 安全攻击路径分析

## 目标

把"已验证"或"仍然站得住"的安全发现，变成三样可核实的东西：

1. **显式的攻击者故事**——谁、从哪个面、怎么打、能拿到什么。
2. **结构化的攻击路径事实**——服务映射、暴露面、信任边界、可达性、现有缓解。
3. **校准后的严重级别 + 最终上报裁决**——并且全部锚定在本仓库的威胁模型上，而不是凭感觉。

**核心原则:证据先于断言。** 攻击链只能由代码与仓库证据支撑，不能靠脑补补全。

## 两个必备输入

开工前先确认手上有这两样，缺一就停下来问任务发起方，别硬编：

- **本仓库/本服务的威胁模型**——哪些组件、哪些角色、哪些攻击面算"在范围内"。这是判定"够不够格上报"的唯一真相源。
- **待分析的候选发现清单**——包括初筛阶段标了"可上报 / 能存活"但还没拿到正式候选编号的那些行，一并纳入，别漏。

## 工作流

```
1. 载入威胁模型 + 候选发现，作为这一轮的两个真相源。
2. 判定:受影响代码在不在威胁模型范围内?是不是真实产品面 / 真实生产链路?
3. 只用仓库证据，搭出一条"事实级"攻击路径:
     - 服务 / 组件映射
     - 暴露面与入口点(监听端口、ingress、路由、网络策略、清单文件……)
     - 身份、权限、信任边界
     - 机密处理与敏感数据流向
     - 可达性(攻击者能不能真的走到这一步)
     - 现有控制与缓解
4. 在锁定"范围 / 上报"结论前，先主动找出最强的"反证"，并说明它到底有没有推翻结论。
5. 从仓库证据出发，校准影响(impact)与可能性(likelihood)。
6. 单独再走一遍"策略调整"——拿既定矩阵机械地套，不要重新吵一遍严重级别。
7. 最终裁决为 `ignore` 的候选，直接丢弃。
8. 给每条存活的发现产出一份可读的攻击路径报告。
9. 给每条候选都留一条"攻击路径回执"——哪怕裁决是 `ignore` 或仍被搁置，也必须留痕(见下「留痕」)。
```

## 范围 + 攻击路径检查表

锁定攻击路径事实或策略裁决之前，逐条过：

- [ ] 这条到底是不是**真**安全漏洞，而不是普通正确性 bug 或误报。
- [ ] 受影响代码是不是落在**真实产品面 / 有意义的生产链路**上。
- [ ] 从仓库证据里映射出相关的服务 / 组件 / 链路上下文。
- [ ] 从仓库证据里确认暴露面与入口点(监听、ingress、负载均衡、服务端口、清单、路由、网络策略)。
- [ ] 确认这条路径上真正起作用的身份、权限、信任边界。
- [ ] 确认是否牵涉敏感数据、机密引用、或特权控制路径。
- [ ] 判定一个**现实**攻击者能不能从"在范围内的攻击面"真正触达并利用它。
- [ ] 锁定字段前，先找出针对"范围 / 上报"字段的最强仓库反证。
- [ ] 证据不全时，宁可降置信度、把字段标成 unknown；**不要仅仅因为"没看到部署证据"就自动压掉一条发现**。

## 反证检查表

对最依赖主观判断的几个字段，逐个反问一句"有没有仓库证据指向相反结论，它够不够把这条发现打死":

- 是否在威胁模型范围内(In-Scope)
- 攻击向量(Vector)
- 认证范围(Auth Scope)
- 暴露面(Exposure)
- 是否跨边界(Cross-Boundary)
- 前置条件(Preconditions)
- 影响面(Impact Surface)

专门去找证据，看这条路径是不是其实属于：

- 不在范围内
- 仅内部可达
- 仅管理员可达
- 并不跨边界
- 攻击者根本够不着
- 没有真正的上报价值

## 严重级别 + 策略校准

按下面「严重级别评定细则」机械执行。先定事实，再套矩阵，不要把两件事混在一起反复争。

## 输出契约

每条存活的发现，报告里都要包含：

- 标题
- 候选编号、实例键、台账行号(若有)
- 受影响代码位置——保留验证阶段标注的 **入口/包装层(entrypoint/wrapper)**、**根控制点(root_control)**、**落点(sink)**、**具体实现(concrete_implementation)** 这几类位置，别丢
- 攻击路径步骤
- 渲染后的攻击路径事实
- 反证小结与挑战点
- 严重级别校准
- 最终策略裁决
- 足够的推理过程，让后来的人能看懂"这条为什么存活 / 为什么被压掉"

## 留痕(攻击路径回执)

每一条走到攻击路径分析的候选，都必须在本任务里留下一条回执，**哪怕最终裁决是 `ignore` 或仍被搁置**。回执至少记清四样：

1. 候选编号
2. 攻击路径上报裁决
3. 攻击路径事实，或——确切的"证据缺口"在哪
4. 对应报告/产物的引用位置

在 my-agent 里，这条回执顺着当前任务回写：用 `task_progress(action=update)` 记进展并更新 item 状态；需要任务发起方拍板的分歧(比如"算不算在范围内"始终判不准)，用 `raise_event` 显式抛出来、把证据和待决选项一并列清，别默默搁置。整条扫描如果是用 `create_subagents` 拆给多个不同分工并自动并行,每个子代理的回执都要并回主线，不能让覆盖率隐性丢失。

## 铁律

- **优先用仓库证据**；但当网络连通性能实质性地帮你确认部署上下文、可达面、或其它影响上报的事实时，可以用——用 `run_command` 去实地核实，别凭空断言。
- **不要编造代码并不支持的攻击链。**
- **不要让候选覆盖率变成隐性的。** 每条走到攻击路径分析的候选都得留回执，`ignore` 和"搁置"也要留。
- 把验证发现转成攻击路径时，**不要丢掉确切的受影响位置**。整仓种子/根控制点行即便有更好讲的包装层或路由，也必须保留它的 `root_control 文件:行`。
- **不要因为隔壁同族发现故事更干净，就跳过一条可上报的验证行。** 要么给这条确切行产出攻击路径事实，要么带着仓库反证给出明确的最终裁决。
- **"没有公网入口证据"本身不构成决定性反证。**
- 把**攻击路径分析、严重级别校准、最终策略压制**当成三个独立子阶段，别揉一起。
- 事实定了之后，**机械地套用最终策略矩阵**，不要从头重新论证严重级别。
- 给每条候选都存一份最终可读报告。

## 攻击路径的判定尺度

- 一条发现要算"真安全问题"：必须是**现实攻击者**能从**与产品相关、合理的攻击面**利用它——尤其当它本来就在威胁模型里。
- 这个攻击面通常得是**对终端用户 / 外部行为者**(或威胁模型里明确在范围内的其它角色)**可能暴露**的，而不是某条任意的、仅内部可达的、或人为构造出来的路径。

## 严重级别评定细则(重评定)

- 要评到 **`high` 及以上**，影响必须是**实质性安全相关**——例如：账号接管、认证绕过、有意义的提权、重大敏感数据泄露/外泄、可信的 RCE、或同等级别的实质性失陷；不能只是"是个 bug / 行为很怪"。
- 一条要保住 `high`/`critical`，其利用路径与影响要清楚到——一位专业安全评审无需长篇思辨就能认账。
- **不要**因为某条只是 bug、或扫描器给它打了高分，就把普通代码 bug 当成 high/critical 安全问题。
- **不要**靠人为构造、高度思辨、或仅边界情形才成立的利用故事保住 `critical`，除非威胁模型明确支持这些条件。`critical` 意味着"立即且大概率的现实威胁"，必须当下就值得处置。
- **不要**对奇怪配置 / 古怪代码行为保留 `high`/`critical`，除非有清楚证据表明在范围内的攻击者能现实地利用它造成重大影响。
- **不要**靠"罕见的运维失误、仅内部访问、攻击者根本够不着的代码路径"来论证严重的外部影响，除非威胁模型把这些角色/路径列在范围内。
- 如果它是**真 bug 但不是安全漏洞**，严重级别归 `ignore`(实在要给也只能 `low`)。
- 如果**确凿证明根本不存在这个 bug**(描述完全错误或臆造，且你真拿到了相反的实证)，标 `ignore`，记为误报。

### 常支撑 `critical` 的漏洞类型(在代码与上下文中被证实时；非穷举)

- 可信的 RCE / 任意代码执行(命令注入、LFI 执行、易触发的内存破坏利用等)；需要实证攻击者输入能从在范围内的攻击面触发。
- 有实质且已证明影响的真实 XSS(如会话/令牌窃取、账号失陷、特权操作执行)。
- 账号接管或强认证绕过，尤其是 0-click。
- 缺失授权检查 / 授权绕过 / 租户边界击穿(易触发的 IDOR、随手换 org/id 就能越权等)。
- 严重敏感数据泄露(LFI、路径穿越、文件下载作用域错误、无授权访问数据、易构造的旁路)，且攻击者具备现实访问权(证明能读到机密、PII、签名密钥、凭据库、私钥、模型权重等高机密信息)。
- 已知利用模式、几乎不费力就能打的内存破坏。
- SQL / 数据库 / 查询注入，且有清楚证据:攻击者输入从在范围内的攻击面到达落点 + 注入影响(泄露敏感数据、写入危险记录)。
- 打破既定隔离边界的沙箱/容器/VM/浏览器/解释器逃逸。
- 导致 RCE 或泄密的服务端模板注入(SSTI)，且实证模板引擎可被利用、且可从在范围内的攻击面触达。
- 在可执行/启动/配置/固件路径上的任意文件写入，且有现实的持久化或代码执行路径；需证明攻击者能从在范围内的攻击面真正触发。
- 允许大规模、不可逆地破坏完整性的逻辑缺陷(未认证删除他人数据、跨租户篡改敏感记录、未授权修改安全关键配置)，且影响被清楚证明到等同于失陷、且可从在范围内的攻击面被触发。
- 其它未列出、但达到同等严重级别与影响的 bug；需实证可从在范围内的攻击面触达。

### 常支撑 `high` 的漏洞类型(在代码与上下文中被证实时；非穷举)

- SSRF，且同时实证:① 攻击者能从在范围内的攻击面控制被请求的 URL(绕过相关防护)；② 很可能存在其它本地/局域网/云服务可被触达以体现真实影响。报 webhook 类要谨慎，除非有清楚证据表明它危险；但也别拿"产品本就提供 webhook/下载/回调功能"或"可选的运维白/黑名单"当压制证据——只要攻击者可控目标仍能触达内网、元数据、文件后端、重定向或有副作用的目标。
- 影响重大或极易利用的可触发内存破坏。
- 暴露较低敏感度用户数据或源码的任意文件读取(若实证能读到环境机密，则升级为 critical)。
- 在可执行/启动/配置/固件路径上的任意文件写入，且有现实持久化或代码执行路径。
- CSRF，当它能触发重要的状态变更动作(改凭据、改权限、改支付/账单、改安全设置等实质有害动作)、所需受害者交互现实、且未被以下任一缓解:`SameSite=Strict cookie、auth 头、CSRF token、PUT/PATCH/DELETE、强制 JSON 请求体 content-type`。
- 有效且可达、能给出有意义访问的硬编码/默认凭据，但其范围或权限不足以评到更高。
- 允许签名伪造、令牌伪造、可信产物伪造、安全信道绕过、或解密高敏数据从而直接导致失陷的密码学缺陷；需实证这些攻击实际可行、可达、可从在范围内的攻击面完成。
- 供应链/更新通道被污染，能把恶意代码或恶意可信产物投递给用户/服务器/代理/端点(含签名绕过、包源替换)且有真实影响。重点是真实供应链与 CI 风险，而非"npm 报了个过期包"。
- 授权绕过/IDOR/提权，暴露或修改了有意义的敏感数据或特权功能，但范围更窄、限于较小对象集、限于同租户边界、或没有上面 critical 那么灾难性。
- XXE，且有清楚证据:攻击者能从在范围内的攻击面控制 XML 文档，且 XML 引擎确实存在 XXE 漏洞。
- 危险的上传/文件处理问题，能导致存储型活动内容、可信源脚本执行、或有真实安全影响的 content-type 混淆；需实证上传与访问都可从在范围内的攻击面触达。
- 反序列化、SSTI、插件滥用、宏/模板滥用、解释器滥用，危险原语清楚可达且有影响，但代码执行或失陷尚未证到 critical 的标准。
- 其它未列出、但达到同等 high 严重级别与影响的 bug；需实证可从在范围内的攻击面触达。

### 把可信的 `high` 推上 `critical` 的强因子

- 从互联网或其它宽攻击面**无需认证/近乎无需认证**即可触达。
- **0-click** 或极低门槛的利用。
- **跨租户 / 跨边界**影响，而非同用户/同租户。
- 直接拿到**签名、身份、控制面、或云凭据**。
- 现实的持久化、大规模利用、可蠕虫化、或一次失陷众多受害者。
- 已有**代码执行、完整账号接管、或皇冠机密访问**的实证，而不仅是一条"看上去可行"的路径。

### 没有极强证据就**不该**保住 `high`/`critical` 的情形

- 通用的正确性/可靠性 bug。
- 攻击者价值不明的古怪边界情形。
- 低影响的信息泄露。
- 缺乏现实可达性的内部缺陷。
- 报告只展示了一个孤立的漏洞类别，却没给出现实利用路径。
- 利用前提是攻击者**已经**握有特权/admin/root/控制台/shell/代码执行权限。
- "如果再叠加一堆假设也许有影响"式的论证。
- Self-XSS、只有弹窗 PoC 的反射型 XSS、或没有证到能拿敏感数据/会话材料/特权操作的 XSS。
- 没有展示攻击者可控、没有展示落点可达、或只有思辨影响的 SQLi/注入声明。
- 针对低影响动作/装饰性动作/登出/偏好设置的 CSRF，或需要受害者做出不现实行为的 CSRF。
- 开放重定向、点击劫持、用户枚举、限流弱点、banner 泄露、版本泄露、目录列举、堆栈跟踪、内部主机名、基础报错信息泄露——除非它们被展示为严肃利用链的一环。
- 理论性、无法从在范围内输入触发、或在目标环境里并不现实可利用的内存破坏。
- 缺失安全头、cookie 标志、CSP 弱点、TLS 观察、密码学卫生问题——没有具体利用路径与有意义的已证影响。
- 本质是"如果跟别的东西组合也许危险"、却没把那个"别的东西"展示出来的报告。
- 短暂、单用户、自我针对、易缓解、需要攻击者付出不成比例资源、或不造成严重现实业务/安全影响的 DoS。
- 需要攻击者已具备与受害者同等权限、或只暴露琐碎元数据的授权类发现。
- 已经需要 admin/root/shell 的 bug——除非"提权差量"本身就是被报告的问题。
- 仅限公开文件/低敏文件/无现实安全后果源码片段的任意文件读取。

### High/Critical 准入检查表(除非威胁模型有强理由破例，否则下列都应为真)

- [ ] 组件在范围内
- [ ] 攻击者现实存在
- [ ] 攻击面合理且在范围内
- [ ] 利用路径可信(不是单纯思辨)
- [ ] 安全影响重大
- [ ] 拿去做严肃审计 / 漏洞赏金定级，很可能被评为 `high`/`critical`，而非"信息级/低危"

## 一句话总结

把发现讲成一个**现实攻击者**的故事，每一步都用仓库证据钉住；定级先定事实再套矩阵；存活的留报告、压掉的留回执——证据先于断言，始终如此。
