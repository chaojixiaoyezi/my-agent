# 完成前必须验证

这个方法只管一个时刻：你正要对外宣布“好了”的那一刻。这句话可能说给用户或父代理听，也可能只是把 `task_progress` 里的一个条目改成完成。开口之前，手里必须有一份在这一轮里刚跑出来、正好能回答这句话的结果；拿不出来，就只说现在真实处于什么状态。

## 哪些话算“宣布”

不止“完成了”这三个字。说“修好了”“测试全绿”“没问题了”，给出最终回复或提交交付物，把条目标成已完成，向上游报告成功，结束手头的任务转去下一个，收下子代理交回的成果，都算。换个说法、只作暗示，或者先来一句“完美”再去补跑命令，性质也一样：这条规则看的是听的人会因此相信什么，而不是你用了哪个词。

## 怎样验证

1. 把想说的话改写成一句能被推翻的陈述，例如“解析模块的单元测试 0 失败”。
2. 找出能直接判定这句陈述的检查，用 `run_command` 现在完整地跑一遍。改动之前的旧结果、只跑了一部分的结果，都不能拿来用。
3. 读完整个输出：退出码是多少，失败和报错各有几条，是不是整套都真的跑到了。
4. 输出支持这句陈述，就连同关键输出一起说；不支持，就按输出显示的实际情况汇报，并附上那段输出。

## 常被错当成证据的东西

- **静态检查干净。** 要说“lint 干净”，得是对全部范围跑出来的 0 报错，而不是查了几个文件再推断其余。即便全部干净，它也只说明 lint 通过，说明不了能编译、能构建；构建成功要看构建命令本身的退出码。
- **代码已经改了。** 改了不等于症状消失，要有一个复现原始症状的用例从失败变成通过。比如修的是“跨月时日期错一天”，就得让跨月的用例跑通。
- **回归用例跑通了一次。** 这只证明它此刻是绿的，不证明它抓得住这个 bug。先撤掉修复再跑，看它失败；把修复放回去再跑，看它通过。
- **测试全部通过。** 测试覆盖的未必是全部需求。回到任务或计划原文，把要求逐条列出、逐条核对，缺什么就报什么。
- **子代理说成功了。** 用 `create_subagents` 派出的子代理会自动启动、自行回报，但回报只是它的说法。要亲自看它改了哪些文件、diff 里是否真有改动，再下结论。
- **抽查的部分没问题。** 局部通过推不出整体通过。

## 开口前看一眼措辞

想用“应该”“估计”“看着没问题”的时候，说明手里还没有证据：要么去跑，要么把不确定照实说出来。心里有底也不能代替输出。累了、急着收工、觉得“就这一次”，恰恰是最容易漏掉问题的时候，不构成跳过的理由。

## 为什么不能省

用户一旦发现某次“已完成”其实没完成，之后每份汇报都得自己再查一遍，你的汇报也就失去了意义。实际损失更直接：漏了一处导入的模块，交出去一加载就报错；说好的导出按钮，要等用户去点才发现根本不存在，只好回头返工。跑一次命令只要几分钟，事后补救贵得多。说到底，这是诚实问题。

判断自己是否真的验证过，有个简单的标准：别人只看你贴出的输出，能不能自己得出同样的结论。能，才算。
