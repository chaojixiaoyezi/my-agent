# 测试驱动开发(TDD)

这套方法的顺序是固定的：先用测试写下代码应当表现出的行为，运行它并确认它失败，再补上恰好能让它通过的实现，最后在测试的保护下整理代码。

其中“确认它失败”最容易被省掉，也最不能省。一个从没失败过的测试，就像装好后从没试响过的报警器：它挂在那里，可你不知道真出事时它会不会响。

## 规则与适用范围

**生产代码只为一个已经失败过的测试而写。** 不论是加功能、改行为、修缺陷还是做重构，都按这个顺序来。

如果实现已经抢在测试前面写好了，就把它整个删掉，从测试重新开始。别把它藏在别的文件里备用，也别开着它对照着写测试：旧代码摆在眼前，测试就会不自觉地去迎合它，结果和事后补测试没有区别。

可以不走这套流程的只有配置文件、由工具生成的代码，以及用完即弃的探索性原型，而且事先要取得任务发起方的同意。觉得眼前这次也可以破例时，去问任务发起方，而不是自己给自己放行。

## 用一个例子走完一轮

需求：写一个版本号比较函数，判断候选版本是否比当前版本新，例如 1.10.0 应当比 1.9.2 新。

### 先让测试以正确的方式失败

```python
from versioning import is_newer

def test_多位数的次版本号按数值比较():
    assert is_newer("1.10.0", "1.9.2") is True
```

写测试时的几条要求：一个测试只管一种行为，一句话概括不了它测什么，通常就该拆开；名字直接说出行为，别起 test_basic、test_it_works 这种看不出测了什么的名字；尽量让测试跑真实代码，mock 只留给确实无法在测试里真实调用的依赖；读测试的人应当能从中看出这个接口打算怎么用。

接下来通过 `run_command` 执行它，别只在脑子里推演结果：

```bash
pytest tests/test_versioning.py -k 多位数 -q
```

第一次运行多半会以 ImportError 中断，因为函数还不存在。这属于“报错”，不算有效的失败：先放一个只有签名、直接返回 None 的空壳，再跑，直到测试停在断言上（None 不是 True）。

判断这次失败是否有效，看三点：它停在断言上，而不是更早就抛了异常；输出里实际值和期望值的差别，与你事先设想的一致；拼写、导入、环境这些低级原因都已排除，剩下的解释只能是功能还没写。

还没写实现，测试却先通过了？说明它没有在描述新行为：要么这个行为早就存在，要么断言写得太宽。改写测试，直到它能失败。

### 写恰好够用的实现，看它通过

```python
def is_newer(candidate, current):
    def as_numbers(version):
        return tuple(int(part) for part in version.split("."))
    return as_numbers(candidate) > as_numbers(current)
```

这就够了。预发布标记、构建元数据、“严格模式”参数，测试都没有要求，就一样也不加；别处的代码也先别碰。

再跑一次，这回要看整套测试，而不只是刚写的那一个：新测试转绿，原有测试一个没坏，输出里也没有夹带报错或警告。如果新测试还是红的，要改的是实现；改测试去迁就实现，等于放弃了这个测试存在的意义。原有测试被连带弄坏了，也在这一步处理掉。

### 在全绿的前提下整理

全绿之后才可以动结构：合并重复的片段、换掉含义模糊的名字、把公用逻辑提出来，比如把 as_numbers 挪到模块级。每改一步就重跑一次，保证始终是绿的。这一步只改写法，不改行为；新行为要等下一轮，由新的失败测试引出来。

### 下一轮：缺陷也从测试开始

修缺陷也是同一个节奏。假设后来发现 1.2.0 和 1.2 明明是同一个版本，函数却认为前者更新。先写测试把缺陷钉住：

```python
def test_补零后相同的版本不算更新():
    assert is_newer("1.2.0", "1.2") is False
```

看它失败（True 不是 False），再修实现（比较前把较短的版本号补零），直到它通过。这条测试会一直留在测试集里：现在它证明修复生效，以后同样的问题再出现，它会最先变红。没有复现缺陷的测试，就不要动手修。

## 先写测试到底换来什么

测试的价值在于对照：功能缺失时它失败，功能补上后它通过，这一前一后才证明测试和功能之间真有关联。先写实现、再补测试，测试从诞生起就是绿的，前一半对照根本不存在。

顺序还决定了你在测什么。先写测试时，你面对的是需求，会去想调用方需要什么、哪些输入会出问题；后写测试时，你面对的是自己刚写的代码，很容易照着实现去挑用例，测来测去都是实现上的细枝末节，而写代码时就没考虑到的那些输入，照样没人去测。

手工验证也替代不了测试。它的问题不在于不认真，而在于留不下东西：试过哪些情况没有记录，下一次改动之后也没人能按原样重做一遍。

至于已经写了几个小时、舍不得删的实现：花掉的时间不会因为保留代码而变得更值，要比较的是接下来哪条路能换来可信的结果。先写测试也谈不上拖慢进度，它让缺陷在刚写下的那几分钟里就暴露出来，那时修正的成本最低。

还有两样收益是顺带得到的：以后谁把已有行为改坏了，测试集会当场报出来；有这张网兜着，重构时才敢放手去改。

## 测试写不下去的时候

无从下手时，从使用者的角度写：假设函数已经存在，你会怎么调用它、期望拿到什么结果？把这两行写出来，测试就有了骨架。仍然没有头绪，就把情况告诉任务发起方，请对方帮忙拿主意。

测试冗长复杂、离开大量 mock 就跑不起来、每个用例都要先搭一大堆准备，这些往往指向同一件事：被测代码承担得太多、依赖得太紧。公共准备可以抽成 fixture 或 helper，但更根本的办法是简化接口，并用依赖注入把外部依赖从参数传进来。测试写起来别扭，常常是接口本身不好用的第一个征兆。

## 几种常见的误区

- 觉得代码简单到不值得测：简单代码出错时往往最不容易被怀疑，而一个测试的成本很低。
- 以探索为名一路写下去：探索性的代码可以写，它的用途是帮你弄明白问题；弄明白以后把它删掉，正式实现从第一个测试开始。
- 因为接手的代码原本就缺测试而放弃：给你正要改动的那部分补上测试。
- 把 mock 用成了主角：断言只落在 mock 身上（比如只检查它收到了某个参数），被测函数的结果反而没验证；为了让测试好写，在正式代码里开后门，加一些只有测试才会调用的方法；没弄清被替换的依赖会做什么，就随手替掉。遇到这些，先回头看看耦合是不是太紧，而不是继续堆 mock。

## 收尾前的自查

任务收尾时，无论是要把任务标成完成、交出成果，还是写最后一条回复，先用下面三组问题自查，每项都得能如实答“是”：

- **证据**：每个测试都在实现之前实际跑出过失败，而且失败原因是功能缺失；此刻整套测试是绿的，运行输出也干干净净，没有夹带任何报错或警告。
- **覆盖**：新增的每个函数和方法，都能指出是哪个测试在守着它；异常输入、临界值和出错分支也都有测试。
- **写法**：让每个测试转绿的，都是当时所需的最少代码；测试跑的是真实代码，mock 只用在确实绕不开的地方。

有一项答不上来，说明那部分跳过了测试先行；按前面的规则，把相应实现删掉，从测试重新来过。

`task_progress` 里的进度要和事实对得上：哪些行为已经有先失败后通过的测试，哪些还欠着，照实更新。子代理遇到阻塞（比如缺条件、写不了或跑不了测试）时，把缺什么写进这一轮的回复，宿主会把它转交父级。交付说明里只写真正运行过的测试和结果，没跑的就写没跑。
