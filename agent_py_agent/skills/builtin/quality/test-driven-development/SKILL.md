# 测试驱动开发(TDD)

## 总则

先写测试,看它失败,再写刚好够用的代码让它通过。

**核心原则:如果你没有亲眼看到测试失败,你就无法确认它测的是不是对的东西。**

**违反规则的字面,就是违反规则的精神。** 钻"这次特殊"的空子,本质上就是没在做 TDD。

## 何时使用

**总是用:**
- 新功能
- 缺陷修复
- 重构
- 行为变更

**例外(需经任务发起方确认):**
- 一次性的探索原型
- 自动生成的代码
- 配置文件

脑子里冒出"就这一次跳过 TDD"?停。那是给自己找借口。

## 铁律

```
没有一个先失败的测试,就不写任何实现代码
```

先写了实现代码再补测试?删掉,从头来。

**没有例外:**
- 不要留着它"当参考"
- 不要一边写测试一边"顺手改改"它
- 不要去看它
- 删就是删,删干净

从测试出发重新实现。就这样,没有商量。

## 红-绿-重构循环

```
RED 写一个失败的测试
  │
  ▼
验证 RED:它确实因为"功能缺失"而失败,失败信息符合预期
  │  ├─ 失败原因不对(拼写错/环境错)──▶ 回到 RED 改测试
  │  └─ 失败原因正确 ─┐
  ▼                  ▼
GREEN 写最小实现让它通过
  │
  ▼
验证 GREEN:目标测试通过 + 其他测试仍全绿 + 输出干净
  │  ├─ 没通过 ──▶ 改实现(不是改测试),回到 GREEN
  │  └─ 全绿 ─┐
  ▼          ▼
REFACTOR 清理代码(保持全绿,不加新行为)
  │
  ▼
下一个失败的测试 ──▶ 回到 RED
```

### RED —— 写一个失败的测试

写一个最小的测试,表达"应该发生什么"。

<好>
```python
def test_失败操作最多重试三次():
    attempts = 0
    def operation():
        nonlocal attempts
        attempts += 1
        if attempts < 3:
            raise RuntimeError("fail")
        return "success"

    result = retry_operation(operation)

    assert result == "success"
    assert attempts == 3
```
名字清楚、测的是真实行为、只测一件事
</好>

<差>
```python
def test_重试能用():
    mock = Mock(side_effect=[Error(), Error(), "success"])
    retry_operation(mock)
    assert mock.call_count == 3
```
名字含糊、测的是 mock 而不是代码本身
</差>

**要求:**
- 只测一个行为
- 名字能说清行为
- 用真实代码(除非实在绕不开,否则不要 mock)

### 验证 RED —— 亲眼看它失败

**强制,绝不跳过。**

```bash
# 用 run_command 真的把这条测试跑起来
pytest path/to/test_xxx.py -k 失败操作最多重试三次
```

确认三件事:
- 测试是"断言失败",不是"报错"(error)
- 失败信息正是你预期的那条
- 它之所以失败,是因为功能还没实现,而不是因为打错字/导错包

**测试一上来就过了?** 说明你在测已有行为。这个测试要重写。

**测试报的是 error 而不是 fail?** 先把 error 修掉,反复跑到它"以正确的姿势失败"为止。

### GREEN —— 最小实现

写能让这个测试通过的最简单的代码。

<好>
```python
def retry_operation(fn):
    for i in range(3):
        try:
            return fn()
        except Exception:
            if i == 2:
                raise
    raise RuntimeError("unreachable")
```
刚好够过,不多不少
</好>

<差>
```python
def retry_operation(fn, max_retries=None, backoff=None, on_retry=None):
    # 测试根本没要求这些参数 —— 你不会需要它(YAGNI)
    ...
```
过度设计
</差>

不要加功能、不要顺手重构别处的代码、不要做任何测试没要求的"改进"。

### 验证 GREEN —— 亲眼看它通过

**强制。**

```bash
pytest path/to/test_xxx.py -k 失败操作最多重试三次
```

确认:
- 目标测试通过
- 其他测试仍然全绿
- 输出干净(没有报错、没有警告)

**测试没过?** 改实现代码,不是改测试。

**别的测试挂了?** 现在就修,别留到后面。

### REFACTOR —— 清理

只在全绿之后做:
- 去重复
- 改好名字
- 抽公共函数

保持测试全绿。不要在这一步加任何新行为。

### 重复

为下一个功能写下一个失败的测试。

## 好测试长什么样

| 维度 | 好 | 差 |
|------|----|----|
| **最小** | 只测一件事。名字里有"和/并"?拆成两个。 | `test_校验邮箱_和_域名_和_空白()` |
| **清晰** | 名字描述行为 | `test_用例1()` |
| **表达意图** | 演示了你想要的接口怎么用 | 看不出代码该干什么 |

## 为什么顺序要紧

**"我先写实现,测试放后面补上去验证一下就行"**

后补的测试一写出来就过。一上来就过,什么都证明不了:
- 可能测错了东西
- 可能测的是实现细节而不是行为
- 可能漏掉了你当初没想到的边界情况
- 你从没见过它真的逮住一个 bug

先写测试,逼你亲眼看它失败,从而证明它确实在测某个东西。

**"那些边界情况我都手动测过了"**

手动测试是临时的、零散的。你以为都测了,但是:
- 没有记录你到底测了哪些
- 代码一改就没法重跑
- 压力一上来就容易漏
- "我试的时候是好的" ≠ 系统性覆盖

自动化测试是系统的,每次都用同样的方式跑。

**"已经写了好几个小时,删掉太可惜了"**

这是沉没成本谬误。时间已经花掉了,回不来。你现在真正的选择是:
- 删掉,用 TDD 重写(再花几个小时,但拿到高把握)
- 留着,事后补测试(半小时,低把握,大概率带 bug)

真正的"浪费"是留着一份你自己都不敢信的代码。没有真实测试托底的"能跑的代码",就是技术债。

**"TDD 太教条了,务实就该灵活变通"**

TDD 本身就是务实:
- 在交付前就抓出 bug(比交付后再 debug 快)
- 防回归(测试会立刻报出谁把什么改坏了)
- 给行为留文档(测试就是用法示例)
- 让重构有底气(放手改,测试会兜住)

所谓"务实"的捷径 = 把 bug 留到线上去 debug = 反而更慢。

**"事后补测试也能达到同样目的,重在精神不在形式"**

不对。事后测试回答的是"这段代码做了什么";事前测试回答的是"这段代码应该做什么"。

事后测试会被你的实现带偏:你测的是你写出来的东西,而不是需求要求的东西;你验证的是你记得的边界情况,而不是被发掘出来的边界情况。

事前测试逼你在动手前就把边界情况想清楚;事后测试只是在核对你有没有都记住(你没有)。

半小时的事后测试 ≠ TDD。你拿到了覆盖率,却丢掉了"测试确实有效"这个证明。

## 常见借口对照表

| 借口 | 真相 |
|------|------|
| "太简单了不用测" | 简单代码照样会崩。写个测试就 30 秒。 |
| "我事后再测" | 一上来就过的测试什么都证明不了。 |
| "事后测试达到一样目的" | 事后=「这段代码做了什么」;事前=「这段代码应该做什么」。 |
| "我已经手动测过了" | 临时 ≠ 系统。没记录、不能重跑。 |
| "删掉几小时的活太可惜" | 沉没成本谬误。留着没验证过的代码才是技术债。 |
| "留着当参考,我先写测试" | 你一定会去抄它,那就是事后测试。删就是删。 |
| "得先探索一下" | 可以。探索完把它扔了,从 TDD 重新开始。 |
| "测着费劲,说明设计还没想清" | 听测试的话。难测 = 难用。 |
| "TDD 会拖慢我" | TDD 比 debug 快。务实 = 测试先行。 |
| "手动测更快" | 手动证明不了边界情况,而且每改一次都得重测。 |
| "现有代码本来就没测试" | 你正在改进它,顺手给现有代码补上测试。 |

## 红旗清单 —— 见到就停,从头来

- 先写了实现再写测试
- 测试是实现之后才补的
- 测试一上来就通过
- 说不清测试为什么失败
- 测试"以后再加"
- 给自己找"就这一次"的理由
- "我已经手动测过了"
- "事后测试也能达到同样目的"
- "重在精神不在形式"
- "留着当参考"或"在现有代码上改改"
- "已经花了好几个小时,删掉太可惜"
- "TDD 太教条,我这是务实"
- "这次情况不一样,因为……"

**以上每一条都意味着:删掉代码,用 TDD 从头来。**

## 示例:修一个缺陷

**缺陷:** 空邮箱被当成合法输入接受了

**RED**
```python
def test_拒绝空邮箱():
    result = submit_form({"email": ""})
    assert result["error"] == "邮箱必填"
```

**验证 RED**
```bash
$ pytest
FAIL: 期望 '邮箱必填',实际得到 None
```

**GREEN**
```python
def submit_form(data):
    if not (data.get("email") or "").strip():
        return {"error": "邮箱必填"}
    # ...
```

**验证 GREEN**
```bash
$ pytest
PASS
```

**REFACTOR**
如果还有多个字段要校验,把校验逻辑抽出来。

## 验收检查表

在标记任务完成 / 提交交付 / 给出最终回复之前,逐项核对:

- [ ] 每个新函数/方法都有对应测试
- [ ] 实现之前,亲眼看到每个测试失败过
- [ ] 每个测试都是因为正确的原因失败(功能缺失,而非打错字)
- [ ] 每个测试都是用刚好够用的最小代码让它通过的
- [ ] 全部测试通过
- [ ] 输出干净(没有报错、没有警告)
- [ ] 测试用的是真实代码(只有实在绕不开时才 mock)
- [ ] 边界情况和错误路径都覆盖到了

勾不全?说明你跳过了 TDD,从头来。这些不是走形式——它们就是你敢说"做完了"的依据。

## 卡住时怎么办

| 问题 | 解法 |
|------|------|
| 不知道怎么测 | 先把你"希望存在"的接口写出来,先写断言;实在不行就向任务发起方求助。 |
| 测试写得太复杂 | 是设计太复杂。把接口简化。 |
| 什么都得 mock 才能测 | 代码耦合太重。用依赖注入解耦。 |
| 测试的前置准备一大堆 | 抽公共 fixture/helper;还复杂就回去简化设计。 |

## 与调试结合

发现 bug?先写一个能稳定复现它的失败测试,再走完整 TDD 循环。这个测试既证明了你的修复有效,又防止以后再回归。

永远不要在没有测试的情况下直接修 bug。

## 测试反模式(写 mock / 测试工具时警惕)

- 测的是 mock 的行为,而不是真实代码的行为
- 为了好测,往生产类里塞只给测试用的方法
- 没搞清依赖关系就乱 mock

一旦发现自己在测 mock 而非真实行为,停下来重新想:是不是设计耦合太重了。

## 最终规则

```
有实现代码 → 必有先它而失败的测试
否则       → 这不是 TDD
```

任何例外都需经任务发起方确认。任务推进过程中如实记录哪些写了测试、哪些还没(用 task_progress / raise_event 同步真实进度),绝不在交付里声称跑过实则没跑的测试。
