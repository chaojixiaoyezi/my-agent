# 系统化排障方法

排障真正要交付的，不是“现象暂时不见了”，而是三样东西：一个被证据确认的原因，一处只针对这个原因的改动，一个能证明问题已经消失的测试。凭直觉连改几次去碰运气，即使碰对了，也说不清为什么对；碰错了，就又多出一个要排查的问题。

整套做法守着一条底线：**原因没有被证据确认之前，不改代码，也不向用户或父代理提出修复方案。** 后面每一步都为这条底线服务；想省掉哪一步时，先想清楚它原本在防什么。

## 适用场合

凡是东西没按预期工作都适用：构建报错、测试变红、几个组件对接不上、性能突然变差、真机或线上出现本地看不到的现象，或者只是输出和预期对不上。

越是下面这些时候，越要按它来，因为这时最容易凭感觉动手：你其实讲不清问题是怎么产生的；之前的一两次修改都没解决问题；看上去“改一行就好”；时间紧，或者上游在催。

“这个问题很简单”也不是跳过的理由：简单问题的取证通常几分钟就能做完，省下的也就是这几分钟；赌输了，却要多花好几倍的时间收拾。

## 排查主线

### 一、让问题稳定地再发生一次

先找出能触发问题的确切步骤，并确认它是不是每次都出现。暂时复现不了，就继续补信息：加日志、对比两边环境、多跑几次记下每次的差别，而不是凭猜测往下推。

复现的同时，把错误信息和调用栈从头看到尾，连警告一起看，尤其留意其中的文件路径、行号和错误码，它们通常就是追查的起点。再回看最近的变化：提交记录和 diff、新加的依赖、配置改动，以及出问题的机器和正常机器之间的环境差别（比如真机、测试机和本机）。

### 二、确定坏在哪一层

问题出在由多个部分串起来的链路上时（例如命令行入口、配置合并、请求组装、外部接口，或者页面表单、接口层、存储），不要猜是哪一环。在相邻两层的交界处各放一个探针：记下上一层交出去的数据和下一层实际收到的数据，环境变量和配置是否一路传到位，以及每一层当时的内部状态。跑一次复现，找出数据最先走样的那一层，然后只对它深挖。探针的写法见“工具箱”。

### 三、追到坏值最初产生的地方

报错的位置往往只是症状露头的地方。要弄清两件事：错误的值是在哪一步第一次出现的；它经过了哪些调用才到达报错点。把这条传递路径倒着走一遍，找到起点；改动放在起点，报错处只是它的下游。

这一步也要拿正常的东西做对照。先看看仓库里有没有功能相近、而且一直工作正常的实现；如果你是照着某个模式或参考实现在写，就把参考实现通读一遍，不能只挑看起来相关的几行，没吃透之前别急着照搬。接着逐条写下正常版本与故障版本的不同之处，包括看似无关紧要的细节，被略过的往往正是那一条。最后确认这段代码运行时要靠哪些外部条件：别的组件、配置项、环境，以及代码里没写出来的默认假设。

### 四、写下猜想，只做一个实验

到这里才开始解释原因。把猜想写成可以被推翻的形式：“如果根因是 A，那么做 B 时应该看到 C。”写不出来，或者只能写成“可能哪里有问题”，说明证据还不够，回到前面继续查。

实验越小越好：只改变一个条件，其余保持原样，结果才说明问题。预测应验了，再去做正式修复；没应验，这个猜想就作废，回到证据里提出下一个，而不是在没起作用的改动上继续加码。

如果卡在一个自己解释不了的机制上，就如实写明哪一点不清楚，别用含糊的说法盖过去。可以继续查资料，也可以求助：子代理只需在本轮回复中说明卡点，宿主会把它转交父代理判断。

### 五、先写失败测试，再改一处

1. 用最小的输入把故障写成测试。形式不限：能纳入项目现有测试体系的，就写成正式的自动化测试；暂时没有这套设施，一个能跑出明确失败结果的一次性脚本也行。它必须在改代码之前就位。这个测试的价值在于前后对比：改之前失败、改之后通过，这一对结果才构成“修好了”的证据。
2. 改动只瞄准已确认的根因，一次一处；旁边看不顺眼的代码和想做的重构，都留到以后另起一次。
3. 用测试 gate 验证，并回到最初的复现步骤再走一遍：原来的现象要确实消失，新测试要通过，原有测试一个也不能坏。

## 改代码前的自检

准备动手修改之前，逐条确认：

- 能按固定步骤让问题重新出现；
- 知道数据从哪一层开始出错，也找到了错误值最初产生的地方；
- 写得出一条可被推翻的原因陈述，并且有实验支持它；
- 复现问题的测试已经写好，而且确实是失败的；
- 这次改动只针对这一个原因，也不是第四次尝试。

有一条做不到，就先回去把它补齐。

## 修了几次还不好

每次修复落空，都先停手，统计一下这是第几次尝试。前两次落空还属正常：把这次失败暴露出的新事实补进证据，从第一步重新走。第三次仍然落空，就不要再换第四种改法了：连续三次落空，说明继续换猜想的收益已经很低，该怀疑的是前提。

下面这些迹象尤其值得警惕：候选修复一个比一个大，最后都指向“先重构一大片”；修好 A 就坏了 B，症状在不同位置轮流出现；越查越发现隐含的共享状态和模块间耦合。此时要讨论的是设计，而不是下一个补丁：当初选这个结构的理由现在还成立吗？如果从头写，还会这样设计吗？继续修补的代价是否已经超过调整结构？

这个问题有结论之前，不再做新的修复尝试，而是把它交出去讨论。如果你是子代理，把对设计的疑虑写进这一轮的回复即可，宿主会负责转给父代理拍板；主代理则在 `task_progress` 里写明修复已暂停、正等待设计层面的决定，后续轮次接手时就不会接着盲试。

## 确实找不到代码缺陷时

偶尔，完整走完调查后，确实能确认问题来自环境、时序或外部系统，而不是代码里的某个错误。这时要把查过的方向和排除它们的依据写下来；在代码里为它做好防护：必要的重试、合理的超时、让人一看就懂的报错；并留下足够的日志或监控，下次它再出现时能直接拿到现场。不过，下“查不到”的结论之前，先确认这不只是“还没查到”。

## 工具箱

### 边界探针

例子：用户在配置里设置了时区，导出的报表却仍按 UTC 显示。在几个边界打印同一个值：

```python
import sys

def probe(layer, value):
    # 直接写 stderr：普通日志可能因为级别或配置根本不显示
    print(f"[probe] {layer}: {value!r}", file=sys.stderr)

probe("读入的用户配置", user_cfg.get("timezone"))
probe("合并默认值之后", merged.get("timezone"))
probe("传给格式化函数的参数", tz_arg)
probe("报表第一行", rendered.splitlines()[0])
```

用 `run_command` 跑一次复现命令，找到第一条走样的输出：它的上一条还是对的，问题就在这两处之间的代码里。

### 顺着调用链倒查

例子：导出的报表里，每条记录都出现了两次。

1. 直接原因：渲染函数收到的列表里本来就有重复项。
2. 往上一层：汇总逻辑对同一个事件做了两次追加。
3. 再往上：事件处理器被注册了两次，所以每个事件都触发两次汇总。
4. 源头：注册代码写在每次重新加载配置都会执行的函数里，每加载一次就多挂一个处理器。

修复应落在第 4 步，让处理器只注册一次。在渲染前去重只是把症状藏了起来，重复的汇总照样在发生。

调用关系太深、靠读代码理不清的时候，就让程序自己交代：在可疑操作执行之前把调用栈打出来——Python 可以借助 `traceback.format_stack()`——脚本里则把相关变量打印出来。记录要赶在这一步执行前完成：等它出错再记，现场往往已经变了；输出走 stderr 这类一定能看到的通道。打印的内容要足以还原现场：涉及的路径、进程当时所在的目录、时间点，以及可能左右行为的环境变量。对比多次运行的输出，找出每次出问题时都在场的那个调用方或参数值。

如果整组测试跑完后多出一个不该有的文件，却不知道是哪个测试留下的，就把测试集对半拆开分别运行，保留仍能复现的那一半继续拆，直到只剩下那个来源。

### 不只在一处拦截

由坏数据引发的缺陷，修复时常见的做法是在出事的地方加一个判断。问题是，这个判断默认了所有数据都会从这里经过；多一个新入口、做一次重构、在测试里换一个替身对象，这个前提就可能不再成立。更稳的做法是先顺着数据流，把它经过的位置列出来，再让每一处各自把关。

具体来说：在入口（接口或工具的边界）拒收明显不合法的输入，比如缺了必填字段、数值越界、标识符格式不对；在核心逻辑执行前，确认这个值对当前操作说得通。另外两道关口常被忽略：一是按运行环境设防，在特定模式下拦住本不该发生的危险动作，比如预演（dry-run）模式下拒绝真正执行删除；二是在高风险操作执行前把现场信息记下来，出了事才有据可查。

每加一道关口，都单独验证它：临时让外层检查放行，看里层能不能独立拦下坏数据。

### 等结果，而不是等时长

固定时长的 sleep 是在赌执行速度：在今天这台机器上够用，换到更慢的 CI 或多个测试并行时就不够了，于是测试时过时不过。要等的应该是结果本身，比如队列清空、文件出现、状态切换，而不是一段估出来的时长：

```python
import time

def poll_until(check, what, timeout=10.0, interval=0.01):
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        if check():  # 每一轮都重新求值，不缓存旧状态
            return
        time.sleep(interval)
    raise TimeoutError(f"{timeout} 秒内没有等到：{what}")

# 原来：sleep(0.2) 之后直接断言队列已空，机器一忙就偶发失败
# 现在：等“队列清空”这件事本身发生
poll_until(lambda: worker_queue.empty(), "后台队列清空")
```

示例里的三个细节不能省：条件在每一轮重新求值；轮询间隔保持在毫秒级的适中水平（示例用 10 毫秒），不要密到空耗 CPU；超时必不可少，报错要写明等的是什么。

例外是测试对象本身就与时间有关，比如防抖、节流或按固定周期触发的逻辑。这时固定等待可以保留，但要先等到触发事件确实发生，时长要能从被测逻辑的已知参数推出来，并用注释交代这个数值的来历。

## 常见的走偏

多数失败的排障，都是在下面三处省了步骤。

**跳过取证。** 还没复现、没追完数据流，就先列出一串“可能的原因和改法”；或者把看到的症状当成理解了原因，认定“就是这里”便动手。

**把实验做成赌博。** 一次改好几处，结果好坏都无法归因；参考实现只看了个大概，就按自己的理解改写；或者先打个补丁让现象消失，打算回头再查。补丁一旦“起效”，就再也没人回头了，真正的原因会换个位置再冒出来。

**把“改过”当成“修好”。** 手动点一下看着正常就收工，没有先失败、后通过的测试；或者已经连续失败两三次，仍然觉得下一种改法“应该行了”。

前两类回到第一步重新取证。第三类回到第五步按顺序重新走，先有失败的测试，再有修复；屡修不好的，转到“修了几次还不好”。

用户或父代理的反应往往比你自己更早发现问题。对方开始要依据、要证据，或者直说别再猜了，说明你在证据不足时就下了结论；对方流露出原地打转的挫败感，说明当前的打法本身不奏效。这些情况都先停下，回到第一步。对方提示往更深一层想时，该审视的是设计本身。

## 前后衔接

- 第五步里那个先失败的测试，按测试驱动开发的节奏来写：先确认它失败，再写修复让它通过。
- 对外说“修好了”之前，不论是提交交付、写最终回复还是把任务标记为完成，都按完成前验证的要求重新运行并读完输出。改过代码只说明你动了手，问题是否消失，要由运行结果来回答。
