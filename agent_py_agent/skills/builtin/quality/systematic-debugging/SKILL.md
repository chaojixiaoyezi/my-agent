# 系统化排障方法

瞎改浪费时间,还制造新 bug;快速打补丁只会盖住真正的问题。

**核心原则:动手修之前,永远先找到根因。修症状 = 失败。**

**违背这套流程的字面规则,就是违背调试的精神。**

## 铁律

```
没有完成根因调查之前,不许提出任何修复方案
```

只要还没走完阶段 1,你就不能提修复方案——一句也不行。

## 什么时候用

任何技术问题都用:

- 测试失败
- 线上 / 真机 bug
- 行为不符预期
- 性能问题
- 构建失败
- 集成 / 联调问题

**尤其在这些情况下必须用:**

- 有时间压力(越急越想瞎猜)
- "就改一个地方试试"看起来很显然
- 你已经试过好几种修法
- 上一个修复没生效
- 你并没有完全搞懂这个问题

**这些借口下也不许跳过:**

- 问题看起来很简单(简单 bug 一样有根因)
- 你在赶时间(越赶越要返工)
- 上游催着"现在就修好"(系统化比来回乱试更快)

## 四个阶段

每个阶段必须走完,才能进下一个。

### 阶段 1:根因调查

**在尝试任何修复之前:**

1. **逐字读错误信息**
   - 不要略过任何 error 或 warning
   - 它们经常直接写着答案
   - 完整读完调用栈 / traceback
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗?
   - 确切步骤是什么?
   - 每次都发生吗?
   - 不能复现 → 继续收集证据,不要靠猜

3. **检查最近的改动**
   - 什么改动可能引发了它?
   - 看改动 diff、最近的提交记录
   - 新依赖、配置变更
   - 环境差异(本机 vs 真机 / 测试机)

4. **在多组件系统里先收集证据**

   **当系统由多个组件串成时(网关 → 服务 → 数据库,适配器 → agent → 工具,主代理 → 子代理 → 落盘):**

   **提修复之前,先加诊断埋点:**
   ```
   对每一个组件边界:
     - 打印进入该组件的数据
     - 打印离开该组件的数据
     - 确认环境 / 配置是否正确传递下去
     - 检查每一层的状态

   跑一次,用证据看清"到底在哪一层断的"
   再分析证据,锁定出问题的那个组件
   再去专门调查那个具体组件
   ```

   **示例(多层链路用 run_command 逐层探):**
   ```bash
   # 第 1 层:入口/调度
   echo "=== 入口拿到的参数: ==="
   echo "TASK_ID=${TASK_ID:-未设置}  OWNER=${OWNER:-未设置}"

   # 第 2 层:子代理 home / 工作目录
   echo "=== 子代理工作目录与环境: ==="
   echo "cwd=$(pwd)"
   env | grep -E 'AGENT_|MY_AGENT_' || echo "关键环境变量缺失"

   # 第 3 层:落盘点
   echo "=== 产物目录状态: ==="
   ls -la "$OUTPUT_DIR" || echo "产物目录不存在"

   # 第 4 层:实际写入
   echo "=== 实际写入结果: ==="
   test -f "$OUTPUT_DIR/result.json" && echo "已落盘" || echo "未落盘"
   ```

   **这样能看出:到底是哪一层断的**(入口 ✓、入口→子代理 ✗,还是落盘点 ✗)。

5. **追数据流**

   **当错误深埋在调用栈里时,反向追踪到源头**(完整技法见下文「支撑技法 · 根因反向追踪」)。

   **简版:**
   - 这个坏值最早从哪冒出来的?
   - 是谁带着坏值调用了这里?
   - 一路往上追,直到找到源头
   - 在源头修,不在症状处修

### 阶段 2:模式分析

**修之前,先找到规律:**

1. **找到能跑通的样例**
   - 在同一个代码库里定位类似的、正常工作的代码
   - 跟坏掉的东西相似、但是好的,是哪一段?

2. **对照参考实现**
   - 如果是在套用某个模式 / 参考实现,把它**完整读一遍**
   - 不要扫读——每一行都要读
   - 套用之前先彻底理解这个模式

3. **找出差异**
   - 能跑的和坏掉的之间,差在哪?
   - 把每一处差异都列出来,再小也列
   - 不要默认"这个肯定无所谓"

4. **理清依赖**
   - 这段代码还需要哪些组件配合?
   - 需要什么设置、配置、环境?
   - 它做了哪些前提假设?

### 阶段 3:假设与验证

**用科学方法:**

1. **提出单一假设**
   - 清楚地陈述:"我认为 X 是根因,因为 Y"
   - 写下来
   - 要具体,不要含糊

2. **最小化验证**
   - 做能验证这个假设的**最小改动**
   - 一次只动一个变量
   - 不要一次修好几处

3. **验证后再继续**
   - 生效了?是 → 进阶段 4
   - 没生效?提一个**新**假设
   - 不要在上面继续叠加修复

4. **当你不懂的时候**
   - 直说"我没搞懂 X"
   - 不要假装懂
   - 求助 / 升级研判（子代理在当前回复里说清疑点，由宿主自动递给父代理）
   - 继续查资料

### 阶段 4:落地实现

**修根因,不修症状:**

1. **先写一个会失败的测试用例**
   - 最简复现
   - 能自动化就写自动化测试
   - 没有测试框架就写个一次性脚本
   - **修之前必须先有它**
   - 先让测试红着,证明你确实复现了 bug;修完它变绿,才算真修好

2. **只做一处修复**
   - 针对锁定的根因
   - 一次一个改动
   - 不要"既然来了顺手"改别的
   - 不要捆绑重构

3. **验证修复**
   - 现在测试过了吗?(跑测试 gate)
   - 有没有弄坏别的测试?
   - 问题是不是真的解决了?

4. **如果修复没生效**
   - 停下
   - 数一数:你已经试过几次修复了?
   - **少于 3 次**:回到阶段 1,带着新信息重新分析
   - **达到或超过 3 次:停下,质疑架构(见下面第 5 点)**
   - 不要不经架构层面的讨论就去试第 4 次

5. **如果 3 次以上都失败:质疑架构**

   **下列迹象说明是架构问题,不是某次假设错了:**
   - 每修一次,就在别处冒出新的共享状态 / 耦合 / 问题
   - 修复都得靠"大规模重构"才能实现
   - 每个修复都在别处催生新症状

   **停下,质疑根本设计:**
   - 这个模式本身站得住吗?
   - 我们是不是纯粹"靠惯性硬扛着"在用它?
   - 该重构架构,还是继续修症状?

   **再多试任何修复之前，先把这个判断升级出去讨论**（子代理在当前回复里说清架构疑问，由宿主自动递给父代理研判；主代理可在任务里用 `task_progress` 标注“疑似架构问题，暂停修复待决策”）。

   这**不是**一次失败的假设——这是一个错误的架构。

## 红旗清单 —— 出现就停,回到流程

如果你发现自己在想:

- "先快速修一下,回头再查"
- "随便改个 X 看看灵不灵"
- "一口气改好几处,然后跑测试"
- "跳过测试,我手动验一下就行"
- "八成是 X,我修了它"
- "我没完全搞懂,但这么改可能管用"
- "参考实现是 X,但我换个方式套"
- "主要问题有这几个:[没调查就列了一堆修复]"
- 还没追完数据流就开始提解决方案
- **"再试最后一次修复"(在已经试过 2 次以上的时候)**
- **每修一次就在别处冒出新问题**

**以上全都意味着:停。回到阶段 1。**

**如果 3 次以上修复失败:** 质疑架构(见阶段 4.5)。

## 「你做错了」的信号

排查中收到这类反馈 / 打断,说明方向不对:

- "那个真发生了吗?" —— 你没验证就假定了
- "这能让我们看到……吗?" —— 你本该先加证据收集
- "别猜了" —— 你在没搞懂的情况下提修复
- "再往深想一层" —— 该质疑根本设计,而不只是修症状
- "我们卡住了?"(带着挫败感) —— 你这套打法不奏效

**看到这些信号:停。回到阶段 1。**

## 常见自我开脱对照表

| 借口 | 真相 |
|------|------|
| "问题简单,不用走流程" | 简单问题也有根因。流程对简单 bug 反而很快。 |
| "紧急情况,没时间走流程" | 系统化调试比"猜一下试一下"的来回乱试更快。 |
| "先试这个,回头再调查" | 第一个修复定下基调。一开始就做对。 |
| "等确认修好了我再补测试" | 没测试的修复留不住。先写测试才证明它真修好了。 |
| "一次多修几处省时间" | 修好了也分不清是哪处生效,还会引入新 bug。 |
| "参考实现太长,我把模式套过来就行" | 一知半解必然出 bug。完整读完。 |
| "我看出问题了,这就修" | 看到症状 ≠ 搞懂根因。 |
| "再试最后一次"(在已失败 2 次以上时) | 3 次以上失败 = 架构问题。质疑模式,别再瞎修。 |

## 速查表

| 阶段 | 关键动作 | 通过标准 |
|------|---------|---------|
| **1. 根因** | 读错误、复现、查改动、收集证据 | 搞懂"是什么"和"为什么" |
| **2. 模式** | 找能跑的样例、做对照 | 找出差异 |
| **3. 假设** | 提单一假设、最小化验证 | 被证实,或换出新假设 |
| **4. 实现** | 写测试、修复、验证 | bug 解决,测试全绿 |

## 当流程显示"没有根因"

如果系统化调查后,确认问题真的属于环境性 / 时序依赖 / 外部因素:

1. 你已经走完了流程
2. 记录你调查了哪些方向
3. 实现合适的兜底(重试、超时、明确的错误提示)
4. 加上监控 / 日志,便于将来排查

**但是:** 95% 的"没有根因"其实是调查不彻底。

## 支撑技法

下面三招是系统化排障的组成部分,按需取用。

### 一、根因反向追踪

bug 经常显现在调用栈深处(在错误的目录初始化、文件写到错误的位置、用错路径打开了数据库)。本能是"在报错的地方修",但那是治症状。

**原则:顺着调用链一路往回追,直到找到最初的触发点,在源头修。**

追踪步骤:

1. **观察症状**——例:`产物写到了源码目录而不是任务工作目录`
2. **找直接原因**——哪段代码直接导致了它?(例:某次写文件用了相对路径)
3. **问:是谁调用了它?**——把上一层调用方写出来
4. **继续往上追**——当时传进来的值是什么?(例:工作目录参数是空串,空串落到了进程当前目录)
5. **找到最初触发点**——这个空串最早从哪来的?(例:某处在初始化时机之前就读了还没赋值的变量)

手动追不动时,**加埋点**:在那个危险操作之前,打印出关键上下文 + 当前调用栈(Python 用 `traceback.format_stack()`,shell 里直接 echo 关键变量),然后跑一次抓日志分析:

- 关键:把日志打在**操作之前**,不要等它失败之后;用直接输出到 stderr 的方式打,别用可能被静默的 logger。
- 带上上下文:目录、当前工作目录、相关环境变量、时间戳。
- 看日志里反复出现的模式:同一个触发点?同一个参数?

**找出是哪个测试在"污染"环境**(某个产物在跑测试时出现,但不知道哪个测试干的):用二分法——把测试逐个 / 分半地跑,定位到第一个制造污染的测试为止。

**永远不要只在报错的地方修。** 追回到最初的触发点。

### 二、多层防御(纵深校验)

修完一个由"坏数据"引发的 bug,只在一个地方加校验会感觉够了。但那一道检查会被别的代码路径、后续重构、或 mock 绕过去。

**原则:在数据流经的每一层都校验,让这个 bug 在结构上不可能发生。**

- 单点校验 = "我们修了这个 bug";多层校验 = "我们让这个 bug 不可能再发生"。
- 不同层抓不同的漏:
  - **入口层**:在 API / 工具边界直接拒掉明显非法的输入(空值、不存在的路径、类型不对)。
  - **业务逻辑层**:确保数据对这一步操作是合理的。
  - **环境守卫层**:在特定上下文里挡掉危险操作(例:测试态下,拒绝在临时目录之外做破坏性写入 / 初始化)。
  - **诊断埋点层**:在危险操作前留下上下文,便于事后取证。

套用方法:① 追数据流——坏值从哪来、在哪用;② 列出所有检查点——数据流经的每一个点;③ 每一层都加校验;④ 逐层测——故意绕过第 1 层,验证第 2 层能接住。

**别只设一道校验。** 每一层都加。

### 三、按条件等待(替代写死的超时)

不稳定(flaky)的测试常靠"睡一个拍脑袋的时长"来赌时序:在快机器上过、一上负载或并发就挂。

**原则:等你真正在意的那个条件成立,而不是赌它大概要多久。**

```python
# ❌ 之前:赌时序
time.sleep(0.05)
result = get_result()
assert result is not None

# ✅ 之后:等条件成立
wait_for(lambda: get_result() is not None, "结果就绪", timeout=5.0)
result = get_result()
assert result is not None
```

| 场景 | 写法 |
|------|------|
| 等事件 | `wait_for(lambda: any(e["type"] == "DONE" for e in events), ...)` |
| 等状态 | `wait_for(lambda: machine.state == "ready", ...)` |
| 等计数 | `wait_for(lambda: len(items) >= 5, ...)` |
| 等文件落盘 | `wait_for(lambda: os.path.exists(path), ...)` |
| 复合条件 | `wait_for(lambda: obj.ready and obj.value > 10, ...)` |

通用轮询函数要点:循环里**每次重新取值**(别在循环外缓存住旧状态)、轮询间隔取 10ms 量级(别 1ms 空转烧 CPU)、**永远带超时**并抛清晰的错误信息。

什么时候"写死的等待"才是对的:当你测的就是定时行为(防抖 / 节流 / 固定 tick),并且——① 先等触发条件成立,② 等待时长基于已知时序(不是猜),③ 写注释说明为什么。

**不要把"测时序"当借口给所有等待写死延时;绝大多数 sleep 都应换成按条件等待。**

## 配合使用的其他方法

- **先写失败测试(测试驱动)**:用于阶段 4 第 1 步,先红后绿。
- **交付前验证**:声称完成 / 提交交付 / 给出最终回复或标记任务完成前,先确认修复真的生效——别把"我改了"当成"我修好了"。

## 为什么值得这么做

同一个 bug,两种打法的差距是实测出来的:

- 系统化:十几到几十分钟修好;瞎试:来回折腾几小时。
- 一次修对率高得多;引入新 bug 的概率趋近于零。

慢即是快:先搞懂根因,再动手。
