# 子代理驱动开发

这是一种把现成的实现计划落到代码上的分工方式：你负责调度和把关，计划里的任务按顺序逐个交给新开的子代理实现；每个任务交回后，再由评审子代理先后把两道关——第一道只核对“做的是不是规格要的”，第二道才评价“做得好不好”。两道都放行，这个任务才算完成。

## 适用条件

三个条件同时满足才用：

- **手上已有一份可以照着执行的实现计划。** 还没有的话，先做需求脑暴和拆解，或者干脆手动完成。
- **任务之间大体互不牵连。** 耦合很紧的，要么手动做，要么先回头把计划拆细。
- **计划要在这个会话内做完。** 如果更想换到独立会话里分批、并行地执行，那是“独立会话批量执行”那套方法的场合。

两者的分界在于是否留在当前会话。留下来，每个任务结束就能马上安排评审、当场回答子代理的提问，中间不需要交接，也不用等人插手，所以周转快；换会话，则更适合批量、并行地推进。

## 开工前

**确认工作区是隔离的。** 新建一个隔离的工作区，或者确认自己已经身在其中。除非用户明确同意，公共主干上不直接动代码。

**计划由你来读，不由子代理来读。** 把计划完整读一遍，把每个任务的原文连同它依赖的背景整段摘出来，逐项登记到 `task_progress`。之后派工时直接把摘好的原文交给子代理，别让它自己去翻计划文件。子代理省下翻文件的工夫，开局手里就有全部所需；该让它知道什么，由你把关。

## 派工

子代理看不到这条会话里发生过的任何事，它知道的只有你写进派工说明的内容。这正是它的价值所在：说明写得越准，它越专注，你自己的上下文也不会被实现细节挤占。所以每次用 `create_subagents` 派实现子代理，说明都要自成一体：

- 任务的完整原文；
- 这个任务在整体中的位置——前面已经完成了什么，做完以后谁会用到它——以及它需要的其他背景。

实现子代理一次只派一个：当前任务的两道评审都放行之前，不派下一个。几个实现者同时改同一份代码，改动会互相踩踏。

给每个角色配刚好能胜任的模型，不必一律用最强的；够用的便宜模型更快，也更省。看三个信号：任务碰多少文件、规格写到多细、需不需要判断力。只动一两个文件且规格已经写死的机械活，交给快而便宜的模型，一份写得细的计划会让多数实现任务落在这一档；要在几个文件之间协调、照着既有写法接入、或者需要排查问题的，交给标准模型；涉及架构和设计取舍、需要通盘理解代码库的工作，以及所有评审，交给手头最强的模型。

子代理提出的问题，不论是在开工前还是做到一半，都优先处理：回答要具体到它能直接照做，必要时顺带补上相关背景，用 `send_guidance` 发给这个仍在运行的子代理。它的疑问消除之前，不要催它先动手。没有疑问的话，它会自行实现、跑测试、自检，然后交回。

## 实现子代理交回之后

交回的结果大致有四种：

- **顺利完成**：直接送规格评审。
- **完成了，但附带疑虑**：疑虑要逐条过目再决定下一步。指向结果可能不对、或者做的范围和要求不一致的，先解决，再送评审；如果只是顺带一提的观察，比如“测试数据是临时造的，以后可能要换成真实样本”，记进备注，评审照常进行。
- **缺少信息**：它指出说明里少了关键内容。查清后补进说明，再派一次。
- **卡住了**：先对症。任务本身太大，就拆成几个小任务；推理难度超出了这一档模型，就换更强的模型重派；只是背景不够，就补足背景，用同一档模型重派；要是问题出在计划本身，就不该由你或子代理硬扛：把依据和需要上层拍板的问题写进当前回复，宿主会自动把这次阻塞作为终态，送到有权决定的直接上层——父代理或用户——那里。

任何一种回报都不能置之不理。重派之前至少要改变一样东西——背景、模型、任务大小或计划本身；原封不动地让同一个模型再试一次，得到的多半还是同样的结果。

## 两道评审

**规格评审在先。** 派一个评审子代理，拿任务原文逐条核对实现：要求的是否都做了，没要求的是否多做了。规格上的偏差没有“小到可以放过”的说法，查出一处，任务就还没做完。

**质量评审在后。** 必须等规格评审放行才开始，顺序不能颠倒。评审子代理检查实现是否扎实、清晰、便于维护，核对依据是项目通用的代码评审清单。

任何一道查出问题，都交回执行方修，你不要亲自动手——那会把你的上下文搅乱。实现子代理还在运行，就用 `send_guidance` 把意见转给它；它已经结束，就用 `create_subagents` 创建一个修复子代理，写清具体缺口，并附上原实现那次运行的引用。修完由同一道评审再看一遍，反复直到放行，复评一次也不能省。实现子代理自己做的检查只是交货前的初筛，正式评审照样要做。

两道都放行后，在 `task_progress` 里把这个任务标为完成，再为下一个任务派一个新的实现子代理。只要还有哪一道留着没关闭的问题，就不开始下一个任务。

## 节奏

执行期间的默认动作是继续往下做：任务与任务之间不停下来问“还要继续吗”，也不发阶段性进度汇报，这些只会占用用户的时间。只在三种时候停下：遇到自己化解不了的卡点；出现真正使工作无法推进的歧义；全部任务已经完成。

## 收尾

全部任务完成后，再派一个评审子代理从整体上看一遍，确认各部分都已齐全、彼此衔接得上。终审放行后进入任务收尾：针对这次改动做一轮验证，接着直接写最终回复，这一整套成果就作为本次交付。最终回复里说的“完成”，要能指向具体的测试输出和评审结论；拿不出这两样，就还不能这么说。

## 示例

计划：给一个命令行记账工具加上“按月导出”，共三个任务。

- **准备**：读完计划，摘出三个任务的原文和背景，登记到 `task_progress`。
- **任务一，按月筛选账目**：实现子代理很快交回，说不清楚账目时间存的是本地时间还是 UTC，属于缺少信息。你查明是 UTC，写进说明后重新派工。第二次交回顺利完成，规格评审和质量评审都一次放行，标记完成。
- **任务二，导出前遮挡卡号**：做到一半，子代理问卡号是否固定十六位；你用 `send_guidance` 答复“长度不固定，一律只露最后四位”。交回时它附了一句“遮挡规则写死在函数里”，属于顺带的观察，记下后照常评审。规格评审发现实现还给备注字段加了遮挡，而规格并没有要求；此时子代理已经结束，于是用 `create_subagents` 派一个修复子代理，写明“去掉备注字段的遮挡”，并附上原运行的引用。规格复评放行后进入质量评审，评审指出三段几乎一样的遮挡代码应当合并；照样交给修复子代理改好，复评放行，标记完成。
- **任务三，写出导出文件并附汇总行**：子代理报告卡住，理由是这一步同时牵涉文件格式、汇总计算和命令行参数。判断为任务过大，拆成“汇总计算”和“写出文件”两个任务，登记后依次派工，各自走完两道评审。
- **收尾**：派终审子代理通看全部改动，确认齐全；验证过这次的改动之后，写最终回复。

## 成本与回报

这套做法的开销集中在三处：调用次数（每个任务至少三个子代理，一个实现、两个评审）、准备工作（开工前要把全部任务原文整理出来）、以及评审来回带来的额外轮次。换来的是：每个任务都在干净的上下文里完成，互不干扰；疑问在动手前就冒出来，偏差在单个任务内部就被拦下，不至于拖到最后集成时才暴露，而那时排查的代价通常高得多。

## 相关方法

- “写计划”负责产出计划，本方法负责把它执行完。
- 每个实现子代理在自己的任务上遵循“测试驱动开发”。
- 评审时对照的是代码评审清单。
- 收尾阶段按“任务收尾”的做法走。
- 需要跨会话、成批并行地推进时，换成“独立会话批量执行”。
