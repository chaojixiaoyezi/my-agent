# 子代理驱动开发

把一份实现计划跑完的方法:**逐个任务派一个全新子代理去做,每个任务做完后接两段式评审——先查规格合规,再查代码质量。**

**为什么用子代理:** 你把任务派给上下文隔离的专职子代理。你精确编排它的指令和上下文,它就只盯这一件事并把它做成。子代理不应该继承你这条会话的历史和上下文——你只给它"为完成这个任务恰好需要的东西"。这同时也保住了你自己的上下文,专心做协调。

**核心原则:** 每任务一个全新子代理 + 两段式评审(先规格、后质量)= 高质量 + 快迭代。

**连续执行:** 任务之间不要停下来跟人确认。把计划里的任务一口气跑完。只有三种情况才停:遇到你解决不了的 BLOCKED、出现真正卡死推进的歧义、或全部任务完成。"要不要继续?"这种确认和阶段性进度汇报都在浪费时间——既然让你执行计划,就执行下去。

## 何时用本方法

```
有实现计划吗?
  否 → 先手动执行,或先做需求脑暴/拆解
  是 ↓
任务之间基本独立吗?
  否(强耦合) → 先手动执行,或回头把计划拆细
  是 ↓
要在当前会话里跑完吗?
  否(想换会话/并行批跑) → 走"批量执行计划"那套(独立会话)
  是 → 本方法(子代理驱动开发)
```

**和"独立会话批量执行"的区别:**
- 同一会话(不切上下文)
- 每任务一个全新子代理(不污染上下文)
- 每任务做完接两段式评审:先规格合规,再代码质量
- 迭代更快(任务之间不等人插手)

## 流程

先做一次性准备,然后对每个任务跑同一套循环,最后收尾。

**一次性准备:**
1. 把计划从头到尾读一遍,**把每个任务的完整原文连同上下文整段抽出来**,登记成任务清单(用 `task_progress` 跟踪状态)。注意:你来读计划,**不要让子代理去读计划文件**——你把完整任务原文喂给它。

**对每个任务,按顺序跑这套循环:**

2. **派实现子代理**(`create_subagents`):把该任务的完整原文 + 场景上下文一次性交给它。
3. **它有提问吗?**
   - 有 → 当场答清楚、补足上下文,再让它继续(必要时 `dispatch_subagents` 续派同一子代理)。
   - 没有 → 它直接做:实现、跑测试、收尾交付、自检。
4. **派"规格合规"评审子代理**:核对"代码是否严格对齐规格——该有的都有、不该有的没多"。
   - 不合规 → 由**同一个实现子代理**(`dispatch_subagents` 续派)补齐规格缺口 → **再评审一遍**,直到合规为止。
   - 合规(规格这关亮绿) → 进下一步。
5. **派"代码质量"评审子代理**:核对实现是否扎实、可维护。
   - 不通过 → 同一个实现子代理修质量问题 → **再评审一遍**,直到通过。
   - 通过 → 把该任务在 `task_progress` 里标完成。
6. 还有任务 → 回到第 2 步,派下一个任务的全新子代理(**一次只派一个实现子代理,不要并行派多个实现子代理**)。

**全部任务跑完后收尾:**
7. **对整套实现派一次"终审"评审子代理**,通看全局是否齐活。
8. 终审通过后做**任务收尾**:用 `submit_for_acceptance` 提交验收;把这一整段交付物交给系统验收。

**铁律:规格合规没亮绿之前,不准开始代码质量评审(顺序不能反);任何一关还有未闭的问题,不准进下一个任务。**

## 选模型(按角色配算力)

用"能搞定这个角色的最弱模型",省成本、提速度。

- **机械型实现任务**(独立函数、规格清晰、改 1~2 个文件):用快而省的模型。计划写得足够细时,大多数实现任务都是机械型。
- **集成与判断型任务**(跨多文件协调、套用既有模式、调错):用标准模型。
- **架构、设计、评审型任务**:用手上最强的模型。

**任务难度信号:**
- 只碰 1~2 个文件且规格完整 → 省钱模型
- 碰多个文件、有集成顾虑 → 标准模型
- 需要设计判断或对代码库的全局理解 → 最强模型

## 处理实现子代理的回报状态

实现子代理会回报四种状态之一,分别对待:

**DONE(完成):** 进规格合规评审。

**DONE_WITH_CONCERNS(完成但有顾虑):** 它做完了但标了疑点。先把顾虑读完再往下走。若顾虑关乎正确性或范围,先处理掉再评审;若只是观察性提示(如"这个文件越来越大了"),记下来,照常进评审。

**NEEDS_CONTEXT(缺上下文):** 它需要你没给的信息。补上缺的上下文,重新派。

**BLOCKED(卡住):** 它做不下去了。先判断卡点性质:
1. 若是上下文不够 → 补足上下文,用同一模型续派。
2. 若是这任务需要更强的推理 → 换更强的模型重派。
3. 若是任务太大 → 拆成更小的几块。
4. 若是计划本身错了 → 用 `raise_event` 上报,交回有判断权的上层(父代理/人)研判。

**绝不**忽视一个上报,也**绝不**在什么都没改的情况下逼同一个模型干重试。子代理既然说卡住了,就一定有东西得变。

## 优势

**相对手动执行:**
- 子代理天然走测试驱动
- 每任务上下文全新(不混)
- 并发安全(子代理之间不互相干扰)
- 子代理能提问(动手前、动手中都能问)

**相对"独立会话批量执行":**
- 同一会话(不交接)
- 连续推进(不等待)
- 评审检查点自动嵌入

**效率收益:**
- 没有读文件的开销(由你这个协调者把完整原文喂过去)
- 你精挑细选"恰好需要的上下文"
- 子代理一开始就拿到完整信息
- 疑问在动手前就暴露(不是干完才发现)

**质量门:**
- 自检在交回前先抓一遍问题
- 两段式评审:先规格合规,后代码质量
- 评审回环保证"修了真的有效"
- 规格合规防止多做/少做
- 代码质量保证实现扎实

**成本(代价):**
- 子代理调用更多(每任务:实现 + 两次评审)
- 协调者前期准备更重(一次性抽出全部任务)
- 评审回环增加迭代次数
- 但问题抓得早,比事后调错便宜

## 红旗清单

**绝不:**
- 在还没拿到明确许可时,就在主干上直接开干
- 跳过任何一关评审(规格合规 或 代码质量)
- 带着未修的问题往下走
- 并行派多个实现子代理(会冲突)
- 让子代理自己去读计划文件(改成把完整原文喂给它)
- 省掉场景铺垫(子代理得明白这个任务嵌在整体的哪个位置)
- 无视子代理的提问(让它继续之前先答)
- 在规格合规上接受"差不多就行"(规格评审挑出问题 = 没做完)
- 省掉评审回环(评审挑出问题 = 实现子代理修 = 再评审一遍)
- 拿子代理的自检顶替真正的评审(两者都要)
- **在规格合规亮绿之前就开始代码质量评审**(顺序反了)
- 任一关评审还有未闭问题就进下一个任务

**子代理提问时:**
- 答清楚、答完整
- 需要就补更多上下文
- 别急着把它推去实现

**评审挑出问题时:**
- 由(同一个)实现子代理来修
- 评审再看一遍
- 重复直到通过
- 别跳过那次复评

**子代理把任务做砸时:**
- 派一个带明确指令的修复子代理(`dispatch_subagents` 续派同一个)去修
- 别自己上手改(会污染你的上下文)

## 配套衔接

**前置/收尾的配套方法:**
- **隔离工作区**:开干前确保有一个隔离的工作区(新建一个,或确认已有的),别在公共主干上直接动手。
- **写计划**:本方法执行的那份计划,由"写计划"的方法产出。
- **代码评审清单**:评审子代理用的核对模板,沿用统一的代码评审清单。
- **任务收尾**:全部任务跑完后,走任务收尾,用 `submit_for_acceptance` 提交验收。

**子代理自身应遵循:**
- **测试驱动开发**:每个子代理对自己的任务都走测试驱动。

**何时改用别的路子:**
- 若想换独立会话并行批跑,而不是在当前会话里串行跑完,改用"独立会话批量执行"那套。

---

**一句话守则:** 一次只推一个任务,先把规格合规这关亮绿、再过代码质量,两关都绿才标完成、进下一个;声称完成、提交验收(`submit_for_acceptance`)前,凭的是真跑过的测试和真亮绿的评审,不是"应该没问题"。
