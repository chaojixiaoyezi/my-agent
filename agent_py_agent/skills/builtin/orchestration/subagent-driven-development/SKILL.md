# 子代理驱动开发

委派是可选执行方式，不是所有实现、Skill 创作或交付的强制前提。

## 选择最小分工

简单任务可在当前会话直接完成，不强制实现代理、双评审代理、终审代理或逐项确认。原生 Skill/Workflow 保持对象类型，不自动打包；创作与验收按 `writing-skills`。

有多个独立子任务时才按职责和文件边界委派。彼此不冲突的工作可以并行；依赖未完成或会改同一文件的任务串行。不要仅为分工增加代理。

高风险工作涉及权限、关键业务或长期运行行为时，安排相称测试和必要独立评审，保留用户授权与适用的机器审批；不能把审批交给子代理模拟完成。

## 派工合同

使用当前实际可用的授权编排工具。工作区按项目约定隔离，不在未经授权的公共主干修改。

每项说明包含目标、验收、必要背景、精确输入引用、可读写范围、文件所有权和验证要求。材料较多时给正文引用让执行者读取，不要求父级先完整吞下所有长材料。

把原计划条目交给子代理时，在 `covers` 复制 exact id。只读分工必须保持只读，不能改写成“发现后直接修复”；角色和工具可用性不增加业务授权。

## 接收与整合

核对交回文件确实存在、引用可读、改动属于任务范围，再复用有效测试证据。文件存在、可导入或代码数量达标只是局部证据，不代表关键路径完成。

需求核对和质量检查都要覆盖，但可以在一次针对性检查中完成；是否另派评审者、是否分两阶段，取决于风险和项目既有要求。没有必要给每项机械套用两道独立评审。

发现缺陷后由仍在运行的执行者修复，或由父级在自己的授权范围内修复；按实际改动重跑相关入口。不能删除、跳过或放宽有效失败测试来伪造通过。已验证且未变化的结果不重复跑。

遇到失败先读真实错误，补输入、调整任务或修正方法；无权限拒绝或隔离证据，不把超时、空日志自动归因于沙箱。

## 收尾

任务有可推进部分就继续，不逐项问“还要继续吗”。等待真实交接后再整合，不编造子代理结果，也不为证明完成重写已合格的交付。

最终验证覆盖当前版本的关键主链路和目标观察点。汇报实际产出、已执行结果、未验证范围及真实阻塞；评审结论不能替代运行证据。
