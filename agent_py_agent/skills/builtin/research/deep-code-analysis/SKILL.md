# 深度代码分析方法

一份有价值的架构分析,是"读了源码的人"才写得出来的。判断标准:每个结论都能指到具体文件和行为。

## 读懂一个项目的顺序

1. **找真入口**:`main`/`bin`/`cli`/`package.json#bin`/`pyproject#scripts`——从进程怎么启动开始,不从 README 开始。README 只用来对照验证你的结论。
2. **跟主循环**:从入口往下追到核心执行循环(请求处理循环/agent 轮询循环/事件循环)。把循环体里每一步做什么记下来——这是项目的心脏,值得读细。
3. **数模块事实**:每个顶层目录/包,打开 2-3 个核心文件,记录:对外暴露什么、依赖谁、被谁依赖。"职责"要从代码读出来,不从目录名猜。
4. **抓一个完整链路**:挑一个典型功能(如"一次工具调用"),从入口到落盘把整条链路走通,引用沿途的文件:行号。能写出一条真实链路,胜过十句概括。
5. **优缺点必须带证据**:每条优点/缺点后面跟"证据:`path/file.py:行号` 的具体做法"。写不出证据的判断删掉。

## 分量的自我校验

- 一个项目的分析至少覆盖:入口与主循环(带文件路径)、3 个以上核心模块的职责事实、1 条完整调用链、3 条以上带证据的优缺点。达不到说明读得不够,继续读,不要硬写。
- 多项目对比时,先把每个项目单独读到上述深度,再做横向——没读深的项目在对比表里如实标注"未深读",不要靠印象填格子。
- 时间不够读完全部时:宁可深读一半项目并明确说明哪些未覆盖,不要全部浅读。
