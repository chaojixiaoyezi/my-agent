# 接收代码评审

## 概述

代码评审是技术评估,不是情绪表演。

**核心原则:** 动手前先核实,假设前先发问。技术正确高于社交舒适。

## 响应流程

```
收到评审反馈时:

1. 读全:把反馈完整读完,先不反应
2. 理解:用自己的话复述这条要求(说不清就直接问)
3. 核实:对照本项目的真实代码去验证
4. 评估:这条建议对「本项目」技术上成立吗?
5. 回应:要么给出技术性确认,要么带技术依据地反驳
6. 落实:一次改一条,每条都验证(跑 run_command / 跑测试 gate)
```

## 禁止的回应

**永远不要:**
- "你说得完全对!"
- "这点很棒!" / "反馈太到位了!"(表演式)
- "我这就去改"(在核实之前)

**应该改成:**
- 复述这条技术要求
- 提澄清问题
- 如果建议有误,用技术依据反驳
- 或者直接开干(行动胜过表态)

## 处理含糊的反馈

```
若有任何一条看不懂:
  停 —— 先别动手改任何东西
  对看不懂的那几条提澄清问题

为什么:各条之间可能相关。理解了一半 = 改错。
```

**示例:**
```
对方:"把 1-6 都改了"
你看懂了 1、2、3、6,4、5 没看懂。

错:先把 1、2、3、6 改了,4、5 回头再问
对:"1、2、3、6 我理解了。第 4、5 条要先澄清才能动手。"
```

## 按来源区别对待

### 来自可信的协作方(任务发起方 / 主代理)
- **可信** —— 理解清楚后落实
- 但**范围不清仍要问**
- **不要表演式附和**
- 直接动手,或给一句技术性确认即可

### 来自外部评审者
```
落实之前先过一遍:
  1. 查:对「本项目」技术上正确吗?
  2. 查:会不会破坏现有功能?
  3. 查:现在这么写,是不是有原因?
  4. 查:在所有平台 / 版本上都成立吗?
  5. 查:评审者是否掌握完整上下文?

若建议看起来是错的:
  用技术依据反驳

若一时无法核实:
  如实说:"没有 [X] 我没法核实这一点,要不要我去 [调查 / 确认 / 直接照做]?"

若与既定决策冲突:
  停下,先和任务发起方对齐再说
```

**通用准则:** 外部反馈——保持怀疑,但要认真核实。

## "做得专业点"类建议的 YAGNI 检查

```
若评审者建议"把这个好好实现一下":
  先 grep 代码看这东西到底有没有被调用

  若没人用:"这个接口没有任何地方调用。直接删掉(YAGNI)?"
  若有人用:那就好好实现
```

**通用准则:** 如果这个功能我们用不上,就别加。能砍则砍。

## 落实顺序

```
面对多条反馈:
  1. 先把看不懂的全部澄清
  2. 再按这个顺序落实:
     - 阻塞性问题(崩溃、安全)
     - 简单修复(笔误、import)
     - 复杂修复(重构、逻辑)
  3. 每条单独验证
  4. 确认没有引入回归
```

## 何时该反驳

出现以下情况就反驳:
- 建议会破坏现有功能
- 评审者上下文不全
- 违反 YAGNI(加了用不上的功能)
- 对当前技术栈而言技术上不正确
- 存在历史遗留 / 兼容性原因
- 与既定的架构决策冲突

**怎么反驳:**
- 讲技术依据,不要防御性辩解
- 提具体问题
- 引用能跑通的测试 / 代码作为证据
- 涉及架构层面,拉上任务发起方一起定

## 确认正确的反馈

当反馈确实对的时候:
```
对:"已修。[简述改了什么]"
对:"发现得好——[具体问题]。已在 [位置] 修复。"
对:[直接改掉,让代码本身说话]

错:"你说得完全对!"
错:"这点很棒!"
错:"多亏你发现!"
错:"谢谢你 [任何]"
错:任何道谢式表达
```

**为什么不道谢:** 行动会说话。直接改就行。代码本身就证明你听进去了。

**如果发现自己正要写"谢谢":** 删掉它,改成陈述这次修复。

## 反驳错了,体面地纠正

如果你反驳了,但是你错了:
```
对:"你是对的——我查了 [X],它确实 [Y]。这就改。"
对:"核实过了,你是对的。我先前理解错是因为 [原因]。在改了。"

错:长篇道歉
错:辩解自己当初为什么要反驳
错:过度解释
```

把纠正说成一句事实,然后继续往前走。

## 常见错误对照表

| 错误 | 纠正 |
|------|------|
| 表演式附和 | 陈述要求,或直接动手 |
| 盲目照做 | 先对照代码核实 |
| 攒一批不测就提交 | 一次一条,每条都测 |
| 默认评审者一定对 | 检查会不会改坏东西 |
| 回避反驳 | 技术正确 > 社交舒适 |
| 只实现一部分 | 先把所有条目澄清清楚 |
| 没法核实却照样硬干 | 说明局限,问清方向 |

## 真实示例

**表演式附和(差):**
```
评审者:"删掉遗留代码"
错:"你说得完全对!我这就删……"
```

**技术核实(好):**
```
评审者:"删掉遗留代码"
对:"在查……目标环境是 10.15+,这个 API 要 13+,得留着做向后兼容。
   当前实现的标识符写错了——是改对它,还是干脆放弃对 13 以下的支持?"
```

**YAGNI(好):**
```
评审者:"把指标统计好好实现:接数据库、加日期筛选、支持导出"
对:"grep 过了——没有任何地方调用这个接口。直接删(YAGNI)?
   还是我漏看了哪里在用?"
```

**含糊条目(好):**
```
对方:"把第 1-6 条都改了"
你看懂了 1、2、3、6,4、5 没看懂。
对:"1、2、3、6 我理解了。第 4、5 条要先澄清才能动手。"
```

## 在任务系统里回应评审

评审反馈往往挂在某条任务的进展记录里:
- 回应就**顺着那条任务回**(`task_progress` / `TaskUpdate`),写清"哪条建议、核实结论、改了还是不改、为什么",而不是另起一条无关的事件。
- 需要任务发起方拍板的分歧,用 `raise_event` 显式抛出来,把技术依据和待决选项一并列清,不要默默搁置。

## 底线

**外部反馈 = 待评估的建议,不是必须执行的命令。**

核实。质疑。然后再动手。

任何"声称完成"或"交付验收(`submit_for_acceptance`)前 / 标记任务完成前"落实评审意见,都按上面这套流程走:一次一条、逐条验证、确认无回归,改完再收尾。

不表演式附和。技术严谨,始终如此。
