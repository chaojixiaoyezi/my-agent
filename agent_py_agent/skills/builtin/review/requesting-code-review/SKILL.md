# 请求代码评审

自己写的代码，自己最难看出毛病：你清楚每一行想干什么，读的时候会不自觉地替它补上意图。独立的评审子代理没有这层背景，只能看到代码实际做了什么，再拿去和需求对照，价值正在于此。

效果好不好，取决于你交出去的材料。材料里只有改动和原始需求时，评审者只能就事论事，判断产出是否达标；一旦掺进你的思路、会话记录和放弃过的方案，它就会顺着你的逻辑去理解代码，漏掉的恰好也是你漏掉的地方。另外，评审在子代理那边完成，你自己的上下文不会被这些材料占满，手上的工作不用中断。

一个缺陷在代码里待得越久，压在它上面的改动就越多，拆起来越费劲。所以评审要跟着改动的节奏走，不要攒到最后一次做。

## 什么时候发起

必须送审的时刻：

- 按子代理分工推进时：子任务一交回就送审，这时缺陷还浮在表面，没被后面的改动盖住，等它修好了再派下一项；
- 按计划逐项推进时：一项收尾或走到阶段节点，就送审一次，改完再接着做；
- 每做完一块主要功能；
- 收工之前，也就是标记任务完成或给出最终回复的前一步；即兴开发、手上没有计划的，也至少在交付验收前送审一次。

不强制但很划算的时刻：卡住的时候，没参与过的人常能一眼看出你绕不出来的地方；动大手术重构之前，先让评审给现状打个底；折腾很久才修好一个缺陷之后，确认修法没有引出新问题。

别用“这点改动很简单”说服自己跳过，出错的往往正是没人多看一眼的小改动。

## 准备材料，派出评审

1. 评审者只该看这次动过的地方，不必通读项目。用 `run_command` 导出从上一个收尾点到现在的 diff，或整理一份本次新增、修改的文件清单，作为评审的全部素材。
2. 任务说明只写四样：原本要达到什么（任务目标或验收标准）；这次做了什么（一两句）；改动在哪里（上一步的 diff 或文件清单）；请重点看什么（逻辑对不对、边界情况处理了没有、是否真正满足需求，而不是挑风格）。
3. 发出之前再读一遍，删掉一切在讲“我当时怎么想”的内容：推理过程、会话历史、试过又放弃的方案。
4. 把这份说明交给 `create_subagents`，建一个只负责评审的子代理，创建后宿主会自动让它开始工作。

## 处理评审意见

按严重程度安排处理时机。严重的：先放下其他事把它修好，修好之前不往下做。重要的：最迟在开始下一项之前解决。次要的：记下来就行，写进 `task_progress` 或另开一个后续任务，等合适的时候处理。

评审者也会看错。你认为某条意见不对时，拿证据说话：指给它看相关的实现和测试，必要时用 `run_command` 跑一次测试 gate 并附上输出；或者请它说明依据。反过来，对方的技术理由站得住，就老实改，不要为了保住原方案去争辩。全盘照收和一概拒绝，都说明你没有真正读意见。

严重和重要两档全部处理完（修好，或用证据证明不成立），才能声称完成或提交交付验收。
