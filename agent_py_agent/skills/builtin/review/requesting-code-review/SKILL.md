# 请求代码评审

在问题扩散之前,派一个**独立的评审子代理**来检查本次改动。要点不在"派子代理"本身,而在**给它什么上下文**:只给它本次改动的 diff 和原始需求,**绝不**把你这一路的会话历史、思路、试错过程喂给它。这样评审者盯的是"产物对不对",而不是"作者当时怎么想的";同时也省下你自己的上下文,继续干活。

**核心原则:早评审,勤评审。** 一项改动越晚被看,埋的问题越贵。

## 何时该请求评审

**必做:**
- 子代理分工开发中,**每完成一项任务**就评审一次
- 完成一个主要功能后
- 标记任务完成、提交交付验收(`submit_for_acceptance`)之前

**可选但很值:**
- 卡住时(换个没有思维包袱的视角)
- 大改重构前(先拿一份基线判断)
- 修完一个绕人的 bug 后

## 怎么请求

**1. 框定要评审的改动范围**

不要让评审者去翻整个项目。明确告诉它"看哪段改动":本次任务新增/修改的文件清单,或本轮改动相对上一个收尾点的 diff。用 `run_command` 取出 diff 文本(例如对比当前与上一个收尾点),作为给评审者的素材。

**2. 派评审子代理**

用 `create_subagents` / `dispatch_subagents`(或 `schedule_child_subagents` 排期)派一个专职评审子代理。给它的任务描述里**只放这四样**,不放别的:

| 给评审者 | 内容 |
|---|---|
| 改动概述 | 一两句话说清这次做了什么 |
| 原始需求 | 它本该做到什么(对应的任务目标 / 验收标准) |
| 改动范围 | 涉及的文件清单,或上一步取出的 diff |
| 评审重点 | 正确性、边界、是否真满足需求(而非风格洁癖) |

**关键:** 不要把你的会话历史、推理过程、试了又删的弯路传给它。上下文越干净,评审越聚焦在产物本身。

**3. 按反馈分级处理**

| 级别 | 处理 |
|---|---|
| 严重(Critical) | 立刻修,不修不往下走 |
| 重要(Important) | 继续下一步前修掉 |
| 次要(Minor) | 记下来(可经 `task_progress` 留痕或开后续任务),择机再修 |

- 反馈若确实有理,照做。
- 反馈若是错的,**有理有据地反驳**:指出能证明它没问题的代码/测试,或请它说清依据——不要无脑顺从,也不要无脑硬刚。

## 与各种工作流的衔接

**子代理分工开发:** 每完成一项任务就评审,趁问题还没和后面的改动缠在一起时拦下来,修完再开下一项。

**按计划执行:** 在每项任务结束、或自然的检查点处评审;拿到反馈、应用、继续。

**临场开发(无固定计划):** 至少在交付验收前评审一次;卡住时也评审一次换视角。

## 红旗清单

**绝不:**
- 因为"这改动很简单"就跳过评审——简单的改动一样会错
- 无视严重(Critical)问题
- 带着没修的重要(Important)问题往下走
- 对有理有据的技术反馈强行辩驳

**当你判断评审者错了:**
- 用技术依据反驳,而不是态度
- 拿出能证明它能正常工作的代码 / 测试结果(必要时 `run_command` 跑一遍测试 gate 当场验证)
- 或请评审者澄清它的依据

## 一句话自检

派评审前问自己:我给评审者的,是**干净的"改动 + 需求"**,还是夹带了我的思考过程?是后者就重新裁剪。声称完成 / 交付验收前问自己:严重和重要问题都清零了吗?没清零就不算完成。
