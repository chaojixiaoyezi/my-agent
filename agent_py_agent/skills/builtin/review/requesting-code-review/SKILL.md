# 请求针对性代码评审

评审帮助发现缺陷，不自动成为每次改动、每个子任务和最终回复前的多代理关卡。

## 按风险选择检查

简单任务可由执行者自查需求、差异和相关验证，不强制独立子代理、多阶段评审或重复确认。原生 Skill/Workflow 的简单创作按 `writing-skills` 验收，不自动打包。

复杂变更、关键接口、跨模块改动或用户明确要求评审时，安排独立检查。高风险变更涉及权限、关键业务、不可逆动作或长期运行行为时，保留相称测试、必要独立评审、用户授权及适用的机器审批。

项目已有明确审查门禁时遵守；不要自行把这种门禁扩展到所有普通文案和小改动。

## 准备材料

给评审者原始目标和验收标准、本次 diff 或精确文件列表、必要接口背景、已有验证结果，以及希望重点核查的风险。不要转交整段会话或作者推理来诱导结论。

使用当前可用的授权编排工具时明确只读范围：评审者检查并报告，不因找到问题自行修改、安装、部署或对外发送。没有子代理工具时可以直接进行范围内评审，不编造独立评审已完成。

## 处理问题

区分观察到的缺陷和原因假设，给文件位置、触发输入、预期与实际结果。严重和重要缺陷应修复，或用证据证明不成立，再交付相关功能；范围外建议单列，不顺手扩大实现。

修复后针对实际变化验证，已有有效证据可复用。必要复评只覆盖受影响风险，不因改了一处机械重启整套流程。

## 汇报

说明检查范围、发现、已解决问题和未验证部分。编译、静态检查、评审通过都不等于启动或业务链路完成；最终结论必须对应当前版本与实际目标观察点。
