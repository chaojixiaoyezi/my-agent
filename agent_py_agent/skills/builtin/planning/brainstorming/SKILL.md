# 把想法变成可执行设计

只澄清会改变实现或验收的未知项，不把讨论变成所有工作的前置关卡。

## 简单任务直接推进

用户已经说清目标、输入、输出和范围的简单任务，可以直接按授权实现并验收；不强制脑暴、逐段确认、设计文件、实现计划或评审串联。必要时用几句话说明理解，不把这段说明变成新的等待门。

原生 Skill/Workflow 保持对象类型，不自动打包；简单创作直接按 `writing-skills` 编写与验收。

## 有歧义时澄清

1. 先读相关文件与约束，区分已知事实和假设。
2. 只问真正影响方案的问题，已有答案不重复询问；不把实现细节变成选择菜单。
3. 存在实质取舍时给出可行方案、代价和推荐；没有取舍不凑两三套方案。
4. 说明组件边界、数据流、失败处理和验收方式。规模大到含多个独立系统时先拆范围。

高风险变更涉及权限、关键业务、不可逆动作或长期运行行为时，确认新增风险与授权范围，保留相称验证和适用的机器审批。只读诊断不能因发现问题自动转成修复；用户已经明确批准的同一方案不重复确认。

## 是否需要文档和确认

复杂、多方协作或用户要求留存的设计才落盘，位置优先遵循用户与项目约定；需要时可用 `docs/specs/YYYY-MM-DD-<主题>-design.md`。短任务可以在当前回复说明，不为流程额外造文件。

只对尚未授权的重要选择等待确认。设计已清楚且实现已获授权，就继续执行；只有用户要求仅设计时才在设计交付后停止。是否需要 `writing-plans` 取决于后续复杂度，不是必经下一站。

## 核实与交付

可低成本查实的假设做只读核查或范围内验证；不能查实的标为假设。图能帮助作决定时再提供可视化，不强制另起一轮确认或搭演示。

最终对照目标、实际产出与验证证据，说明偏离和未验证内容。设计被确认不证明实现或业务链路已经完成。
