# 写可执行计划

计划服务于执行，不替代执行，也不自动增加确认和评审关卡。

## 先判断是否需要计划

简单任务可用几行步骤或直接完成，不强制完整计划文件、多阶段确认、每步提交或多子代理。原生 Skill/Workflow 的简单创作按 `writing-skills` 执行，不自动打包。

复杂任务沿用同一份 `task_progress`，使用稳定条目记录实际完成情况；已有获批需求不重走脑暴。只有用户要求计划文件或确实需要交接时才落盘，遵循指定位置，未指定时可用 `docs/plans/YYYY-MM-DD-<主题>.md`。

高风险任务要在计划中写明权限、关键业务或长期运行风险，保留相称测试、必要用户授权和适用的机器审批；计划文字不能替代审批。

## 计划的最小内容

- 目标、范围、不做什么和最终验收入口。
- 真实文件路径及各自职责，复用已有结构，不顺手规划无关重构。
- 可独立验收的任务、依赖关系及写入边界；并行任务不得争用同一文件。
- 每项的实现要点、必要输入、错误处理和验收标准。
- 实际检查命令或人工步骤，以及预期结果；预期与已执行结果分开写。

会改变代码行为时，优先设计能暴露当前缺陷的测试，再修实现并重跑同一入口。普通文案和简单 Skill 按风险做正式加载、读回与代表性输入验收，不制造多代理必败基线。

步骤具体到可执行即可，不要求每步两到五分钟，也不把整份实现复制进计划。只有容易歧义的关键接口、数据结构或测试需要代码示例；不能留下影响执行的 TODO 或不存在的函数名。

## 一次自查

核对名称、签名、字段、路径和依赖是否一致；需求是否各有实现与验收；是否包含未授权操作。发现问题直接修正，不因修改计划自动再开一轮审查。

## 继续执行还是交接

用户只要求计划时，交付计划及未决问题。用户同时授权实现且方案明确时，计划完成后继续，不再要求选择执行模式或逐批批准。

当前会话直接执行或按文件边界委派都可以。只在真实阻塞、新增范围或新增风险需要决定时停下来；完成后交付产物、实际验证证据和未验证部分。
