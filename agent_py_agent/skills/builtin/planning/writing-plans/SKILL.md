# 写实现计划

设想计划的执行者是这样一个人：会写代码，但从没见过这个仓库，不熟悉这里的工具和业务，也不太会设计测试。计划要写到这个人拿着就能一步步做完。所以文件路径、代码、测试、命令、预期结果、需要参考的文档，凡是执行时要用到的都写进计划；测试代码直接给出来，不能只留一句“补个测试”。整份计划坚持不重复（DRY）、不做眼下用不到的东西（YAGNI）、先写测试再写实现（TDD），并且每完成一小步就收一次尾。

开写之前跟用户说一声，这份计划是按 writing-plans 的做法来写的。计划默认保存为 `docs/plans/YYYY-MM-DD-<功能名>.md`；用户或任务指定了别的位置时，以指定的为准。

## 计划文件的样子

每份计划都以一段总述开头，让执行者一眼看清要交付什么、打算怎么做：

```markdown
# 实现计划：<功能名>

> 执行说明：按任务顺序逐个完成，每一步用 `- [ ]` 复选框记录进度。可以每个任务派一个独立子代理来做，也可以在当前会话里分批做。

**要交付什么：** 一句话。

**实现思路：** 两三句话。

**用到的技术与库：** 列出关键项。

---
```

总述之后是一个个任务，格式统一：先列涉及的文件，再按“先测试后实现”排步骤。下面是一个任务的示意（路径和用例名只是举例，写计划时换成仓库里的真实值）：

````markdown
### 任务 3：解析时长字符串

涉及文件：
- 新增 `src/timekit/duration.py`
- 修改 `src/timekit/cli.py:40-58`（`--timeout` 改为调用新函数）
- 测试 `tests/test_duration.py`

- [ ] 先写测试，此时它应当失败：

```python
def test_parse_duration_minutes():
    assert parse_duration("5m") == 300
```

- [ ] 运行 `pytest tests/test_duration.py::test_parse_duration_minutes -v`，预期失败，原因是 parse_duration 还不存在。
- [ ] 补上让测试通过所需的最少代码：

```python
def parse_duration(text: str) -> int:
    if text.endswith("m"):
        return int(text[:-1]) * 60
    raise ValueError(f"无法解析的时长：{text}")
```

- [ ] 再运行同一条命令，预期通过。
- [ ] 收尾：在 `task_progress` 里记上一笔，或者做一次提交，提交内容只包括这一步碰过的文件。
````

## 动笔前先定两件事

**一份计划管多大。** 一份计划只对应一块能独立交付的东西：照着它做完，应当得到一个能运行、能测试的结果。如果需求同时牵涉几个互不依赖的子系统，说明需求阶段就该拆而没拆，这时先向用户提议按子系统各写一份计划。

**文件怎么分工。** 拆任务之前，先把会涉及的文件排成一张表，逐项注明是新增还是修改、承担什么职责；任务怎么拆，基本由这张表决定。已有仓库先守它原来的习惯，本来就习惯写大文件，就不要借机重组；例外是你正要修改的那个文件已经大到很难下手，这时可以把拆分它列为计划里的一个任务。新写的部分倾向于小而专一的文件（能一次读完的文件，推理和修改都更稳）：按职责而不是按技术层次划分，会一起修改的代码放在一处，文件之间用清楚的接口衔接。理想状态下，任何一个任务的改动单独拿去评审也能看懂。

## 每一步写到什么程度

拆步骤时以“一个动作”为单位，每步的工作量控制在两到五分钟。写失败的测试是一步，运行它、确认确实失败是一步，写实现是一步，再运行确认通过是一步，收尾又是一步。

步子小之外，还要具体到能直接照做：改代码的步骤附上代码，要运行的步骤写出确切命令和预期结果。下面两类写法看似完整，其实把思考推给了执行者，要逐一替换掉：

- **留了空的**：用“TODO”或“这里之后再定”占位；写着“测试见后”，却始终没有测试代码；步骤只有目标没有做法。这些都要当场写完，凡是改代码的步骤一律带代码块。
- **写了却没法照做的**：“注意异常情况”“把输入检查一下”这类笼统要求，要写明捕获哪个异常、检查哪些字段、各种边界值分别怎么处理；“参照前面的任务照做”，要把代码重新写一遍，因为执行者未必按顺序读；某个步骤调用的类型、函数或方法在整份计划里找不到出处，要么增加一个定义它的任务，要么换成已经定义过的名字。

## 保存前自查

计划写完，自己再审一遍，不要派子代理代劳。把需求原文放在旁边，重点看三件事：

- **名字前后是否一致**：后面任务里的函数名、签名、字段名，是否和前面定义时一模一样？前面定义的是 `load_profile()`，后面写成了 `load_user_profile()`，执行时就会出错。
- **有没有含糊的地方**：按上一节的两类情况，在计划里搜一遍。
- **需求是否都有着落**：需求里的每一条，能不能指到一个具体实现它的任务？指不到的，补一个任务。

查出来的问题随手修正即可，不需要为此再完整走一轮审查。

## 交给谁来执行

保存好之后，告诉用户计划的位置（例如 `docs/plans/<文件名>.md`），请对方在下面两种方式里选一种：

- **每个任务派一个新子代理（推荐）**：每个独立任务用 `create_subagents` 新建一个子代理，创建后自动开始；它只带着这一个任务的上下文，做完即结束，前面任务的细节不会越积越多。任务交回后先做针对性验证、汇总结果，复查通过再派下一个。
- **在当前会话里分批执行**：不派子代理，由你在这次会话里自己做。任务按批推进，每批做完停下来给用户复查；每一小步完成后在 `task_progress` 留个记录；卡住时在当前回复里摆出证据，说明需要对方定什么。每批结束按“保存前自查”再看一遍，确认没有引入回归再继续。
