# 写实现计划

## 总则

把实现计划写成"执行者对这套代码库零上下文、品味也未必可靠"的前提下也能照做的程度。该写的全写清楚:每个任务动哪些文件、写什么代码、怎么测、可能要查的文档、怎么验证通过。整份计划拆成一口一个的小任务。遵循 DRY、YAGNI、TDD、频繁收尾(每个小步做完就落一次)。

假设执行者是熟练开发者,但对本项目的工具栈和问题域几乎一无所知,也不太懂好的测试设计——所以测试代码要直接给出,不能只说"写个测试"。

**开始时声明:** "我在用 writing-plans 这个方法论来写实现计划。"

**计划存放位置:** `docs/plans/YYYY-MM-DD-<功能名>.md`(若用户/任务对计划存放位置另有要求,以其为准)。

## 范围检查

如果这份规格覆盖了多个互相独立的子系统,本应在需求梳理阶段就拆成多份子项目规格。若没拆,先建议拆成多份计划——每个子系统一份。每份计划都应能独立产出可运行、可测试的软件。

## 文件结构先行

定义任务之前,先把会新建/修改哪些文件、每个文件负责什么列出来。分解的决策在这一步就定下来了。

- 按清晰边界、明确接口来划分单元。每个文件只承担一个明确职责。
- 你对"能一次性放进上下文的代码"推理最准,改动也最可靠。优先用小而聚焦的文件,别让一个文件什么都干。
- 一起变化的代码放在一起。按职责拆,不按技术分层拆。
- 在既有代码库里,遵循已有约定。如果代码库本来就用大文件,别擅自重构;但若你正在改的某个文件已经臃肿到难以下手,在计划里顺手安排一次拆分是合理的。

这套文件结构直接决定任务怎么分解。每个任务都应产出一组自洽的改动,单独看也说得通。

## 一口一个的任务粒度

**每一步就是一个动作(2-5 分钟能做完):**
- "写一个会失败的测试" —— 一步
- "运行它,确认它确实失败" —— 一步
- "写出让测试通过的最小实现" —— 一步
- "再跑测试,确认通过" —— 一步
- "收尾(记录进度 / 落一次改动)" —— 一步

## 计划文档头部

**每份计划都必须以这个头部开始:**

```markdown
# [功能名] 实现计划

> **给执行子代理:** 本计划按任务逐个执行。每一步用复选框(`- [ ]`)语法跟踪进度。
> 执行方式见文末"执行交接"——既可派独立子代理逐任务执行,也可在当前会话内分批执行。

**目标:** [一句话说清这要建成什么]

**架构:** [2-3 句说清做法]

**技术栈:** [关键技术/库]

---
```

## 任务结构

````markdown
### 任务 N:[组件名]

**涉及文件:**
- 新建:`exact/path/to/file.py`
- 修改:`exact/path/to/existing.py:123-145`
- 测试:`tests/exact/path/to/test.py`

- [ ] **第 1 步:写一个会失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **第 2 步:运行测试,确认它失败**

运行:`pytest tests/path/test.py::test_name -v`
预期:FAIL,报 "function not defined"

- [ ] **第 3 步:写出最小实现**

```python
def function(input):
    return expected
```

- [ ] **第 4 步:运行测试,确认它通过**

运行:`pytest tests/path/test.py::test_name -v`
预期:PASS

- [ ] **第 5 步:收尾这一小步**

通过 `task_progress` 记录这一步已完成,或在版本控制里落一次聚焦的改动(diff 只含本步涉及的文件)。
````

## 不许留占位符

每一步都必须含有执行者真正需要的实际内容。下面这些是**计划失败**,绝不能写:
- "TBD"、"TODO"、"稍后实现"、"细节待补"
- "加上合适的错误处理" / "加校验" / "处理边界情况"(不给具体做法)
- "为上面写测试"(却不给出实际测试代码)
- "和任务 N 类似"(把代码重复写出来——执行者可能不按顺序读任务)
- 只说做什么、不展示怎么做的步骤(改代码的步骤必须带代码块)
- 引用了任何任务里都没定义过的类型、函数或方法

## 牢记

- 永远给精确文件路径
- 每一步都给完整代码——只要这步动代码,就把代码贴出来
- 给精确命令和预期输出
- DRY、YAGNI、TDD、频繁收尾

## 自我复查

整份计划写完后,带着新鲜的眼睛回看规格,逐条对照计划。这是你自己跑的检查表,不是派子代理去做。

**1. 规格覆盖:** 把规格里每个章节/需求过一遍。每条都能指到某个实现它的任务吗?把缺口列出来。

**2. 占位符扫描:** 在计划里搜上面"不许留占位符"那节列的所有红旗。搜到就改掉。

**3. 类型一致性:** 后面任务里用的类型、方法签名、属性名,和前面任务里定义的对得上吗?在任务 3 里叫 `clearLayers()`、到任务 7 又写成 `clearFullLayers()`——这就是 bug。

发现问题就地改掉,不用重新复查一遍,改完往下走即可。如果发现某条规格需求没有对应任务,补上那个任务。

## 执行交接

计划存好后,给出执行方式的选择:

**"计划已完成并存到 `docs/plans/<文件名>.md`。两种执行方式:**

**1. 派子代理逐任务执行(推荐)** —— 每个任务派一个全新子代理(`create_subagents` / `dispatch_subagents` / `schedule_child_subagents`),任务之间做一次复查,迭代快、上下文干净。

**2. 当前会话内分批执行** —— 在本会话里按任务执行,分批推进、每批设检查点供复查。

**选哪种?"**

**若选派子代理逐任务执行:**
- 每个任务派一个全新子代理,执行完完成针对性验证并汇总结果，复查通过再进下一任务
- 子代理只拿到当前任务所需的上下文,做完即收,避免上下文累积

**若选当前会话内分批执行:**
- 分批推进,每批设检查点;每个小步做完用 `task_progress` 记录,撞到阻塞用 `raise_event` 上报
- 一批完成后回到自我复查那节,确认无回归再继续
