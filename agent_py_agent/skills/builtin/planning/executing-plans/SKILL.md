# 执行计划方法

计划已经写好，现在轮到你落地。它可能来自上游会话，也可能是你早先自己拆的。执行者要交出的不只是改动，还有开工前查出的漏洞、每一项的验证证据，以及对任何偏离的如实交代。

## 一、开工前：给计划做体检

- 从头读到尾，每一步改什么、怎么验收都要看到；只看目录式的步骤名，等于没读。
- 重点查三类毛病：衔接（前一步的产出接不接得上后一步）、前提（依赖、权限、环境交代了没有）、可行性（有没有哪一步凭现有信息根本做不了）。例如第 4 步要改的函数已在第 2 步改名，这种断链要现在指出，别等做到第 4 步再猜。
- 查出问题就先别动手。在这一轮回复里写明问题所在、依据和需要对方拍板的点，交给上游或提出任务的人；如果你本身是子代理，宿主会自动把这条回复和阻塞终态转交父级，不用另找渠道。
- 体检干净，就调用 `task_progress(action=update)`，以计划的步骤作为 `items` 建好清单，然后开工。
- 动手的位置也要先定：主干分支只有拿到明确授权才可以直接改，否则先开一个隔离的工作区。

体检通过后，顺序、颗粒度和验证方式都以计划为准；想偏离，先停下说明理由。

## 二、能并行的交给子代理

先按依赖关系把任务分开：必须接力的留在主线上顺序做；彼此独立的交给子代理，一次 `create_subagents` 调用就能给每块工作配好分工，宿主会让它们同时开跑。分头并行通常比一个人串行更快，也更稳。

## 三、逐项执行

1. 开始某一项时，先调用 `task_progress(action=update)`，让它的状态变成 `in_progress`。
2. 计划切成几步就做几步：不并步，不跳步，不顺手捎带计划没要求的改动。
3. 计划指定了哪条命令或哪个测试 gate，就用 `run_command` 实际执行，看到输出再下结论；凭感觉说一句“应该没问题”，代替不了这一步。
4. 没通过就先查清原因；放宽断言、让实现迎合测试都不算修好。
5. 看到通过的输出，再调用 `task_progress(action=update)` 把状态推进到 `done`，证据一并附上：执行了什么，得到什么结果。
6. 计划点名某份方法论 skill 的地方，就加载它照做，不凭印象代替。

## 四、停手与回炉

依赖缺失或测试失败、某条指令读不懂、计划缺了关键一环无从起步、同一条验证几轮都修不好——出现任何一种，这一项就不再往下推。停下以后，这一轮回复就是你的报告：说明卡在哪里，附上证据，列出需要谁拍板。用猜测补空白、绕过障碍接着走、拼一个表面能运行的东西交差，都等于把问题埋到交付之后。

还有两种情况要退回第一节重新体检。一是计划换了版本（多半是上游采纳了你的意见），之前的体检结论不再有效。二是你意识到要改的是整个思路，而不是哪一步写错了——这时硬推只会越陷越深，应先把问题报上去，等修正后再继续。

## 五、交付前的最后三件事

1. 各项分别通过，合起来未必没问题。最终回复之前的最后一道关，是用 `run_command` 对整体测试 gate 做一次从头到尾的完整运行；有任何一处不绿，就回到对应的项去处理。
2. 拿 diff 和计划对账：每处改动都要能指回某一项，对不上的要么撤回，要么在汇报里说明。
3. 汇报要经得起核对：列出完成的项和各自的验证方式，把没做完或留了尾巴的地方写明白。汇报交出去以后，才把任务标记为完成。
