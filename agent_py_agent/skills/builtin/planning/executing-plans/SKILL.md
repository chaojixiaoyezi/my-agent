# 执行计划方法

拿到一份实施计划,不是从第一条开始闷头敲。先看懂、再照做、做完验、卡住停。一句话:**计划是约束不是建议,但执行前你要先确认它没坑。**

子代理能显著提升这类工作的质量:计划里相互独立的任务,优先派子代理并行执行(`create_subagents` / `dispatch_subagents`),需要排期再补的用 `schedule_child_subagents`。

## 流程

### 第一步:加载并批判性通读计划

1. 读完整份计划文件,不要只扫标题。
2. **批判性审视**——把疑问和隐患列出来:步骤之间有没有断链?有没有前置依赖没说清?有没有一上来就做不下去的关键缺口?
3. 有疑虑:执行前先把疑虑提出来(向上游/任务发起方反馈,用 `task_progress` 或 `raise_event` 把卡点显式抛出),不要带着没解决的疑问开干。
4. 无疑虑:建好任务跟踪(`TaskCreate` 登记本次要执行的任务),再开始。

### 第二步:逐条执行任务

对每一条任务:

1. 标为进行中(`TaskUpdate` → in_progress)。
2. **严格照步骤做**——好的计划会把步骤切到很小的颗粒度,照着做就行,不要自作主张合并或跳步。
3. 按计划指定的方式跑验证(`run_command` 跑命令 / 跑测试 gate),计划让验证就一定验证。
4. 验证通过,标为完成(`TaskUpdate` → completed)。

### 第三步:收尾交付

所有任务都做完并验证通过后:

1. **不要跳过最终验证**:在声称完成、走交付验收(`submit_for_acceptance`)之前,先把整体测试 gate 完整跑一遍,确认全绿。
2. 整理本次改动 diff,确认每一处改动都对应计划里的某条任务,没有夹带计划外的改动。
3. 把执行结果如实回报(哪些做完、哪些验证过、有没有未尽事项),再标记任务完成。

## 什么时候立刻停下求助

**遇到下列情况立刻停止执行:**

- 撞上卡点(缺依赖、测试失败、指令看不懂)。
- 计划有关键缺口,根本起不了步。
- 某条指令你理解不了。
- 同一个验证反复失败。

**宁可停下来问清楚,也不要靠猜往下做。** 把卡点用 `task_progress` / `raise_event` 显式抛出,而不是默默绕过或硬凑一个看起来能跑的实现。

## 什么时候回到前面的步骤

**回到第一步(重新通读)的触发条件:**

- 上游根据你的反馈更新了计划——拿到新版必须重新批判性通读,不要在旧理解上继续。
- 发现底层方案本身需要重新设计,不只是某一步的问题。

**不要硬闯卡点**——停下来,反馈,等修正。

## 红旗清单(出现就是没照方法做)

- 没通读就开始敲第一条任务。
- 计划让验证,你跳过了("应该没问题"不算验证)。
- 把多个小步骤擅自合并成一大步,理由是"这样快"。
- 验证失败了,改了实现让它"看起来过",但没搞清为什么失败。
- 卡住了不抛出,自己猜一个实现填上,继续往下。
- 没跑整体测试 gate 就声称完成 / 提交交付验收。
- 改动 diff 里有计划里没有的内容,没说明。

## 铁律

- 先批判性通读,再动手。
- 严格照计划步骤执行,不擅自合并、跳步。
- 验证一步都不能少;声称完成前必须跑整体 gate。
- 计划引用了别的方法论 skill,就照引用去用。
- 卡住就停、就抛出,绝不靠猜。
- 没有明确授权,不要直接在主干分支上开始实现——先隔离出独立工作区。
