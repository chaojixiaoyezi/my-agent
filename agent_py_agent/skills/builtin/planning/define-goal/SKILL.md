# 定义目标

把用户的意图塑造成一个代理能诚实追求的目标。优先要"可度量的结果 + 明确的证据 + 有界的范围",而不是一句"干活描述"。

本 skill 只管"把目标定清楚"这一步:不在这里建中间计划产物、不写台账/决策日志/续跑文件、也不展开执行。

## 何时该用

- 用户明确要"定个目标""明确成功标准""把这个模糊意图变成清楚的目标",或一个任务开工前你拿不准"什么算做完"时。
- 用户只是要你直接实现一个普通功能时——直接干,不要硬套"先定目标"这一步。
- 已经在跑的、目标清楚的活儿,不要重复定目标。

## 工作流

1. **确认确实需要定目标。** 见上节。不需要就别套流程。

2. **用具体的话把目标复述一遍。** 一个能用的目标要说清:
   - 做完之后,什么具体的事实会成立
   - 牵涉的主产物 / 系统 / 模块 / 运行环境 / 用户可见的行为是什么
   - 怎么验证它做完了
   - 范围内包含什么
   - (当模糊会出岔子时)范围外明确排除什么
   - 停止条件:什么情况下该回头问用户,而不是闷头硬磕

3. **能量化就量化。** 选那些代表"真成功"的数字,不要为了精确而精确:
   - **通过/失败的判定器**:具体的测试、检查、gate、评测、命令、或验收条件
   - **质量阈值**:延迟、错误率、成本、准确率、召回、精度、覆盖率、波动率、包体积、内存、可用性、完成率,或人工评审标准
   - **产物约束**:文件路径、涉及模块、允许动用的命令、输出格式、目标环境、截止时间,或最大影响半径
   - **证据计数**:复现的失败数、成功重跑的次数、评审过的样例数、迁移的记录数、处理掉的评论数、验证过的用例数

4. **弱目标先修好再立。**
   - 当本地上下文足够、改写是安全的,就把含糊的目标重写成可度量的目标。
   - 当缺的那个细节会改变"想要的结果"或"怎么验证",简短地问一个澄清问题。
   - 纯"干活"型目标——比如"推进一下""继续查""优化一下""搞搞 X"——拒绝接受,除非把它磨成一个可验证的结果。

5. **复用已有任务,别造重复。** 普通任务只使用当前 conversation 的 `task_progress`；只有用户或系统明确要求持续 `/goal` 时，才使用 `get_goal` / `create_goal` / `update_goal` 这套特殊 overlay。
   - 先用 `task_progress(action=read)` 看当前任务:有没有一项仍在跑、且仍匹配用户意图。
   - 有且匹配 → 沿用它、按需 `task_progress(action=update)` 更新,不要新建重复任务。
   - 有但与新需求冲突 → 问用户:是先收尾当前任务、还是(若已完成)标记完成、还是另起一条独立的任务线。
   - 没有匹配的、且用户开始的是普通新任务 → 继续当前 conversation，并用 `task_progress(action=update)` 建立清单；不要另造第二份上下文。

6. **过了质量门才正式定下来。**
   - 用一句话把目标说清楚。
   - 把"怎么验证"的证据写进目标本身,而不是留在脑子里。
   - 当范围边界会约束这活儿时,写进去。
   - 只有用户明确要求"按目标驱动跑"时,才把它立成一个独立任务;普通的多步任务直接做,不必为它专门建目标。

## 目标质量门

正式定下目标前,这句目标描述要能回答:

- 做完时,什么具体的事实会成立?
- 什么证据能证明它成了?
- 什么量化的或二元的阈值定义了"成功"?
- 哪些范围边界是要紧的?
- 什么情况该让代理停下来问?

**好的例子:**

> 把结算 API 那条已知慢路径的 p95 延迟降到 250ms 以下,改动取最小且安全的服务端改法,然后用 `run_command` 跑结算测试套件 + 现有本地延迟基准,验证 p95 连续 3 次都低于 250ms。

**好的例子:**

> 处理掉那个改动评审里要求改代码的待办评论,只动受影响的鉴权相关文件和测试,用针对性的鉴权测试命令验证全绿,且改动 diff 里不再留有未解决的"请修改"评审线。

**弱的例子:**

> 把结算搞快点。

**弱的例子:**

> 继续看那些评审评论。

## 量化套路(按场景)

- **修 bug**:成功定义为——先复现、再修、能给出一个"先红后绿"的判定器最好。
- **测试**:点名具体命令 + 必须达到的通过条件。
- **性能**:点名指标、目标阈值、测量方法、跑几次。
- **质量类工作**:定一个可观察的验收线,比如评审过的样例、lint/类型检查/测试全过、或用户拍板认可的产物。
- **调研**:定清楚——这次调研要支撑哪个决策、范围内的来源或系统是哪些、证据标准是什么。
- **运维**:定清楚——健康态长什么样、监控窗口多长、失败阈值在哪、什么触发回滚或升级。

## 澄清问题

只在"按常理改写会有追错目标的风险"时才问。问题要短,围绕缺失的那个判定器或范围边界。

好用的问法:

- "这里用什么指标定义成功:延迟、成本、准确率,还是用户可见的行为?"
- "对着哪个环境验证:本地、预发,还是生产?"
- "标记这个目标完成前,你想看到的最低证据是什么?"

如果用户给不出指标,就提出当前能拿到的、最诚实的二元判定器,然后请他确认。

## 铁律

- 目标里写的"怎么验证",到任务收尾时是要真兑现的:声称完成 / 最终回复前 / 标记任务完成前,要真的把那个判定器跑出来(`run_command` / 跑测试 gate),而不是凭印象说"应该好了"。
- 把活儿派给子代理时(`create_subagents` / `dispatch_subagents` / `schedule_child_subagents`),把同一句带验收证据的目标传下去——子代理也照同一个判定器收尾,用 `task_progress` 回报进展、卡死时 `raise_event` 上报,不要让"什么算做完"在传递中走样。
