# 编写 Skill 的方法

一份 skill 的读者，是将来某个接手类似工作的代理。它不认识你，也没见过你踩过的坑，只能从这份文档里拿到现成、可靠的做法。衡量 skill 好坏只有一个标准：代理读过之后，行为有没有朝预期的方向改变。作者自己读着顺，证明不了这一点；能证明的只有一组对照——没有它时代理怎么做，有了它之后又怎么做。

所以本方法沿用测试驱动开发的节奏（也就是“红、绿、重构”）：给子代理设计的压力场景充当测试用例，SKILL.md 充当被测的实现。先让子代理在没有 skill 的条件下跑场景、把问题暴露出来，再只针对暴露出的问题动笔，然后用同一批场景复测，把它新找到的绕行路线一条条封掉。

## 一、先想清楚：值不值得写，写成哪种

skill 收录的是能反复套用的东西：一种技巧、一个思考框架、一份工具或接口的参考。某次排障的来龙去脉、某个会话里的心路历程都不算，换一个任务就用不上了。

值得动笔的信号：

- 这个做法不直观，能力不错的代理第一次碰到也未必想得到；
- 同样的需求隔三岔五就会冒出来，而不是只服务眼前这一次；
- 它不依附于某个具体项目，别的代理拿去同样适用。

不该写成 skill 的情况：

- 只解决眼下这一回、以后不会再碰到的问题；
- 教程和官方文档早已讲透的常识；
- 某个项目自己的约定——放进那个项目的配置里更合适，公共 skill 不收；
- 规则明确到可以用正则或校验脚本机械判定的——写成自动检查更可靠，skill 的篇幅要花在需要权衡取舍的地方。

skill 大致有四种形态，写法和测法各不相同：

- 纪律型：一条必须守住的规矩，例如“没有明确授权，不直接在主干分支上改动”。难点不在理解，而在压力之下守不守得住。
- 技巧型：告诉代理具体怎么操作，照着步骤就能做出来，例如把一份计划拆成可以并行派发的子任务。
- 模式型：不规定步骤，而是换一种眼光看问题，例如先把每个外部输入都当作不可信，再推演它能走到哪里。
- 参考型：接口说明、命令手册、格式规范这类供查阅的材料。

## 二、动笔之前：先看子代理失败一次

这一步叫摸底，不能省，也不能事后补。

1. 设计压力场景。场景要贴近真实：有具体任务，有时间要求，还有诱人走捷径的理由。纪律型 skill 至少叠加三种压力，比如“已经投入大半天 + 截止时间将到 + 有人在催结果”。
2. 把场景交给一个没加载这份 skill 的子代理去做。
3. 记录要具体到原话：它在哪些节点怎么选的；它拿什么理由替自己开脱——一字不改地抄下来，别用自己的话转述；压垮它的是哪一种压力。

这份记录是后面写作的唯一依据。没有它，写下的每条规则都只是猜测：很可能在反复叮嘱代理本来就会做的事，却漏掉它真正会犯的错。

对已有 skill 的改动，也逃不开这一步。哪怕只改一句措辞、补一个小节，或者觉得这次“不过是更新一下文档”，也得先有一个在旧版本上失败的场景。如果已经先写了内容才想起测试，就把这部分整段删除，回到第 1 步。别把它挪到草稿里“留作参考”，也别在跑场景时对着它修修补补——只要它还在眼前，摸底就会不自觉地朝它靠拢。这些要求按字面执行，“我遵守的是精神”不构成绕开字面的理由。

## 三、起草：只回应摸底里出现的问题

写作范围由摸底记录决定：代理在哪里出错、用了什么理由，skill 就针对哪里；场景里没出现过的假想情况，先不写。

### 头部元数据（frontmatter）

- `name`：字母、数字、连字符之外，什么字符都别用，括号也不行。
- `description`：概括代理读完后会采取的行动，一句话足矣。
- `when_to_use`：只写什么情况下该加载它，不写加载之后怎么做，原因见下一小节。
- `tags`：供检索用的中文标签，三到六个为宜。
- `scope` 和 `risk_level`：分别说明这份 skill 在哪个范围生效、风险有多高。

### 触发条件只写“什么时候”

`description` 和 `when_to_use` 是代理在索引里就能看到的两行字，它据此决定要不要往下读正文。要是触发条件里已经透露了做法，代理会以为自己心里有数，拿这半句当全部操作指南，正文就被跳过了。

举个例子：某份发布 skill 的正文要求依次跑完整测试、更新变更记录、确认回滚方案、最后打标签。触发条件若写成“发布前跑测试并打标签时”，代理多半只做测试和打标签两件事；改成只描述场景——“准备发布新版本时”——代理才会去读完整的四个步骤。

写触发条件时：

- 用代理当时能观察到的东西来写：正在做什么、看到了什么现象、卡在什么环节。
- 写问题的性质，不写某种语言里的具体写法。一份讲“等条件满足再继续”的 skill，如果触发条件写成“代码里出现 `sleep` 或 `setTimeout` 时”，那些靠轮询或回调等待的场景就全都匹配不上了。
- 技术名只在一种情况下出现：这份 skill 离开那项技术就没有意义。这时反而要把技术名写进触发条件，免得在不相干的场景被加载。

```yaml
# 不好：太空泛，看不出何时该用
when_to_use: 处理数据时

# 不好：夹带了做法，代理可能照这半句做完就走
when_to_use: 导入表格时先校验表头、再去重、最后写库

# 好：只描述场景和症状
when_to_use: 要把外部表格数据导入系统，或导入后出现字段错位、重复行时

# 好：本身绑定某种格式，就在条件里写明
when_to_use: 需要读取或填写 PDF 表单字段时
```

### 正文怎么组织

代理读 skill 是分层的：先凭索引里的两行字决定打不打开；打开后只扫开头，判断是否对口；对口了再看速查；要落手操作了，才会去看例子和细节。正文顺着这个顺序排：

1. 开头：这份 skill 管什么事、最要紧的原则是什么，控制在一两句；
2. 适用范围：哪些症状或场景该用、哪些情况别用；判断点不直观时，可以配一张很小的流程图；
3. 速查：把最常用的操作压成一张表或几行要点，让人扫一眼就能用；
4. 做法：技巧型、模式型最好放一组“原来这样写 / 应该这样写”的对照；
5. 实现：篇幅小的代码就地写出，大段参考和能复用的工具另存文件，正文里给链接；
6. 常见错误：会在哪里出错，出错后怎样纠正；
7. 效果（可选）：用了之后改善了什么，最好有具体数字。

### 让代理搜得到

- 代理搜索时会用的词，要在索引字段和正文前部反复出现：报错原文（如“权限被拒绝”“连接被重置”）、症状说法（如“输出乱码”“越跑越慢”“偶尔丢数据”）、同义说法（如“导出 / 另存为 / 下载”），以及真实的命令名、库名和文件类型。
- 起名时让人一看就知道“在干什么”：动词打头、主动语态，要么点出动作，要么点出核心洞见；过程类的 skill 用 -ing 形式读起来最自然。本项目的 `writing-skills`、`executing-plans`、`dispatching-parallel-agents`、`define-goal` 都是这样命名的；`plan-execution`、`review-helpers` 这种堆名词的名字，就看不出在做什么。

### 控制篇幅

常驻或经常被加载的 skill，每次会话都要占一份上下文，多写一段，每一轮都要多付一段 token。参考预算按词数算：引导入门的工作流每份控制在 150 词以内；会被频繁加载的几份加起来别超过 200 词；其余的也以 500 词为上限，能更短就更短。写完可以用 `wc -w skills/path/SKILL.md` 看一眼篇幅。

压缩的办法：

- 命令行参数不必逐个列出，告诉代理用 `--help` 查；
- 别的 skill 已经讲过的流程，引用名字即可，不要再抄一遍；
- 示例只保留说明问题所需的最少内容，对话式示例删掉寒暄；
- 看名字就懂的命令不加解释，一个模式配一个例子就够。

### 怎样指向别的 skill

文中需要借助另一份 skill 时，写出它的名字，并讲清楚是“动手前必须先读”还是“了解一下有帮助”，例如：

- 前置（必读）：修复之前，先按 `systematic-debugging` 定位根因；
- 背景（建议）：想了解先写失败测试的节奏，可以看 `test-driven-development`。

要避免两种写法：只贴一个目录路径，读者分不清是不是非读不可；用会强制载入整份文件的方式引用，一引用就把全文拉进上下文，而这时代理多半还用不上它。

### 流程图、示例与拆分文件

流程图只在三种地方有用：容易走错的判断点；需要来回循环、容易半途就以为做完了的过程；两种做法之间的取舍。其他内容换更合适的形式：查阅材料用表格或列表，代码用代码块，线性步骤用编号列表。节点名要有含义，也不要把代码写进节点。

示例只放一个，并把它写好。语言挑最贴近场景的：测试相关用 TypeScript 或 JavaScript，系统排障用 Shell 或 Python，数据处理用 Python。判断一个示例好不好：它来自真实问题，而不是为了演示硬凑的；拿去改几处就能用在自己的任务上，而不是等人填空的模板；能直接跑通；注释解释“为什么”，而不是复述“做了什么”；读完能看清背后的模式。同一段代码也不必翻成五六种语言各放一份，代理自己就能改写成别的语言。

SKILL.md 必须有，其他文件确有需要才加。值得拆出去的只有两类：上百行的参考资料（比如整套接口说明或语法全集），以及可以直接复用的工具（脚本、模板、改一改就能用的样例代码）。原则、概念、50 行以内的代码模式和其余内容都留在 SKILL.md 里。三种常见布局：

```text
skills/
  reviewing-migrations/      # 内容不多，一个文件装得下
    SKILL.md
  retrying-network-calls/    # 附带可复用的工具
    SKILL.md
    scripts/retry_wrapper.py
  editing-invoice-xml/       # 参考资料太长，拆出去
    SKILL.md
    references/field-table.md
    references/error-codes.md
    scripts/
```

## 四、复测与加固

1. 让子代理加载新写的 skill，重新跑摸底时那批场景，对照前后两次的记录：原先出错的地方，现在应该做对了。
2. 它若又找到新的理由绕开规则，就把理由原样记下，在 skill 里补一条针对性的反制，然后再跑。
3. 反复进行，直到再也找不出可钻的空子。

复测怎么设计，要看 skill 属于哪种形态：

- 参考型：给一个必须查资料才能完成的任务，看代理能否在 skill 里找到正确的信息、找到后用得对不对，再核对常见用法是否都有覆盖。
- 技巧型：先看标准场景能否正确套用，再换几个边界情况，并故意少给一些信息，检查说明里有没有缺口。过关的标准：换一个它没见过的场景，它照样用得对。
- 模式型：混着给几个场景，有的该用这个思路、有的不该用，看代理能不能分辨出来，并在该用的地方真正用上。
- 纪律型：先问几个问题，确认代理懂这条规矩；再放进有压力的场景；最后把几种压力同时压上去。只有压力最大时它仍然守住，才算过关。

### 纪律型 skill：预判绕行，提前封路

这类 skill 要防的不是读者看不懂，而是读者看懂了还想绕：赶时间、怕返工的时候，代理会很有创意地为例外找理由。所以光写出规则不够，还要替它把绕行的路先堵上。

- 点名堵死绕路。以“没有明确授权，不直接在主干分支上改动”为例，只写这一句，代理可能会说“只是改个错别字”“马上就切分支”“用户在另一个任务里同意过”。加固后的写法把这些直接列出来：授权必须针对本次任务、明确给出；上面几种说法都不算授权。
- 在开头就声明规则按字面执行，提前堵住“我遵守的是精神”这类辩解。
- 整理借口对照表：摸底和复测中代理说过的每一个理由都收进来，一边是原话，一边是它为什么站不住。
- 写一份自检信号清单：列出代理快要越界时心里会冒出的念头，看到任何一条就该停下重来。
- 把“快要违规”的时刻写进 `when_to_use`，例如“准备改动文件、但还没确认当前所在分支时”，让代理恰好在最容易犯错的时候加载这份 skill。

如果你发现自己在反复琢磨“该用哪几种压力”“漏洞按什么顺序补”“怎么确认场景本身没设计歪”，说明这部分值得另立一份 `testing-skills` 专门沉淀；常用的压力来源包括截止时间、已经投入的沉没成本、上级或用户的权威、连续工作后的疲劳。本文只点到为止。

## 五、交付：写完一份，收尾一份

skill 要一份一份地交付。前一份的复测和收尾没做完，就不开始下一份；并排起草五份、最后一起测，看似省事，实际上每一份都会带着没被发现的漏洞出门，“批量处理更高效”不能成为跳过测试的理由。在交付标准上，skill 和代码一视同仁：没测过就不上线。

想跳过测试时找的理由，通常都站不住：作者觉得清楚，是因为作者心里有读者没有的上下文；自己通读一遍，检验的是文字顺不顺，而不是代理用起来会不会出错；等出了问题再测，等于让第一个真正用它的人替你踩坑；参考型也不例外，至少要测一次“查不查得到、查到后用得对不对”。场景跑一轮的成本很低，而一份有缺陷的 skill 会在每次被加载时重复出错。

交付前对照下面各项自查；条目较多时，可以把它们放进 `task_progress` 当待办，逐个勾掉：

- [ ] 摸底记录齐全：压力场景（纪律型至少三种压力叠加）、没有 skill 时的原话表现、从中归纳出的借口和失败规律
- [ ] frontmatter 六个字段齐全（`name`、`description`、`when_to_use`、`tags`、`scope`、`risk_level`）；`name` 里没有字母、数字、连字符以外的字符；`when_to_use` 里没有夹带做法，只有触发条件和症状
- [ ] 读完开头一两句就知道核心原则；报错、症状、工具名这些检索词在正文里铺开了；摸底中的每一种失败都能在正文里找到对应的回应
- [ ] 示例只有一个且写得扎实；代码短的就地写、长的另存并给链接；拆出去的文件只有工具或长篇参考
- [ ] 正文里能找到速查和常见错误这两块；流程图只出现在不直观的判断点；没有回忆录式的叙述
- [ ] 复测记录显示，同一批场景里代理这次按 skill 做了；复测中新冒出的借口都补了明确反制；纪律型附上了借口对照表和自检信号清单
- [ ] 在对的目录下能找到这份 SKILL.md，而不是只停留在草稿或对话里
- [ ] 如果这是一项任务：计划可以按需记进 `task_progress`；做完针对性的验证再写最终回复；中途被卡住，就在这一轮回复里摆出证据、说明需要谁决定什么（子代理不用另行上报，宿主会把状态自动交给父级）
- [ ] 要并行跑多组场景、或把测试面铺得更广，就交给 `create_subagents`：一次调用建好几个分工不同的子代理，创建后自动开跑
- [ ] 说“完成”之前，先用 `run_command` 把验证或测试 gate 跑通；没验证过的任务不标完成

## 六、写坏的几种典型样子

- 回忆录：“那次导出报表超时，我们最后发现是分页参数传错了……”——细节全绑在一次事件上，换个任务就用不了。应当提炼成“遇到什么情况、按什么步骤处理”。
- 多语言平铺：同一个示例用 Python、Shell、TypeScript 各写一份，每份都浅尝辄止，维护时还得几处同步修改。
- 流程图里写代码：节点里塞具体语句，既不能复制粘贴，读起来也费劲。
- 空洞的标签：“处理一”“工具函数 B”“阶段 X”这类名字不传达任何含义，应当换成说明用途的名字。

判断一份 skill 写没写完，不看它篇幅多完整，而看复测记录里代理的行为是否真的变了。
