# 编写 Skill 的方法

## 核心

**写 skill 本质上就是把测试驱动开发(TDD)用在"流程文档"上。**

你先写测试用例(用子代理跑加压场景),看它失败(没有 skill 时的基线行为),再写 skill(文档),看测试通过(子代理开始照做),然后重构(堵掉钻空子的口子)。

**核心原则:如果你没有亲眼看过一个子代理在没有这份 skill 时失败,你就不知道这份 skill 教的是不是对的东西。**

整个流程跟着 RED-GREEN-REFACTOR 走。

## 什么是 skill

**skill 是一份"经过验证的技巧/模式/工具"的参考指南**,帮助以后接到同类任务的代理找到并复用有效的做法。

- **skill 是**:可复用的技巧、模式、工具、参考资料。
- **skill 不是**:你某一次怎么解决某个问题的流水账叙事。

## TDD 与 skill 的对应关系

| TDD 概念 | 写 skill 时对应 |
|----------|----------------|
| **测试用例** | 给子代理的加压场景 |
| **业务代码** | skill 文档(SKILL.md) |
| **测试失败(RED)** | 没 skill 时子代理违反规则(基线) |
| **测试通过(GREEN)** | 有 skill 后子代理遵守 |
| **重构** | 在保持遵守的前提下堵住钻空子的口子 |
| **先写测试** | 写 skill 之前先跑基线场景 |
| **看它失败** | 逐字记录子代理用了哪些借口 |
| **最小实现** | 只针对这些具体违规去写 skill |
| **看它通过** | 验证子代理现在确实照做 |
| **重构循环** | 发现新借口 → 补堵 → 再验证 |

## 什么时候该建 skill

**该建:**
- 这个技巧对你来说不是一眼就能想到的。
- 你以后会在不同任务里反复用到它。
- 这个模式适用面广,不只对某一个项目有意义。
- 别人(以后的代理)也会受益。

**不该建:**
- 一次性的临时解法。
- 在别处已经有完善文档的通用常识。
- 只对某个具体项目有意义的约定(那属于项目级配置,不属于公共 skill)。
- 纯机械约束:如果用正则/校验脚本就能强制,那就去自动化它——文档留给需要判断力的事。

## skill 的三种类型

### 技巧型(Technique)
有明确步骤可照做的具体方法(如"按条件等待""根因追溯")。

### 模式型(Pattern)
看待问题的一种思路(如"用标志位拍平嵌套""测试不变量")。

### 参考型(Reference)
API 文档、语法手册、工具说明。

## 目录结构

```
skills/
  skill-name/
    SKILL.md              # 主参考(必需)
    supporting-file.*     # 仅在确有需要时
```

**何时拆出单独文件:**
1. **大块参考资料**(100 行以上)——API 文档、完整语法手册。
2. **可复用的工具**——脚本、模板、可直接改用的样例代码。

**保持内联(写在 SKILL.md 里):**
- 原则与概念。
- 代码模式(50 行以内)。
- 其余一切。

## SKILL.md 的结构

**frontmatter(YAML)字段:**
- `name`:只用字母、数字、连字符,不要括号或特殊字符。
- `description`:一句话说清这个 skill 让代理"做什么"。
- `when_to_use`:**只描述触发条件**(什么场景该用它),**不要**在这里复述 skill 的工作流程。
- `tags`:3~6 个中文检索标签。
- `scope` / `risk_level`:作用域与风险级别。

正文骨架:

```markdown
# Skill 名

## 核心
这是什么?用一两句话讲清核心原则。

## 何时使用
[只有当判断点不显而易见时,放一个很小的内联流程图]
带"症状"的要点清单 + 什么时候不该用。

## 核心模式(技巧型/模式型用)
改造前 / 改造后的代码对照。

## 速查
表格或要点,便于扫读常用操作。

## 实现
简单模式直接内联代码;大块参考或可复用工具则链接到单独文件。

## 常见错误
哪里会出问题 + 怎么修。

## 真实效果(可选)
具体的、可量化的结果。
```

## 让 skill 能被检索到(检索优化)

**关键:以后接到同类任务的代理得能"找到"你的 skill。**

### 1. description 与 when_to_use 要精准

代理是靠 `description` 和 `when_to_use` 来决定"现在要不要加载这份 skill"的。

**铁律:`when_to_use` 只写触发条件,不要复述工作流程。**

为什么重要:实测发现,一旦触发条件里把流程也概括进去,代理可能直接照着这句概括去做,而不去读 skill 正文。比如触发条件写成"任务之间做代码评审",代理就只做了一次评审——尽管 skill 正文里的流程图清楚写着要做两次(先查规格符合度,再查代码质量)。把触发条件改成只写"在当前会话里执行含多个独立子任务的实施计划时",代理才会去读流程图、按两阶段走。

**陷阱:把工作流程概括进触发条件,等于给代理开了一条捷径,正文就成了被跳过的摆设。**

```yaml
# 反例:把流程概括进去了——代理可能照这句做而不读正文
when_to_use: 执行计划时——每个子任务派一个子代理,任务间夹一次代码评审

# 反例:塞了太多流程细节
when_to_use: 做 TDD——先写测试、看它失败、写最小实现、再重构

# 正例:只写触发条件,不带流程概括
when_to_use: 在当前会话里执行含多个独立子任务的实施计划时

# 正例:只写触发条件
when_to_use: 实现任何功能或修复 bug 时,在写实现代码之前
```

触发条件的写法:
- 用具体的触发点、症状、场景来说明何时适用。
- 描述**问题本身**(竞态、行为不一致),而不是某种语言的特定症状(`setTimeout`、`sleep`)。
- 除非这份 skill 本身就绑定某项技术,否则触发条件保持技术无关。
- 如果确实绑定某技术,就在触发条件里写明。

```yaml
# 反例:太抽象、模糊,没说何时用
when_to_use: 用于异步测试

# 反例:提到了某技术,但这份 skill 并不专属于它
when_to_use: 测试用了 setTimeout/sleep 且时灵时不灵时

# 正例:描述问题,不带流程
when_to_use: 测试存在竞态、依赖时序、或时而通过时而失败时

# 正例:技术专属型,触发条件写明
when_to_use: 在某框架下处理鉴权重定向时
```

### 2. 关键词覆盖

用上代理会去搜的词:
- 报错信息:"超时""目录非空""竞态条件"。
- 症状词:"时灵时不灵""卡住""僵尸进程""污染"。
- 同义词:"超时/挂起/冻结""清理/拆卸/收尾"。
- 工具:真实的命令名、库名、文件类型。

### 3. 命名:动词优先、主动语态

- ✅ `creating-skills`,不要 `skill-creation`。
- ✅ `condition-based-waiting`,不要 `async-test-helpers`。
- ✅ 用"你实际在做的动作"或"核心洞见"来命名:`root-cause-tracing` 优于 `debugging-techniques`。
- 进行时(-ing)很适合描述"过程类"的 skill:`creating-skills`、`testing-skills`。

### 4. token 节省(很关键)

**问题:入门类、被高频引用的 skill 会被加载进**每一次**会话,每个 token 都算钱。**

**字数目标:**
- 入门工作流:各 <150 词。
- 高频加载的 skill:总共 <200 词。
- 其他 skill:<500 词(依然要精炼)。

**手法:**

**把细节挪到工具自带的帮助里:**
```bash
# 反例:在 SKILL.md 里把所有参数都列一遍
some-cli 支持 --text、--both、--after DATE、--before DATE、--limit N

# 正例:让人去看 --help
some-cli 支持多种模式和过滤,细节运行 --help。
```

**用交叉引用,别重复别人的内容:**
```markdown
# 反例:把另一个 skill 的工作流又抄一遍
检索时,派子代理并带上模板……
[20 行重复的说明]

# 正例:直接引用那个 skill
检索一律用子代理(省 50~100 倍上下文)。【必读前置】见 <某 skill 名>。
```

**例子要压缩:**
```markdown
# 反例:啰嗦(42 词)
用户:"我们之前在某框架里是怎么处理鉴权错误的?"
你:我去检索过去的对话里关于该框架鉴权的模式。
[派子代理,检索词:"某框架 鉴权 错误处理 401"]

# 正例:精炼(20 词)
用户:"我们之前怎么处理某框架的鉴权错误?"
你:检索中……
[派子代理 → 汇总]
```

**消除冗余:**
- 不要重复交叉引用过的 skill 里已有的内容。
- 不要解释命令本身就显而易见的东西。
- 不要同一个模式塞好几个例子。

**校验字数:**
```bash
wc -w skills/path/SKILL.md
# 入门工作流:争取各 <150
# 其他高频加载:争取总共 <200
```

### 5. 交叉引用其他 skill

引用别的 skill 时,只写 skill 名,并加上明确的"必读/前置"标记:
- ✅ `【必读前置】先掌握 <test-driven-development>`
- ✅ `【背景要求】你必须理解 <systematic-debugging>`
- ❌ `见 skills/testing/test-driven-development`(看不出是不是必须)
- ❌ 用强制立即加载整份文件的写法去引用(会在你还没用到时就吃掉大量上下文)

## 流程图怎么用

```
要展示信息?
  └─是→ 这是一个"我可能走错"的判断点吗?
          ├─是→ 放一个很小的内联流程图
          └─否→ 直接用普通 markdown(表格/列表/编号步骤)
```

**只在这些情况用流程图:**
- 不显而易见的判断点。
- 容易"过早收手"的过程循环。
- "什么时候用 A、什么时候用 B"的取舍。

**绝不用流程图来表达:**
- 参考资料 → 用表格、列表。
- 代码示例 → 用代码块。
- 线性步骤 → 用编号列表。
- 没有语义的标签(step1、helper2)。

## 代码示例

**一个出色的例子,胜过一堆平庸的例子。**

挑最贴切的语言:
- 测试类技巧 → TypeScript/JavaScript。
- 系统调试 → Shell/Python。
- 数据处理 → Python。

**好例子:**
- 完整、能跑。
- 注释解释**为什么**这么做。
- 来自真实场景。
- 把模式讲清楚。
- 拿来就能改用(不是填空模板)。

**不要:**
- 用 5 种以上语言各实现一遍。
- 写成填空模板。
- 编造刻意造作的例子。

你很擅长在语言之间移植——一个好例子就够了。

## 文件组织

### 自包含 skill
```
defense-in-depth/
  SKILL.md    # 全部内联
```
适用:内容都装得下,不需要大块参考。

### 带可复用工具的 skill
```
condition-based-waiting/
  SKILL.md      # 概述 + 模式
  example.ts    # 可直接改用的辅助代码
```
适用:工具是可复用的代码,而不仅是叙述。

### 带大块参考的 skill
```
some-format/
  SKILL.md         # 概述 + 工作流
  api-reference.md # 几百行 API 参考
  structure.md     # 几百行结构说明
  scripts/         # 可执行工具
```
适用:参考资料太大,内联放不下。

## 铁律(与 TDD 相同)

```
没有先写出一个会失败的测试,就不写 skill
```

这条对**新建** skill 和**修改**已有 skill **都**适用。

先写 skill 再测?删掉,重来。改了 skill 没测?同样是违规。

**没有例外:**
- "只是小补充"不行。
- "只是加一节"不行。
- "只是更新文档"不行。
- 不准把没测过的改动留着"当参考"。
- 不准一边跑测试一边顺手"改两笔"。
- 删就是删。

**违反规则的字面要求,就是违反规则的精神。** 这一句堵死了一整类"我是在遵守精神"的借口。

## 各类 skill 的测试方法

不同类型的 skill,测法不同。

### 纪律型(规则/硬要求)

**例子**:TDD、"完成前先验证"、"写码前先设计"。

**测法:**
- 知识性提问:他们理解规则吗?
- 加压场景:在压力下他们还遵守吗?
- 多重压力叠加:时间紧 + 沉没成本 + 疲劳。
- 找出借口,逐条加明确反制。

**通过标准:子代理在最大压力下仍遵守规则。**

### 技巧型(怎么做)

**例子**:按条件等待、根因追溯、防御式编程。

**测法:**
- 应用场景:他们能正确用这个技巧吗?
- 变体场景:边界情况能处理吗?
- 缺信息测试:说明里有没有漏洞?

**通过标准:子代理能把技巧正确用到新场景上。**

### 模式型(心智模型)

**例子**:降低复杂度、信息隐藏。

**测法:**
- 识别场景:他们能认出何时该用这个模式吗?
- 应用场景:他们能用上这个心智模型吗?
- 反例:他们知道什么时候**不**该用吗?

**通过标准:子代理能正确判断"何时、如何"套用这个模式。**

### 参考型(文档/API)

**例子**:API 文档、命令参考、库指南。

**测法:**
- 检索场景:他们能找到正确的信息吗?
- 应用场景:找到后能正确用吗?
- 覆盖测试:常见用法都覆盖到了吗?

**通过标准:子代理能找到并正确运用参考信息。**

## "跳过测试"的常见借口

| 借口 | 真相 |
|------|------|
| "这 skill 明显够清楚了" | 对你清楚 ≠ 对别的代理清楚。测。 |
| "它只是个参考" | 参考也会有漏洞、有含糊处。测检索。 |
| "测试太多余了" | 没测过的 skill 一定有问题。15 分钟测试省下好几小时。 |
| "出问题了我再测" | 出问题=代理用不了这 skill。投入使用前就测。 |
| "测起来太烦" | 比起到处debug一个烂 skill,测试一点都不烦。 |
| "我有信心它没问题" | 过度自信必然出问题。照样测。 |
| "我自己读一遍就够了" | 读 ≠ 用。测应用场景。 |
| "没时间测" | 投入一个没测的 skill,后面修它更费时间。 |

**这些全都意味着:投入使用前先测,没有例外。**

## 给纪律型 skill 做"防钻空子"加固

纪律型 skill(比如 TDD)必须能扛住钻空子。代理很聪明,一旦有压力就会找漏洞。

### 把每个空子都明确堵死

不要只陈述规则,要点名禁掉具体的绕路:

反例:
```markdown
先写码再写测?删掉。
```

正例:
```markdown
先写码再写测?删掉,重来。

没有例外:
- 不准留着"当参考"。
- 不准一边写测试一边"改用"它。
- 不准再看它一眼。
- 删就是删。
```

### 应对"精神 vs 字面"的抬杠

在靠前的位置就放上这条基础原则:

```markdown
违反规则的字面要求,就是违反规则的精神。
```

这一句直接掐掉整类"我是在遵守精神"的借口。

### 建一张"借口对照表"

把基线测试里抓到的借口全部收进表(基线测试见下文)。代理说的每一句借口都进表:

```markdown
| 借口 | 真相 |
|------|------|
| "太简单了不用测" | 简单代码也会坏。测一下 30 秒。 |
| "我之后再测" | 测试立刻就过,什么都证明不了。 |
| "事后补测达到同样目的" | 事后测问的是"这段在干嘛";事前测问的是"这段应该干嘛"。 |
```

### 列一张"红旗清单"

让代理在自己快要钻空子时能一眼自检:

```markdown
## 红旗——停,从头来

- 先写了码再写测
- "我已经手动测过了"
- "事后补测能达到同样目的"
- "重点是精神不是仪式"
- "这次情况不一样,因为……"

以上任意一条出现,都意味着:删掉代码,从头按 TDD 来。
```

### 把"快要违规的症状"也放进触发条件

在 `when_to_use` 里写上"你正要违反规则"的那一刻的症状:

```yaml
when_to_use: 实现任何功能或修复 bug 时,在写实现代码之前
```

## skill 的 RED-GREEN-REFACTOR

### RED:先写会失败的测试(基线)

派一个子代理,在**没有**这份 skill 的情况下跑加压场景。逐字记录真实行为:
- 他们做了哪些选择?
- 用了哪些借口(原话照抄)?
- 哪种压力触发了违规?

这就是"看测试失败"——写 skill 之前,你必须先看清代理自然状态下会怎么做。

### GREEN:写最小的 skill

只针对那些具体借口去写 skill,不要为假想情况堆额外内容。

用同样的场景**带着** skill 再跑一遍,子代理这次应当遵守。

### REFACTOR:堵掉口子

子代理找到了新借口?加一条明确反制。反复测,直到滴水不漏。

**测试方法论:写加压场景的具体手法(压力类型——时间、沉没成本、权威、疲劳;如何系统性补堵;元测试)可单独成一份 `testing-skills` skill 来沉淀,这里只引用。**

## 反模式

### ❌ 流水账式例子
"在某次会话里,我们发现空的 projectDir 导致……"
**为什么不好**:太具体,不可复用。

### ❌ 多语言稀释
example-js.js、example-py.py、example-go.go
**为什么不好**:每个都平庸,还增加维护负担。

### ❌ 在流程图里写代码
```
step1 [label="import fs"]
step2 [label="read file"]
```
**为什么不好**:没法复制粘贴,也难读。

### ❌ 无意义标签
helper1、helper2、step3、pattern4
**为什么不好**:标签应当带语义。

## 停:在转去下一个 skill 之前

**写完任何一个 skill,你都必须停下来,把"收尾流程"走完。**

**不要:**
- 一口气批量造好多个 skill 却每个都不测。
- 当前这个还没验证就跳去下一个。
- 以"批量更高效"为由跳过测试。

**下面这张收尾检查表对每个 skill 都是强制的。**

投放未经测试的 skill = 投放未经测试的代码,是对质量底线的违反。

## skill 创建检查表(TDD 改编版)

**建议:为下面每一条建一个待办项跟踪(可用 `task_progress` 上报进度)。**

**RED 阶段——写会失败的测试:**
- [ ] 设计加压场景(纪律型至少叠 3 重压力)。
- [ ] 在没有 skill 的情况下跑场景,逐字记录基线行为。
- [ ] 归纳借口/失败里的规律。

**GREEN 阶段——写最小 skill:**
- [ ] `name` 只含字母、数字、连字符(无括号/特殊字符)。
- [ ] frontmatter 含 `name`、`description`、`when_to_use`、`tags`、`scope`、`risk_level`。
- [ ] `when_to_use` 只写触发条件/症状,不复述流程。
- [ ] 全文铺好检索关键词(报错、症状、工具)。
- [ ] 概述清楚、有核心原则。
- [ ] 针对 RED 阶段抓到的具体失败逐条回应。
- [ ] 代码内联,或链接到单独文件。
- [ ] 一个出色的例子(不搞多语言)。
- [ ] 带着 skill 重跑场景,确认子代理现在遵守。

**REFACTOR 阶段——堵口子:**
- [ ] 找出测试中冒出的新借口。
- [ ] 加明确反制(纪律型)。
- [ ] 把历次测试的借口汇成借口对照表。
- [ ] 列出红旗清单。
- [ ] 反复测到滴水不漏。

**质量检查:**
- [ ] 只在判断点不显而易见时才放小流程图。
- [ ] 有速查表。
- [ ] 有"常见错误"一节。
- [ ] 没有流水账叙事。
- [ ] 单独文件只用于工具或大块参考。

**收尾/交付:**
- [ ] skill 落到正确目录,文件确实写出。
- [ ] 涉及任务的,按需 `task_progress` 上报、`submit_for_acceptance` 交验收;有阻塞用 `raise_event` 上抛;需要并行验证或扩大测试覆盖时,派子代理(`create_subagents` / `dispatch_subagents` / `schedule_child_subagents`)。
- [ ] 声称"完成"之前,先跑通验证/测试 gate(`run_command`),别在没验证时标记任务完成。

## 发现路径

以后接到同类任务的代理,是这样找到你的 skill 的:

1. **遇到问题**("测试时灵时不灵")。
2. **找到 SKILL**(`description`/`when_to_use` 匹配上)。
3. **扫概述**(这跟我相关吗?)。
4. **读速查表**。
5. **真要动手时才加载例子**。

**为这个流程做优化**——把可检索的词尽量靠前、多处铺。

## 一句话总结

**写 skill 就是把 TDD 用在流程文档上。**

同一条铁律:没有先写出会失败的测试,就不写 skill。
同一个循环:RED(基线)→ GREEN(写 skill)→ REFACTOR(堵口子)。
同样的收益:质量更高、意外更少、结果滴水不漏。

如果你对代码遵守 TDD,那就对 skill 也遵守它——这是同一种纪律,只是用在了文档上。
