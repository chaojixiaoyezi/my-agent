# DISCUSSION BACKLOG

这个文件专门记录“功能开发之外”的系统问题。

它不是普通 feature TODO，而是我们后面一起讨论 agent 怎么变得更稳、更像框架、更少埋坑的地方。写法尽量说人话：先说这个东西是干啥的，再说现在哪里不够稳，最后说之后可能怎么补。

记忆系统的专门讨论已经移到 `MEMORY_BACKLOG.md`。后续关于长期记忆、召回、flush、任务状态同步、lesson 和自学习预留的问题，优先在那里合并去重。

## 本轮已先处理

### 1. subagent 文件修改边界要变成真正的门禁

之前的问题：

subagent 的工单里会写清楚 `allowed_write_roots`、`forbidden_write_roots` 和 `locked_files`。大白话说，就是“这个子任务只能改哪里，不能改哪里，哪些文件已经被别人接管不能碰”。

但这之前更像是写在纸上的规矩。模型看到 prompt 后一般会遵守，可真正执行 `write_file`、`append_file`、`replace_in_file` 的工具层还没有强制拦截。也就是说，如果模型误写了工单目录外的文件，系统之前主要靠提示词挡，挡得不够硬。

本轮处理：

工具执行前新增了写入边界检查。只要是 subagent runner 带着 `write_boundary` 调用写文件工具，目标路径必须在 `allowed_write_roots` 里面，不能落在 `forbidden_write_roots` 里面，也不能碰 `locked_files`。如果越界，工具直接返回“写入被阻止”，不会真的写磁盘。

### 4. JSONL 追加写入要加锁

之前的问题：

JSONL 是一行一条记录的流水账，比如记忆、LocalStore 事件、gateway 请求历史、subagent 审计日志都用它。

如果只有一个进程写，通常没事。可我们现在已经开始有 gateway worker、runner、watch 这些并发场景。以后多个地方同时往同一个 JSONL 文件追加时，就可能出现两条记录互相插进去、半行 JSON、日志损坏这类问题。

本轮处理：

新增了统一的带锁 JSONL 追加 helper。以后关键 JSONL 追加会先拿文件旁边的 `.lock`，写完一整行再释放。这样多个本地执行者同时写时，会排队写，不会把账本写花。

## 暂不开发，后续讨论

### 2. gateway 的任务领取凭证需要会续期

`worker` 可以理解成后台干活的人。gateway 收到请求后，不是主程序一个个慢慢处理，而是把请求放进队列，让 worker 去领任务做。

`lease` 可以理解成任务的”临时领取凭证”。某个 worker 领走任务后，系统会标记：这个任务现在有人在做，别人先别碰。这个凭证通常有过期时间，目的是防止 worker 崩掉后任务永远卡在处理中。

本轮已处理：

新增了两个配置项 `lease_heartbeat_interval_seconds`（默认 60 秒）和 `lease_stale_without_heartbeat_seconds`（默认 300 秒）。前者控制 worker 刷新一次 lease heartbeat 的间隔，后者控制超过此时间没有收到 heartbeat 就认为 lease 失效。

gateway worker 在处理请求时会启动一个心跳线程，定期刷新 `lease_heartbeat_at` 字段，防止被误判为卡死。恢复逻辑 `recover_gateway_processing_requests()` 优先使用 `lease_heartbeat_at` 判断 stale，如果传入了 `lease_stale_seconds` 参数则用它作为超时判断依据。

安全边界保持：dry-run 优先，高风险操作需要确认。默认配置下 gateway 会自动启动调度，但用户仍可通过配置关闭。

### 3. adapter file 超时后，晚到的结果要能接住

`adapter file` 可以理解成“用文件当中转站”。调用方把请求写到文件里，另一边处理完再把结果写回文件。

现在的问题是：

如果调用方等结果等超时了，它会认为这次请求失败或没结果。但后台处理可能只是慢了一点，过一会儿其实成功了。这个晚到的成功结果现在还没有一个很清楚的追踪和关联机制。

风险是：

用户看到的是“超时失败”，后台却后来写了成功结果。两边状态对不上，之后排查会很烦：到底是失败了，还是只是回来晚了？

后面可以讨论：

每个 adapter 请求是否要有稳定 request_id；超时后是否继续保留一个“等待晚到结果”的状态；晚到结果回来后，是写入历史、通知用户，还是自动更新本地状态。

### 5. 验收不能只看“有没有证据”，要逐步变成真实执行

现在我们有 `ACTION_RECEIPTS.md`、`TEST_CHECKLIST.md`、`ACCEPTANCE.md` 这些文件。它们的作用是让 subagent 留下“我做了什么、我测了什么、证据在哪”的记录。

这个方向是对的，但它现在更像“看有没有填表”。填了表不等于代码真的没坏，写了“测试通过”也不等于系统真的跑过测试。

风险是：

subagent 可能输出一份看起来很完整的交付材料，但里面的测试没有真的执行；上级如果只看证据文字，就会把“自称完成”误判成“真的完成”。

后面可以讨论：

哪些任务必须自动跑测试；测试命令从哪里来；测试失败时如何回写到工单；什么时候允许人工验收；验收记录里要不要保存命令、退出码、stdout/stderr 摘要和证据文件。

### 6. 大文件需要逐步拆开，不然以后维护会越来越吃力

本轮进展：

已经先把 gateway 文件队列、adapter 文件协议、gateway processing 恢复和 gateway 索引重建从 `__main__.py` 拆到 `agent_py_agent/agent/gateway.py`。这样 CLI 入口少背一块底层协议细节，后续 gateway 继续升级也不用在 main 里堆。

这一步还没有把 `subagent.py` 拆完。它会是下一块更大的整理对象，建议按 `models / rendering / parsing / dispatch / acceptance` 这些边界继续拆。

现在 `agent_py_agent/__main__.py` 和 `agent_py_agent/agent/subagent.py` 都已经偏大。

大白话说，就是很多职责堆在一个文件里：命令行参数、gateway 控制、状态检查、修复逻辑、subagent 调度、验收、日志写入都挤在一起。

短期能跑，但长期会有几个问题：

想改一个小功能，要在很大的文件里找半天；测试会越来越难写；一个改动容易影响很多不相关逻辑；新同学或者未来的我们自己回来读，也会更费劲。

后面可以讨论：

先拆哪一块最划算。比如 gateway 相关逻辑单独成模块，subagent 的验收/调度/日志也分别拆开。不要为了“好看”硬拆，而是按真实边界慢慢拆。

### 7. 配置解析要更框架化

现在配置能用，但整体还是比较朴素。简单字段没问题，一旦配置项变多，尤其是嵌套配置、默认值、类型校验、兼容旧字段，就容易变脆。

风险是：

配置写错时提示不清楚；某个字段看起来写了但其实没生效；以后新增配置项时，要到处补解析逻辑；用户不知道一个值到底来自默认值、配置文件，还是命令行覆盖。

后面可以讨论：

要不要引入更明确的 schema；配置加载时是否输出“最终生效配置”；错误信息要不要直接告诉用户哪一行、哪个字段不合法；旧配置字段迁移要不要做兼容层。
