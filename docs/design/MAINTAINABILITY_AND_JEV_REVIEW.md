## 解决问题与结论

本评估回答三个问题：为什么修改成本高、是否需要调整结构、现有底座能否使用桌面工具和 Jev。

- 建议做渐进式内部重构。现有模块化单体适合继续演进，收益主要来自缩小职责、显式接口和减少重复编排。
- Computer Use 已通过现有 MCP 和 Tool Gateway 接入；部署依赖、身份、权限和图形会话决定能否实际使用。
- Jev 可以作为可选判断工具接入，适合筛选、分类和评分；当前代码没有 Jev 适配，不能作为主对话模型直接配置。
- 重构优先级高于把 Jev 自动插进每轮执行。两者解决的问题不同，模型判断不能修复持久状态或协议错误。

## 修改成本来自哪里

1. **一次行为横跨多种职责。** 中断、续跑或历史保存会经过 Gateway、主子运行器、后台调度和投递。
   修改前需要确认同一事实在哪生成、提交和展示，阅读成本高于局部实现本身。
2. **稳定依赖仍有隐式接口。** `object`、动态属性和 mixin 共享状态使调用方需求分散。
   `getattr` 本身不是错误，插件探测也可以合理使用；优先显式化主链中已经稳定的必需依赖。
3. **存储与流程边界不好分离。** 拆文件容易，保持锁、CAS、幂等、事件消费和投递顺序更难。
4. **文档维护范围广。** 最近提交需要同步多份文档；详述应留在模块权威文档，其余入口只保留状态和导航。
   仍须遵守项目文档同步要求，不能以提速为由省略必要合同更新。

这些是静态源码支持的维护成本判断。本次没有开发过程计时或完整依赖图，不能给出“重构后快几倍”的承诺。
模型服务延迟和真实环境测试成本也需单独测量，不能全部归因于代码结构。

## 拟议重构顺序

保留现有模块化单体和 ToolRegistry / ToolExecutor 主链。分批建立边界，每批都更新直接调用方并删除已失效路径。
不新增一套同义状态、通用巨型上下文或只转发的服务层，不把引入更多类当作改善的证据。

### 第一批：拆分后端协议，建立可重复的整理方式

将 `backends/base.py` 的稳定公共类型、HTTP 共用行为、OpenAI Chat、Anthropic Messages 与工厂分别归位。
复用已经独立的 Responses 实现，逐一调整真实调用方。
公共模型协议不因此变化；若存在已发布 import 兼容需求，先识别具体调用方，再明确迁移期限。
冻结请求、流式事件、原生思考、用量、取消和错误分类必须等价。

这一批不触碰会话持久化，适合作为范围较小的起步。既有中断误分类等行为缺陷另开改动，避免混入文件搬迁。

### 第二批：会话执行与调度分离

独立重构 Goal 按本节及第三、四批实施，现已完成主要运行链验收；auth 与 Jev 不在重构完成条件内。

按职责逐块整理 `conversation/runtime.py`，候选边界是：

- 上下文读取与请求准备：读取 canonical 历史、模型配置和工具快照。
- 单工作片执行：调用现有 runner，透传取消、原生事件和结构化结果。
- 历史提交与投递：沿现有提交和 delivery ledger 顺序保存、去重、发布。
- 后台调度：选择 thread/wake/goal，处理准入和退避，再调用同一执行能力。

用小型 dataclass / Protocol 明确真正需要的依赖；稳定必填能力缺失时暴露明确错误，
不能因动态属性未找到而静默降级。不要建立一个重新包含所有 Agent 属性的“大上下文”。
主、子、前台、后台共享通用执行能力，其差异用已有结构字段表达，不能从文本推断执行模式。

当前实施边界：先把后台上下文准备与原生历史种子从 runtime 独立出来。上下文准备保留原有预算、
任务 lineage/创建锚点过滤、展示字段排除和读取错误传播；原生历史仍调用统一历史投影与 Compact 权威。
上下文准备中既有 `task_runtime_state` 会对账子代理进度，不能把整个模块宣称为无副作用；
该调用的时机和副作用保持，存储、调度、唤醒消费和投递事务不迁移。模块加载不依赖调度运行时。
只保留一处策略快照提取，删除被后定义覆盖的同名函数；不保留旧模块转发实现。

执行拆分批次（已落地，本批恢复验收完成）：`background_execution.py` 负责单工作片内的模型调用、活动展示、
原生历史保存与 Compact 重试。依赖限定为 Agent、唯一 ConversationStore 和显式参数准备接口；
每次压缩后参数准备仍读取最新线程与同一份 Goal 采样，不把旧 RunParams 重复用于新代次。
请求使用字段 Protocol，结果使用具名 dataclass，替代九项位置元组；原模型作用域仍包住参数准备和整片执行。
执行模块不选择 wake、不申请执行租约、不改 Goal 状态，也不负责外部投递。显示快照仍随 canonical final 提交。
技术续跑判据迁入既有 `turn_end.py`，CLI、finalization 和后台统一直接引用，不因读取纯判据加载调度器。

### 判断重构是否有效

- 一次协议修改能够局限于对应适配器和少数直接调用方。
- 从请求入口可以沿明确参数追踪到执行、提交和交付，不依赖猜测对象隐藏属性。
- 公共边界有能描述实际行为的定向测试；不为了拆文件批量增加镜像实现的测试。
- 已有 owner 隔离、run/attempt 身份、权限、取消、未知副作用、历史顺序与投递去重保持等价。
- 按既有合同单测、fake tool、fake LLM、replay、少量真实环境顺序验收；发布前仍遵守严格 gate。

## Jev：可接入，但需要独立适配

截至本次核对，官方模型为 `jev-1.13.0`，接口为 `POST /v1/systemone`。
接受文本或 JSON 状态，返回 Choice、Score、Noul 等受约束的概率判断；不生成普通回答或代码，也不接收图像。
这与现有 Chat/Messages/Responses 后端不同，不能仅在 `/model` 中换一个模型名或 URL 就完成接入。
当前生产代码及配置未发现 Jev 适配，本次 `.venv` 也没有 `typesafe-sdk`；可通过 HTTP 接入，不必强制引入 SDK。
接口与模态依据：[官方模型说明](https://docs.typesafe.ai/models)、[官方快速开始](https://docs.typesafe.ai/introduction/quickstart)。

### 建议的最小接入

优先验证一个按需调用的通用判断工具，经现有 MCP 入口调用 Jev API。
这里的 MCP 包装是拟开发适配，不表示 TypeSafe 已提供本项目可直接使用的官方 MCP server。
暂不新增主 Agent 后端、不在每一轮隐式发起分类，也不为每个任务建立专用分类工具。

```text
主模型提出需要比较的候选
  → 宿主提供有来源的候选 ID 与必要状态
  → 既有 MCP / ToolExecutor
  → Jev 受约束判断
  → 返回评分、概率、模型版本和输入快照引用
  → 主模型参考结果；实际动作仍通过既有执行器
```

初版输入应包括明确问题、候选 ID、评价标准和来源引用；输出保留模型版本、各项结果、
输入版本/摘要、耗时及用量。Choice/Score 的 confidence 与 Noul 的概率分别处理，不编造统一置信度字段。
宿主校验候选有效性、结果范围和快照新鲜度；低把握或候选不足明确返回无法建议。
置信度阈值依赖具体用途的验证，不设一个通用阈值控制所有动作。

沿现有显式 MCP 配置默认不启用；后续若进入产品自动调用，必须增加对应能力配置及消耗说明。
凭据使用经过确认的 owner/部署范围，最小化发送内容；不能从共享配置顺便取得别人的私有 API Key。
错误、超时和限流返回结构化失败，取消遵守现有工具合同，不在适配器里另建无限重试。
首版使用固定版本评估，避免 `latest` 变更后继续沿用未经复验的阈值。

### 接入后值得验证的用途

| 用途 | Jev 负责什么 | 宿主及主模型仍负责什么 |
| --- | --- | --- |
| 检索结果、记忆片段筛选 | 按问题评价相关性、排序候选 | 来源真实性、访问权限、完整原文、引用和最终回答 |
| Skill / 工具候选推荐 | 比较已授权候选与当前任务的匹配度 | 工具是否可用、读取合同、参数生成和执行权限 |

| 浏览器或桌面动作候选 | 从 DOM / OCR 转成的有 ID 候选中建议下一步 | 观察、文字输入生成、节点/坐标有效性、审批、执行和后置核验 |

最先建议做检索片段筛选的离线对照：只读、可标注，容易测出是否有增益。
同参数重复调用、时间比较、数值统计这类可精确计算的事实继续用代码，不能为了使用 Jev 改成模型猜测。

### 与 Computer Use 配合时的边界

Jev 的输入是 DOM/OCR 文本候选，不是截图本身。主模型负责复杂目标拆解和待输入文字，
Jev 可参与快速选候选，现有浏览器/桌面工具负责执行。
候选是当次观察生成的动态集合，不能把整个开放世界写死成全局封闭枚举。
页面变化、窗口焦点和遮挡变化后，旧候选或坐标必须重新核对。

[browser-use/jev-ultrafast](https://github.com/browser-use/jev-ultrafast) 展示了动态元素候选、
Jev 选择操作/元素、辅助 LLM 生成输入文本的组合。它证明有可借鉴的局部方式，
其演示耗时不能作为本项目端到端速度承诺；OCR、页面加载和工具执行可能才是本项目耗时主体。

受约束输出只保证结果形状，不保证判断正确，更不赋予机器权限。
不能把 Jev 输出用作身份授权、任务完成、未知副作用重试、删除记忆或推进恢复状态的依据。
官方也列出计数、时间比较、复杂推理和恶意输入等弱点，见
[已知局限](https://docs.typesafe.ai/model-jaggedness/jev-1.13)；中文真实任务需要独立对照验证。

## 后续验证与协作边界

1. 先进行后端协议拆分的小批重构，用定向回归确认请求和事件等价，再推进会话运行时。

   通过后再接可选工具；没有实测结果前不承诺自动路由或整体提速。

后端与运行时的共同入口由一个实现方负责；其他 agent 可以独立做参考审阅、只读评估或复验。

第 1 步盘点时，五个 mixin 还共享 `scheduler_service`、`collaboration_store`、准确的子代理恢复库与任务事实、owner 路径、配置及 claim 心跳参数。
ThreadLane 负责准备/消费编排；Tick 负责维护、恢复与持久入队；Wake 负责来源与定时任务租约；Goal 负责原目标状态、时钟与路由；Execution 负责最终准入、会话租约和 policy 记账。
这些是后续收窄依赖的清单，不能照搬为五个持有完整 Agent/Store 的服务。诊断使用 `threading.local()`，当前 worker 可追加自己的诊断列表，不改成 owner 或全局共享列表。

装配生命周期与读取时机也属于行为：

- Gateway supervisor 长期持有 base/owner scheduler；规划轮用同一个 `planned_at` 做准备和就绪查询，明确关闭同步孤儿监督，再按车道冷却和并发空位提交。
- worker 调用 `tick_thread(thread_id)` 时重新取时间、重读来源；不能复用规划阶段的旧状态直接执行。Gateway 独立孤儿监督保持原归属。
- CLI 的 tick 与 service 循环每次经 `_run_tick` 新建 runtime/scheduler 及 FakeDeliveryService，进程内退避和维护节流随实例重置；提取类不能顺手延长其生命周期。
- claim TTL/心跳和供应退避配置在 scheduler 构造时读取，消费数量等 `_config_limit` 在调用时读取；车道缺模型恢复读取当前线程模型引用，且配置读取不持有冷却表锁。

原有顺序需作为迁移约束逐项核对：

1. 后台准备保持进程完成对账、旧账维护、协作处理、可选孤儿监督、定时入队、孤儿 attempt 回收、未完成任务唤醒的现有顺序。
2. 车道消费保持 wake → observation → policy；领取 claim 后再查终态与恢复阻断，避免准备阶段之后的停止竞态。
3. 每片退出先停止续租再关闭本 claim；Compact 让出保留未处理来源，具体来源确认仍留在原调用位置。
4. 同批唤醒确认仍以模型轮开始时的采样时间为界；期间新到的孩子结果保留 pending，不能顺带消费。
5. 插件停用要先撤销执行资格，再清理其进程/订阅；冻结旧快照不能重新激活已撤销贡献。此项是待实现合同，不代表当前注册表已有能力。

定时任务另有外层 `scheduler_service` claim/心跳，不能与内层会话 claim 合并：
正常返回时，先结束内层工作片并收口会话 claim，再停外层心跳，按真实报告释放、等待或结束定时 claim，最后按原条件确认来源。
异常时，原 `except` 分支先按 typed 错误处理定时 claim，之后 `finally` 停外层心跳；quota 路径仍沿原专用处理，不能改写成统一收尾顺序。
`wake_handled` 来自实际外发或 canonical 提交事实，不来自 claim finished；Compact 让出关闭本次执行租约，但保留未处理来源。
未完成任务恢复还使用 wake_queue 的独立行租约：向 ConversationStore 成功发布后才完成原行，失败释放重试，不能将不同租约合并成一个状态。

上述调度复核只读取实现和已有回归入口，本轮未重跑后台测试；相关入口为 `test_background_main_wake_recall.py`、`test_gateway_lane_retry.py`、`test_background_main_agent_runtime.py` 和 `test_wake_queue_state_machine.py`。
插件侧现有 17 项合同回归已通过，实际 handler、权限视图、MCP 重连及 Skill 文件身份见[接线核对](PLUGIN_LIFECYCLE.md#第-1-步接线核对与迁移约束)。

资源归属继续分三层：Goal 管自动续跑，当前回合管模型/工具执行链，进程与子代理由精确任务/attempt 管理。
实际 TUI 另暴露拒绝记忆只存在内部工具参数中、跨同一子代理 Goal 回合丢失；当前修复由宿主运行参数承接原列表，
并让前后台 Compact 保持同一对象。不同孩子/新调用隔离、批准不提升；模型结束与 Goal 状态仍按各自原合同处理。
参考定向读取 Codex `tools/approvals.rs` 的结构化拒绝结果和 Hermes `tools/approval.py` 的上下文隔离；未复制其策略或宣称整库审阅。
插件的执行进程、订阅和注册贡献也必须带显式归属；卸载不能据名称相似清理无关资源。
第 1 步框架基线收口后开始纯策略切片；清单和实现均不引入空 SDK、替代 Store 或兼容转发。

### 第 2 步首片：进度策略纯计算

`background_progress_policy.py` 只接收失败次数、策略 ID、原无进展次数和结构化物质进展数。
`runtime.py` 保留回合后读取 metadata、成功/失败持久记账、三次失败退休和供应错误分类；没有迁移租约或调度器内存状态。
失败退避保留 MD5 派生的确定性抖动，3600 秒是抖动前的基数上限；无进展次数本身不封顶，间隔上限仍归 `store_progress.py`。
原函数、专属常量和导入删除，调用方及既有回归直接使用新实现，无旧名别名或转发层。
定向参考 OpenAI Agents SDK `run_internal/model_retry.py` 的延迟计算与等待分离，及 Codex Python SDK `retry.py` 的调用/等待边界；只用于核对职责，不复制其随机抖动、配置或重试策略。
自动验证和新安装版真实 TUI 分列；普通长任务若未产生进度策略落账，不能声称命中该内部支路。当前验收进展见执行 Goal。

### 第 2 步次片：进程内供应退避

`background_supply_backoff.py` 集中会话冷却状态、消费守卫和失败/恢复日志，不依赖 Agent、Store、Goal 或唤醒类型。
runtime 的 `_supply_backoff_from_agent` 仍在 scheduler 构造时读取原 30/900 配置，传入数值；Gateway 长驻与 CLI 每次 tick 新建的实例寿命保持。
同一实例同时供 wake、observation、due-policy 消费和 ready-thread 扫描使用；原来源筛选、数量限制及落账顺序不动。
异常锚点仍为 tick 时刻加本次回调的 monotonic 耗时；冷却期间不执行回调，回调返回 None 不清状态，任何非 None 报告才清零。
只吸收 typed transient，额度耗尽、配置错误、普通失败及 KeyboardInterrupt/SystemExit 保持各自传播边界；事件字段和打印格式不变。
删除旧类/guard 定义和空 TYPE_CHECKING，不留旧名别名；配置说明同时纠正“额度耗尽进入自动长退避”的过期描述，配置值与实现行为不变。
既有时钟替身直接指向新模块，恢复用例同时检查就绪筛选共享冷却，另覆盖 None 与假值报告的区别；新安装版验收独立记账。

### 第 2 步租约与恢复切片（实施中）

路由片的 TUI 120—123 所测框架链路已收口，模型交付失败继续单列。本片先补领取后的终态/unknown 竞态、

- `background_claim.py` 承担后台 claim 领取、最终准入、共享心跳及本次 claim 结算；

- `background_recovery.py` 承担权威恢复阻断查询与相同阻断日志去重；只持有 checker 读取能力和进程内日志指纹，
