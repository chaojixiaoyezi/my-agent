## 秘密的使用边界

| 加密初始化前 PermissionError/EACCES | 0 | 0 | reported=CREDENTIAL_STORAGE_UNAVAILABLE，外层 UNKNOWN；错误地把未发送当结果未知 |

因此现场“卡没发出”仍需原发送事实确认，而“所有存储失败都必须 UNKNOWN”已经被反例否定。存储是本机受管凭据链，写表是外部飞书 API；两者都涉及副作用阶段分类，但这不证明它们共享一个坏存储子系统。

### 要修的两个缺陷

1. **受管存储可用性及诊断（总清单 S21）**：沿原交互密钥、密文记录、owner 配额和私有写入入口区分初始化、密钥读取、空间/锁、记录提交、回执保存等阶段。宿主诊断保留异常类型、errno、准确操作编号和阶段，不记录密钥、表单值或原异常任意正文；能力自查需能说明依赖/存储不可用。缺失与损坏分开，已有密钥不能重置，不能靠放宽 owner 权限、广泛 chmod、改放可读文件来修复。现场准确原因仍待受管日志或同版本运行环境证据。
2. **副作用与重试判断（S22）**：未进入发送且内部记录可确认清理/复用时，返回明确未发送，修复原因后可沿原幂等记录重新尝试；不在永久错误上无限重试。已经发送、发送结果丢失或回执保存失败则核对原卡/原操作，不能为解除 UNKNOWN 换调用编号重复发卡。失败、取消、到期须结算原输入并释放等待，不留下无人可提交的长期占位。旧 UNKNOWN 记录按原恢复入口核对，不能升级时批量清掉。

### 群内与私人卡片路由（S23）

用户最新定稿是群助手直接在原群发卡，普通用户/管理员个人助手在自己的私聊发卡。群卡可由本群成员提供，普通群表单或仅本人可见输入均可，选择可用、简单的实现，不再要求必须进入私密页面或先接入定向可见运输。此定稿覆盖此前“只许原发起人看到和填写”的候选方案。

- **群来源**：群卡绑定准确原群、owner、原请求人、任务/监控、输入代次、有效期和实际 message ID；实际提交者由可信飞书回调确认并记录，不凭卡上手填姓名或最后发言人决定身份。允许本群其他成员为本次请求提供，不代表他能覆盖既有凭据、取消别人的请求或把本群凭据用于其他空间。
- **个人来源**：继续发送给本人私聊。管理员 TUI 来源沿原已绑定身份；不能回落到另一个人或猜测群目标。
- **最少接线**：复用原卡片传输、签名引用、TaskCredential、输入依赖和 Wake。普通群卡需要正式扩展呈现范围、成员提交权限与原任务授权，不只是替换 target；不另建凭据库。原 `resolve_private_interaction` 的私人首设/解锁不能一刀切套到群输入，也不因开放群卡就放开个人配置、工具审批或别人的凭据。
- **实际平台验收**：原 adapter 走普通消息接口，尚未实现本轮群卡交互。官方[发送卡片指南](https://open.larkenterprise.com/document/feishu-cards/send-feishu-card)中的群内定向可见能力保留为实现选择，不是发布依赖。表单字段、密码输入兼容、实际可见性、提交和清空需真客户端验证，并如实说明，不能用模拟发送证明已经可用。
- **保存和回执**：用户不要求隐藏整张卡，不改变宿主加密保存、跨 owner 隔离和不把秘密写入模型/日志/记忆的既有约束；提交后不把密码再回显到群卡结果。卡片权限与密码正确性是两件事。

### 简单凭据卡与用户发起重填（S23 用户定稿，待实施）

用户操作保持自然：告诉助手目标链接，再说“发个卡片，我填账号密码”或“只填密码”；没有给链接时，助手直接发增加链接字段的卡。发错卡或填错密码后，用户再要求发一张。名称/备注是可选的人类标签，不是飞书身份或授权依据。

| 用户已提供的信息 | 卡片字段 |
|---|---|
| 已有链接，需要账号密码 | 目标链接展示 + 账号 + 密码；名称/备注可选 |
| 已有链接，只需要密码 | 目标链接展示 + 密码；名称/备注可选 |
| 没有链接，需要账号密码 | 链接 + 账号 + 密码；名称/备注可选 |
| 没有链接，只需要密码 | 链接 + 密码；名称/备注可选 |

1. **收集不要求先懂认证协议。** 用户只需说明收哪些字段，不必选择 basic/bearer/login/signature。当前 `RequestCredentialsTool` 的 schema 和执行入口强制先有 url/authentication，`request_credential_card` 在发卡前生成准确 origin/校验认证配置；这正是要改造的入口。沿原工具/记录区分收集字段与使用时的认证方法，卡片可暂待用户填目标，不凭缺失 URL 猜 origin 或给无限目标权限。密码只有密码字段，不额外把用户名设成必填。
2. **提交链接后绑定目标。** 卡上链接先做格式、无内嵌密码等结构校验，再保存准确目标；实际访问仍经过原网络权限。没有在卡片填完链接前发登录请求，也不因为用户填了内网链接就自动取得网络权限。名称/备注仅用于区分凭据；实际提供者姓名和身份取飞书回调。
3. **先保存可以，验证状态如实说。** 当前 `submit_credential_card` 仅检查字段后加密保存、置 ready，并未证明密码正确。没有可靠验证方式时允许保存并返回“已保存，尚未验证”，不把验证成功设置成收集完成的必经门，也不强制多跑登录或业务写入。能验证时或后续实际使用时，按目标服务的结构化认证结果更新状态。
4. **错误只汇报，重发由用户提出。** 确认账号或密码错误时向来源会话说明；无法区分二者就说“账号或密码错误”。网络、超时、权限、验证码或宿主存储故障分别报告，不冒称密码错。不会因此自动弹新卡、催填、后台反复尝试登录或占住会话等待。用户说重新发卡后，由模型调用原结构化工具完成，不用关键词规则直接改状态。
5. **发错卡可重发，旧卡不能串任务。** 用户要求修改字段、重发或重填时沿原输入代次处理，旧待填卡失效，迟到或重复提交不能覆盖新卡；发送结果未知先核对原卡，不借“重新发”掩盖不确定投递。修改目标链接需要新的明确目标绑定，不悄悄扩大既有凭据允许发送的 origin。
6. **重填不毁有效版本。** 新输入先作为加密候选，错误认证不替换旧有效凭据；无验证方式可以保留未验证候选，不假报已验证。提交不预填/回显旧密码。并发提交、更新、撤销继续沿原 generation/CAS 和提供者授权事实；其他群成员的提供权限不等于任意替换权。只恢复原任务或准确监控，不影响群里其它聊天与任务；取消和过期沿原输入账结算，无人填写也不占执行片。

验收：三种 owner 的前置/发送后存储错误保留原事实；四种字段组合均可收集，缺链接不再发卡前失败、仅密码无需用户名、名称不影响身份；同群成员提供、私人本人提交和跨群/离群/转发/过期拒绝范围一致；错误卡重发后旧卡失效、重复/并发/迟到提交不串任务；明确认证失败只汇报且不自动再发卡，无验证方式可先保存；网络/权限问题不误报密码错；错误候选不毁有效旧版本，不阻塞其它消息。合成秘密不进入模型/日志/记忆/子代理/提交后回执，真实客户端验证可用的群/私人表单和平台回执。本轮只确认代码缺口并同步设计，未实施或真实发卡。

建议下一步：先修 S21/S22 存储和发送状态，再沿原 request_credentials 完成四种表单与用户要求重发；群卡客户端兼容可并行验证，提交代次、目标绑定和凭据版本由同一实现负责人收口。普通群表单或仅本人可见方式均可，不再为私密页面阻塞整个需求。

## 准确原卡取消

各简单字段组合及带/不带URL的凭据表单沿同一取消按钮。有效MAC和原actor（已签群卡需当前成员事实）可取消准确原卡，个人锁或卡片期限不阻止仅关闭操作；错误chat/message、旧代次和伪造引用仍拒绝。取消不写秘密、不撤销旧ready引用，也不取消父或兄弟任务。原输入账锁内pending变cancelled、armed=false并保存resolved_at，移除原task等待refs并清理截止调度；不启动业务Wake。取消后容量立即释放，可重新发卡；若记录保存后输入收尾失败，原卡重试仅补准确输入退休，不重复审计。首次真实取消者ID、身份索引展示名与UTC时间存在原行，群重复取消展示首个决定；已完成提交收到取消只返回已处理。

卡片静默取消在原输入行明确保存 `resolution_delivery=retire`，原arm与归档边界只对此准确标记禁止重臂/等待；泛用 `resolve_input_dependency(cancelled)` 不带此标记，继续原终态Wake与容量释放合同，不能按cancelled状态一概静默。

## 2026-10-19 准确引用状态与站点发现分责（源码修复，真实复验另记）

已有`credential_ref`时，用`request_credentials(operation=status, credential_ref=...)`查询原授权引用的保存状态。此入口仍核当前owner/actor/task及原锁，只返回状态、origin、期限、verification和replacement元信息，不解密或返回凭据内容。`find`仅用于真实URL的同origin发现；空匹配只说明该发现条件未选出凭据，不说明其它引用没有填写。不得编造占位URL代查原引用。

`find`分支复用原`x-exclusive-argument-groups`声明URL与引用互斥；因为URL为必填，存在任何`credential_ref`字段（含空串/null）都拒绝。原execute也在发现调用前返回`TOOL_INVALID_ARGUMENTS`，不忽略引用、不自动转status、不发送新卡。原scope默认、本人优先、群成员、权限、审批与存储保持。

输入等待的既有软指导区分：发卡成功不等于提交；pending/waiting_input且result_available=false仍未收到该项输入；ready+result_available=true才能说已提交。不透明引用不是账号或密码，不能替代填写值，也不能虚构本地文件或卡片副本已保存。指导只影响模型表达，不通过关键词判断状态、不增加请求或固定回复。真实673证明出现了find+ref被忽略及错误推断，canonical原记录不是独立provider wire；本修复仍需新源真实复测。
