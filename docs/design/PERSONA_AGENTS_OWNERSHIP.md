# AGENTS.md 归属、指向与自动学习分离

状态：**设计已定（用户 2026-10-08 拍板；第 2 版按 mc4 设计审查修正），第 0 期实施中，第 1 期待实施**。本文是这一主题的唯一权威设计；`DESIGN_LEDGER.md` 只保留摘要和链接。

## 1. 背景（结构化事实，2026-10-08）

- owner `local/main` 的 `AGENTS.md` 有 170KB、489 条：475 条由 memory-promotion 自动写入，13 条由 `update_persona` 工具写入，1 条是基线。
- **10-07 一天自动加了 246 条，10-08 加了 191 条**，以前每天 0–13 条。
  - 437 条全部是 `auto_eligible`，430 条被标成 `user_explicit`。
  - 来源只有 9 个线程，全是开发派活会话（ds1–ds8、mc3）：派活任务书以"用户消息"的形式输入工人 TUI，被当成了用户本人说的长期工作约定。
- 根源有两点：
  1. 程序把 AGENTS 设计成"模型可以自主维护"，自动晋升不需要确认（`promotion.py` 的 `_commit_persona` 和 `_absolute_authority_block`）；
  2. 会话、回合和候选都没有"是否参与学习"的结构化来源事实。
- 注入时每个人格文件预算 2 万字符，取开头 75% 和结尾 25%（`persona_repository._bounded_prompt_content`），中间看不到；结尾现在全是开发纪律。注入帽不是写入帽：28,012 字符的文件照样能写入。文件硬上限 2MB，到了会写入失败。
- 对照主流产品（Claude Code、Codex、Gemini CLI、Cursor、Copilot、Hermes、OpenClaw、ChatGPT），共同做法是：
  - 指令文件归人写；
  - 自动记忆另存，可以查看和删除；
  - 子代理、定时、后台、外部内容不学，来源不明的不算用户说的；
  - 写入时有硬上限；
  - 满了就合并、替换或过期淘汰，保留出处和旧版本。

## 2. 用户决定（2026-10-08，要点）

1. **AGENTS.md 只能由用户写**。不同用户只能改自己的；管理员在完全访问模式下有权限，但不动别人的。
   - 用户可以配置自己的 AGENTS.md **指向哪个文件**，自己改或让 my-agent 改都行；默认是自己的。
   - 可以指向本地文件，也可以指向网络文件，但必须有权限，不能越权。重点是多用户隔离。
2. 自动学到的内容另放一处，参考 Codex 和 Claude Code：重复或相似的直接合并或更新。
3. 子代理可以学，但要打标签；其它自动化来源（派活、定时、后台等）不学。
4. 写入时有硬上限。
5. 清理已经误加的条目：先留快照，再移到归档；可以检索，但不注入。

## 3. 目标设计

### 3.1 指令文件归属、授权与隔离

- 写 AGENTS（包括 add、replace、remove、rollback）只有两个入口：
  1. 用户直接编辑来源文件；
  2. 用户在**当前请求里直接要求** my-agent 修改。
- "用户直接要求"必须是一个**结构化授权事实**：由直接用户入口（TUI 或飞书里用户本人发起的回合）生成，绑定 request_id、owner、动作和目标版本。**模型提交的 `source_quote`、`confirmed` 字段，或者正文里的关键词，都不能证明授权**。派活、子代理、定时任务、后台任务不能生成这个事实。
- memory promotion 在**最终提交入口**一律拒绝 `agents` 目标，不管是自动、积压重试、人工晋升还是审核后提交。被拒的候选保持待定，带结构化原因码，不丢弃，也不标成失败。
- 写入身份只取运行时的规范 owner（可信组合入口构造的 PersonaRepository），**不接受参数里的 owner**。缺身份或身份冲突时直接拒绝，不回退到管理员的 home。
- 管理员跨 owner 操作走**独立的宿主授权分支**，以下三者缺一不可：管理员身份、Full Access、用户明确指定的目标 owner。审计要记 actor、目标 owner、动作、请求身份、修改前后摘要和结果。这条规则不能被理解成"管理员的默认来源可以指向别人"。
- 初始化和模板升级是宿主的例外：只在文件缺失、或文件内容仍是精确旧模板时生效；不覆盖用户内容，也不重置指向。
- 人格写保护（`_persona_write_guard`、沙箱规则）必须跟随**实际来源的身份**，同时保护来源配置和缓存，不能只认 `AGENTS.md` 这个文件名。

### 3.2 指向配置（第 1 期）

- 唯一权威位置：当前 owner 的 **`persona/agents_source.json`**，内容是 `{kind: owner_default | local_path | url, value, revision（单调递增）, updated_by, updated_at}`。
  - 参数中心、TUI 和飞书只负责展示和调用，不另存覆盖值。
  - 配置本身不增加任何路径权限或网络权限，权限仍归 owner policy。
  - 历史记录和缓存都是附属记录。
- **本地文件**：
  - 先按当前 owner 的路径权限裁决，再做来源专用的禁区检查：其它 owner 的 home、宿主运行和控制目录、密钥目录一律排除。
  - 用可信根目录句柄逐段打开（`common/nofollow_fs.py`：nofollow、inode 和设备身份核对、有界读取），最后读取的是**同一个已经核验过的文件描述符**；不能"先检查 realpath，再普通 open"。平台给不了同样的保证就明确拒绝，不静默降级。
  - **可以写**：当前请求带有用户授权事实、并且 owner 对该路径有写权限时，经专用仓库入口写入。写入要绑定来源 revision、内容摘要，以及同样的安全打开规则，防止配置后换了文件还继续写进去。
- **网络地址**：
  - 只允许 https。每一跳都要检查 https、公网地址和目标身份，并关闭通用网络策略里的私网例外。
  - 走系统代理时，代理实际连接的目标仍要受已验证地址的约束；不能先在本地检查域名、再让代理重新解析到内网。
  - 设超时、响应大小和解压后大小上限，内容要过注入扫描。
  - 可以复用 `web_fetch_runtime` 的地址固定和逐跳处理，但它目前不走系统代理，需要补上。
  - 缓存放在 owner 自己的 persona 缓存目录，绑定 owner、来源 revision、规范来源和内容摘要。读取完整、大小检查和注入扫描都通过后，才原子替换"上次成功"的缓存；提交前再核对一次 revision，防止旧请求覆盖新配置。
  - 同一个来源、权限仍有效时拉取失败，就用上次成功的缓存，回执里给出 `used_cache`、`stale`、原因码和缓存版本。第一次就失败、又没有缓存时，报告来源不可用。换了来源或撤销了权限时，绝不套用旧来源的缓存。
  - **远端来源只读**：在定义写回协议之前，不能声称支持编辑远端文件。
- **冻结前缀**：
  - 区分"待生效来源"和"当前已激活的快照"。换来源只在约定的刷新点切换，不经动态差分提前注入新来源。
  - 不把抓取时间、检查状态或来源 revision 放进每轮的 epoch。
  - 清理迁移、撤销权限属于一次性的安全失效事件，用受控刷新处理，不能为了保住缓存继续注入已撤销的内容。
- **命令入口**：走现有公共链路 `command_catalog → conversation/control_commands → gateway_parts/control_service → 共用 persona 服务`。TUI 的两种模式和飞书共用同一套语义；覆盖查看、设置、恢复默认、刷新状态和显式修改授权，都带版本检查和结构化回执。owner 的来源配置不放进管理员的 `/settings`。

### 3.3 自动学到的约定另存（第 1 期）

- curator 识别出的 `working_agreement` 进**现有的长期记忆 JSONL**（唯一权威）。要补齐：正式 promotion 的类型白名单和 kind 映射、来源、scope、版本和撤回。
- 相似度只用来找候选。真正合并必须同时满足：同一个 owner、同一个 scope、精确的 entry_id、预期版本一致。现有 `merge` 本质上是"用候选正文替换"，不会自动做语义合并。
- 合并保留来源引用和旧版本，不能因为文字相似就跨项目合并。
- 子代理和推断来源的约定走专门的审核规则，不能借机放松正式事实的可信来源限制。

### 3.4 学习来源事实（贯穿线程、回合和候选）

| 来源 | 接线点 | 规则 |
|---|---|---|
| 普通用户线程 | `store_threads`、`request_context` | 创建时写入宿主来源和学习策略版本；旧记录缺这个字段时，**不能默认当成用户明确说的** |
| 子代理 | `agent_thread_store`（已有 thread_kind、run、谱系） | 学；由宿主在候选来源引用里写 `source_kind=subagent`，保留 `source_run_ids`、`source_task_ids`；不冒充 `user_explicit` |
| 定时任务 | scheduler 的 job/run 信封 | 不学；来源从信封生成，不从提示词猜 |
| 后台、会话间派活 | `conversation/runtime` 现有的 `origin_kind` | 不学；来源要落到每个回合、每条消息和审计证据上，不能只给整个线程打标签 |
| TUI 派活工人 | 派发器先执行一条明确的宿主命令，或者在创建线程时带结构化派活标记 | 不学；**不识别正文**（不靠"3a 派活"这类文字判断） |

curator 要覆盖三处：
1. 读消息正文之前先按线程排除；
2. 过滤 audit 输入里的来源；
3. 对已经存在的待晋升候选再核验一次（旧候选在没有新消息时也会被重试晋升）。

### 3.5 上限（三层）

1. **写入硬帽**：在 JSONL 或人格提交锁内，按写入后的状态判断。AGENTS 写入后不能超过注入预算（2 万字符）。已经超限的文件允许受控的净缩减，这样清理才能进行。
2. **工作约定的注入子预算**：接在 `agent_core/runtime/loop_support.py` 的正式召回预算下，同时受总预算约束。
3. **可重建索引的上限**：导航投影的行数、字符数和 UTF-8 字节数要写清楚口径。它不是全部历史正文的存储上限。

### 3.6 清理迁移（第 0 期）

- **归属判定**：按版本历史追踪**当前条目最后一次有效写入的来源**。
  - 只有当前条目确实由 memory-promotion 写入、并且之后没有被用户或工具改写或重新添加过，才算自动条目。
  - 条目 ID 由目标和正文散列生成。"自动添加 → 用户删除 → 用户重新添加相同文字"时 ID 相同，这种情况必须识别为用户条目。
  - 有歧义的一律保留，并在报告里列出。
- **事务和恢复**：
  - 和 PersonaRepository 用同一套锁入口和固定锁顺序，每一步都带预期摘要。不依赖配额锁来互斥（配额关闭时那个入口直接放行）。
  - 快照要包括：AGENTS.md、`persona/versions.jsonl`、版本记录引用的 `persona/backups`、候选账本、排除名单，以及迁移归档和事务状态。
  - 中途崩溃可以幂等续作。恢复前先比较当前状态，不能覆盖迁移期间用户新做的修改。
  - 执行（apply）要绑定空跑（dry-run）计划的摘要；两次之间发生过变化就拒绝，要求重新预览。
- 移出的条目连同出处（entry_id、candidate_id、来源会话、原版本号、内容）写进归档。归档"可以检索"，但在结构上**不参与自动召回、不再被学习、不再被晋升**。
- 来源会话写进学习排除名单。名单是数据，运行迁移时传入，**不写死在代码里**。
- 清理之后，**让受影响线程的冻结人格快照受控失效**，并验证旧约定不再出现在固定前缀里（删除很多条时，动态尾部只会显示一个数量）。
- 写一条结构化迁移记录：迁移编号、各项计数、快照位置、排除的会话、执行者。
- 生产上执行前，必须先在 pytest 隔离 HOME 里用数据副本演练，然后先空跑、再执行。

## 5. 风险与必测点

- **最容易出错的三处**：
  1. 把"消息角色是 user"当成"用户授权"，派活污染会继续发生；
  2. 把通用的路径或网络允许当成 AGENTS 来源的允许，漏掉代理、竞态和缓存身份；
  3. 只清正文，不清候选重试、自动召回和冻结快照，表面上迁移成功，旧约定仍在继续注入。
- **越权**：跨 owner 写；参数 owner 冒充；父目录或叶子文件被替换；`..`；任意文件名绕过保护；管理员隐式写到别人那里；伪造或重放用户授权。
- **网络**：访问内网或本机地址（包括重定向和代理二次解析）；超大内容或解压炸弹；注入内容；首次拉取失败；撤权；旧抓取覆盖新配置。
- **记忆连贯**：迁移不能丢用户本人写的条目，能从快照完整恢复；待定候选不能因为硬拦而丢失；归档不能被重新召回或学习。
- **缓存**：指向或内容变化只在冻结刷新点生效，不能让每一轮的固定前缀都变。
