## 单一事实源与入口

- `scheduler/repository.py` 保存原 job/run、版本、claim epoch、开始时间和终态；`run_preparation.py` 在同一事务里冻结来源和预检观察。
- `scheduler/service.py` 仍负责 reserve → wake → claim → TaskLink；`scheduler/execution.py` 接入原 `background_claim.run_claimed`。
- `conversation/runtime.py` 只接执行开始、模型作用域、交付来源三处边界；原停止、输入领取、Compact 与 outbox 仍由各自模块负责。
- job 修改只影响以后预留的 run。已预留 run 的 prompt、执行策略、预检定义和 Skill 引用保持原快照；固定档案保存 ID，不复制凭据。

## 用户可配置字段

新增能力按 job 显式启用，不增加全局后台任务或默认模型请求。默认值来自 schema 对应的规范函数，旧 job 缺字段沿用原行为。

| 字段 | 默认值 | 语义 |
| --- | --- | --- |
| `execution.mode` | `followup` | 沿计划的执行会话；新 IM 计划默认已绑定独立后台，TUI 默认沿原会话 |
| `execution.mode=isolated` | 显式启用 | 每个 run 一个无通道绑定的独立上下文 |
| `execution.model_policy` | `inherit` | 初始与后续安全点继承来源会话的显式模型选择 |
| `execution.model_policy=fixed` | 显式启用 | 必须给出具体 `profile_id`，不接受可变 `default` 别名 |
| `policy.misfire` | `skip` | 超出原宽限期的错过周期跳过；`coalesce` 只补一次 |
| `policy.queue_timeout_seconds` | `0` | 预留后尚未实际开始的最长等待；0 关闭 |
| `policy.failure_pause_after` | `0` | 连续 failed/unknown 达阈值暂停未来周期；0 关闭 |
| `policy.failure_backoff_seconds` | `0` | 未来新 run 的指数退避基数；0 关闭，最长七天 |
| `precheck` | `null` | 关闭；对象显式指定只读工具及观察字段 |

`execution`、`policy` 是完整配置对象；提供对象中的缺省字段按表补齐。更新未提供的整个对象不变。`precheck=null` 明确关闭预检。

示例字段：

```json
{
  "execution": {"mode": "isolated", "model_policy": "inherit"},
  "policy": {"misfire": "coalesce", "queue_timeout_seconds": 900},
  "precheck": {"tool_name": "example_read_tool", "arguments": {}, "json_pointer": "/revision"}
}
```

工具名仅示意，产品没有内置 `example_read_tool`；实际必须是当前 owner 可用、按本次参数被原 ToolRuntimePolicy 判为 `read_only` 的工具。不能凭工具名字、自然语言或模型保证跳过权限判断。

## 执行与交付分离

独立上下文的线程 ID 由原 run ID 确定，重复物化沿同一 ThreadStore 记录，保留已存在的 Compact、模型和消息状态。创建线程不会复制来源历史或通道绑定。

独立指会话上下文独立，**不意味着文件系统隔离**。执行沿原会话 cwd、授权根和 owner 上界；有同目录写入需求时仍使用原资源与权限合同。

新 IM 计划先固定原布置者；显式 isolated 的 run 从原计划引用冻结同一来源，其他来源在 run 入队时冻结通道绑定，独立线程仅保存结构化来源引用。结果通过原路由与 outbox 投回创建会话；每次真正投递前确认冻结绑定仍指向原会话。来源重置、删除或绑定变化不会转投后来出现的会话。

投递失败保留冻结内容、回执和原 run。重试只发送该内容，不再调用模型或预检工具，也不重做业务操作。业务终态与投递状态分别展示。

子代理完成后的 waiting run 不能只凭 TaskLink completed 收口。仍有同任务存活或未知执行 claim、待处理生命周期 wake（含冻结投递）时保持 waiting。最终交付已确认后，先将该片的 response/delivery_status/delivery_reason 写回原 run，再确认原 wake，最后结束 run 并提交 checkpoint。重启对账读取同一组字段，不能把“孩子正在处理”的第一片回执当作最终结果；ended_at 使用实际收口时刻。

## 领取与开始时间

领取 scheduler claim 表示持有调度运行资格，尚不代表取得后台会话执行权。

真实顺序是：预留原 run → 原 wake → scheduler claim → 核对 TaskLink → 后台 claim 准入及中断登记 → `mark_run_running` → 可选预检 → 原模型工作片。

`started_at` 只在取得后台车道后首次写入。车道繁忙、准入未通过或开始前退出仍不产生开始事实。领取后再次校验原 claim/epoch，旧领取者不能确认新领取者的 wake。

队列期限冻结于预留时刻。未开始的 run 到期记 skipped 和 `SCHEDULER_QUEUE_EXPIRED`；已经执行、等待子任务或欠投递结果不按队列期限终止。期限不是模型总运行时长上限。

领取但未执行的进程死亡沿原身份恢复；已开始后死亡继续使用原 unknown/恢复合同，不能用“只是定时任务”作为重放副作用的依据。

## 模型来源

`inherit` 的选择权威是原会话。实际执行线程与选模来源线程分别记入原模型调用账；下一次安全请求边界复用 M1 刷新，不新建一套切换循环。

`fixed` 在每片开始解析指定档案，原会话后来的选择不改变它。固定的是档案引用，档案本身后续被修改时按最新有效定义解析；并非把所有采样参数永久封存。创建和修改计划时校验引用，执行时再次校验撤销、删除和权限变化。

档案不存在不自动切回默认或第三个模型。已开始的响应与工具仍按原请求依赖收尾；新请求采用时配置、backend、prompt、工具视图、上下文容量、历史与用量来源一起变化。

M2 中 `bound` 只证明宿主当前依赖，`last_request` 来自实际模型调用账。供应方未报告缓存数据时显示未知，不能把选模等同于服务端收到或缓存失效。

## 结构化预检和检查点

预检配置只包含 `tool_name`、`arguments`、可选 `json_pointer`。省略指针时比较完整工具输出；含时间、延迟等易变字段的结果应显式选择稳定字段。提供指针时输出必须可解析为 JSON。

`create/update` 可直接填写这个对象，例如 `{"tool_name":"read_file","arguments":{"path":"source.txt"}}`。`prompt` 描述检查有变化后的工作。模型如果只在 prompt 中写“先检查”，而没有保存 precheck，运行时仍按关闭预检执行，不从自然语言补造配置。

预检使用同一 ToolRegistry snapshot、ToolExecutor、原 task/run、workspace 和 authority。`agent_core/tool_only_execution.py` 装配原工具循环参数，经 `execute_traced_tool_call` 与 `_record_tool_call` 写入原归档和 `tool_completed` 事件，actor 为 `host`，不伪造模型 tool_use。原归档后的只读观察回调交付完整正文，比较不使用模型预览、脱敏展示或截断部分；归档失败按失败处理。该工作片不构造 fake LLM；中断令牌传入执行器，因此取消后不会继续只读重试。

| 观察结果 | 后续行为 | 检查点 |
| --- | --- | --- |
| `changed` | 执行原模型工作 | 原 run 成功并完成交付后提交 |
| `no_change` | 本周期静默 skipped，不调用模型 | 保持原已确认点 |
| `failed` | failed，保存原因码，不调用模型 | 不推进 |

无变化仅说明所选观察值与上一次已确认观察一致，不能证明全部外部状态无变化。摘要包含预检配置；修改配置会触发新比较，不能继承不同检查的结论。

观察写入原 run 一次，恢复复用；job checkpoint 在同一 done 终态事务推进。动作失败、unknown、投递待重试或期间 job 的预检配置已修改，都不覆盖 job 的已确认点。第一次没有 checkpoint 时视为 changed。

预检原参数和工具完整回执仍归原工具账；schedule 元数据仅投影 enabled、状态、调用 ID、时间和错误码，不返回参数或正文。

## 错过周期与失败策略

`skip` 保留原宽限期语义；`coalesce` 把多个错过周期合成一个原 run，并记录 scheduled_for 与 lateness，下一自然周期仍按原时区计算。不产生每个错过周期各跑一次的积压。

同 job 不重叠规则保留。连续失败策略只控制后续周期，不自动重跑 failed/unknown 的旧 run。成功重置连续失败和退避；跳过不算业务成功；成功也不会悄悄解除手动暂停。

手动运行仍是显式的新 run；不复用失败 run 的副作用身份。暂停、恢复和夏令时计算沿原 schedule/repository 合同，须用可控时钟测试，不能从普通触发外推。

## 验证边界

定向测试入口：`test_scheduler_execution.py`、`test_scheduler_precheck.py`、`test_scheduler_policy.py`，与原 scheduler runtime/service/unknown/frozen delivery 组合测试一起运行。异常注入覆盖开始写入失败、旧 claim、停止、预检配置变更和服务恢复。

## 预检工作目录与失败原因

预检与后续模型工作共享原后台请求的 thread cwd、runtime workspace roots、Skill 与 task 属性装配。宿主工具入口不得自行拼接一套 cwd 合同；既有 owner 目录权限继续生效。原 ToolResult 失败码保存在观察的 `tool_error_code`，配合 call_id 可定位共享工具账，不在状态查询中复制参数或输出正文。

## 子代理完成后的续接来源

scheduler run 的 ID 是持久任务来源，不是聊天请求 ID。生命周期续接先核实原 repository 中同 run/thread 的记录，复用后台 durable_task 投影；目标仍来自原 run/TaskLink，普通额外用户请求仍需在 canonical 历史中存在。不会为续接补造聊天消息，也不重新预检或新建定时 run。

预检字段说明：json_pointer 允许 null，与省略同义，比较完整工具输出；空字符串仍是 RFC 6901 的 JSON 根指针，要求工具输出本身是 JSON。schema 与原规范化函数保持一致，不把错误指针默默改为全量比较。

### 展示建议

`/status` 保持简短；以下是拟议显示样式，不是当前版本输出：

```text
定时计划（本人）：共 6 个｜启用 3｜暂停 2｜一次性已结束 1
当前执行：运行 1｜排队/待开始 1｜等待后续 1
查看每项计划和最近执行：/schedule
```

- 计划数和执行数是两个维度，不能相加。没有到点的启用计划正常显示待下次触发，不能叫停止；一次性已结束按终态继续注明成功/失败/跳过/未知。
- 当前源码在一次性计划结束后写 `status=paused, paused_reason=one_shot_finished`；错过一次性触发为 `misfire_grace_expired`。显示投影按这些结构化原因区分“已结束”与“暂停”，不改原状态协议，不凭任务名称或回复正文猜。
- 暂停现有计划会取消未开始的 queued/claimed，但保留 running/waiting；显示“计划已暂停，本轮仍在运行/等待”。一次失败也不必然暂停后续计划，须看原失败策略及当前 job 状态。
- `running` 按原执行状态展示，不宣称整个时段都在消耗模型；`waiting` 只在有明确子任务/审批/交付事实时细化原因，否则显示等待后续。无法读取显示未知或部分可读，不能用不可用快照中的 0 冒充没有任务。

建议同一个只读命令提供以下用法，正式实现前均不可当成已支持命令：

| 命令 | 用户得到什么 |
| --- | --- |
| `/schedule` | 平铺整体任务，每项一行：监控名、ID、短描述、running/stop、last；默认 10 项，超出再给翻页入口，不加平台层级 |
| `/schedule <任务ID>` | 首行监控名、ID、run 次数、整体 status；每项规则一行短语和 LLM/NO，时间可写进短语，仅有在途或异常时追加必要短提示 |
| `/schedule history <任务ID>` | 默认最近 3 条已结束执行记录，每行时间、规则、结果；耗时和投递异常择需简短展示，不自动贴结果正文 |

列表提供可复制的准确查询命令；列表序号和任务名称不作为任务身份。同名任务通过原 job ID 区分，分页 cursor 只定位已授权记录，不授予访问权。用户最新追加要求管理员可在 IM 管理从 TUI/IM 创建的本人监控，因此范围已从只读展示扩为 [跨入口查看与控制](#owner-schedule-recovery-control-review)；暂停、恢复、删除、立即执行仍复用原管理动作，不改变 `/endtask` 的专门用途。


显示口径：

- 整体 `running` 表示任务已启用、持续接受到期调度，包括等待下次触发；`stop` 表示整体停止后续调度，不声称在途已全部结束。实际有在途时详情补一行“当前：rule2 执行中”；局部暂停在对应规则后追加 stop。正常记录保持短格式；读取不可用显示 unknown，不错误归类为 stop。
- `run` 是该监控内部各规则已经实际开始的执行次数总和，按原 run ID 去重；包括成功、失败及尚在途者，未开始的排队/取消/跳过不计，同一次执行的续接或投递重试不重复计。`last` 取原 started_at 的最近值，不用结束或投递时间冒充开始；从未开始显示 `—`，旧记录不足则显示未知。
- 历史仍读原终态账本，默认最近 3 条收口记录，行内时间显示实际开始；未开始就跳过的行显示“计划时间 … 未开始/跳过”。三条记录按每次执行列，不把三个时间放在一行导致规则/状态对应不清；在途状态放详情，首次无记录明确提示暂无执行记录。
- `LLM`/`NO` 来自逐规则的实际执行配置；短语包含必要周期/条件，不把内部工具参数和长需求正文塞进一行。规则的最近结果事实仍保留在原查询投影，正常不全部铺开，异常短提示按各规则独立判断，不被其它规则的成功覆盖。
- 成功时通常只给状态和短耗时，失败时给短原因；执行成功但发送失败必须区分，不能把它显示为已送达。不增加每项固定的建议、解释段落或业务正文。

本轮只修改展示评估，没有实现命令、新计数或状态映射；固定显示文本只用于这些显式控制查询。

用户关注的“最近一次”由查询层保留以下事实；默认按上面的紧凑格式展示，不把全部字段常驻输出：

1. **最新这一轮**：run ID、触发方式、计划触发时间、排队/执行/等待/终态；存在在途 run 时优先展示，不把历史上一轮的 done 冒充这一轮完成。
2. **最近已结束一轮**：实际开始、结束、耗时、成功/失败/取消/跳过/未知及明确原因码。尚未实际开始就跳过时写“未开始”，不用创建时间补造开始时间。
3. **结果投递**：单独显示已送达、待投递/重试、失败、不适用或未知，按原回执取值；例如“执行成功，飞书发送失败”。`done` 只证明执行链结束，不证明业务目标全部达到。
4. **结果查看**：有授权时展示已经保存的最终结果短摘要或产物入口，不为查询重新调用 LLM；群内默认显示运行元数据和固定原因说明，详细结果沿原授权私聊/产物入口查询。旧记录没有对应结果或回执就明确缺失。

时间同时显示计划时区和明确时间，耗时为实际 started_at 到 ended_at 的墙钟时长；在途显示已持续多久，不混为 CPU/LLM 活跃时长。历史按原记录的时间/ID 排序，当前执行与最近终态两块分别标注；暂未跑过、最近跳过和上次成功不能混用。

### 查询范围与原权限接线

- 普通私聊查可信身份所对应 owner 中本人可见计划；群里默认查“本群由你创建”的计划，概览和详情使用同一范围。群 owner、原布置者和聊天范围不同，不直接把整个群 owner 的计数发给任意成员，也不把私聊任务列到群里。
- 原 IM 后台执行线程 `host_execution_origin.v1` 已冻结 source_thread_id 和 channel/conversation_id/actor_id；从原 job/执行线程读取受理事实，不能取后来活跃的群发送者充当创建者。owner、actor、源会话和目标群须共同核验；旧计划缺少可证明的来源时明确范围不可判定，不猜归属。
- 管理员 TUI 与已绑定的管理员 IM 私聊默认查询同一可信用户的监控总表，包含该 owner 下由任一会话创建的计划，不再按当前 thread 过滤；`/status`、列表、详情、历史和管理动作范围一致。本人总表不等于所有用户总表，具体身份映射、群来源与接管见 [跨入口管理](#owner-schedule-recovery-control-review)。

## 一个整体任务包含多项定时规则（2026-10-12，评估完成，待实施）

### 用户视角与当前差距

用户举例：“监控 A 日志平台，每 30 分钟分析，每天 9 点和 18 点汇报，每 5 分钟探测存活。”这是一个持续监控目的，内部有三种工作节奏；创建回执、任务列表和整体控制都应围绕同一个任务。以下只是评估例子，本轮没有创建实际监控。

```text
日志监控〔一个任务〕
  存活探测：每 5 分钟
  日志分析：每 30 分钟
  定时汇报：每天 09:00、18:00
容量监控〔另一个任务，可有自己的多项规则〕
其它独立监控〔另一个任务〕
```

A 平台有 3 个独立监控、B 平台有 3 个独立监控时，用户看到平铺的 **6 个整体任务**，不显示平台分层。如果每个都有 3 项规则，内部共有 18 项规则，但不显示成 18 个互不相干的监控。平台可出现在用户取的监控名称中，不新增必备平台/分组模型；同平台不同目的不自动合并，同名或同一条消息中创建的任务也不必属于同一整体。

当前源码事实：

- `SchedulerJobCreateRequest` 及 `scheduler_job.v1` 为一条 job 保存一个 `schedule`、`prompt`、执行 thread 和策略，没有 `rules` 或整体/规则身份。正常表达三种不同动作与周期通常需要三次 create；这不证明某个现场模型一定会拆成恰好三条。
- 09:00 和 18:00 同一种汇报动作可以使用一条 `0 9,18 * * *` cron，无须拆成早晚两项。已用原 cron 解析器验证两小时值，未调用调度执行。
- `source_task_id` 是创建来源，不等于长期组合任务身份；不同计划即使来自同一次聊天，也不能据此自动认定一起暂停、共享数据或归并计数。
- `_job_has_active_run` 目前按整个 job 防重复/重叠；新模型若直接把三项规则塞入同一个现有执行车道，耗时分析会挡住存活探测。只有列表缩进还不够，需补准确的规则执行身份。
- `precheck.py` 当前比较观察摘要是否变化，提供 changed/no_change/failed；还不等于连续失败阈值、跨规则数据依赖或任意条件工作流。现有 Goal 按 agent thread 管理持续目标，不能用一个常驻聊天 Goal 管多个监控、占住用户聊天。

### 已确认的产品边界：对话制定、一个监控包含 1～N 项规则

用户确认：通过与 my-agent 对话制定或调整监控，用户管理一个整体监控任务，内部包含 1～N 项执行规则，每项可明确是否使用 LLM。本节将此前建议收敛为待实施的产品边界：

- **对话负责制定，记录负责执行。** 用户可说“给 A 监控增加一项检查”“把这个监控的汇报改到十点”；模型解析后用准确的监控/规则 ID 创建或修改，返回实际登记结果。归属必须持久保存，重启和压缩后不依赖模型记忆，不要求用户手写配置、JSON 或 cron。
- **一个监控至少有一项规则。** 每项规则归属一个明确的监控任务；需要复用其它规则的结果时保存显式结果引用，不把同一执行项同时挂给多个监控、造成暂停和权限语义不明。N 仍受原用户资源额度及明确配置约束。
- **规则包含时间、动作、条件和执行方式。** 是否使用 LLM 是逐规则设置，建议以单一 `execution.kind=agent|tool` 作为事实，界面据此显示“使用 LLM/不使用 LLM”，不再维护互相矛盾的布尔开关。该字段是待实施设计，不是当前工具已接受的参数；原 `execution.mode` 继续只表示执行上下文方式。
- **不使用 LLM 指该规则到点执行时不请求模型。** 对话制定方案仍由 my-agent 完成；工具型规则沿原受控工具入口执行，不悄悄改成模型任务。若结果需要模型解释、汇总或撰写通知，安排明确使用 LLM 的规则，并保存结果依赖；模型型规则继续沿原模型选择与配额。
- **保留原时间能力。** 固定间隔 every 仍为 60 秒～1 年，当前代码上限为 366 天；每天 9/18 点这类用原 cron，一次性用原 at。该范围是触发间隔，不是监控存续期限，也不是一次执行允许持续一年的承诺；未指定结束条件的周期监控不会因此满一年自动停止。
- **显示一项监控任务，展开看规则。** 只含一项规则时同样按监控任务保存；多规则不抬高任务计数。每项规则保存时间、是否使用 LLM、条件、最近运行与结果，默认只显示规则短语和 LLM/NO，异常再补短提示；允许整体控制或只调整某项规则。

本轮只确认产品语义并同步评估，没有实施新 schema、工具执行模式或查询命令。

### 推荐结构：原调度任务内包含规则

推荐扩展现有 SchedulerRepository 的 job，而非再建“监控专用调度器”或另一张任务总表：

| 层次 | 职责与身份 |
| --- | --- |
| 整体定时任务（原 job） | 稳定 job ID、名称/短描述、owner、原布置者和投递绑定、整体启停及版本；用户日常管理这一层 |
| 任务内规则 | 稳定 rule ID、时间规则、动作定义、局部启停、条件、明确输入/结果引用及版本；按需展开 |
| 每次执行（原 run） | 原 run ID，增加准确 job/rule/规则版本及触发时点；保留原 claim、TaskLink、工具/模型账、终态与投递回执 |

整体字段只在 job 保存，run 保存本次所需冻结版本；索引只用于查找，不能反过来决定归属。整体创建须一次验证和提交，失败返回明确的未创建事实，避免“监控创建成功”实际只落了探测或汇报一部分。普通用户继续用自然语言布置，模型通过结构化参数创建；回复按真实创建结果说明包含哪几项规则、时区和通知方式。

保留一个 `schedule` 工具及既有调度链，扩展其参数/操作以表达规则。它是通用的“一个持续定时任务包含多个动作和周期”，同样可用于数据同步、对账、备份和资料汇总；产品代码不写 A/B 平台、日志或“监控”关键词分支。

### 各规则之间怎样配合

1. **独立到点，准确归属。** 每项规则按自身时间触发；默认同一规则不重叠，重叠/补跑沿明确策略。不同规则可按既有 owner 额度准入，慢分析不能因为共用聊天互斥而挡住探测。执行会话复用原独立后台机制，按规则或显式 isolated 模式隔离，实际进程和 LLM 并发仍受原限制。
2. **共享结果，不共享一锅聊天历史。** 分析产物和观察沿原工具账/产物引用保存，携带任务、规则、run、数据时间范围和 observed_at。汇报明确引用属于本任务的分析结果，不能依赖另一个线程“记得看过”，也不从任意同名文件猜最新结果。
3. **汇报的数据截止明确。** 默认汇总截至汇报时点已经完成且在有效期内的分析，注明截止时间与缺口；09:00/18:00 同时到点的分析尚未完成时，不把半成品当结果。若用户要求包含该轮，保存显式依赖与有界等待策略；到期仍未完成则报告缺口或按已确认规则延后，不能无限等。缺失或过期不当作正常，也不擅自再跑一遍完整分析。
4. **简单探测可不调用 LLM。** 建议增加通用的受控工具执行动作，复用现有 `execute_read_only_tool`、工具权限、状态账与调度身份；5 分钟只做客观存活检查，30 分钟分析/定点总结按需求使用 LLM。当前 precheck 还不能完整代替工具型计划，此项明确列为待实现，不把脚本旁路当作已支持。
5. **条件成为持久事实。** 如“连续三次失败才通知”“仅工作时间分析”“异常时追加检查”，由模型将要求转为明确条件、观察引用、窗口/阈值与动作；状态保存在同一原调度记录/检查点中，重启可恢复。语义分析可用 LLM，执行分支消费结构化决策，不搜索回复中的“异常/完成”等词，也不执行任意条件表达式字符串。
6. **告警有连续事件身份。** 同一故障的重复观察按显式通知策略去重/冷却；恢复通知沿同一事件。鉴权失败、探测工具失败、观察过期和被监控对象异常分开记录；通知失败重试原冻结内容，不重新触发整套分析。条件未满足标明跳过及原因，不当作任务失败。

不同规则的更新不能互相污染：用户修改汇报时间不重置存活检查的连续观察，不改变分析周期或收件人；在途 run 沿原冻结版本收口，后续执行使用新规则。涉及共享输入更新时以版本和明确引用判断，而非按任务名称关联。先支持上述有限依赖与条件，不为此引入完整通用 DAG/工作流框架。

### 展示和操作要保持整体感

- `/status` 主计数是整体任务数；另列正在执行/排队的运行数。启用任务可带“部分规则暂停/异常”提示，不把规则数、子代理数和任务数混在一起。
- `/schedule` 默认平铺、一行一个整体任务；详情每项规则一行短语和 LLM/NO，异常按规则另给短提示。各规则最近结果仍独立保留，最近一次 5 分钟探测不能盖住上次分析失败或上次汇报未送达。具体格式以 [紧凑展示](#schedule-compact-display) 为准。
- `/schedule history <任务ID>` 按原 run 展示并标记规则，可筛探测/分析/汇报的准确 rule ID；整体摘要不是只挑时间最近的一条 run。监控对象是否健康与调度是否启用是不同事实，不能用“已启用”显示为“A 平台正常”。
- 整体暂停阻止该任务所有规则的新触发，保留局部开关；整体恢复只恢复原本启用的规则。仅暂停“汇报”时探测/分析继续，详情清楚显示部分暂停。
- 暂停未来触发与停止当前执行是两种动作；停止整体要沿原准确任务/run 控制覆盖其在途执行，明确列出停止未确认者，不能影响其它任务或只关页面。只改某规则时不顺带中断其它规则。
- 普通用户能管理自己有权管理的整体和规则，主/子身份、群 actor、来源绑定与个人锁沿前节边界；改名称不会改变 owner 或授权。消息回执也要标明所属监控，避免多平台通知无法分辨来源。

### 资源、迁移与落点

整体任务不要求一个常驻 LLM/主代理。真正执行按原后台会话、模型、工具与子代理额度计量；6 个整体下的 18 项规则不能借整体归属绕过 owner 额度。若需要增加规则数量上限，统一进原能力配置与配额合同，不能只数顶层 job 导致无限内嵌规则。

旧版每条 job 显式迁移为一个整体任务中的单项规则，保留原 job/run/来源和历史，不根据名称、平台或创建时间偷偷合并。若以后要把旧三条合为一个监控，必须有准确 ID 的显式迁移与在途处理方案。迁移完成后只保留一套规范字段，不长期并存 `schedule` 和 `rules` 两套权威定义。

## 用户级监控、Gateway 重启与 IM 接管（2026-10-12，需求确认，待实施）

### 用户要求与统一语义

监控属于可信用户，TUI 和 IM 是创建、查看与控制入口。管理员从任一入口布置的持久监控都应在 Gateway 重启后恢复调度，不要求停机期间仍然执行，也不要求重新打开原 TUI、恢复原聊天或再发一条消息才能启动。普通用户的持久计划复用同一恢复合同，管理权限仍按其身份判断。

`/schedule`、`/schedule <job_id>`、`/schedule history <job_id>` 与 `/status` 的监控统计以本人全部获准监控为范围；TUI/私聊会话的来源只作查询条件，不能成为管理员只能看到当前聊天任务的限制。前节已确认的紧凑格式不变，无须把内部 owner、thread、claim 等字段加到正常输出。

本节替代此前“管理员默认仍查当前会话范围、首批只读”的设计建议。已发布版本的 TUI/IM 执行线程选择仍是当前事实；本次没有把设计当作产品改动，也没有修改已有计划或进程。

### 当前可复用的实现与缺口

| 已核对代码 | 当前事实与实施含义 |
| --- | --- |
| `scheduler/repository.py`、`service.py` | job/run 持久保存于 owner 账本；原服务以 run ID 去重 wake，支持重新构建服务后继续派发。`list_jobs` 原本按 owner 读取，并未要求当前聊天。新查询应复用这个范围 |
| `cli/gateway_loops.py::_GatewaySchedulerDueController`、`scheduler/due_index.py` | Gateway 有独立的到期 owner 索引和后台调度入口；local/main 由基础调度器负责，其它到期 owner 由索引唤起。索引只是发现投影，原 owner 账本仍作准 |
| `scheduler/execution_policy.py`、`conversation/execution_threads.py` | 新 IM 计划已有独立执行线程和冻结来源；TUI/旧计划沿原线程。线程选择、模型继承和原来源可复用，但跨入口查看/恢复不能依赖 TUI 客户端存活 |
| `gateway_parts/request_worker.py::_resolve_request_owner_identity`、`admin_channel_identity_for_request` | 功能启用且私聊渠道/用户精确绑定时，管理员 IM 与本地基础 TUI 同为 local/main；群消息仍是群 owner，不能凭管理员昵称或群里一句话变成本机管理入口 |
| `gateway_parts/execution_control.py`、`turn_recovery_control.py` | 一般活动控制仍先从当前认证会话解析目标；`/recover` 主要处理当前 thread，owner 子入口只处置特定无 thread 的历史 unknown。不能把这些直接宣称为任意本人监控跨会话接管 |
| `gateway_parts/end_task_control.py` | 已有管理员按准确 task ID 处理本 owner 停滞的定时任务，可作为同 owner 控制的接线参考；它不是常规“继续执行”入口 |

运行恢复已有重要边界：claim 到期并且原 runner 确认死亡后，未实际开始的 claimed 可退回 queued；已 running 的轮次会记 unknown，不能自动重做可能已经生效的动作。单纯租约超时、TUI 无刷新、IM 收不到文字都不足以证明 runner 已死。上述行为已有测试，但不等于新“IM 接过来”入口已支持。

### 重启后的具体行为

1. **计划与状态保留。** 原 job/rule ID、名称、启停、周期/时区、模型和工具配置引用、连续观察状态、最近结果、历史与通知绑定保持。原来暂停的继续暂停；重启不重新创建计划、不重置次数、不复制凭据。
2. **后续调度自动恢复。** Gateway 启动后从持久事实重建到期发现、待执行队列和后续工作，覆盖暂时未驻留的 owner；不等待用户重新聊天。故障造成的未就绪/待恢复要可查询，不能以空列表冒充没有计划。
3. **停机错过的时点沿既定策略。** 宽限期及 `policy.misfire=skip|coalesce` 保持唯一依据：超期默认跳过，明确 coalesce 时至多补一次；不把停机两小时漏掉的所有五分钟探测瞬间补发。原有一次性计划也按该合同处理，并在历史中说明原因。
4. **在途执行先核对。** 若后台执行者仍活着就接回观察，不另起一份；未开跑且旧 claim 已可释放时重新领取。已开始后异常中断的按原运行账、工具 operation 和检查点对账；可证明可续作的恢复原任务，效果未知的明确指出待核对动作，不自动从头执行。
5. **交付单独恢复。** 已有完整冻结结果但尚未送达时，只恢复原投递与去重；不得为补发消息再运行分析、命令或外部写操作。新触发、执行恢复和投递恢复各用原身份，不把一次未知/重试算成多次正常执行。
6. **TUI 上下文不绑定 TUI 生命周期。** TUI 创建可保留用户选择的模型、来源上下文和权限，退出客户端不取消计划；多规则执行复用前节的后台归属。旧执行线程需要调整时做显式版本迁移，保留原来源和历史，在途 run 不静默换线程。

以上要求针对已经通过原 schedule 服务登记的持久计划；任意前台 shell 循环不会因提示词含“监控”就变成调度任务。创建与变更仍用结构化登记结果确认。

### IM 接管：控制原任务，按需改变结果送达位置

用户可以在已绑定的管理员私聊说“看看 job01 为什么没动”“暂停 job01”“把 job01 接到这里继续，之后结果发给我”。模型把意思转成准确 job/rule/run 的原控制动作；查询、暂停/恢复等显式命令走同一服务。无需先向 TUI 的模型转发一句话，等待那个已卡住的回合批准。

| 现场情况 | 应有行为 |
| --- | --- |
| TUI 卡住/SSH 断开，原任务正常 | IM 读取原任务状态并可继续管理；原执行、子代理和工作目录不动，不重复起任务 |
| 用户只要求在 IM 接着查看、下指令 | 关联当前 IM 控制入口与准确任务目标，原创建来源和执行归属保留；通知地址不因打开详情自动改变 |
| 用户明确要求“以后结果发到这里” | 验证当前私聊绑定后版本化更新未来通知目标；改变的是结果路由，不是任务 owner 或运行身份 |
| 原 runner 已死或执行明确停滞 | 读取原 attempt/工具效果/检查点，走原停止与恢复协议；需要替换执行者时先确认旧执行停止并取得新 claim，防止两边同时做 |
| 用户要求处理待审批或待恢复动作 | IM 展示准确目标和状态，用原权限/审批/恢复入口提交；TUI 的临时批准不扩大为所有未来工具权限 |
| Gateway 整体不可用 | 任务记录保留，服务恢复后继续；IM 业务控制依赖可用的服务，不能承诺通过同一个已停的 Gateway 自己启动自己 |

通知切换要明确生效点：默认作用于后续 run；已经冻结的本轮通知和失败重试继续原路由。若用户同时要求接收本轮结果，按准确 run/交付记录建立可审计的投递变更，旧新路线共用去重与回执，不悄悄丢掉在途回复，也不给两个地方无意重复发送。

“接管”不是复制聊天、新建同名监控或任意重绑外部会话；它由原控制请求记录指向准确目标，实际执行仍走原 claim/TaskLink。IM 与 TUI 同时操作时按 job/rule 版本和 run/attempt 代次核对，迟到的停止、恢复、批准不能打到后来新开始的一轮。普通对话说明由模型依据回执生成，斜杠控制结果可固定渲染。

跨入口控制应落成通用的本人 thread/task/run 能力，也适用于管理员在 TUI 中启动的普通长任务及其子代理；不为“监控”另写一套权限或恢复逻辑。`/schedule` 仍只列定时监控，普通任务沿原会话/任务查询入口定位；接管保留原工作目录、产物和任务状态，可用的上下文由原持久记录恢复，不要求用户复制整段 TUI 聊天。

### 本人总表与权限范围

- **管理员 TUI、管理员私聊：** 经现有绑定解析同一 local/main，默认列出该 owner 从全部会话创建的监控；`/status` 与 `/schedule` 同一快照、同一计数口径。进入另一会话、关闭旧 TUI、Gateway 重启均不缩小为当前 thread。
- **普通私聊：** 按自身可信 owner 聚合本人可见监控，不能靠传入管理员 job ID 或伪造 target_owner 获得访问；不把当前会话过滤误当成权限隔离。
- **群来源：** 群任务继续保存原群 owner、原发起 actor 和原通知授权。若在本人私聊聚合其群来源监控，必须用冻结 actor、已验证渠道身份和当前获准范围查询，仍回到原 owner 执行；不能搬到 local/main 后继承管理员权限。这个聚合需补原来源查询接线，不能用遍历所有 owner 代替身份证明。
- **输出位置：** 管理员个人总表默认在 TUI/绑定私聊显示；群里的查询仍限获准的本群范围，不把本地或其它群的监控名称、结果和凭据发进群。管理员私聊绑定不会自动授权群内其它成员发控制命令。
- **旧身份与访问撤销：** 管理员绑定前在普通 owner 创建的旧计划不自动挪账；需用准确原来源做显式关联/迁移。解除管理员绑定、失效凭据或个人会话锁按原入口规则生效，既有合法后台告警不靠入站解锁状态才能发出。

### 实施落点和验收

实现仍落在原模块：SchedulerRepository/Service 负责计划与恢复；ConversationStore 保持 thread/TaskLink；命令目录和会话控制共用本人查询与管理投影；`request_worker`/`control_scope` 解析可信身份；`execution_control`/原恢复入口支持明确目标；原 DeliveryService 与交付记录负责通知变更。控制请求必须持久保存发起身份、精确目标、预期版本、动作和回执，使用既有控制操作记录，不新建一套任务/接管账本。权限可由控制入口完整核验后授予特定操作，不能让模型参数覆盖调用方身份。

本轮在临时目录运行已有测试，共 **40 项通过**：`test_scheduler_service.py::test_service_reuses_deduped_wake_after_restart`、`test_scheduler_policy.py`、`test_scheduler_unknown_recovery.py`、`test_scheduler_due_index.py`、`test_admin_identity_gateway.py`。验证了已有唤醒去重、错过周期处理、死亡证明/旧 claim 失效、到期 owner 发现和管理员私聊绑定；其中时间、进程死亡与通道输入采用替身，不是新跨入口功能或真实 Gateway 重启的端到端证明。

待实施验收按以下次序进行：

1. **合同/fake/replay：** TUI 与管理员 IM 各建监控后，在任一管理员入口查询得到同一总数/ID/历史；普通用户、两个群 actor、解绑、锁定、旧来源缺失和伪造 ID 都保持正确范围。
2. **重启矩阵：** 正常重启、异常退出分别覆盖到期前、已排队、执行中、等待子代理/审批、结果已生成待发；多次恢复不重复登记、不重复执行、不把未确认动作改成成功。启用/暂停和条件检查点均保留，冷 owner 无需聊天即能被唤起。
3. **跨入口控制：** TUI 断开而后台正常时，IM 查询/暂停/改时间不新建执行；原 runner 停止后按准确记录恢复；两个入口并发控制及迟到确认只能作用于匹配版本。监控与普通 TUI 长任务各验一组，子代理、工作目录与产物保持原归属；只接管与同时改通知位置分别验证，本轮冻结结果和后续结果均有明确去向。
4. **真实 Linux/IM：** 在独立单 Gateway 测试实例中，从真实 TUI 与管理员 IM 布置合成监控，退出 TUI、重启 Gateway、不先发聊天，再核对下一触发和原 ID；随后从 IM 接管查看/控制并验证实际送达。只观察被测对象自己执行，不手补产物，不读取无关业务正文。

建议下一步：把此需求与整体监控模型、紧凑 `/schedule` 一起实施，先贯通本人范围与耐久状态，再接 IM 管理。恢复/控制/投递的身份衔接由一个负责人贯通；安装更新、只读查询展示和测试场景可独立准备。当前仅完善评估，未修改产品、真实任务或发布包，等待用户实施指令。


## IM 调度诊断与崩溃恢复收口（2026-10-13，已实现，待整合验收）

本节覆盖此前评估中的只读可用性、死亡恢复、坏运行健康和旧群创建人边界，主链继续使用原 owner 的 `store.json`、`history.jsonl`、ThreadStore 与 due index。

### 查询与写入

- `list/get/status/queued/waiting/active/corruption` 读取 `store_snapshot.py` 的完整只读快照，不创建锁文件、不申请写方配额，不因另一个线程持有写锁阻塞。
- 写方保留原 quota→JSON/flock 锁顺序、版本 CAS 与 claim epoch 栅栏，仍通过临时文件原子替换 JSON。锁文件持续存在属于 flock 锁锚点；不能按文件存在或 mtime 删除活跃锁。
- 读方拒绝符号链接、硬链接或非普通叶子。并发替换或违规原地写入导致签名变化时最多重读三次；不回放历史替代当前权威，不无限等待。读取权限/文件系统故障保留 errno，坏内容提供行列，schema 与 owner 不匹配分开报告。
- 稳定错误码为 `SCHEDULER_STORE_BUSY`、`SCHEDULER_STORE_UNREADABLE`、`SCHEDULER_STORE_INVALID_CONTENT`、`SCHEDULER_STORE_SCHEMA_MISMATCH`、`SCHEDULER_STORE_OWNER_MISMATCH`。命令文案和结构化日志复用这些事实；无需用户刷新客户端。
- 健康汇总包含 job 与 run 的解析错误。坏 run 可以被隔离，但不能被悄悄丢弃后显示 healthy。

### 启动、周期与终态

`SchedulerService` 初始化与后续调度 tick 均复用同一恢复函数；无候选时只读，不写锁或刷账。已过期且 PID/启动指纹证实死亡时：未开工的 claimed 清为 queued，保留原 run 身份和 epoch 后重新领取；已开工的 running 结算 unknown，进入原历史并移出活动账，不自动重做动作。

正常结束、waiting 收尾、领取时发现死亡和周期恢复共用 `_record_terminal_unlocked` 更新原 job 与活动 run，历史由原写入事务入口提交。history 已提交而 store 替换失败时，仅采纳同 owner/run/job/thread/epoch 的准确终态，不能把真实 done 覆盖成 unknown。旧版误留活动账的合法 unknown 只迁移到原历史，不重做任务。

租约到期不是死亡证明。活 PID/相同指纹、缺失身份、指纹不可读或不可比较均保留；删除/暂停 job 也不强行终止活跃 running/waiting。调度恢复不调用 `runtime-stale-attempts --settle`，后者属于 RuntimeDB 的另一张 attempt 账本。

### 旧群监控创建人

`creator_migration.py` 仅在原 group owner 冷启动，从计划线程的 `host_execution_origin.v1` 与准确 source/thread/owner/operation 引用恢复冻结 actor，不使用群的最新发言人，也不回落管理员。迁移写原 job 的显式版本记录，规则和在途 run 来源不变。

缺少不可变来源证据时记 `creator_migration.status=unmanaged` 与原因码，不赋予当前查询者控制权。管理员诊断只投影未归属数量/准确 job ID，不展示其它成员监控名称或正文。冷查询本身仍只读，不偷偷迁移；已有准确 creator 的监控维持原过滤和普通用户隔离。

### 验证边界

`test_scheduler_repair.py` 先复现旧只读锁故障、unknown 遗留、健康假正常与创建人缺口，再覆盖只读锁拒绝、写锁持有时十次查询、错误类别/errno、有界竞争、启动和 tick 恢复、已删除 job、history 提交后替换失败、旧 unknown 迁移、冻结 actor/跨 owner 拒绝。原死亡/PID 重用/CAS、扫描缓存、quota、服务与命令测试一起回归。

测试使用临时账本和进程状态替身，不是用户生产数据的证明。真实 Linux Gateway kill/restart、IM 命令及安装包验证由集成线执行；活跃运行、投递身份与未确认副作用边界必须一同复核。


## 群监控发起人统一与旧任务恢复（2026-10-13，已实现，待发布）

解决“创建成功后本人 list 为零、准确编号也被拒绝”的身份口径差异。前台 Gateway 将认证 scope 冻结成 RunParams 的专有 HostChannelActor；schedule 创建和管理共用 conversation/host_actor.py，模型 attributes 的同名键以及旧 channel/user 别名不提供权限。

主根身份只经 TaskStore.bind 的 typed keyword 保存到原 ThreadTaskLink，子孙身份保存到原 SubAgentTask 专有字段；已有主根不允许换人或改写原 entry_request_id。同一个人从新的认证消息继续准确原任务时，新入口编号可以变化，但孩子继承原根出处。full_access 不扩大身份或跨群成员控制权。

后台恢复先核对准确 task/root、owner 和线程，再读取该根专有身份或该根自己的不可变 execution_origin；不能拿模型属性指向另一成员的工作线程来借用身份。旧无证明的非身份类后台工作可以继续，敏感监控/审批/子代理身份派生明确拒绝，不自动认领成最新发言人。

首次 IM 委派唤醒还没有 ThreadTaskLink 时，只读取准确 SessionTask，并要求目标是原 delegated 工作线程、原策略 session_task_id 相同、发送线程等于不可变来源、owner 一致。后台装配使用 request.task_id 或原 session_task 引用，不把 claim 的空 task_id 偷换成消息身份。普通会话派活没有这套证明时 actor 为 None，仍能继续非身份工作。

定时 run 已复制 creator，execution_context 首次冻结 origin_bindings；关掉 IM 默认后台执行开关也使用原 creator，不把后来群成员当布置者。新 isolated IM 线程复用 host_execution_origin.v1，并在原 TaskLink 首次绑定时保存同源专有 actor。followup/isolated、开关开/关四组都经过实际领取、后台参数、监控工具、审批收件人和孩子创建验证，身份仍是 A；新成员 B 不能复用 A 的准确根。

升级时，已存在的旧 isolated queued 线程若尚无 execution_origin，在原 TaskLink transition 锁内继续持原 repository mutation scope（quota→store），从同一锁内账本重读准确 run，仍为 queued、started_at 为零且 owner/thread/creator/context 没变，才在原 ThreadStore 锁内复核旧三字段身份、owner/home 和无绑定后追加来源。写来源之前不能插入 claim/start，调度账本本身不重写。来源仍取该 run 的准确冻结事实，cwd、模型及其它元数据保持不变。已领取、已开工、身份不匹配或无冻结证明均不迁移，不能用最新群成员补旧身份。

本机无外部绑定的普通请求在 TaskLink 晋升前仍可用 actor=None 创建和管理本 owner 监控；这不是一个 IM 身份。群和外部来源缺证明仍明确拒绝，不能把本机合法未晋升任务误报成身份坏账，也不能为测试或运行凭空造一个 IM actor。

错误区分：SCHEDULER_NOT_FOUND 表示本 owner 没有该编号，SCHEDULER_NOT_AUTHORIZED 表示记录存在但属于另一发起人；CHANNEL_ACTOR_IDENTITY_REQUIRED/INVALID/CONFLICT/SCOPE_MISMATCH 分别表示缺证明、坏记录、身份冲突和归属不匹配。固定文案不包含原任务正文、路径或凭据。

验收沿真实 Repository/ConversationStore/TaskLink/子代理原序列化执行，覆盖主群前台、普通用户和管理员私聊、后台工作、孩子与孙级、旧伪造属性、同群不同人、两种审批冲突以及本人新入口续原根。生产飞书卡片运输仍由原签名、claim/attempt 和密码锁合同守门；本测试没有对真实用户外发。
