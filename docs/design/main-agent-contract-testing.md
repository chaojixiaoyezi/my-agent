# 主代理测试分层

本规范只约束开发验证，不增加生产任务完成的机器验收门槛。状态、权限、身份和路径归属以结构化事实为准。

## contract

定向单测覆盖配置、状态机、工具参数、权限、身份和账本。先定位所属模块，不针对用户提示词增加生产分支。

## fake-tool

确定性工具替身覆盖成功、拒绝、超时、长输出、重复事件和进程消失。检查工具结果与实际执行状态是否一致。

## fake-llm

模型替身覆盖流式分片、工具调用、插话、长度限制、模型切换和压缩边界。模型口头说完成不能修改结构化任务状态。

## replay

脱敏事件回放验证真实故障；保存调用身份、顺序、状态码和预期结果，不提交真实凭据、私人对话或测试机配置。

## real-tui

最终验收通过真实 TUI。用户需求用普通中文表达，由底座承担参数、权限和状态约束。记录供应商、会话范围、工具结果和产物；不能用测试者补写的文件冒充被测代理产物。

短场景验证单个行为；长任务、连续对话和多子代理验证运行稳定性。未覆盖环境必须标明未验证，不从一次成功推断全面通过。

## 执行方式

运行 `python3 scripts/check_contract_test_pyramid.py --repo-root .` 检查分层，再运行相关 focused tests。提交前遵循 `AGENTS.md` 的严格 gate。测试目录、夹具与本说明一起维护。

**不变量**

  - 二进制附件被闸门拦下时，canonical 记 `CREDENTIAL_ATTACHMENT_WITHHELD` / `not_started`，没有发送证明；必要通知仍由调度补发，且只补一次。
  - 普通回合未用凭据，闸门不介入：二进制附件照常经真实 handler 与渠道回执外发，同样只占用一次回复槽；闸门若误作用于普通回合，`[normal]` 用例即失败（Layer-2 M01-fix）。

## 2026-11-19 M02：CI 波动节点的确定性定序夹具与双源留存回归（Conveyor）

本节记录 Conveyor M02 建立的测试不变量与验收证据。基线 `d9caa95af`，父提交 `a4f4a2e82`（M01）。本模块只改四个测试文件与本说明，不改生产代码。

**不变量**

- 25 ms 墙钟片只读测试推进的单调时钟：
  - 四个文件各有一个 autouse 夹具，把 `RetentionScanBudget`、`StorageLaneBudget` 与 Curator 消息扫描所读的 `time.monotonic` 换成测试时钟，写法沿用 `curator_slice_test_support` 与 `retention_slice_clock`。
  - 条目与字节预算、真实目录分页、锁、读取与 unlink 照常执行。片只在测试显式推进时到期，宿主负载不能让片在观察点之前到期。
- 锁忙成员（行 6–8）：
  - 事件依次固定三点：持有者已持同一规范锁，并记下锁文件 inode；lane 本片已尝试该成员，锁入口观察器记下成员名、inode、片剩余时间、已计读取字节与结果；锁已在上下文退出后释放。
  - 断言 inode 相同、片未到期、成员只在扫描时读一次、`skipped == {'lock_busy': 1}`、游标停在忙成员之前；释放后，同一续点删除该成员。
  - 覆盖两种合法成员顺序，以及本进程线程与另一进程两种持锁者。另一进程经生产锁入口只占 OS 锁层。
- Curator busy（行 9）：
  - 按发生顺序记录租约 id 与代次、正式读取中断、候选提交点（`candidate_count`、`per_thread_cursors`）与租约释放。
  - 正式读取真实失败时，仍在同一租约内提交候选，并给出 `formal_memory_read_skipped` 告警。
  - 持有者竞争与扫描片到期分开测。两者都是 busy，都不提交候选、不推进游标，原因各自可追溯：前者领取为空，状态文件逐字节不变；后者给出 `message_scan_partial`。原因消除后，同一输入才成功；busy 从不当作成功。
- 双源留存（行 10，L27）：
  - 测试只在同一原生页内重排两个线程成员，任一顺序都是合法的 readdir 结果。事件证明较短来源本轮 post 已完成、较长来源仍 pending，之后才注入等长改写。
  - 正反两种成员访问顺序各有一个用例。生产数据 pin、读取预算与部分覆盖合同不变。
- 工作流维护续跑（行 12）：
  - 唯一中断点是首个进度写入失败，账本停在原 `operation_id` 的位置 0。
  - `content_edit` 在两拍之间写入，编辑时刻由测试时钟给定。生产用 `time.time()` 记编辑戳，所以这里控制的是墙钟戳；保留扫描片读测试单调时钟。
  - 续跑沿用原 `operation_id`，行 CAS、引用与年龄守卫成立。已编辑对象原样保留：`last_content_edit_at == orphan_since == 编辑时刻`，定义修订号已变。
- 同步只用 `threading.Event` 与子进程握手行，不用 `time.sleep`；每个有界 `Event.wait` 都断言返回值。

**验收证据**

- 父提交上，本地不注入时六个节点都通过；一次单点注入即复现 CI 原文：
  - 行 6–8：引用投影自建的 25 ms 片在 lane 尝试锁之前到期，成员按 `pins_incomplete` 保留，得到 `:412 assert (1 == 0)` 与 `:233 KeyError: 'lock_busy'`。持锁本身没有失败。
  - 行 9：持租约的消息扫描片在读取首个线程前到期，得到合法的 `message_scan_partial` busy，即 `:302 assert 'busy' == 'succeeded'`。成因不是租约与正式读取的竞争。
  - 行 10：Linux 目录次序让 `u.json` 先于 `t.json`。2 MiB 来源先被验证，热期内一轮不能完成，注入点永远到不了，得到 `:1695 assert []`。
  - 行 12：第二拍的保留扫描片到期，`scan_partial` 使维护判为 `retention_not_safe`，得到 `:331 assert (False is True)`。成因不是 `content_edit` 的墙钟戳。
- 本提交上，六个节点在 3.12 与 3.14t（`-X gil=0`）上各连续 200 轮通过（`-p no:randomly`，壳层循环；每轮连同新增用例共 14 个用例）。四个文件在两个解释器上都是 210 passed。
- 慢宿主探针让每次读取单调时钟都比上次晚 30 ms，超过两种 25 ms 片：
  - 父提交上，五个依赖时钟的节点（行 6、7、8、9、12）全部失败。
  - 本提交上，行 6、7、9、10、12 通过；行 8 及其跨进程用例在持锁窗口内的断言全部通过，只在释放后的排空中失败。
  - 原因是 `.records.lock` 的 20 ms 有界等待（`agent/assets/turn_extractor.py:825`）仍读真实时钟，锁空闲时也检查期限。探针让排空的 100 片每片都超时；真实宿主上单次停顿只让该片返回 `lock_busy`，下一片即重试。
- 临时错误次序变体（未提交）都使原断言失败，恢复正确次序后全部通过：
  - 引用投影片先到期：`assert (1 == 0)`、`KeyError: 'lock_busy'`；
  - 持有者在尝试前释放：原循环断言 `path.exists()`、`KeyError: 'lock_busy'`；
  - 消息扫描片在首个线程读取前到期：`assert 'busy' == 'succeeded'`；
  - 较长来源先被访问：两个用例都是 `assert []`；
  - 第二拍保留片到期：`assert (False is True)`。
