# Gateway 安全重启与代理自助重启

状态：第一期已实现（2026-09-26）；终端 `gateway restart`、部署工具与 TUI/IM 客户端缺口按“分期”继续。
实际落地与设计的差异见文末“已落地（第一期）”。

## 背景与目标

2026-09-25 真实会话里，模型在回合中执行 `my-agent gateway restart`，重启的正是承载自己这一轮的 Gateway。
那条命令被自己的重启切断，结果没有落账，重启后的自动续跑按“结果不可知”拒绝，会话卡死，后来用 `/recover` 解开。
随后加了托管自停闸（`cli/gateway_host_guard.py`），一律拒绝代理停止或重启托管自己的 Gateway。

用户要求：代理必须能自己重启 Gateway，重启后不出事，所有 TUI 和 IM 都不出事。

## 现状（已核对代码）

- 停止：`cli/gateway_process.py::_cmd_gateway_run_cleanup` 置停止事件、停 HTTP、对心跳/请求/后台三个循环各 join 2 秒后退出，
  不等在途回合。正在执行的工具子进程、模型调用随进程退出被切断；模型调用按 `MODEL_CALL_INTERRUPTED_HOST_SHUTDOWN` 结清。
- 启动恢复：`gateway_parts/recovery.py` 在启动时把 processing 里的请求按“同一回合”重新排队，不计失败次数；
  `request_execution._recover_gateway_active_turn_authority` 调 `RuntimeRepository.recover_recorded_active_turn_attempt`，
  只有“所有已启动的有副作用工具都已终态且有耐久记录”才放行续跑，否则报 `ACTIVE_TURN_OUTCOME_UNCERTAIN`，run 停在 unknown。
- 结论：重启那一刻没有“执行中”的工具，被打断的回合会自动续跑成功；有执行中的工具，那个会话就会卡住。
  代理自己执行重启命令时，这条命令本身永远处在“执行中”，所以必然卡住。别的会话正在跑长命令时被重启，同样会卡住。
- 工具开跑的唯一关口：`tooling/tool_operation_coordinator.py` 先经 `claim_tool_operation` 把操作写成 CLAIMED→EXECUTING，
  再进入工具实现。只读工具不经过这里，被切断也不影响续跑核对。
- 生产上 Gateway 是脱离终端的独立进程（父进程为 1），没有 launchd/systemd 托管；`gateway start` 以新会话方式拉起。
- 部署工具（仓库外 `switch_gateway.py`）要求 pending/processing 为 0 且没有 running attempt 才肯切换，靠“等空闲”规避上面的问题。

## 对照项目（2026-09-26 核对两家上游 main）

**Hermes（NousResearch/hermes-agent）**
- 入口：聊天 `/restart`、`hermes gateway restart`、systemd reload，都落到同一个 `request_restart`。命令行发现运行中的网关是自己的祖先进程时，
  只给它发 SIGUSR1 请它自己重启，然后立即返回。代理在终端里执行 `hermes gateway stop/restart` 被列为危险命令；从托管网关内部发出的
  停止或 kill 命令另有自我定位保护。
- 流程：立即拒绝新回合，但保持运行，让在跑的回合把最终回复发完；最多等 `restart_after_turn_timeout`（默认 1800 秒，定位是防卡死的安全阀），
  卡死的回合不等。进入停机后先通知所有还在跑任务的聊天，强制排空默认 0 秒（定时任务保底 30 秒），中断剩余回合并标记 `resume_pending`，
  杀工具子进程，以退出码 75 交给 systemd/launchd 拉起；没有托管时起一个脱离的 helper，等旧进程消失后执行重启。
- 恢复：启动后自动给 1 小时内被打断的会话跑一轮续跑回合，续跑期间真实消息先排队（最多 30 秒）；续跑说明写明“历史里的重启命令已经执行，
  不要再执行或验证”；交互式聊天续跑时不重做旧工具调用，而是告诉用户已恢复、问下一步，无人值守渠道才接着做完。
- 防护：`/restart` 重复投递去重；同一会话连续 3 次在重启时处于运行中就自动挂起；重启完成后通知发起的聊天；最终回复记投递账本，重启后补发而不重跑。

**OpenClaw（openclaw/openclaw）**
- 4 月版：代理的 `gateway` 工具有 `restart` 动作（主人专用）。它写一份“重启哨兵”（发起会话、回投地址、完成说明、续跑指令），
  再安排重启：默认延迟 2 秒、30 秒冷却、重复请求合并；到点后轮询“待处理工作”（排队命令、待发回复、进行中的运行、活动任务）归零，
  最多等 5 分钟（`gateway.reload.deferralTimeoutMs`），超时仍重启。网关标记排空、关闭服务并告诉客户端预计 1.5 秒后恢复，
  优先以新进程号重启或交给 launchd/systemd，失败才进程内重启。新进程读哨兵：给会话记系统事件、经投递队列通知用户、以续跑指令发起一轮回合。
- 7 月起（#107237 第三阶段）：从普通代理的工具里移除 `restart` 与改配置动作，理由是这些直接写入绕过了人工批准。系统级操作改为交给
  `openclaw` 系统代理，持久写入进入运维审批队列，只能由人在控制台批准，被委派的代理不能自己批准。代理只保留主人明确要求时的 `update.run`
  （更新后自动重启并发完成通知）。人可用 `/restart`（主人专用，`commands.restart` 开关）或 `openclaw gateway restart --safe`（默认等空闲，
  可 `--skip-deferral`）。重启哨兵已改存 SQLite，最终回复先入队再发送。

**据此调整本设计**
- 排空分两段：先像两家一样等回合自然结束（拒绝新回合、让在跑回合发完回复，设上限）；到上限后再用本设计的工具关口，只等执行中的工具，
  然后换进程并自动续跑。发起重启的那一轮通常能先正常答完用户。
- 续跑事实写明“重启已完成，历史里的重启请求不要再执行或验证”；重启前通知有回合在跑的会话，重启后给发起方一条“已重启”。
- 30 秒冷却、重复请求合并；同一会话连续 3 次在重启时处于运行中就暂停它的自动续跑，等用户发话。
- 权限是两家分歧最大的地方：Hermes 要审批，OpenClaw 已改成必须人批准。本设计保留“管理员专用 + 按审批模式”的默认，是否免确认由用户决定。

## 设计

### 1. 统一的安全重启流程

任何来源的重启都走同一流程：终端 `gateway restart`、部署工具、代理工具。

1. **重启请求**：写一份结构化请求 `gateway_restart.request`（发起方类型、发起回合身份、原因、时间、目标进程号与启动标识）。
   服务循环像识别停止请求一样识别它；重复请求合并，不叠加。
2. **排空**：服务进入 `draining` 状态并写进 `/status`。
   - 第一段先等回合自然结束：不再开始新回合，在跑的回合照常完成并发出回复，上限由配置决定；到上限后进入第二段。
   - 请求循环停止领取新请求；新消息照常写入 pending，不丢，由新进程处理。
   - `tool_operation_coordinator` 在领取前经进程级重启闸：排空期间新的有副作用工具在领取前等待，不写 CLAIMED；
     已经在执行的工具照常跑完、结算、写记录。闸同时统计执行中的工具数。
   - 执行中的工具数归零后，再给在途模型调用一个短宽限，然后收尾。被切断的模型调用在续跑时重新发起，只多花一次调用。
3. **接班**：旧进程收尾时先起一个脱离的接班进程，再退出。接班进程确认旧进程号已经消失，再用同一配置和同一运行版本执行
   `gateway start`。必须是新进程号：原地 `execv` 会保留进程号和启动时间，现有“旧执行者已死”的判定会误以为旧回合还活着。
4. **续跑**：沿用现有启动恢复。排空保证了没有执行中的工具，`recover_recorded_active_turn_attempt` 的核对能通过，
   每个被打断的回合用原请求号在新进程里继续。给每个续跑回合追加一条结构化事实“Gateway 已重启（旧/新进程号、时间、发起方），
   历史里的重启请求已完成，不要再执行或验证”，发起重启的那一轮不会再次重启。重启前通知有回合在跑的会话，重启后给发起方一条“已重启”。
5. **防抖与防循环**：两次重启至少间隔 30 秒，排队中的重复请求合并为一次；同一会话连续 3 次在重启时处于运行中，就暂停它的自动续跑，等用户发话。

### 2. 代理怎么发起

- 新增结构化工具 `restart_gateway`，只给本机管理员 owner 注册；普通用户（例如飞书用户）的代理不能重启共享 Gateway。
  效果按危险动作走审批门，full-access/auto 下按现有审批模式处理。
- 工具只写重启请求并立即返回“已安排”，所以它自己这次调用在排空开始前就已结算落账，不会卡住自己。
  同一回合只允许安排一次，重复调用返回已安排的那份请求。
- 托管自停闸保留：代理在命令行里执行 `gateway stop` 仍然拒绝，因为停了就没有进程把它拉起来；执行 `gateway restart`
  改为拒绝并提示使用 `restart_gateway`，避免命令行这条路绕过管理员身份核对。
- 审批语义（2026-09-26 澄清）：用户在对话里说“重启一下”只是请求，只是模型决定调用工具的上下文，不构成批准；否则任何一句话，
  甚至模型自称“用户已同意”，都能越过边界。批准只来自结构化事实：
  - 默认确认模式：代理调用 `restart_gateway` 时，TUI 弹出现有的工具确认框，用户点允许才算批准；可选“本会话允许”或“以后都允许这类操作”。
  - 自主或完全访问模式：用户事先通过 F4 或 `/permissions` 选定的模式就是批准，按 `action_policy` 现有规则不再弹框。
  - 用户亲自下令：新增管理员专用的 `/restart` 聊天控制命令，命令本身就是结构化授权，不经过模型，TUI 与 IM 共用。
- IM 里当管理员（待用户确认）：现在只有本机 TUI 的 local/main 是管理员，飞书账号一律是普通用户，飞书客户端也不支持确认框，
  需要确认的操作会得到“无法确认”并被拒。要在飞书里以管理员身份重启，需要两块：一是在配置里显式登记管理员的渠道身份
  （例如 `feishu:ou_…`，参照 OpenClaw 的 `commands.ownerAllowFrom`），只按结构化身份匹配，不按昵称或正文猜；二是 IM 的批准方式，
  用飞书交互卡片按钮，或带一次性确认码的回复命令（宿主核对确认码与操作指纹，参照 OpenClaw 的三道门）。

### 3. 超时与失败

- 排空等待上限用新配置项控制，`0` 表示一直等。超时后默认取消这次重启、恢复正常服务，并在 `/status` 与发起方回执里列出
  还在执行的工具，不强杀。终端可显式加 `--force` 强制，强制时被切断的工具仍按现有 unknown 与 `/recover` 规则处理。
- 接班进程启动失败：写结构化失败事实到 Gateway 状态目录，客户端下次探活时显示；不静默吞掉。

### 4. 续跑顺序与重启窗口（TUI 与 IM 共同）

- 启动恢复把在途请求放回 pending 时带 `not_before_at`（约 10 秒）且排在新请求之后；在途回合崩溃前把会话执行通道钉在自己身上，
  只有它自己结束才释放。此时同一会话来一条新消息：新消息先被领取并占住会话名额，再无限等待执行通道；原回合因会话名额被占拿不到执行权。
  两者可能一直互等（读代码推断，需用测试坐实）。安全重启要求：带续跑标记的请求在同一会话内优先于新请求领取；排空已证明旧执行者退出，
  安全重启产生的续跑去掉这 10 秒延迟。
- 这 10 秒窗口里控制面只在 processing 里找活动回合，`/stop`、`/status`、`/btw` 找不到续跑回合：TUI 的 Esc 被拒并一直显示“正在中断”，
  插话文本被丢；IM 的 `/stop` 回“当前没有运行中的内容”。控制面要把带续跑标记的 pending 请求视为同一活动回合。

### 5. 客户端

**TUI（已核对代码）**：TUI 提交回合是直接写 `requests/pending/<id>.json`，跟随回合是按偏移读 `processing/<id>.chunks.jsonl`，
回合只在 `requests/terminal/<id>.json` 出现时结束；HTTP 只用于通知、插话、控制、历史等旁路。所以：

- 已经成立：重启后启动恢复把请求以同一请求号放回 pending（`not_before_at` 约 10 秒后），再领取时写回同一个 chunks 文件，
  TUI 不需要重新挂接，续跑输出接在同一回合下；等待不会超时、不会重发；后台状态同步失败时页脚提示并以 0.5→8 秒退避自动恢复；
  控制命令和输入先存盘再重试，重启期间发的消息不丢；重启前已受理的停止在续跑时仍然生效；打开着的 TUI 不会因重启退出。
- 要补的缺口：
  1. 没有“正在重启/已续跑”的边界：旧回合里未关闭的回复块会和续跑文本拼在一起，死掉那次的执行中工具卡可能一直显示运行中。
     续跑时由 Gateway 在流里写一条结构化的续跑事件，TUI 据此关闭旧回复块和旧工具卡、标注“因重启中断，已自动续跑”，再接新输出。
  2. 授权确认框：重启时正开着的确认框在续跑后作废，新确认框因“已有待确认”被吞，回合可能一直等。排空收尾时给在途确认写结构化作废，
     TUI 收到后关闭旧框；同一请求的新确认替换旧确认，不再报“已有待确认”。
  3. 重启窗口里的停止和插话见第 4 节。
  4. 页脚只有“状态刷新失败”：`/status` 为 `draining`/重启中时改为显示“Gateway 正在安全重启，回合会自动继续”。
  5. 新开的 TUI 启动检查只等 3 秒，重启慢时会退出；看到重启中状态时改为等待。

**IM 适配器（已核对代码）**：适配器是独立守护进程，每次调用都是对固定回环端口的独立 HTTP 请求，不依赖 Gateway 进程号或启动标识，
不需要跟着重启。

- 已经成立：入站消息先写私有落盘记录再提交，Gateway 不在时按 1→2→…→32 秒、之后每 60 秒一直重试；稳定的 `gwreq-msg-…` 编号保证只提交一次；
  已受理请求的结果监视在重启期间继续等，续跑后同一请求号只产生一个最终结果，回复只发一次；“思考中”表情的句柄落盘，重启后照常清除；
  续跑失败时发一条指向 `/recover` 的错误回复。
- 要补的缺口：
  1. 重启期间用户没有任何反馈，也不标记通道状态。排空开始时对 `/ask` 返回结构化的“正在安全重启”，适配器照常受理并加上“思考中”表情，
     首次遇到时回一句“服务正在重启，消息已排队”。
  2. 恢复慢且可能乱序：每条记录各自退避，Gateway 回来后旧消息可能再等 60 秒，新消息反而先提交。探测到 Gateway 恢复后把到期时间全部提前，
     同一会话按到达顺序提交。
  3. 结果不明时静默：被重启切断的输入或控制最终为“结果未知”时只清表情不发文字，改为发一句说明。
  4. 永不结束的监视：结果为 ok 但正文为空（例如回合被中断）会被投递服务拒绝并无限重试；“已完成但投递状态未知”的停止命令会一直等。
     前者按终态发一句简短说明，后者设等待上限后给出说明。
  5. 永久性 4xx（例如幂等冲突）也会被无限重试。改为有限次后停止并告诉用户。
  6. 版本不同步：适配器不跟随 Gateway 升级。部署工具已在适配器代码有变化时重启它；代理自助重启不换版本，不受影响。

### 6. 配置与开关

- `gateway_restart_turn_wait_seconds`：第一段等回合自然结束的上限，参考 OpenClaw 默认 300 秒（Hermes 为 1800 秒安全阀）。
- `gateway_restart_drain_timeout_seconds`：第二段只等执行中工具的上限，`0` 不限制，超时取消重启。
- `enable_gateway_restart_tool`：是否给管理员代理注册 `restart_gateway`，默认开启。
- 两项都写进 `agent_config.yaml` 中文注释与 `AgentConfig` 默认值。

### 7. 不做的事

- 不做原地 `execv` 重启。
- 不让普通用户的代理重启共享 Gateway。
- 不从命令文本或模型正文判断“这是重启”，只认结构化请求与进程号事实。
- 直接 kill 进程号、HTTP `POST /stop` 仍不在保护范围内；前者属于系统级操作，后者只对可信本机来源开放。

## 验收

1. 代理在对话里调用 `restart_gateway`：Gateway 换成新进程号，同一回合自动续跑，模型看到“已重启”的事实后继续完成任务。
2. 另一个会话正在跑一条长命令时发起重启：等它跑完才重启，那个回合续跑完成，没有 unknown。
3. 重启期间飞书发消息：用户先收到“正在重启、已排队”，重启后按顺序照常回复，只回复一次。
4. 重启时 TUI 开着且有回合在跑：续跑输出接在同一回合下，旧回复块和工具卡被正确关闭；重启期间按 Esc 能停下；开着的确认框被作废后新确认能弹出。
5. 排空超时：重启被取消，服务恢复，回执列出还在执行的工具。
6. 部署工具改走同一流程后，有回合在跑也能安全切换版本。

## 已落地（第一期，2026-09-26）

用户决定：full access 下代理重启不需要确认；支持把飞书账号登记为管理员；飞书里的确认用管理员密码；本设计的安全重启与边界照做。

- 请求与合并：`gateway_parts/restart_service.submit_restart_request` 写 `gateway_restart.request`；同一目标进程已有待执行请求时只追加
  `additional_requesters` 并返回 `coalesced`。冷却 `gateway_restart_cooldown_seconds`（默认 30 秒，0 不限）；防循环改为
  “同一会话 10 分钟内最多安排 3 次”（设计里的“连续 3 次在重启时处于运行中就挂起续跑”未做，按请求次数拦更简单且可测）。
- 两段排空：第一段等本进程 admission 在飞数归零（不数 processing 目录，避免遗留文件拖满等待），期间派发器不认领、后台只回收已完成车道；
  第二段关闭 `concurrency/restart_gate`，新副作用工具停在领取之前等待，不给模型返回假结果，等待中被中断才按 not_started 收口。
  超时撤销请求、恢复服务，不强杀，并给发起会话写 `gateway_restart_cancelled` 通知。排空期间收到停止请求时按停止处理。
- 换进程：非托管时旧进程收尾后拉起 `gateway run --after-pid <旧进程号>`，接班进程先等旧进程退出（最多 60 秒）；
  systemd 单元 cgroup 或 launchd 标签托管时以退出码 75 交给管理器（systemd 自己拉起的子进程会随旧 cgroup 被清理）。
- 续跑：接班进程在启动恢复前消费新鲜（10 分钟内）且旧进程已退出的完成标记，恢复以 `gateway_safe_restart` 原因立即重排旧回合、排在新请求前；
  恢复后给记录了会话存储根的发起方写 `gateway_restart_completed` 持久唤醒（“重启已完成、不要再次重启或验证”）。
  设计里“给每个续跑回合注入已重启事实”简化为只通知发起方：其它续跑回合不需要知道重启；发起方自己的回合在历史里已有 `restart_gateway`
  回执，回执写明完成后不要再次调用。
- 入口：`restart_gateway` 工具（main_agent 专用，effect=dangerous，完全访问模式直接执行，其它模式走危险动作审批）与 `/restart`
  控制命令（local/main owner 专用，含之后绑定为管理员的 IM 身份）。托管自停闸的拒绝文案改为指向这两个入口。
- `/status`：HTTP `/status` 投影 `restart_drain`（阶段、请求编号、在飞回合数、执行中工具数）。
- 已知边界：只读工具（含被判为只读的命令，例如 `sleep 20 && echo`）不经过关口也不计数，第二段不等它们；换进程时它们被切断，
  续跑回合会重跑，结果正确但多花时间（2026-09-26 真实验收 C 轮观察到）。接班进程启动失败只记在它自己的状态文件里，没有进程再拉起它；排空期间在飞的后台会话工作片不计入第一段等待，
  靠第二段关口挡住新工具，换进程后按既有孤儿恢复接续；子代理 runner 若是独立进程，不经过本进程关口。
- 未做（后续分期）：终端 `my-agent gateway restart` 与部署工具改走安全重启（`--force` 保留硬重启）；重启窗口内 `/stop`、`/btw`
  找续跑回合；TUI 页脚“正在安全重启”、续跑边界与确认框作废；IM 重启期间的“已排队”反馈、恢复后按序提交与结果不明时的说明。
