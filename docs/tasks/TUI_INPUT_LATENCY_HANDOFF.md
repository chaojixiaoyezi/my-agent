## 现场报告的源码核对结论

- `tui_threading._start_worker_threads → tui_worker._tui_worker_body → tui_worker_paths._worker_gateway_path → poll_gateway_chunks` 是后台 worker 链路。
- chunk 候选已包含 processing/done/failed；客户端终态权威为 requests/terminal，同 ID 终态与目录投影必须分别核对。
- 低 CPU 和所有线程低 CPU 不足以排除锁等待；如果主线程栈在 select/epoll，还需读异步任务等待链及输入 reader 是否 detach。
- 现场四次低 CPU、零输出冻结比先前 5 KiB/s 慢输出复现更有针对性；不把二者合并成一个已确认根因。

重复组在进程内复核 CPU quota=200000/100000、亲和性 0/1、memory.limit=4294967296。
KiB/s 是测试者对 PTY 输出读取速度的控制，不是实测用户网络吞吐；短历史、长历史、正常输出与受控慢输出不能混算。
GUI 计时是从 X11 按键注入到服务端 Buffer 更新/渲染结束，不等于 Windows 可见字形延迟。
Windows/Wine 崩溃、初次缺少 PTY 的启动，以及把退出命令字符误配为前面输入的计算结果都不计入有效样本。

源码链路：`tui_ui_setup._assemble_tui_application` 在 UI 事件循环创建全屏 Application、静态 20 fps 刷新；
发行版 prompt_toolkit 的 `Renderer.render → Vt100_Output.flush → flush_stdout` 在同线程同步写出，`flush_stdout` 明确使用 blocking I/O。
慢消费使滚动的大面积重绘积压，UI 线程等待输出时不能继续处理输入。该问题已在受控条件复现，但还未证明用户现场就是同一原因。
增加只计时的 flush 观察后再次复现：最大 flush=3730.95 ms、render=3743.40 ms、输入等待=3673.03 ms，确认主要等待落在输出写入，而非鼠标处理（最大 0.49 ms）。观察器初版错误导入类名导致启动失败，修正为 `Vt100_Output` 后重测；无效启动排除。
用户随后反馈另一 SSH 工具也会卡，而此刻模型持续大量输出却不卡。不能归因于 PuTTY 或以模型输出量判定：需区分实际重绘字节量、输出消费速度、鼠标模式及现场卡顿时的 flush/事件循环时长。
现场需用同一 TUI 的 F6 鼠标模式对照，并用同一服务器/会话的另一 SSH 客户端区分 PuTTY、客户端设置与链路因素。

## 已定位并修复的通用问题

`cli/chat_parts/tui_input.py` 的两个异步辅助入口实际执行同步计算：

- 历史建议：原 AutoSuggest 的异步默认实现直接调用同步历史搜索，慢搜索会占用事件循环。
- 路径补全：插件 HTTP 已在后台，但随后候选生成、目录枚举和排序仍在事件循环执行。

参考安装版 prompt_toolkit 的 ThreadedAutoSuggest/ThreadedCompleter：把辅助计算交给后台执行器，
由原 Buffer 校验 Document 并丢弃迟到结果。同步候选算法、历史文件、目录版本、输入草稿、消息 ID、发送队列和执行目标不变。
本次没有增加依赖、配置项、额外模型请求或第二套输入状态。
