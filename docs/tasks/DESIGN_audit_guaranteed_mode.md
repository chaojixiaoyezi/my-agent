# /audit 逐条保证研判模式 — 设计文档

> **状态(2026-07-08):已落地并真机 M2.7 验收通过。** 实现落点与 A–G 验收见
> `AUDIT_GUARANTEE_ACCEPTANCE.md`;单测 `tests/test_watch_audit_guarantee.py`(22 项)。
> 本文保留为设计依据。

> 领域无关。全篇用中性词:一条条**记录**流进来,**判读器**逐条判断每条是不是**需要关注的命中**,
> 判完给**结论**。不涉及任何具体业务领域。

## 0. 一句话 & 为什么

**给"必须一条不漏"的场景一个可点的模式 `/audit`:每条记录都过模型判、判完才算数、一条不丢、
随时能出"全看过了"的回执。** 像 终端应用 的 `/loop`(干到完)、`/goal`(咬住目标)——一个附在
任务后、改变执行契约的斜杠指令。这里的契约 = **每条都判 · 一条不漏 · 不瞎判 · 给覆盖证明**。

存在理由:现有"引擎先筛一部分候选、判读器再判"的路子会漏(筛的时候丢、判读器空转时也丢)。一旦漏,
人就得把全部数据重审一遍,自动化等于白做。`/audit` 用"全量 + 逐条 + 判完才签收"换来一个**可信的零漏保证**。

## 1. 两档:洪水档 vs 保证档(明确分开)

| | 洪水档(默认,现有) | `/audit` 保证档(新) |
|---|---|---|
| 适用 | 高速流、只需看大概 | 必须一条不漏的源 |
| 筛选 | 引擎 triage 有损筛(可采样) | **不筛**,每条都判 |
| 追不上时 | 可采样/降维 | **队列涨,绝不丢、绝不瞎判** |
| 产出 | 抓到的高危 | 每条一个结论 + 覆盖回执 |
| 成本 | 低 | 高(每条烧一次模型)——所以只对该开的源开 |

## 2. 用户怎么用(两步)

1. **先对好数据格式**:用户给样品,判读器学"这类记录长啥样、怎么解析、关键信号在正文哪"。
   产出一个**可复用的解析/判据画像**(存起来,下次同类数据不重学)。
   **红线**:这个画像**只用来判得准,绝不能变成有损筛去跳过任何一条**。它治的是"冷启动没学会判据就漏",
   不是"学会了拿来筛"。
2. **布置任务带 `/audit`**:例如"盯这 5 个 API,几个月,逐条研判,不丢任何数据"。命令一加即进保证档。

## 3. 一条记录的一生 —【回答:来不及判的数据放哪儿】

```
到达 → ①入队(落磁盘,durable) → ②分给某判读分片 → ③模型逐条判 → ④记结论 → ⑤签收(acked) → ⑥归档
                                     ↑ 判不过来时,记录就安全地堆在①这个磁盘队列里,涨、但不丢
```

**积压落在哪:每源一条 durable 追加队列,在磁盘上**(现有 `watch_state/ws-*.spool.ndjson`,owner 家目录内)。
- **入队**:记录一到就**追加**进队列(带全局序号 + 入队时间戳),**永不覆盖、永不删**,直到判完归档。
- **待判就堆着**:判读器追不上,记录就**留在磁盘队列里等**——是**涨,不是丢**。持久,重启也在。
- **签收后归档**:判完 + 记了结论的记录标 `acked`;定期把"连续已 acked 的前缀"**移到归档区**
  (`ws-*.archive/`,可压缩),让"活跃待判"工作集有界——月级跑几百万条也不会让单个队列文件无限胀。
- **待判数 = 入队数 − 已acked数**,随时可数,进回执(第 6 节)。
- **重启**:队列 + 每分片游标都在磁盘 → 原位续判,一条不重一条不漏(见第 8 节)。

**磁盘真满了怎么办(边界,别丢)**:先对"**源拉取**"施加背压——慢拉/暂停拉新的,让积压留在源端,
而不是丢已经收进来的;并告警。**宁可源端慢/堆,也不丢已入队的**。真·洪水速率本就该走洪水档,不该 `/audit`。

## 4. 判读工弹性伸缩 —【回答:有富裕就多派子代理帮忙】

判读工数**不写死**,按"积压深度 × 有没有余量"动态定:

- **建议判读工数** = ceil(待判数 ÷ 单工判读速率),再夹一个上限 `max_judge_workers`(资源闸)。
- **有富裕就多派**:当 待判涨、当前判读工 < 建议数、**且系统有余量**(总代理数没顶格、CPU/并发没打满)
  → 主代理 `create_subagents` 多开几个判读子代理,各领一个**新分片**(spool 按 `序号 % 分片数` 切,不重不漏)。
- **没富裕**:资源顶格时**不硬开**——让队列涨(还是不丢),等有余量再补。即"富裕→多派帮忙,不富裕→稳住不丢"。
- **追平就缩**:待判降下来,多出来的判读工判完自然退,不再补。
- 每个判读分片一条独立读游标(`ws-*.read.sNofM.json`),各判各的、各自签收,互不重叠。

> 现成基础:R6 的判读分片 + `recommended_judge_workers(积压)` 已实现并真机验证能铺开(实测 1→36 工、
> 某路按积压 2→6 工)。本设计把它固化成保证档的"弹性帮手"机制。

## 5. 判完才签收 + 不丢不瞎搞(核心正确性)

- **判完才签收(ack-on-judge)**:分片游标 / ACK **只在"该条真判完 + 记了结论(命中上报,或明确判为无事)"
  之后**才推进。空转的判读工(领了活不判)**推不动游标**→ 它那份记录不会被当成判过、会被重新分配,
  **不会被静默吃掉**。(这是上一轮崩的直接根因:判读工空转、抽干游标却不判,真命中被悄悄跳过。)
- **来不及也不许"缺"**:落后只能表现为**延迟**(队列涨、诚实挂 pending),**绝不丢任何一条**。
- **来不及也不许"瞎搞"**:**绝不允许**因为积压就盖章、猜、批量放行/批量报。每条最终都得有**真模型**的
  逐条结论。过载时**宁可慢、宁可 pending 数很大**,也不产出未经真判的结论。回执如实显示待判数,不假装判完。

## 6. 覆盖回执(用户敢不重审的凭证)

任意时刻可查一张回执:

```
源A:入队 12,431 · 已判 12,431 · 待判 0 · 丢弃 0   ✓ 全覆盖
源B:入队  9,780 · 已判  9,102 · 待判 678 · 丢弃 0  ⏳ 判读中(积压678,已加派2工)
...
合计:丢弃 0(硬保证)
```

- **丢弃恒为 0** 是硬约束(丢了就是 bug)。待判>0 只表示"还在判",不是"漏了"。
- 有了这张回执,用户看"待判归零、丢弃0"就知道**全看过了**,不用人重审。

## 7. 子代理契约继承（命令一加,整支编队一样）

`/audit` 一旦生效,契约**沿 spawn 树继承到每一个判读子代理 / 孙代理**:
- 没有哪个子代理能偷偷 triage、批量跳过、盖章放行。
- 每个判读工要么**产出逐条结论**,要么**不签收、把记录让给别人**——不存在"我判不完就随便结掉"。
- 主代理派判读子代理时,把 `/audit` 契约(逐条 / 判完才签收 / 不丢不瞎搞)一并下传,子代理再派孙代理同理。

## 8. 月级长跑稳定性(这模式的生命线)

用户要"盯几个月不丢数据",所以下面是硬指标,不是加分项:
- **重启恢复必须覆盖所有源,含判读落后的源**。恢复要按"**谁有未判积压**"来驱动,不按"谁已经在健康跑"——
  否则月级里必然多次重启,每次都把落后的源落下 = 慢性丢数据。(上一轮只恢复了健康的源,落后源躺平,必须修到全恢复。)
- **不许无界涨**:队列落盘 + 已判归档 + 活跃工作集有界,长跑不爆内存/磁盘。
- **常驻自愈**:判读工静默死 → 监督者补活(保活/supervisor 思路),月级零人工干预。
- **回执连续可查**:不是测完打一次,是任何时刻都能给当前"入队/已判/待判/丢弃0"。

## 9. 取舍(如实告诉用户)

- 逐条判每条都烧一次模型 → **贵**。中等速率的流(API 盯守)完全扛得住;真·洪水(每秒上百/百万行日志)
  模型追不上 → 队列**涨(不是丢)**、持久滞后。别为追速把有损筛偷偷加回来。
- 海量日志若成本吃不消,治本是加一层**无损结构去重**(只合并完全相同的、绝不按语义丢),而不是恢复有损筛。
  这属于以后遇到真实规模再优化,现在不提前做。
