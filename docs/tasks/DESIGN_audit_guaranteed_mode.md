# `/audit` 通用来源工作者设计

> 当前权威验收状态见
> [`AUDIT_GUARANTEE_ACCEPTANCE.md`](AUDIT_GUARANTEE_ACCEPTANCE.md)。

## 1. 设计边界

`/audit` 是统一 Agent runtime 上的命名后台任务，不是固定安全 Workflow。

用户用普通自然语言说明监测目标、来源资料、评分方式、汇报要求和是否联合调查；模型负责业务判断、
解释、复核、调查和用户回复。程序不得按关键词、设备类型、攻击类型、固定阈值或固定步骤决定业务结果。

程序只强制不可绕过的通用边界：

- owner、命名 Audit、来源和运行身份；
- 工具 Schema、权限、sandbox 和 Secret 引用；
- 完整记录边界、游标、耐久队列、幂等和原子写账；
- 来源工作者归属、租约、取消、恢复、背压和上下文预算；
- `ack_id`、`source_ref`、原文哈希、结论账、发现账、投递账和覆盖对账。

## 2. 唯一来源身份

1. 一个命名 Audit 使用稳定 `audit_id`，当前实现以它的 typed 根任务 ID 表示。
2. 一个来源在一次 Audit 中只对应一个 `watch_id`；同一来源被两个 Audit 使用时产生两个独立 watch。
3. 每个 `watch_id` 必须对应一个专属逻辑来源工作者。
4. 逻辑身份 `worker_key` 只由 `audit_id + watch_id` 得出，不另造竞争性的永久绑定 ID。
5. 一次实际执行使用现有子代理 `run_id` 和 runner `attempt_id`；重启或接替可以更换它们，
   但 `worker_key` 不变。

## 3. 来源工作者是权限边界

来源工作者只能：

- 拉取自己 task attributes 中绑定的 `watch_id`；
- 对该 watch 的在途 `ack_id` 提交首次 verdict；
- 读取完成该来源任务所需的来源资料和原始记录引用；
- 使用统一 `record_finding`、`raise_event` 等能力把有价值事实交给上级。

工具执行入口必须同时校验 owner、`audit_id`、`watch_id`、`worker_key`、`run_id`、
`attempt_id` 和当前租约。Prompt 中写“你只能看某一路”不能代替程序校验。

主 Agent、Audit 协调者和调查子代理可以读取结构化状态和指定 `source_ref`，也可以追加复核结论，
但不能拉取来源队列、抢占来源工作者租约或提交原始记录的首次 verdict。

## 4. 复用统一 Delegate Kernel

来源工作者必须通过现有 `create_subagents` 的同一创建、权限快照、自动启动、runner attempt、
取消、故障回收和 Compact 主链运行。`/audit` 只增加结构化来源绑定和执行权限，不增加：

- Audit 专用 Agent loop；
- Audit 专用 Memory 或 Compact；
- Audit 专用子代理管理器；
- 第二套 scheduler；
- 固定 judge、固定 watch-lane、固定来源类型或固定处理步骤。

每次 `watch_stream(open)` 成功形成 Audit watch 后，运行时按稳定 `worker_key` 幂等确保一个逻辑
来源工作者。1、5、7、9、13 个实际 watch 分别得到同样数量的逻辑工作者；数量不写死。

容量不足或启动失败时，采集仍可安全落盘，但该 watch 必须显示
`waiting_for_worker`/`degraded` 和真实错误，主 Agent不得偷偷代消费。

## 5. 生命周期与租约

1. 来源工作者不是永久占用一个模型请求。它可以领取一批完整记录、判断并写账，然后释放本轮。
2. 统一长期任务生命周期负责继续同一个逻辑工作；无数据时可以等待，有数据时重新运行。
3. 同一 `worker_key` 同时只能有一个有效消费租约。租约由结构化 `run_id + attempt_id` 持有。
4. 租约续期、过期和接替使用 owner 范围内的耐久状态与文件锁；旧 attempt 的迟到 pull/verdict
   必须 fail-closed。
5. 服务重启后，统一子代理监督器根据仍有效的 Audit watch 和现有任务状态恢复或补建来源工作者。
   这一步是宿主层结构化巡检，不周期性调用主 Agent 模型；正常来源进展不会占用用户对话入口。
   有时限的 watch 在最终补拉、游标和原始队列同一事务提交后，会发出一次结构化窗口完成事件，
   立即调用同一来源工作者终态投影；宿主周期巡检仅作为进程退出或回调失败后的恢复兜底。
   两条入口共用同一个 `window_finalized_at + ACK ledger` 完成条件，不维护第二套完成状态。
6. `/audit <名称> clear` 取消该 Audit 的来源工作者和调查任务、停止采集并保留账本；
   `/stop` 只中断当前前台 turn，不影响后台 Audit。
7. 逻辑来源工作者的单次 runner attempt 使用有限工作片，但累计 `runner_attempts` 不是
   300 天 Audit 的生命周期上限。正常完成一轮后，同一 `worker_key` 和同一任务继续运行，
   不创建替代任务。
8. 故障恢复区分三类结构化事实：
   - runner PID 已退出且心跳过期：按进程崩溃废弃旧 attempt；
   - runner PID 仍在但整个宿主心跳过期：只有宿主上的运行全部是已停滞来源工作者时，才先按
     进程组终止宿主，再废弃旧 attempt 并接替；同宿主仍有健康运行时不得误杀整个宿主；
   - 模型、供应商传输或工具调用卡住但独立心跳仍然新鲜：由来源工作者单次 runner 工作片的
     外层超时先封禁 attempt、请求中断当前传输，再把同一耐久任务放回队列。旧调用即使迟到返回，
     也不能越过 attempt 与 watch 租约继续写账。
   普通子代理仍保持保守的活进程保护；上述“活进程接替”只适用于工具已精确限权、pull/verdict
   又受 attempt 与 watch 租约双重约束的来源工作者。
9. 接替会撤销旧来源租约、把原任务重新置为可派发状态并记录恢复原因和累计次数。
   旧 attempt 即使迟到恢复，也不能再 pull、verdict、ACK 或覆盖新 attempt 的结果。
10. 未 ACK 的原始记录继续留在同一耐久队列；新 attempt 获得同一批欠账。恢复不删除
    原始记录、verdict、finding 或投递账，也不把“已重新派发”误写成“已经处理完成”。
11. 正常工作片到时但最近仍有真实进展时只记为 slice rotation（工作片轮换），不能误报卡死；
    没有进展的超时才累计为 stall。两者都复用同一任务、队列和 Compact 主链。
12. 多个子代理并发保存到同一个父任务工作区时，`child_run_ids` 的读取、单调合并和原子替换必须
    持有同一任务状态锁。父任务自己的后续投影也只能保留或增加已有子任务链接，不能用较旧的
    内存快照把已登记子任务覆盖掉；这条规则属于统一任务账，不是 Audit 专用分支。

## 5.1 命名 Audit 的准备与发布

1. `/audit <名称> prepare <内容>` 是当前 conversation 的一次普通 Agent turn，只临时绑定准确
   Audit 的 `audit_id` 与 `audits/<audit_id>/` 工作区；不建立 Audit 专用会话、Memory、Compact
   或 Agent loop，也不让后续普通消息黏在该 Audit 上。
2. 名称是区分大小写的 owner/thread 内用户句柄；执行、clear、来源和批次仍以稳定 `audit_id`
   为权威。程序不从正文猜名称、来源类型、字段含义或用户是否确认修改。
3. 当前生效要求、准备中内容和验证引用分别持久化。提问、读样例、试接口、写脚本或比较方案只
   更新准备内容；只有 prepare turn 中按当前结构化 scope 暴露的 `publish_audit_update` 能发布。
   来源说明、脚本、Skill、字段文档和测试记录都是主 Agent 在普通工作区按现场需要形成的材料；
   底座不要求固定 `source profile`，也不规定来源类型、研判模板或业务处理流程。
4. 发布来源集合时必须显式选择结构化更新方式：`upsert` 只增加或更新列出的稳定 `source_id`，
   `replace` 使本次列表成为完整生效集合并停止已移除来源。程序不从正文猜用户想追加还是替换。
5. `validation_status=failed`、缺失证据或越出当前 Audit 工作区的证据引用不会改写旧配置。
   发布成功后，正在处理的完整批次继续使用领取时的旧要求，新要求从下一批领取开始生效。
6. `/audit <时长> <名称> <任务>` 启动已准备项时复用原 `audit_id`；若已有发布要求，启动文字
   只用于本次人类说明，不能覆盖权威生效要求。

## 6. 数据和上下文

完整记录先落耐久队列，再提交来源游标。来源工作者按等待时间、累计字节、上下文预算和自己声明的
目标条数形成批次；程序只在完整记录边界之间缩小批次，不以固定 5、8 或其他魔法条数决定吞吐。

容量事实中的摄取速率以最近一次完整提交的短时间窗口计算；来源窗口已经结束，或该速率样本超过
新鲜度期限时，当前摄取速率必须显示为 0。不得用“累计写入量除以 Audit 总运行时间”的历史平均值
判断积压正在扩大，否则有限回放结束数小时后仍会产生错误容量结论。

`ack_id` 是处理与签收身份，`source_ref` 是可稳定找回完整原始记录的引用，两者用途不同。
首次 verdict 与真实在途 `ack_id` 原子写账后才 ACK。未交齐、重复、跨批、未知或旧租约提交均不得推进。

来源工作者复用统一 task-local Memory、Compact、工具归档和上下文预算；长期 Persona、Memory、
来源文档和用户资料仍归 owner 主 Agent，不给来源工作者再造长期人格或记忆库。

来源工作者的读取能力也采用统一 Tool Gateway 边界，而不是只靠 Prompt 约束。它只能读取：

- 自己的 agent run 工作目录；
- 当前来源绑定中显式引用的本地说明和字段文档；
- 自己当前 `run_id` 产生并登记的工具输出 artifact。

同一 owner 的其他项目、其他 Audit 来源文档和兄弟子代理 artifact 即使文件系统层可见，也必须在
工具 handler 执行前拒绝。这个 exact read scope 是通用结构化边界；普通子代理未显式启用时维持
原有 owner 范围，不把 Audit 的最小权限规则误套到所有任务。

## 7. 发现、调查和汇报

模型依据用户目标决定哪些判断值得形成 finding、是否复核或联合调查。程序只保存稳定
`finding_id`、`source_ref`、证据、阶段和投递状态，不按 verdict 文本或分数硬编码路线。

来源工作者一旦显式调用 `record_finding`，该 run 的追加式 finding 账同时充当耐久 outbox。
程序把这条结构化 finding 投影成统一会话 observation/wake；投影游标在成功发布后才推进。
因此 finding 落盘后进程立刻崩溃、发布重试或服务重启，都沿同一 `finding_id + revision`
补发且去重，不要求模型重新判断原始记录，也不为 Audit 新建消息系统。

健康来源工作者的普通批次进展不会定时叫醒主 Agent。主 Agent只在 finding、故障/阻塞、
来源生命周期终态或用户主动查询等结构化事件发生时参与协调；这与来源工作者自身的租约、
接替和宿主巡检相互独立。

后台协调者优先协调来源工作者、调查或汇总子代理；主 Agent保持与用户聊天和接受其他工作的能力。
只有获得真实 `investigation_run_id` 后，模型才可说明调查已经开始。

任何新的 Audit 优化都必须先判断它属于“不可绕过的运行边界”还是“模型应自主决定的业务路线”。
前者可以进入底座；后者只能作为用户目标、Skill 或当前任务上下文提供，不能固化进程序。
