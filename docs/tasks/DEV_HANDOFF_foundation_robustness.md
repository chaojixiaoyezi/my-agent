# 通用能力底座提升 —— 稳健性 / 一致性 / 交付保障(零上下文,纯工程口径)

> **给谁**:从零接手的开发代理　**日期**:2026-07-04　**来源**:四类真机测试(长时盯守 / 大体量建站 / 多项目分析 / 大文件全扫)+ 终端应用 同模型对照 + 公开研究
> **总方针(重要)**:**不要加强行限制/硬规则**(如"必须写够 N 行""禁止返回空")。这些问题的本质不是"做不到",而是"**同样的能力时好时坏、最后一口没送到**"。要治的是**底座的稳健性与交付保障**,让已经具备的能力**稳定复现**。参考 终端应用 / 会话运行时 的做法与公开可靠性研究。

---

## 0. 定性:能力是有的,缺的是"稳定"和"送达"

**反复被证明有能力**:
- 大文件全扫分析——本轮用户A **四问全答对、数字精确**(总额、超阈值笔数、最高类、散布异常账户 7 笔合计精确),质量媲美 终端应用。
- 长时盯守——本轮用户A **3 小时逐条报 217 条、全真、0 误报、不死**。
- 建站——本轮两个用户都**真交付了能跑的多模块项目**;历史上代码/分析任务也多次做得不错。

**所以病灶不是"不会",是"不稳 + 最后一口交付断"**。公开研究的判断一致:**"agent 能解一个任务 ≠ 每次都能解"(一致性低)**,且**长任务成功率随时长骤降(meltdown)**。→ 治本方向:**加底座保证一致性与交付,不加限制。**

---

## 1. 【头号】最终交付"空手":活干完了,送到用户面的却是空的

**现象**:任务实际完成了,但**用户收到的最终响应是空的**;或成果落在内部 `work/` 目录、没进交付目录 `output/`。
- 大文件分析(用户A):**答案全对,但最终响应体为空**——正确结论卡在流式输出中间层,没进最终响应/`output/`。
- 多项目分析:主报告落 `work/` 内部,**没进 `output/`**。
- 建站:成果在 `output/`(可拿到),但最终响应文本也是空的(无收尾汇总)。

**证据**:`u-t4a` 的 chunks 里有完整正确分析、其 `responses/*.json` 的 text 长度=0;`u-t3a` 最大报告在 `work/` 内部而非 `output/`。留档见 `evidence/t4_u-t4a_analysis.txt`。

**今昔**:盯守类(Test1)因上一棒 §2 "逐条送达兜底"机制,**结论稳定送达**了(217 条到账);但**普通任务的"最后一口汇总/交付"没有等价兜底** → 一到普通任务就空手。

**底座方向(非限制)**:加一个**"交付保障"收口层**——任务收口前做**确定性自检**:①最终响应是否非空、是否说清"干了啥+结论/交付在哪";②声明的交付物是否真在 `output/`(而非 `work/` 内部)。不满足则**自动从已完成的工作里合成一份收尾汇总 + 归集交付物**,再收口。这是把"可观测/验收建在'任务真完成'上"(研究共识),对标 **终端应用/会话运行时 每个任务必以一段面向用户的收尾汇总结束、绝不空手返回**。

## 2. 双用户方差大:同任务同模型,一个漂亮一个残废

**现象**:每类都派 2 个普通用户跑同一个任务,结果经常**一个很好、一个明显拉胯**:
- 盯守:用户A 217 条 vs 用户B 18 条。
- 分析:用户A 覆盖 5/5 vs 用户B 只做 1/5。
- 大文件:用户A 全对 vs 用户B 漏了异常账户。

**证据**:各 owner_home 下 findings/报告的对比(见测试发现报告 §1-4)。

**今昔**:这不是"新退化",是 agent 领域的**老难题——"能力强但不一致"**(采样随机性 + 受提示措辞的细微变化影响大)。本轮把它量化暴露了。

**底座方向(非限制)**:公开研究开的方子——**自检 + 有界重试 + 结构化确定性环节**。具体到底座:①关键步骤后加**"够不够/全不全"的结构化自检**(如"要分析 5 个,现只覆盖 1 个 → 继续");②把易漂移的动作从"纯靠模型自觉"改为"**结构信号驱动的循环**"(对标 终端应用 的 todo 列表逐项闭环:每项做完打勾、没打勾的继续)。目标是把方差压下来,不是禁止某种行为。

---

## 3. 把"持续型任务"派给子代理 → 子代理提前完事 → 整任务停摆

**现象**:盯守(持续型任务)被主代理**委派给一个子代理**,子代理按"做完即退"的语义**提前判成 DONE 退出**,主代理随后挂起,盯守停摆(用户B 只 18 条)。

**证据**:`u-t1b` 的 `wake_queue` 里 `subagent-finished...DONE`、spool 停在低位。

**底座方向(非限制)**:让**任务生命周期语义**下沉到底座——**持续/驻守型任务**(有盯守窗口、无终态)委派时,子代理应**继承"不到窗口不退"的语义**,或干脆**由主代理自己扛不外包**。这是补底座对"任务类型"的认知,不是禁止派子代理。

---

## 4. 耐力不足:大体量任务半道自认完成

**现象**:要求做"功能齐全的大应用",两个用户都**到 ~5000 行就自认做完**(4692 / 5456),没堆到预期体量;终端应用 更少(1822)。

**证据**:`u-t2solo|u-t2disp/**/output/` 行数。

**今昔**:对上研究里的 **"长任务 meltdown / 成功率随时长骤降"**;也对应本产品一直想要的"熬到正经完成"。

**底座方向(非限制)**:强化**"持续干到真完成"的主循环**——用**完成度验收驱动**(功能清单逐项核对:要求的功能是否都实现且可跑,没实现的继续),而不是靠模型"觉得差不多了"。对标 终端应用 **todo 驱动的持续迭代 + 收尾前功能核对**。不是硬性"必须 N 行"。

---

## 5. (监控专项,非通用底座)语义判定型目标的引擎召回天花板 ~26%

**现象**:盯守中,891 个真事件只被引擎抬出 234 个(26%)给模型判;**某些类型(源D)0/177 全漏**。判 + 报无误(0 误报),漏在"抬"这一环。

**底座方向**:属监控子系统(引擎宽抬),见测试发现报告 §1/§5;此处不展开,与通用底座分开治。

---

## 6. 参考(方法来源)

- **终端应用 / 会话运行时**:①任务必以面向用户的**收尾汇总**结束,不空手;②**todo/清单驱动**的持续闭环(逐项打勾、未完成继续);③**收尾前核对**成果。→ 对应 §1/§2/§4 的底座方向。
- **公开研究**:reliability=一致性+健壮性+容错;**验收建在"任务真完成"而非"组件返回"**;**自检/重试/确定性合成**保证输出;长任务防 meltdown。
- **可上网续查**:*agent reliability consistency*、*task completion verification / self-check*、*long-horizon agent robustness*、*deterministic output validation*。

## 7. 优先级(建议)

1. **§1 交付保障收口层**(头号,普适、见效快:普通任务从"空手"→"必送达")。
2. **§4 持续干到真完成的主循环**(治耐力,也顺带压 §2 方差)。
3. **§2 关键步骤结构化自检 + 有界重试**(治一致性)。
4. **§3 持续型任务的委派语义**(治盯守被外包停摆)。

> **贯穿原则**:每条都是"**给底座加一层保障/闭环**",不是"给模型加一条禁令"。目的是让已被反复证明的能力**每次都稳定发挥、且结果一定送到用户手里**。
