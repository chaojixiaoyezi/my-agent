# 四类真机测试 —— 发现汇总(纯工程口径,零上下文)

> **测试方**:独立测试代理　**日期**:2026-07-04　**环境**:常驻网关(testbox)+ 真模型 M2.7 + 飞书普通用户普通口吻发任务　**对照**:终端应用(同压 M2.7)
> **口径**:全程纯工程/机制口径,不含任何具体业务领域内容词。每类 2 个普通用户并行、四类串行。

---

## 0. 一句话结论

- **§7 修复(引擎宽抬+逐条重判)真机大考通过**:长时盯守端到端**从修复前 0 → 3 小时逐条报出 216 个真目标、0 误报、全程不死**。
- 但四类测试**挖出 5 类新问题**,头号是**「最终响应空/交付位置不稳」**(活干完了、结论卡在中间层没送到用户面)和**「双用户方差大」**(同任务一个干得漂亮、另一个残废)。
- **my-agent vs 终端应用**:建站(代码量)my-agent 胜、专职盯守 my-agent 完胜;**代码分析深度 终端应用 明显胜**;大文件全扫两边都能对,但 终端应用 交付更干净。

## 1. Test1 长时盯守(3 小时 · 5 路 · ~250/s · 目标 ~1/3000)

**设定**:5 路高吞吐数据流,每条是一对内容(A 段 + B 段),判定"目标事件"需**读懂两段是否吻合**(语义判定,非匹配单字段);目标极稀疏(3h 共约 891 个)。飞书普通用户普通口吻发盯守任务,**不提示用哪个工具**。

**结果(证据:owner_home 的 `findings.jsonl` + 旁路 answer-key 对账)**:

| | 引擎抬候选(funnel A) | 逐条报真目标(funnel B) | 误报 | 3h 耐力 |
|---|---|---|---|---|
| 用户A | 234/891 | **216 真命中** | **0** | ✅ 3h 仍在报(最后 finding 距终评 4s) |
| 用户B | 19/891 | 18 | 0 | 派子代理托管后停摆 |
| 终端应用 | — | **4 真** | — | 自写脚本轮询,远不如 |

**✅ §7 坐实**:用户A 逐条报出 216 个真目标、**0 误报**、3 小时不死——修复前同类是 0。**§7.2 也修好了**:两个用户都**没自写脚本**、走了内置盯守机制(修复前会自写破轮询脚本刷海量误报)。

**⚠️ 新发现 1【引擎侧天花板】**:funnel A 仅 **234/891 ≈ 26%**(收割游标全程跟得上流、非滞后)。即引擎的**结构化预筛对"语义判定型"目标只抬得出约 1/4**——其余 3/4 的真目标结构上和常态没区别,引擎抬不出来、就到不了模型面前。**端到端召回因此被压在 ~24%**。逐条重判环很强(报出了抬出来的 91%、0 误报),但"抬"这一环对语义目标是硬瓶颈。(注:对"结构化结果端字段"型数据 §7 能到 13/13;这是"成对内容语义判定"型数据的独有短板。)

**⚠️ 新发现 2【把盯守派给子代理→停摆】**:用户B 的主代理**把盯守任务派给了一个子代理**,该子代理**提前判成"完成"退出**(盯守不是"做完就结束"的任务),主代理随后挂起,整轮只报 18 个(vs 用户A 216)。证据:`wake_queue` 里有 `subagent-finished...DONE`、spool 停在低位。

**证据坐标**:`owners/.../u-t1a|u-t1b/**/findings.jsonl`;答案 `t1_ak.jsonl`(891 目标);收割游标 vs 源 seq 均 ~31.5 万(跟得上)。

## 2. Test2 万行代码(solo vs 明确要求派子代理)

**设定**:同一个"功能齐全的多模块应用"任务,飞书 2 用户:用户solo 不提子代理、用户disp 明确要求派子代理。

**结果(证据:`output/` 下代码文件行数)**:

| | 交付 output/ | 代码行 | 结构 | 派子代理 |
|---|---|---|---|---|
| 用户solo | ✅ 41 文件 | 4692 | 单模块 | 自发派了 1 个 |
| 用户disp | ✅ 122 文件 | **5456** | backend+frontend+docker-compose+start.sh+README(更完整可跑) | 7 个 |
| 终端应用 | ✅ | 1822 | | |

**✅ 都真交付**(在 `output/`,非假 done)。**✅ dispatch>solo**(结构更全更可跑)。**✅ my-agent 代码量 ≈ 3 倍 终端应用**。

**⚠️ 新发现 3【耐力不足:堆不到万行】**:目标是"足够大的应用",两个用户都**到 ~5000 行就自认完事**(4692 / 5456),没堆到万行;终端应用 更少(1822)。主代理"沉不住气、提前收工"在大体量任务上明显。

## 3. Test3 代码分析(5 个开源项目 · 布置时不提子代理)

**设定**:5 个真实开源项目代码放进用户 home 的 `projects/`,飞书发"逐个分析、出报告"任务,**不提子代理**。

**结果(证据:分析报告行数 + 覆盖项目数)**:

| | 覆盖项目 | 报告深度 | 交付到 output/ | 派子代理 |
|---|---|---|---|---|
| 用户A | **5/5** | 159 行 / 6KB(浅) | ❌ 主报告落 work 内部 | 1(自发) |
| 用户B | **1/5**(漏 4 个) | 65 行(浅) | ❌ | 1(自发) |
| 终端应用 | 5/5 | **575 行**(厚实) | ✅ | |

**✅ 会自然派子代理**(没明示也派)、**够得到 owner_home 子目录的输入**。

**⚠️ 新发现 4【分析浅 + 覆盖不全】**:my-agent 分析报告**又短又浅**(159/65 行),用户B **只分析了 1/5 就收工**;终端应用 明显**厚实得多**(575 行、5 全覆盖)。**这与 Test2 相反**——建站 my-agent 强、分析 终端应用 强。

**⚠️ 交付位置**:主分析报告落在 `work/` 内部、**没进 `output/`**(用户看交付目录拿不到)。

## 4. Test4 100M+ 大文件分析(必须全量扫完才对)

**设定**:110M / 220 万行交易流水,答案设计成**必须全扫才算得对**(总额、超阈值笔数、各类聚合、散布全文的 7 笔异常大额);头部采样必错。飞书 2 用户 + 终端应用。

**结果(证据:助手输出 vs 全扫真值)**:

| | 全扫脚本 | ①总额 | ②超阈值笔数 | ③最高类 | ④散布异常账户 | 送到用户面 |
|---|---|---|---|---|---|---|
| 用户A | ✅ 真跑 python 全扫 | ✅ | ✅ 439,955 精确 | ✅ utility 精确 | ✅ **7 笔/合计精确** | ❌ **最终响应空** |
| 用户B | ✅ 写对全扫脚本 | 部分 | | ✅ utility | ❌ 漏了异常账户 | ❌ 响应空 |
| 终端应用 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ 写进 analysis.md |

**✅ 大文件全扫分析能力在**:用户A **四问全答对、且数字精确**(需真全扫,头部采样出不来),**质量媲美 终端应用**。

**⚠️ 新发现 5【交付/最终响应空】(与 Test2/3 同源、头号)**:用户A 把活干得完美,但**最终响应体是空的**——正确分析卡在**流式输出 chunks 里**,没进最终响应/`output/`。用户"收到"的是空消息。**Test2/3/4 都中招**:活干完了(代码在 output/、分析在 chunks/work),但**最终送到用户面的那口"结论/汇总"经常是空的**。

**⚠️ 双用户方差**:用户A 全对、用户B 漏异常账户(脚本没跑全/没抓 needle)。

## 5. 跨类问题清单(下一棒靶子,按轻重)

1. **【头号】最终响应空 / 交付位置不稳**(Test2/3/4 都中):活干完了,但**送到用户面的最终结论/汇总常是空的**,或落在 `work/` 内部而非 `output/`。盯守类(Test1)因 §2 逐条送达机制兜住了,但**普通任务的"最终一口汇总"没兜住**。→ 收口/送达层要保证:最终响应带上"干了啥+结论/交付路径",别空手。
2. **双用户方差大**(Test1/3/4 都有一个用户明显拉胯):同任务同模型,一个漂亮一个残废。指向**行为稳定性**(是否派子代理、是否提前收工、是否全跑完)不稳。
3. **把"持续型任务"派给子代理→子代理提前完事→停摆**(Test1 用户B):盯守/长任务被委派后,子代理按"做完即退"收场,拖垮整任务。→ 委派持续型任务要么别退、要么主代理自己扛。
4. **耐力不足**(Test2):大体量建站到 ~5k 行自认完事、堆不到万行。
5. **语义判定型目标的引擎召回天花板 ~26%**(Test1):引擎结构预筛抬不出"要读懂成对内容才判"的目标(3/4 漏在"抬"这一环)。逐条重判很强但只作用于抬出来的。→ 语义判定型数据要么把更多候选宽抬给模型重判、要么换判据。

## 6. my-agent vs 终端应用(同压 M2.7)一句话

- **建站/代码量**:my-agent 胜(≈3×)。**专职盯守**:my-agent 完胜(216 vs 4)。
- **代码分析深度**:终端应用 胜(575 vs 159 行)。**大文件全扫**:两边都能对,**终端应用 交付更干净**(my-agent 最终响应空)。
- 归纳:**my-agent 强在"建"和"专职机制(盯守)",终端应用 强在"读懂/分析"和"干净交付";my-agent 的短板集中在"最终一口交付"和"行为稳定性"。**
