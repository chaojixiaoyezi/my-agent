## 2026-11-09 新版本十窗口及另外七窗

用户在新版本另开十个新会话，确认5个DeepSeek、5个MiniMax，与原来十个线程无重合；随后增加七个窗口。Gateway观测到17个在途请求，这不能换算为20以上代理数的实测。17窗口下跟踪Gateway自身CPU与physical footprint；单核满载为100%。同一102秒窗口平均约597%、峰1336%，另取同峰三份正式Python栈。多条请求线程在等模型队列，多条模型线程在等网络，维护线程在等事件；HTTP通知计算活动状态、模型账本更新与进程身份读取都出现过，三个栈不能把CPU按业务层分摊。前十窗中的5个MiniMax请求约19分钟后以HTTP 400结束，供应商提示模型需要adaptive thinking而请求禁用了thinking，后继须核实际请求来源。已收集到证据，不再补发任务。

同一进程连续采样65分钟（7,495条）。09:50:32–10:20:38 PST连续30分06秒在途为零；354次心跳均无处理中文件，整段没有dispatcher_stalled。压力窗口退出后只见一份启动于本次升级前的终端。Gateway physical footprint：采样开始1.81GiB，首次在途归零5.33GiB，零在途30分钟后5.45GiB（RSS 5.51GiB）；最后15分钟平均CPU 3.64%。退出能让CPU回落，本次未观察到内存回落。vmmap的tag100驻留约5.4GiB，标签不能区分活对象和分配器保留，也不是显存泄漏证明。

首批十个新请求均有正式终态：五个MiniMax失败前各执行35–49个工具轮，五个DeepSeek为INTERRUPTED，各执行18–41个工具轮；没有把中断算成游戏完成，也没有重投。MiniMax实际采用Anthropic接口、线程档位low；供应商返回拒绝关闭思考。既有程序至少有两条能产生无效参数的路径，但历史回执没有保存最后一次请求体，不能反推它究竟走了哪一条。

后继源码复现并修复了活动通知重复读取、多模型账本查询扫描全部明细、原生流式重复累积全文、模型线程退出后多持有一份请求上下文、展示页复制期间阻塞写者，以及多线程后台展示环没有合计字节上限。展示归档与中断前的正式记录保持原权威。上述修复通过各自的本地行为回归；不能从合成微基准反算实机5.45GiB各项分摊或17窗总CPU降幅。

## 2026-11-09 慢窗口与对象生命周期补查

本机c868同PID的区间CPU观察先捕获约35秒高占用，90秒窗口平均42.12%、峰189.89%；同时段没有观察到新request登记，仍不能排除后台或只读HTTP工作。之前原生栈采样落在峰外，未取得该峰的Python栈，不能按维护日志无时间戳的文字定因。随后三段触发采样有单位错误：Apple Silicon的proc_pid_rusage时钟计数须乘mach_timebase_info的125/3才能转为纳秒。独立单线程CPU时间0.238592秒，同窗口内核计数换算后为0.238557秒；原未触发阈值不能作为峰值证据。最后20分钟校正后平均35.37%、峰186.52%，RSS从1,377,615,872到1,377,632,256字节。该窗RSS近乎不变，不代表CPU稳定在个位数。

同一PID下一段20分钟（含一条自然请求）校正后平均CPU 48.22%、峰197.75%，RSS由1,537,228,800增至1,566,064,640字节；两段间10分52秒未采样，增加159,596,544字节，不能据请求时间或无时间戳的维护日志认定分配者。四worker同一小负载连续四轮的独立3.14t实验，退出后的footprint约115、139、141、141MiB，未观察到每轮再增加完整工作集；不能据此解释真实20.94GiB。

07:53 PST仍是同一出生时间的旧版Gateway，RSS为2,678,702,080字节，physical footprint为2,660,552,448字节，两者只差17.3MiB。03:31与07:52的vmmap摘要中，tag100（IOAccelerator）驻留约从1.0G增至2.4G。该标签可来自Python分配器；无法据此区分存活对象、分配器保留或其他同标签分配，不相加共享页与虚拟保留。先前1.57GB是06:17 PST的RSS，不是此刻的footprint。

用户截图对应同一实际会话的03:38:47、03:40:35、03:42:45 PST三条完成记录。140.198秒一轮含七次模型调用118.286秒和一次窗口观察16.692秒；53.088秒一轮含三次模型调用39.633秒、准备FTS5.385秒、窗口观察0.979秒及read_artifact4.266秒。工具时间包含校验、handler及输出归档，不能称为纯磁盘读取。79.422秒的零工具问题只有一次模型调用75.899秒，其中首输出等待46.896秒、之后29.003秒；排队0.175秒、锁等待0.004秒。模型阶段包含调用链路，并非供应商内部推理计时。

实际会话verbose_level为off；模型端仍记录首输出增量，但公开chunk只在完整提交后发送正文。另确认TUI网络订阅的assistant_text_delta/reset/done缺消费接线，显式stream消费已在候选源码修复，用户默认配置与当前运行版本未变。只读归档定位另发现主索引负命中重复解析及历史发现线性工作，合成重现不等于本轮4.266秒的完整分摊。

共享延时线程在回调结束后保留局部call/fn/context，成功及异常两条弱引用回归均先失败；finally清局部引用后通过，调用方持有句柄的原语义不改。根3.12五文件78项、原生3.14.3t三文件12项通过。该修复未部署，不估算真实可回收GB。

四worker纯标准库六组隔离实验：3.14.3t对象弱引用全灭且worker退出后footprint仍约114MiB；标准3.14.4同负载约19–21MiB。只证明该分配形状下的宿主保留，不证明真实20.94GiB全部同因，也不支持直接回收线程作为解决方案。纯标准库FT同样出现IOAccelerator标签；mimalloc的Mach tag100与SDK该名称重合，标签本身不证明GPU分配。

## 当前验收约定

先完成审计补修及严格本地门，在用户指定的 2C4G Linux 主机验证基础功能和关键回归；不在那里做大规模资源压测。随后按正式升级链更新本机，记录客户端与 Gateway 的实际源码版本和安装路径，再复用已打开的十个 TUI。

模型分组为五个 OpenCode 的 `deepseek-v4.1-flash`、五个 `minimax-M3.1-FLASH`。复用已有模型配置，核验真实请求使用的 provider/model。选择下面一至两个用例作一轮测试即可，不要求每个用例各执行两次。

单轮运行约一小时或收集足够诊断证据。用户最新要求让现有任务自然收尾，不再发第二轮、也不主动中断；保留日志、运行账本与退出事实。产物完成度、游戏玩法完整度、画面质量不作为本轮验收指标。额度耗尽单独记录，不算框架容量缺陷；未知工具结果与资源未确认仍须调查。

## 长期资料的升级与恢复验收

本机大量长期资料按线上级资料对待。升级须保留原owner/home和配置，沿正式自动迁移及恢复入口完成旧数据加载，尽量不打断正常使用；不要求用户手动清理目录、重建个人资料或补账。下列均为待验证条件，不是已经做到或绝对无损的承诺，程序能启动也不能代替数据验收。

- 升级前后对同一owner做结构化盘点并实际加载核对：会话/完整任务历史与活跃任务、正式记忆及候选状态/版本、技能和插件的身份/版本/启用配置、模型provider/model与既有显式配置、监控及调度任务的身份/范围/启停状态。盘点记录数量、稳定ID、版本与摘要，不在报告中记录凭据正文。
- 对原有长期会话、记忆条目和组件做实际读取/加载核对，区分物理表示迁移与逻辑事实变化。partial/unknown、缺源和损坏须明确记录并沿正式恢复链处理，不能变成“空数据”或用新home掩盖迁移失败；监控/调度恢复不得重复触发旧任务。
- 迁移和恢复期间核对持续进展与对应入口预算，记录已完成和未完成范围；安装成功、启动成功或一条新会话成功，均不能证明旧资料已完整迁移和加载。

候选旧JSONL会迁移为HAMT manifest和记录家族，thread.task_ids改为最近128条及全部活跃项，并用分页索引保留完整历史，Compact散节点会迁移为SQLite节点仓。保留旧程序不足以回滚这些数据变化，此边界已告知用户。本轮全量备份按用户最新要求停止并清理，不再阻塞切换，未完成副本不作为恢复来源；继续核对原配置和组件，禁止清空或重建用户资料来制造通过。

## 首次迁移与稳态的分别验收

用户接受刚升级第一次进行一次性历史扫描/迁移时的短时卡顿，不要求所有首次迁移都在50毫秒内分片完成。受管handoff仍保持原每拍最多16个物理位置及50毫秒合同，此约定不放宽该入口预算。

首次迁移完成后，常规启动、发消息和轮询不得反复全历史扫描。需验证持久完成标记、完成后的重复操作、进程重启后的跳过行为，以及迁移中断后的正式恢复；不能只凭同一进程的缓存命中认定稳态通过。普通旧线程当前首次写入经initialize做一次全量初始化，已有manifest后跳过全量初始化；主控制方仍在复核中断与后继行为，尚未据此宣布升级或稳态通过，也不承诺程序所有时刻无卡顿。

升级首迁的扫描量、耗时、CPU/RSS峰值与临时磁盘开销单独记账；完成后的常规启动、重复发消息/轮询及重启恢复资源另记。长期历史十TUI的稳态评估不能用首迁峰值替代，也不能掩去完成后反复扫描的成本。

## 资源评估范围

本机已有历史按一名长期重度用户处理；以十个真实TUI并发为验收基础，不新增五千用户实压。远期目标为同时五千用户、每人20–100个主/子/后台代理、10–30个监控，以及数月至数年的Gateway、单会话上万次Compact。此次只用实际资源增量按用户要求相乘估算，外推不是已验证的集群容量。

LLM推理硬件不计入本服务预算。共享Gateway、已有后台负载与本次TUI增量分别记录；CPU采用区间累计时间差，内存注明RSS共享页重复计数。给出十TUI合计、每活跃TUI增量和停止后回落，并标记本机其它活动造成的归因限制。合理扩容须随实际活跃工作量增长，不能靠持续堆加硬件掩盖历史扫描、泄漏或无人消费的后台任务。

## 观察协议

每个被测会话仅提交一次原始需求。开发者只观察真实 TUI、Gateway、模型与工具账本，不替被测代理编辑文件、补产物、执行其任务或反复提示推进。发现框架缺陷时先保留复现证据，按原模块合同修复和回归，再明确记录是否重新开始对应实测。

记录总耗时、各进程及整体 CPU/RSS、内存压力、进程/线程/FD 数量、首响应与持续输出停顿、工具执行与等待、Compact 时间、自愈触发/成功/未收口事实以及停止后资源回落。停顿需区分模型供应等待、工具长执行、资源竞争和框架阻塞，不能只凭界面不刷新判定死锁。

升级前记录既有运行版本与进程归属，按正式排空和升级协议操作。测试结果必须绑定实际提交与真实模型身份；本地单测、Linux 基础回归、真实 TUI 观察和 GitHub CI 分别记账。

建议下一步：由主控制方在后继回归通过后沿正式启动链切换并核对原资料，用正式诊断观察后续自然请求；已完成的十TUI单轮不重复派发。分支CI独立并行，安装与服务切换保持单一负责人。
