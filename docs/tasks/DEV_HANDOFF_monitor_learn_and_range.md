## 1. 任务一【头号 · 治本】per-源「学判据 → 配过滤器 → 再监控」,扛住又花又杂的真实日志

**问题(真机实锤)**:摄取引擎靠【通用结构稀有度 + 少数派取值】做候选预筛。在【干净、结果端字段突出】的数据上能到 29/30;但换一套【又花又杂、混了高基数噪声字段(随机串/随机 ID)】的源,引擎**冷启动后候选归 0**——噪声把「结果端那一栏」的信号淹了,少数派车道几乎不触发(实测 escalated_minority≈1)。**真实世界的日志就是这样:几百种格式、一堆无关字段。** 所以「通用规则猜稀有」根本不够,这是产品硬短板。

**根子**:引擎**故意做成"笨的"**(只结构化计数、不理解内容——这是"代码禁自然语言判断"的铁律)。笨东西天生搞不定又花又杂的数据。真正能看懂花数据的是 **LLM**,但它读不过来那么快。矛盾:笨的快但不懂,懂的慢但读不过来。

**治本(learn → configure → monitor)**:
1. **【学】** 每个源接入时,先抓一批样本,由主代理(或一个专职校准子代理)**看懂**这个源:哪个字段是「结果端/结论」字段、什么取值代表「目标事件」、哪些字段是高基数噪声该忽略。产出一份**结构化判据 spec**:`{result_field 路径, target_values 集合, ignore_fields 清单, 可选阈值}`。
2. **【配】** 把 spec 灌进摄取引擎,让它对**这个源**只盯 spec 指定的字段/取值抬候选(精准盯),不再对全字段瞎猜稀有;忽略字段不进签名,防噪声淹信号。spec 随源持久化,**每源一份**。
3. **【盯】** 精准过滤后的候选 → LLM 逐条判 → 命中即报。
4. **【一源一学,扩到几百类】** 新源来先学一份 spec;格式漂移了重学。

**铁律(必须守,否则白做)**:
- **理解由 LLM 干,代码只结构化执行**:LLM 负责「看懂样本、定出判据」这一步(理解=模型);**输出必须是结构化 spec**(字段路径/取值/阈值),不是自然语言。引擎/过滤器**只按 spec 做结构化匹配与计数**,代码里零自然语言判断。这样既扛花数据、又不破铁律。
- **你写的是通用机制,别硬编码判据/内容**:你只实现「抓样本 → 喂 LLM 一个通用提示 → 拿回结构化 spec → 配过滤器」这套**通用机制**;代码/提示里**不写死任何具体源的判据或领域内容**——判据由 my-agent 运行时从样本自己推出(这样几百类日志才能一源一学、自动扩,不用人给)。
- **不许依赖源自报判据**:真实日志不会自带「哪个是目标」的说明。学习必须从**样本数据本身**推出判据,不能靠源提供的 schema 提示走捷径(自测台的源会把这类提示藏掉,逼你真学)。
- **别回退已对的**:通用稀有度/少数派车道在干净数据上是对的,保留作兜底;治本是**在其之上加 per-源学习配置**,不是推翻。

**验收**:用 §3 自测练功房(【花数据】那批):主代理先学出 spec、再监控 → 成绩单里**「引擎抬候选(召回)」显著上去**(目标不再被噪声淹、卡在引擎那环),端到端命中显著 > 0。**同一套练功房复跑才算数**(别换干净数据集自证)。

## 2. 任务二 并发公平:取消原有「全局总 10」,改为「每用户 8 + 全局 500」两层限流

**现状**:真实 /ask 链路的并发上限就是**全局工位 `gateway_request_workers`=10**——所有用户共抢这 10 个,一个用户猛甩就能占满、把别人饿死;而且**没有 per-用户上限**。per-租户配额代码(`LLM_TENANT_RPS`/`TOKEN_BUDGET`/admission,在 `worker_handler.py`)只挂独立 worker、**没接真实链路**,生产上等于没生效。

**要做**:把原有「全局总 10」这个限制**换成两层限流**,都接到**真实 /ask 网关链路**,都提配置、可调:
- **每用户「小坑」= 8**:单用户同时在飞上限 8(防一个用户独吞)。
- **全局「大坑」= 500**:总在飞上限 500(高天花板,超了排队/拒绝、不崩)。
- (8 和 500 是**先设的限制值,不是要打到这么多**。)

**架构判断(别做错)**:当前【单机、几十到几百用户】阶段,单进程 + 线程池够用(agent 活是 I/O 密集、等 LLM,不卡 GIL),**不要改多进程**;重点就是这两层限流公平。真要上千/万用户才走横向扩(企业级 Tier 已建),那是另一步。

**验收**:压一次 ~100 并发,量出:不崩、超 500 排队、单用户占不满全局(每人小坑 8 生效)、没有用户被饿死;硬编码提为配置。**「先量化再动手」**——网关 `GET /metrics` 探针已齐,拿数据说话。

## 3. 搞完后怎么测(监控为主 + 代码 + 并发,可一起做)

测试**都用中性数据**,你能看能测、自己闭环;**安全类日志由测试方单独复验,不在你这**。因为并发总坑到 500,下面三块**可以同时跑、互不饿死**。

### 3-A 监控测试(主 · 验任务一治本)
用中性「花数据」测试台 `scripts/watch_harness/messy_source_simulator.py`——**故意做得又花又杂,像真实日志**:多种格式 + 每源混高基数噪声字段(随机串/随机 ID) + 结果端稀疏目标 + 游标 `/pull` + 目标写旁路 answer-key。
```bash
# 1) 起花数据源(与运行机同网段;跨机先授权私网出站)
python3 scripts/watch_harness/messy_source_simulator.py \
    --base-port 8901 --sources 5 --rate 120 --duration 1800 --hits 24 --answer-key /tmp/mk.jsonl
# 2) 投监控任务(普通人口吻:盯这几个地址、发现目标即报、判据自己看记录里的结果端字段)
curl -X POST http://<运行机>:8420/ask -H 'Content-Type: application/json' \
  -H 'X-User-Id: u-montest' -H 'X-Channel: feishu' -d '{"kind":"ask","goal":"<盯守全文,含各源地址>"}'
# 3) 对账
python3 scripts/watch_harness/fleet_score.py --answer-key /tmp/mk.jsonl \
  <owner_home>/.../conversations/messages/ <owner_home>/tasks/
```
my-agent 应:**先学每源判据(spec)→ 配过滤器 → 盯 → 报**。看:
- **引擎召回**(目标进候选没):治本前在花数据上召回≈0(被噪声淹);治本后应**显著上去**。审计账 `watch_state/*.audit.ndjson` 可证「目标曾被抬为候选」。
- **命中率**:`fleet_score` 命中显著 > 0;漏的能归因到哪环(引擎没抬 / 抬了没报)。
- **同一套花数据复跑才算数**,别换干净数据集自证。

### 3-B 代码测试(顺带 · 验建站交付)
投普通人口吻建站任务(一个 solo 主代理自写、一个 dispatch 派子代理),看:交付行数、`output/` 成型可跑、task 根 `.agent_delivery/closeout.json` 的 `ok=True`、**dispatch 不比 solo 薄**(写边界自锁修复的延续)。

### 3-C 并发测试(验任务二)
**同时投 ~100 个任务**(混监控 + 建站,不同 `X-User-Id`),观察:不崩、超 500 排队、**单用户占不满全局(每人 8 生效)**、没有用户被饿死;每 30s 抓一次 `GET /metrics` 存档,用探针(排队等待/worker 忙数/在飞数)定位。

**判定方法(通用)**:会话 jsonl 逐轮 + 产物落盘位置 + closeout ok;监控命中在**会话上报面**看,别只看 output 目录。
