## 1. 任务一【头号 · 治本】per-源「学判据 → 配过滤器 → 再监控」,扛住又花又杂的真实日志

**问题(真机实锤)**:摄取引擎靠【通用结构稀有度 + 少数派取值】做候选预筛。在【干净、结果端字段突出】的数据上能到 29/30;但换一套【又花又杂、混了高基数噪声字段(随机串/随机 ID)】的源,引擎**冷启动后候选归 0**——噪声把「结果端那一栏」的信号淹了,少数派车道几乎不触发(实测 escalated_minority≈1)。**真实世界的日志就是这样:几百种格式、一堆无关字段。** 所以「通用规则猜稀有」根本不够,这是产品硬短板。

**根子**:引擎**故意做成"笨的"**(只结构化计数、不理解内容——这是"代码禁自然语言判断"的铁律)。笨东西天生搞不定又花又杂的数据。真正能看懂花数据的是 **LLM**,但它读不过来那么快。矛盾:笨的快但不懂,懂的慢但读不过来。

**治本(learn → configure → monitor)**:
1. **【学】** 每个源接入时,先抓一批样本,由主代理(或一个专职校准子代理)**看懂**这个源:哪个字段是「结果端/结论」字段、什么取值代表「目标事件」、哪些字段是高基数噪声该忽略。产出一份**结构化判据 spec**:`{result_field 路径, target_values 集合, ignore_fields 清单, 可选阈值}`。
2. **【配】** 把 spec 灌进摄取引擎,让它对**这个源**只盯 spec 指定的字段/取值抬候选(精准盯),不再对全字段瞎猜稀有;忽略字段不进签名,防噪声淹信号。spec 随源持久化,**每源一份**。
3. **【盯】** 精准过滤后的候选 → LLM 逐条判 → 命中即报。
4. **【一源一学,扩到几百类】** 新源来先学一份 spec;格式漂移了重学。

**铁律(必须守,否则白做)**:
- **理解由 LLM 干,代码只结构化执行**:LLM 负责「看懂样本、定出判据」这一步(理解=模型);**输出必须是结构化 spec**(字段路径/取值/阈值),不是自然语言。引擎/过滤器**只按 spec 做结构化匹配与计数**,代码里零自然语言判断。这样既扛花数据、又不破铁律。
- **不许依赖源自报判据**:真实日志不会自带「哪个是目标」的说明。学习必须从**样本数据本身**推出判据,不能靠源提供的 schema 提示走捷径(自测台的源会把这类提示藏掉,逼你真学)。
- **别回退已对的**:通用稀有度/少数派车道在干净数据上是对的,保留作兜底;治本是**在其之上加 per-源学习配置**,不是推翻。

**验收**:用 §3 自测练功房(【花数据】那批):主代理先学出 spec、再监控 → 成绩单里**「引擎抬候选(召回)」显著上去**(目标不再被噪声淹、卡在引擎那环),端到端命中显著 > 0。**同一套练功房复跑才算数**(别换干净数据集自证)。

## 2. 任务二 并发公平:每用户「小坑」+ 全局「大坑」接到真实链路

**现状**:真实 /ask 链路上只有全局工位(`gateway_request_workers`=10)和 agent 池(64),**没有 per-用户并发上限、没有全局在飞总量闸**。per-租户配额代码(`LLM_TENANT_RPS`/`TOKEN_BUDGET`/admission,在 `worker_handler.py`)**只挂独立 worker、没接真实链路**——生产上等于没生效。一个用户猛甩就能占满全局,把别人饿死。

**要做**:把 per-租户 admission 接到**真实 /ask 网关链路**,两层限流(都提配置、都可调):
- **每用户「小坑」**:单用户同时在飞上限,先设 **8**(暂定,只是先限住,不是要打到这么多)。
- **全局「大坑」**:总在飞上限,先设 **500**(暂定,高天花板)。超了排队/拒绝,不崩。

**架构判断(别做错)**:当前【单机、几十到几百用户】阶段,单进程 + 线程池够用(agent 活大多在等 LLM=I/O 密集,不卡 GIL),**不要改多进程**;重点就是这两层限流公平。真要上千/万用户才走横向扩(企业级 Tier 已建),那是另一步。

**验收**:压一次 ~100 并发,量出:不崩、超限排队、单用户占不满全局(小坑生效)、没有用户被饿死;硬编码提为配置。**「先量化再动手」**——网关 `GET /metrics` 探针已齐,拿数据说话。

## 3. 任务三 怎么自测:监控练功房(自助闭环)+ 铁律

有一个**常驻练功房**给你自助验证监控修复,你只管跑一条命令、读一张纯机制成绩单,看自己哪一环出问题,改了再跑:

```
bash mrange_run.sh [盯守分钟] [成绩单输出目录]
```

它会:注入一轮 my-agent 真机监控 → 盯守 → 采集 my-agent 的**机制遥测**(游标/候选计数/稀有度/线程/时刻,天生纯机制、不含内容)→ 对账隐藏答案 → 吐出:
- `scorecard-*.json`:**纯机制漏斗成绩单**——发射 N → 引擎抬候选 → 消费 → 上报;分环漏在哪(A 引擎没抬 / B 抬了没报出)+ 合成事件ID + 中性源标签(source-A/B)+ 机制级提示。
- `health-*.json`:**机制健康**——线程活性/收割在拉/错误/停摆。

**怎么读定位**:漏斗哪一环掉得多,哪就是瓶颈。治本任务一做对了,`引擎抬候选` 这环会明显上去(目标不再卡在引擎)。

**铁律(必须守)**:
1. **不许**去拉/curl 被监控的数据源接口本身,也**不许**看数据源的判据/格式说明——那是待判的数据内容,与你要修的机制无关(而且看了会被内容带偏)。
2. **不许**读 my-agent 的「内容侧」日志(子代理 spool 里的候选事件原文、会话里对事件的研判文字)。
3. 你**只读**:①纯机制成绩单 ②机制健康摘要。据此定位、改、再跑。
4. 这不是限制你——机制侧信息足够定位所有问题(成绩单已能指到具体环);目的是保证你判断的是**机制**,不被数据内容带偏。
5. 有一批**纯中性**的等价源(零具体领域内容、机制相同)供你理解「数据形状 + 机制」用,**可以看**;真练功房(自测跑的那个)机制一样但内容不能看。
