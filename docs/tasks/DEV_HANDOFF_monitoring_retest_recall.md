## 一、你做对的(别动,是地基)

- **主代理自由**:主任务 46 秒就把活委派给一个 long_running 子代理然后撒手,没被盯守占死。✅
- **真用盯守引擎**:5 个数据源各开一个 watch(不是裸拉),审计/spool/后台摄取都在转。✅
- **轻量记忆**:子代理逐源**学出判据、configure 了 source_spec**(result_field + 目标/常态词表)、
  写了 judgment_note。机制通。✅
- **判读质量**:凡是**递到模型眼前**的事件,判得很准——能读响应正文细节区分"真正生效 vs 看着像其实没生效"。✅
- **耐力(部分)**:watch 持续开、游标推进、上报数缓慢增长("DONE"是子代理形态假象,
  唤醒机制在续报)。✅ 但**慢,且越跑越多误报**(见下)。

## 二、两个真洞(要修)

### 洞 1【头号】引擎在模型看到之前就把要紧事丢了 —— 抓取率 32%

- 硬数据:定格 22 件要紧事,抓到 7、漏 15。**漏的 15 件里 14 件是"引擎从没 surface 它"**
  (审计 `escalated_pos` 并集里根本没有这些 seq),只有 1 件是"引擎抬了模型没报"。
  → **瓶颈在引擎的候选 surface,不在模型判读。**
- 逐源:A 源 0/2、B 源 0/4(且误报 5 条)、C 源 2/6、D 源 2/3、E 源 4/7。
  A/B 两源要紧事**一件没抬**,却把一堆迷惑项抬上去让模型误报。
- 根因(实证):
  1. **子串 spec 分不开"请求内容几乎一样、成败只在响应措辞里"的要紧事和迷惑项**。B 源 `rule_hits`
     全是 `normal_contains`(压掉 73 条),**`target_contains` 命中 = 0**——你配的目标词一次没
     命中过真要紧事。因为要紧事和迷惑项请求几乎一样,响应也都像"200 OK",区别是响应正文里
     一句"生效了 / 被挡住了"。子串匹配要么两个都中要么都不中。
  2. **冷启动读存量时判据还没学出来**。从 `since=0` 读的那批存量要紧事,是在子代理"学判据 +
     configure spec"**之前**流过去的,当时没有任何有效 surface 规则兜着 → 直接漏。
     (漏的 A-42/B-20/E-7 等时间戳都早于子代理开工时刻。)
  3. **多源判读积压把"正常量直通"顶回了降维分诊**。`full_read_per_pull=48` 配着,但 5 源并发、
     一个子代理判、`max_candidates_per_pull=8` → 判读积压 → `judge_headroom` 被吃光 →
     整批直通逐条读的路退回结构化粗筛 → 内容型要紧事被粗筛漏掉。
     (佐证:持久化 totals 里**没有 `escalated_full_read` 这个账**——直通路基本没落到账。)
- **这对"读大文件"(存量回扫)是重伤**:大文件本质就是一大批存量,会同时踩 1+2+3。

**修的方向(供参考,别照抄):**
- **存量/冷启动阶段:先学后读,或读存量时 surface 宁滥勿漏**——存量批不靠"还没学出来的
  结构规则"筛,先整批喂模型/或先抽样学判据再正式起游标,别在学会之前就把存量放走。
- **让"正常量直通"在判读积压时也别把内容型源整批降维**——积压时可以放慢(多派子代理分担、
  或存量宁可慢慢判),但不能"判不过来就退回结构粗筛把要紧事筛掉"。内容型源要留一条"每条
  都到模型"的通道(哪怕降速)。
- **多源要一源一子代理(头等结构问题)**:这次是**一个子代理独扛 5 个源**的拉取+判读,串行判
  必然积压,既顶回粗筛(根因3)又拖慢实时性。改成**一个数据源/一个接口/一份大文件 = 一个专属
  子代理**(各自开 watch、各自判、各自报,天然并行);单源量大时该子代理还能**再派孙代理**分片,
  保证每个源都实时不积压。
  - 参考 **终端应用 的派发模型**:一个委派任务 = 一个隔离子代理、多个并发跑、子代理可再派自己的
    子代理(就是它的 Task/Agent 工具那套"一任务一代理、可嵌套")。本仓库已有 `create_subagents`
    派发底座,是把盯守流接到"按源扇出"上,不是造新轮子。
  - 想看**可读的扇出/嵌套实现**去 `~/study-agent/all-agent/` 的开源体(通道运行时 / 长期助手 / 会话运行时);
    注意 `终端应用-main` 只是它的公开仓库(README/examples),agent 循环是打包码读不到。
- `max_candidates_per_pull=8` 对存量批太小,存量回扫时应能放大。

### 洞 2 精度 47%,且越跑越差 —— 硬迷惑项被当成功

- 8 条误报:
  - **3 条"状态码像成功、正文说没成"**:响应是成功类状态码,但正文里明说该操作实际被降级/改写/
    拦在后一层/未真正生效。模型只看状态码就报"成功",**漏读了正文里的否定语义那半句**。
  - **1 条张冠李戴**:把 A 事件的判断内容写到了 B 事件的 id 上(判对了内容,引用错了 event_id)。
  - **4 条随时间新增的误报**:子代理续报时又把 4 条迷惑项判成成功。**耐力续报在"多报噪声"
    而不是"补齐漏掉的要紧事"。**
- 修的方向:判"真正生效"必须让模型读全响应正文语义——正文表达"没真生效/被改写/被降级/被回退/
  被后置拦下"这类否定含义时,即使状态码是成功也不算数。
  **⚠️ 明确禁止的降级解法:把某几个固定字符串攒成黑名单硬编码"一票否决"。** 这既违反铁律
  (禁自然语言关键词匹配),又只能过这一套料——换套措辞、换个领域立刻崩,是假修复;要的是让模型
  真读懂正文语义。上报时 event_id 引用要和判读对象对齐(防串号)。

## 三、怎么复现(这是领域无关的能力问题,用中性料就能复现)

**别用任何专业领域的料。** 这能力的难点跟具体领域无关,任何"结果状态码看着成功、但正文里说其实
没真生效"的场景都能复现。比如:接口返回 `200 OK` 但正文 `{"result":"rolled_back"}` / `已超额丢弃` /
`未实际入账` / `命中缓存未执行`——状态码像成功,真没生效。造一批这样的中性事件就行。

- 5 个数据源的事件流,每源 `GET /pull?since=&limit=`,每条含 event_id + 一个来源标识字段 + request + response。
- **真正生效的事件很稀**(约 1/100~1/3000);真事件都带某个固定标识值,但**该标识上约 420:1 是
  "看着像其实没生效"的迷惑项**(靠标识蒙全报 → 报准崩)。真/假都返回 200 类状态,**区别只在响应正文措辞**。
- 任务:从 `since=0` 持续盯 5 源,把**真正生效**的挑出来上报 event_id;答案键旁路记录(agent 够不着)。
- 算分:抓到/漏/瞎报 + 逐源"引擎 surface 了没有"(拿审计 `escalated_pos` 对答案键 seq)。
