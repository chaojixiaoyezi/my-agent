## 1. 【头号】盯守转非阻塞后"睡死叫不醒":自唤醒到点不续跑

**问题(真机实锤)**:长时盯守任务,主代理跑几轮后按设计**转"非阻塞挂起、等提醒/事件叫回"**,并登记了循环自唤醒提醒。但**提醒到点后没有把任务重新拉起**——一次 20 分钟的真机盯守里,主代理跑约 4 轮后挂起,此后**整整 0 次续跑**(该请求全程只有 1 个 run);查 owner_home 的 `progress_policies/policy-*.json`,`next_due_at` **已过期约 280 秒仍未触发**。后台收割线程还在把新候选攒进 spool,但**主代理再没醒来消费+产出结论**,盯守等于中途停摆。

**后果**:候选在 spool 里越攒越多,没人消费,用户端零结论。这是"盯守出不了结果"的**头号根因**。

**方向**:打通"**提醒登记 → 到点 → 重新入队 → 主代理被拉起 → 真去读 spool 新候选并产出结论**"整条链。重点排查:到点的 policy 由谁消费、消费后有没有真的往网关 pending 里投一个续跑请求、`cli/gateway_loops.py` 的派发循环有没有把它派起来。参考已有 `wait_tool.py` 的提醒机制与派发循环——别新造一套。

**验收**:真机长盯守(≥15 分钟),该任务续跑次数 **> 1 且随时间稳定增长**(不是挂起后归零);`policy-*.json` 的 `next_due_at` 到点后短时内出现新 run。

## 2. 【头号】结论"不挨条报":出聚合概述,不出逐条结论

**问题(真机实锤)**:主代理盯守时,发现目标后产出的是**聚合口径**("目标计数在涨 / 某车道候选 +N / 仍在被正确捕捉"),**而不是逐条结论**(哪条 `id`、在哪个源、凭什么判成目标)。真机:引擎已把**约一半目标抬成了候选**(审计账可证),但主代理**逐条上报到用户面的 ≈ 0**(一整轮 22 个目标里报出 0~1 条具体 id)。

**后果**:就算候选被抬出来了,用户拿到的也只是"有一些在涨"这种没法行动的概述,**收不到"具体是哪条"**。

**方向**:**发现一条目标即产一条结构化结论**(`id` + 依据),经 `record_finding` 落增量结论账,并推到用户面;**禁止用聚合概述替代逐条上报**。`record_finding` 机制已存在,但盯守链路现在没把它用起来——接上它。

**验收**:真机盯守里,被引擎抬为候选的目标,**逐条出现在结论账 / 用户上报面**(带具体 id 与依据),而非只有聚合数字。

---

## 3. 批量逐条产出"掉约 1/5":长列表输出提前收尾

**问题(真机实锤)**:让主代理对一批条目**逐条产出结论**(枚举型任务),输出到一半会**提前收尾、后面条目直接跳过**——真机:200 批 × 每批 50 条,约 **19% 的条目没有任何结论行**(不是判错,是压根没产出);同一批往往前 ~40 条有结论、后 ~10 条空缺;两次独立跑都稳定掉 ~19%。

**后果**:搁盯守上,等于**约 1/5 的事件被静默漏掉**(既不判也不报)。与 §1/§2 同属"结论产不全/送不达",一并治。

**方向**:逐条产出要**"报满不早停"**——可选:分块产出(每块产完自查条目数对齐、缺口补产)、产出前后校验"应产 N 条、实产 M 条,M<N 则续产"。排查是模型长列表自行收尾、还是产出/截断层的上限。

**验收**:同样"N 条逐条判"的任务,产出条目数 **≈ N(缺口 < 2%)**,不再稳定掉两成。

## 4. 引擎召回:结果端是"文本消息"时只约 30%(引擎侧残留,非头号)

**问题(真机实锤)**:当每条记录的"结论字段"是**一句带高基数尾巴的文本消息**(而非布尔/枚举取值)时,引擎抬候选的召回只有 **~30%**;而结果端是布尔/枚举时是 **100%**。两套**同结构、不同表皮**的真机数据一致复现(一组 4/14、另一组 5/14 文本源),证明**与内容无关、由结构决定**。

**根因**:此形态下主代理学出的判据(常态记号清单)**易漏列**,导致"常态之外"过度匹配、把稀疏真目标挤出候选名额;引擎纯结构无法兜底(文本被高基数尾巴带得折叠成同一签名,真目标与漏列常态在引擎眼里一样)。

**方向(上一棒已标 roadmap)**:对结果端文本**按分隔符取"首记号/结论记号"、做窗口频次统计**,让稀有结论记号优先于漏列的高频常态。这仍是**纯结构(切分 + 计数,零自然语言判断)**,不破铁律。

**验收**:同一套"文本结果端"真机数据,文本源召回从 ~30% 显著上去;布尔/枚举源保持 100%。
