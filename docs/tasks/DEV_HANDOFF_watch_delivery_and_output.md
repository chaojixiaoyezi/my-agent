## 1. 【头号】盯守转非阻塞后"睡死叫不醒":自唤醒到点不续跑

**问题(真机实锤)**:长时盯守任务,主代理跑几轮后按设计**转"非阻塞挂起、等提醒/事件叫回"**,并登记了循环自唤醒提醒。但**提醒到点后没有把任务重新拉起**——一次 20 分钟的真机盯守里,主代理跑约 4 轮后挂起,此后**整整 0 次续跑**(该请求全程只有 1 个 run);查 owner_home 的 `progress_policies/policy-*.json`,`next_due_at` **已过期约 280 秒仍未触发**。后台收割线程还在把新候选攒进 spool,但**主代理再没醒来消费+产出结论**,盯守等于中途停摆。

**后果**:候选在 spool 里越攒越多,没人消费,用户端零结论。这是"盯守出不了结果"的**头号根因**。

**方向**:打通"**提醒登记 → 到点 → 重新入队 → 主代理被拉起 → 真去读 spool 新候选并产出结论**"整条链。重点排查:到点的 policy 由谁消费、消费后有没有真的往网关 pending 里投一个续跑请求、`cli/gateway_loops.py` 的派发循环有没有把它派起来。参考已有 `wait_tool.py` 的提醒机制与派发循环——别新造一套。

**验收**:真机长盯守(≥15 分钟),该任务续跑次数 **> 1 且随时间稳定增长**(不是挂起后归零);`policy-*.json` 的 `next_due_at` 到点后短时内出现新 run。

## 2. 【头号】结论"不挨条报":出聚合概述,不出逐条结论

**问题(真机实锤)**:主代理盯守时,发现目标后产出的是**聚合口径**("目标计数在涨 / 某车道候选 +N / 仍在被正确捕捉"),**而不是逐条结论**(哪条 `id`、在哪个源、凭什么判成目标)。真机:引擎已把**约一半目标抬成了候选**(审计账可证),但主代理**逐条上报到用户面的 ≈ 0**(一整轮 22 个目标里报出 0~1 条具体 id)。

**后果**:就算候选被抬出来了,用户拿到的也只是"有一些在涨"这种没法行动的概述,**收不到"具体是哪条"**。

**方向**:**发现一条目标即产一条结构化结论**(`id` + 依据),经 `record_finding` 落增量结论账,并推到用户面;**禁止用聚合概述替代逐条上报**。`record_finding` 机制已存在,但盯守链路现在没把它用起来——接上它。

**验收**:真机盯守里,被引擎抬为候选的目标,**逐条出现在结论账 / 用户上报面**(带具体 id 与依据),而非只有聚合数字。

## 3. 批量逐条产出"掉约 1/5":长列表输出提前收尾

**问题(真机实锤)**:让主代理对一批条目**逐条产出结论**(枚举型任务),输出到一半会**提前收尾、后面条目直接跳过**——真机:200 批 × 每批 50 条,约 **19% 的条目没有任何结论行**(不是判错,是压根没产出);同一批往往前 ~40 条有结论、后 ~10 条空缺;两次独立跑都稳定掉 ~19%。

**后果**:搁盯守上,等于**约 1/5 的事件被静默漏掉**(既不判也不报)。与 §1/§2 同属"结论产不全/送不达",一并治。

**方向**:逐条产出要**"报满不早停"**——可选:分块产出(每块产完自查条目数对齐、缺口补产)、产出前后校验"应产 N 条、实产 M 条,M<N 则续产"。排查是模型长列表自行收尾、还是产出/截断层的上限。

**验收**:同样"N 条逐条判"的任务,产出条目数 **≈ N(缺口 < 2%)**,不再稳定掉两成。

## 4. 引擎召回:结果端是"文本消息"时只约 30%(引擎侧残留,非头号)

**问题(真机实锤)**:当每条记录的"结论字段"是**一句带高基数尾巴的文本消息**(而非布尔/枚举取值)时,引擎抬候选的召回只有 **~30%**;而结果端是布尔/枚举时是 **100%**。两套**同结构、不同表皮**的真机数据一致复现(一组 4/14、另一组 5/14 文本源),证明**与内容无关、由结构决定**。

**根因**:此形态下主代理学出的判据(常态记号清单)**易漏列**,导致"常态之外"过度匹配、把稀疏真目标挤出候选名额;引擎纯结构无法兜底(文本被高基数尾巴带得折叠成同一签名,真目标与漏列常态在引擎眼里一样)。

**方向(上一棒已标 roadmap)**:对结果端文本**按分隔符取"首记号/结论记号"、做窗口频次统计**,让稀有结论记号优先于漏列的高频常态。这仍是**纯结构(切分 + 计数,零自然语言判断)**,不破铁律。

**验收**:同一套"文本结果端"真机数据,文本源召回从 ~30% 显著上去;布尔/枚举源保持 100%。

### 6.1 §1 盯守"睡死叫不醒" —— 已修

**根因(比文档更精确)**:后台唤醒循环只 tick「进程内最近活跃 owner 登记表」(`ActiveOwnerRegistry`)。该表是**易失**的——网关重启清零、LRU 逐出、且**只有新入站请求才补记**。长盯守转非阻塞挂起期恰恰没有新请求 → scoped owner 的到点 `progress_policy` 从此**无人消费**。真机现场坐实:`u-mix-6` 的 policy `enabled=True`、`next_due_at` 过期 2 万秒,spool 攒 445 个候选没人读。这不是 wait/派发循环本身坏,是"哪些 owner 该被 tick"的发现机制断了。

**修复**:新增磁盘级 owner 唤醒发现 `agent/owner_wake_discovery.py`——后台循环按 `background_owner_wake_rescan_seconds`(默认 120s)周期性扫 `owners/providers/*/{users,groups}/*`,把「有 enabled 进度策略 / 待处理唤醒信号」(纯结构化:读 policy 文件 `enabled` 标 + `wake_queue/{urgent,normal}` 有无文件)的 owner **种回**活跃登记表。重启/逐出后自愈,登记表退化为热路径加速。接线在 `cli/gateway_loops.py` `_BackgroundMainSupervisor`(启动即扫一次 + 按间隔重扫)。

**附带机制修**:`progress_policy_retirement.py` 原来收口(ok=True)无条件退休本任务**所有**提醒,把**窗口未走完的盯守 policy** 也误杀——模型判读层若在盯守窗口未满时提前收口(§A-1 圈禁、不归本棒改判读),盯守唤醒链就断了。改为:owner 名下有「窗口未满且未 close」的盯守时(纯结构化:`opened_at`+`watch_window_seconds`+`closed`),不退休 watch 登记的提醒(`metadata.watch_run_id` 辨认),非 watch 提醒照常退休。

**真机回归**:隔离 home + 常驻网关(8423)+ 种一个「enabled、next_due_at 过期 240s」的 scoped-feishu owner 进度策略(复刻真机睡死),启动网关 → 日志出现 `wake-pending owners seeded from disk: 1` → **该任务续跑 4 轮**(此前恒 0),`next_due_at` 到点后短时内出新 run。网关**中途重启**后磁盘发现再次生效、续跑不断。

### 6.2 §2 结论"不挨条报" —— 已修

**根因**:两处断。① 盯守唤醒轮的工具集(`SCHEDULED_BACKGROUND_ALLOWED_TOOLS` / `SUBAGENT_INTEGRATION_ALLOWED_TOOLS`)**根本没有 `record_finding`**——模型字面上记不了逐条账,只能出聚合概述。② 即便模型口头逐条,送达层没有兜底,聚合正文一句"计数在涨"就把逐条结论盖掉了。

**修复**:① 把 `record_finding` 加进两个唤醒轮工具集 + 提示词(`_scheduled_continuation_prompt` / `PULL_GUIDANCE`)明写「一条命中=一条结论,逐条入账再逐条报,禁止聚合替代」。② 送达机制层兜底:`conversation/runtime.py` 后台轮跑完后,把**本轮新入账**的逐条结论(纯搬运 id+claim+证据指针,零定性)自动附进出站消息(`_content_with_findings_delta`);正文若以内部信号记号开头(会被投递枢纽整条拦),结论块单独出站,保证逐条结论到用户面。**真机坐实的关键**:`record_finding` 属 deferred 类(collaboration),网关轮 catalog 里没有 → 模型转而用 `write_file` 逐条落 `output/findings.jsonl`(自定 schema:event_id + ts 字符串时戳,无 claim)。送达层因此**两条通道都读**(record_finding 的 `work/shared/findings.jsonl` + 模型的 `output/findings.jsonl`)、schema 容忍(id/finding_id/event_id 任一标识,created_at/ts 任一时戳,claim 缺则从 result_field/outcome/confidence 合成一行)、跨账本按标识去重——无论模型用哪个工具落逐条账,都能送达用户面。

**真机回归**:文本源盯守(`u-watch3`,窗口 600s),主代理逐条入账 **6/6 真命中**(EVT-000150/450/900/1500/2200/3000,与 ground truth 完全一致),每条带 `event_id`+结果端依据+引擎判据。实录一条:
```json
{"event_id":"EVT-000150","outcome.log":"diverted ref=e465ff8e9b t=150","first_token":"diverted",
 "normal_tokens":["accepted","returned","retried","queued"],"hit":true,
 "confidence":"minority_field_value: token=s1:diverted, count=1/151 in window"}
```
`s1:diverted` 正是 §4 首记号车道抬的候选记号(证明 §4 在真机 spec 路也在跑)。把这份真机 `output/findings.jsonl` 直接喂送达层 `_content_with_findings_delta`,聚合正文"候选计数在涨"后被机制层附上 **6 条逐条结论**(id+依据),坐实"哪怕模型 write_file 落逐条账、送达层照样把逐条推到用户面"。

### 6.3 §3 批量逐条产出"掉 ~1/5" —— 已修

**根因**:纯文本响应撞输出上限(`stop_reason=max_tokens`)时,此前**不被视为截断**(截断检测只认"半截 tool_use 参数缓冲"),半截枚举被当完整交付,尾部条目静默丢。

**修复**:`backends/base.py` 纯文本响应自动续写——`stop_reason∈{max_tokens,length}` 且无 tool_use 块、无半截工具缓冲时,以已收文本作 assistant 预填续问、原文接续拼接;有界 3 轮;续写请求失败保留已收文本(绝不丢已有产出)。半截 tool_use 参数仍走原 native 截断恢复,互不干扰。`ModelResponse` 增 `stop_reason` 字段(观测)。

**真机回归**:强制 `max_tokens=2500` 的网关(8424)跑「逐条输出 120 条」→ 触发续写 → **120/120 全到、0 缺口**(不改上限的 16314 下 220 条也 220/220)。单测 8 例覆盖:触发续写并拼接、end_turn 不续、有界 3 轮、续写失败保底、半截工具不误续、非流式 stop_reason。

### 6.4 §4 引擎文本结果端召回 ~30% —— 已修

**根因(比文档更精确,真机复现坐实)**:结果端是"结论词+高基数尾巴"的文本消息时,信号在**首记号**、噪声在尾巴。两条路都因"要求整串相等"而失明:

- **通用兜底车道**:整值折叠成同一高基数签名(`s:*`),真目标与常态在引擎眼里一样;
- **spec 车道(测试方实测的路)**:模型学出的 spec 常把裸词常态清单(`normal_values=[accepted,returned,…]`)配到整句文本字段上。整句永不等于裸词 → `outside_normal` 把**每条**都判成"常态之外" → 候选洪泛(真机 2621 条),`max_candidates_per_pull` 一截,稀疏真目标全被挤进 overflow,模型收不到 → 这才是那 ~30% 的真身。

**修复(两处,共用一个纯结构 helper)**:新增 `ingestion/text_tokens.py` `head_token()`(按空白/结构符切首记号,纯字面)。
- `engine.py` 少数派取值通道增**首记号子车道**:高基数文本按首记号做窗口频次,先过首记号基数闸(结论词低基数才参与,trace/id 类高基数首记号该字段关死)。
- `source_spec.py` 集合匹配(`target_values`/`normal_values`)增**首记号兜底**:整串不命中时再拿首记号比一次——裸词常态清单于是能正确匹配文本字段的结论词(常态句判常态、目标句判候选),洪泛消失。裸词/枚举字段 canon 本身即裸词、行为不变。全程纯切分+集合成员,零自然语言。

**真机回归(离线对照 + 真机 spec 路,都不依赖模型判读)**:同结构不同表皮的稀疏目标数据(14 目标、300s 滑窗、240 事件/pull、候选上限 8)。
- **spec 路(测试方那条,决定性)**:裸词 `normal_values` 配文本字段,**修复前召回 4/14=29%**(≈文档 ~30%,候选洪泛=800 把真目标挤进 overflow)、**修复后 14/14=100%**(候选量 800→17,真目标不再被淹)。
- **无 spec 通用路**:摘掉首记号车道=修复前 text **0%**(我的合成噪声全字段高基数、比 30% 更极端)、带修复 **100%**;enum 结果端两路恒 **100%**(裸词==canon,行为不变)。

单测:`test_ingestion_source_spec.py` 加首记号兜底 2 例(normal/target 裸词匹配文本首记号、枚举字段行为不变);`test_ingestion_engine.py` 加首记号车道 3 例(稀有文本结论抬候选、高基数首记号关闸、画像快照恢复)。

## 7. 测试方独立复验 —— 机制四块已改善,但端到端仍不可用(下一棒靶子)

> 复验 `7a64e277`(常驻网关 + 真模型 + 真实长盯守):**机制层四块确认都改善**——§1 磁盘唤醒发现上线(启动日志 `wake-pending owners seeded from disk`)+ 盯守持续(单 run 内 37 次拉取,不再 4 轮就挂死);§2 逐条结论真落账(`output/findings.jsonl` 带 `event_id`+`result_field`+`reason`,不再只出聚合概述);§4 引擎文本结果端召回 **~30%→53%**。**但监控端到端仍收不到正确结果**,卡在下面两条【本次修复范围之外】的问题。

### 7.1 【头号·下一棒】主代理"学判据学错":样本无目标时把常态取值当目标

**现象(真机实锤)**:文本结果端源,真目标极稀疏,主代理 `sample` 阶段拉到的样本里往往**一条真目标都没有**。此时模型不按"把可见取值全当常态、盯常态之外"来,而是**从可见取值里挑一个次常见的当 target**——真机实录:模型把某个**常态取值**配成了 `target`,于是逐条报出的每一条都是该常态(全误报),真目标全漏。**funnel B 因此仍 ≈ 0(送达机制是通的,送出去的判据是错的)。**

**根因**:这是【判据学习】层(模型从样本推 target),不是机制层。§6 那四块修的是"机制";"判据学得对不对"是另一层。上一棒 doc 给过 guidance("样本没目标别猜 target、把常态列全、盯常态之外"),但模型**不稳定遵循**。

**证据(真机 u-verify2,常驻网关 + 真模型,同结构中性花数据,24 个真目标)**:
- 引擎侧 funnel A(抬为候选)**14/24 = 58%**——目标大多被引擎抬出来了。
- 但 `output/findings.jsonl` 落账 **4 条,reason 全部是"结果端字段含【某常态取值】，命中"**;把该常态取值配成了 target。对账:这 4 条 event_id **全部非答案目标(误报)**,answer-key 里的真目标**逐条上报命中 0/24**。
- 即:**引擎抬出来了(58%),但主代理配错 target、逐条报出的全是常态 → 用户端真目标 = 0**。

**方向**:①「样本无目标」这一情形更强制地收敛到"只配 `normal_*`、不配 `target_*`"——结构化判定 sample 是否可能全是常态(目标取值频次为 0 / 取值基数与分布),据此在 `configure` 侧拒配 target、只留常态判据。②候选入账前经**二次逐条研判**(§A-1 证明逐条研判能力强、误判≈0),把"配错的 target"在研判环挡掉再落 findings。**②是首选,见 §7.5 推荐路子。**

### 7.2 主代理有时【绕过内置盯守工具、自写轮询脚本】(判据还错)

**现象(真机实锤)**:同一个盯守任务,主代理有时**不用内置 `watch_stream`,自己写脚本轮询**,且脚本自定判据错(把常态当命中、海量误报)。提示里加一句"必须用 watch_stream"后才回到内置机制。

**证据(真机 u-verify,同任务未加强制提示)**:任务 `work/` 目录下出现主代理**自写的 `poll_streams.py` + `hits.log`**;`hits.log` **50419 行**,全部把**同一个常态取值**当命中(海量误报);该 run **0 个 `watch_stream` 调用、0 spool 候选**(完全没走内置摄取)。加"必须用 watch_stream"后重投(u-verify2):**37 次 `watch_stream` 调用、774+ 候选**,走回内置机制。

**后果**:一旦绕过,§1–§4 的机制修复**全用不上**;自写判据又不可靠。

**方向**:盯守任务的提示词/工具装配更强地把主代理**导向内置盯守机制**(而非放任自写脚本);排查 §2 改动是否无意间弱化了走 `watch_stream` 的引导。

### 7.3 引擎侧残留:文本结果端召回只到 ~53%(布尔/枚举更易)

**现象 + 证据(真机 u-verify2)**:§4 首记号车道把文本结果端召回从 ~30% 提到 **8/15 = 53%**,但**仍有近半没被抬为候选**;结构化的布尔/枚举结果端天然更易(接近满)。即便 §7.1 判据学对了,文本源引擎召回也只有一半——**§4 改善了、没到位**。

**方向**:继续加强首记号频次车道对"结论词稀有度"的识别力(越稀的结论词越该优先抬);或对文本结果端源自动放大候选名额上限(该源目标天生稀、名额别卡太死)。

### 7.4 待复验:§3 批量输出完整性(修复方已单测+自压,测试方本轮未真机独立复验)

§3(长列表输出掉 ~1/5)修复方以单测 8 例 + 强制 `max_tokens` 网关压测 120/120 佐证。但**测试方本轮真机监控没干净触发该路径,未独立复验**。下一棒验收时,用"逐条判 N 条"的批量真机任务**一并复验产出条目数 ≈ N(缺口 < 2%)**。

### 7.5 【推荐治本路子】把"先学判据"换成"引擎宽抬 + 主代理逐条重判"

复验交叉坐实两件事:
- **§A-1**:把候选**逐条丢给主代理判**,它判得**极准**(大规模硬数据 F1 0.88、误判 ≈ 0)。
- **§7.1**:让主代理**从样本自学判据**,它学得**不稳**(样本没真目标就把常态当 target)。

→ 结论:**别在"学判据"这个不稳的环节上使劲**。治本首选把链路改成:**引擎用宽松结构规则(稀有度/首记号)多抬候选(宁多勿漏)→ 主代理对每条候选用它强的判断力逐条重判、判是目标才 `record_finding` 上报**。这样**绕开不稳的"学判据"、直接用稳的"逐条研判"**,§7.1 的误报和漏报同时解掉。判据可保留作"引擎侧宽筛"用,但**最终是不是目标由逐条重判说了算**,不由学出来的 target 说了算。
