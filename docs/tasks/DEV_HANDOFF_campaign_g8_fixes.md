## 问题 A · 假需求能被标"完成",污染对账正确性　【优先级最高 · 可干净修】

### 现象(前因后果)

清单自动种子里,除了真功能项(req-01 用户登录、req-09 通知……),还会混进几条**非功能的约束碎片**——任务文字里"别用占位、别省略、别留 TODO、别写半截"这类叮嘱,被枚举器当成条目种了进来(req-21~24)。

同一个大工程任务、两个用户并行,对这 4 条约束碎片的处理**分裂了**:

| 用户 | req-21~24(别用占位 / 别省略 / 别留TODO / 别写)| 对不对 |
|---|---|---|
| u-gc1 | 4 条全 **skipped** | ✅ 对(约束碎片本就不是交付物,跳过合理)|
| u-gc2 | 4 条全 **done** | ❌ 错(把叮嘱当成"做完的功能"计入了)|

→ u-gc2 的 24 项里凭空多了 4 条假"完成",**对账数字虚高、且两个用户各摇一边**——上一棒想消除的"done / pending / skipped 三态摇摆"根本没消除。

### 证据

`docs/tasks/evidence/campaign_g8/01_02_coverage_evidence.txt` 顶部:同一 4 条 id,u-gc1 全 `skipped`、u-gc2 全 `done`,一字排开。

### 根因

上一棒加的"done 证据闸"判据是 **"evidence 字段非空即放行"**。这太软:模型给约束碎片标 done 时,随手写一句**看着像、实为填充**的话("已确保无占位""全程无省略")就把 evidence 填非空了→闸门放行→假需求照样 done。**"非空" ≠ "真功能交付证据"**,闸门分不清一句场面话和一个真产物。

### 修法方向(结构化 / 守铁律)

把"证据非空"升级成 **"证据必须指向一个真实存在的交付产物"**(结构信号:产物路径 / artifact id **存在且非占位**,复用已有的占位检测)。逻辑链:

- 真功能项(req-09 通知)标 done → 能指出对应产物文件(真实存在)→ 放行。
- 约束碎片(别用占位)标 done → **指不出任何产物**(它本就不对应交付物)→ 闸门拒绝,只留一条出口:**标 skipped + reason**。

这样约束碎片在结构上**无法**被标 done(拿不出产物),分布强制收敛到 skipped,两个用户从此一致。判据全是结构信号(产物存在性 / 占位检测),**不碰自然语言**。

> **别做**:别去用关键词判断"这条标题是不是约束碎片"(NL,破铁律)。改判据只加在**证据端(产物是否存在)**,对所有枚举项一视同仁。

### 验收(真机由测试方跑,你先本地保证判据正确)

同一 24 模块大工程、2 用户并行,复跑:两个用户的 req-21~24 **都稳定 skipped**(不再一个 done 一个 skip);真功能项(能拿出产物的)照常 done、不误伤。

## 问题 B · solo 路对账少认:上一棒修的是"派工路",没覆盖主代理自己干的活　【谨慎 · 极易破铁律】

### 现象

u-gc2 这个大工程,**主代理基本是自己 solo 干**(前后端都建了:通知 `NotificationsPage.tsx` + 后端 `notification.py` / `email_notification.py`,还有 Dashboard、Settings、Board、Tasks……~20 个模块的真代码文件),但:

- coverage **卡在 12/24**(真功能项只认到 8 个:req-01~07 + req-09),req-08、req-10~20 这 **十几个模块文件都建了、却没被 credit**。
- 它派的 **5~6 个子代理各自产出代码文件 = 0**(活全在主 run 里,子代理是空壳 / 打杂)。
- 上一棒新加的"后代账本自声明"credit 路 **触发 0 次**。

### 证据

`docs/tasks/evidence/campaign_g8/01_02_coverage_evidence.txt` 中段:u-gc2 归因统计全是 `requirement-enumeration`(=主代理自打勾)+ 2 条 `covers-binding`,**后代账本 0**;6 个子代理代码文件全 0;通知模块的前后端文件真实存在。

### 根因

上一棒三条对账 credit 通道(covers-id 绑定 / 子代理树归并 / 后代账本自声明)**全是冲"子代理干的活"设计的**,主代理自己在主 run 里 solo 干的活**一律不 credit**("solo 不动"是它明写的设计)。solo 的打勾**只能靠模型自己去调 task_progress**——而模型打勾又懒又漏(u-gc1 的模型全打了→24/24,u-gc2 的模型漏了一半→12/24)。这一轮活恰好几乎全在 solo、且没触发"递归乱派几百子代理"那种上一棒针对的病态场景,所以后代账本一次没 fire。

### 修法方向(**先读"别做",这题极易翻车**)

- **别做(否则破铁律)**:别去建"主 run 的 output 文件 → 对应哪条 req"的自动映射来补打勾——那必然要拿文件名 / 内容和 req 标题做**关键词 / 语义匹配**(NL),**直接违反铁律**,且会制造假 credit。这条路**堵死**。
- **该做(结构 / 行为侧)**:solo 大工程的完整性,本质得靠**返工门 + 续推(#3)把模型一直摁在"还差 X 项、去补做 / 补打勾"上,直到模型自己如实打勾**。所以这题的正解不是"新开一条 solo 自动 credit 机制",而是**确认 #3 的返工门在 solo 长任务上能持续推到清单如实闭环**(u-gc2 被推着从 7→12 是好苗头,但**停在 12 没到底**——续推的耐力在 solo 大工程上还不够久)。
- **诚实边界**:solo 打勾天然依赖模型行为,这是"如实但可能不全"的**稳妥方向**(它只会少认、不会假认;精度那头没问题)。修的目标是**让返工门把"少认"一直暴露、一直催,直到模型补齐**,而不是偷偷替模型打勾。

### 验收

同一 24 模块大工程、2 用户并行:solo 为主的用户,返工门能**持续**把"还差哪些"如实回报、**一直推到清单闭合或明确到底**(不再干到一半 12/24 就熄火);打勾项的 evidence 都指得出真产物(与问题 A 同源);**全程零假 credit**(不许为了好看自动替 solo 打勾)。

## 问题 C · 长时盯守召回上不去(#4 未达标)　【诊断中 · 等测试方 8 小时实验结论再定修法】

### 现象

盯守任务要求"把记录流里的【目标事件】(少数派)一条不落地上报"。g8 用的是**高速记录流**(每秒几十条),两个用户实测(对"自己捞进待判队列的目标"为基数的精确召回):

| 用户 | 召回(报对 / 已捞进队列的目标)| 精度(报对 / 所报)| 备注 |
|---|---|---|---|
| u-gm1 | **65%**(460 / 713,漏 253)| 99%(误报仅 5)| 健康但仍漏三成 |
| u-gm2 | **43%**(213 / 491,漏 278)| 98% | **开头约 40 分钟完全停摆**(啥也没捞),后半才苏醒 |

- **精度极好**(误报个位数,不瞎报);**召回是短板**(而且这还只是"对已捞进队列的目标"的召回,真流的端到端召回更低,因为队列本身只截到了流的一部分)。
- 召回随时间在爬(u-gm1 从 55%→65%)——说明它在**追赶积压**,但高速流下**积压涨得比追得快,永远追不平**。
- u-gm2 还暴露一个**冷启动停摆**(某用户开头 40 分钟零动作)的独立毛病。

### 证据

`docs/tasks/evidence/campaign_g8/03_monitoring_recall.txt`(精确召回)、`03b_firehose_trajectory.log`(整条时间线,u-gm2 前 40 分钟全 0)。

### 诊断结论(8 小时低速实验实测,已定性 —— 见 `04_lowrate_recall_timeline.txt`)

测试方把流降到每用户 ~3 条 / 秒(慢到 LLM 绝对判得过来),跑长时盯守。**结果:召回照样趴在 ~8%(u-lm1)/ ~5%(u-lm2),而且随时间还在缓慢往下掉**(u-lm1 8.5%→8.1%,u-lm2 5.3%→4.4%)。往下掉是关键信号:说明它**越跑越落后、根本追不上**,不是"慢慢会追平"。

**所以 #4 不是吞吐性质(不是 LLM 判读慢),是机制 bug——而且 bug 在【摄取 / pull】环,不在【判读】环**。把引擎内部拆开看死死指向这里:

- `consumed ≈ funnelA`、backlog 一直很小(~90)→ **判读这步没问题**:它把 pull 进篮子的基本都判了,篮子里的目标报对 ~78%、精度 96~98%(u-lm1)。
- 但 `funnelA`(pull 进篮子的量)**只占整条流的 ~8%** —— 每用户 ~3 条 / 秒的流,pull 环只摄进来 ~0.25 条 / 秒,**92% 的流从没被拉进来过**,自然无从判、无从报。
- 端到端召回 ≈ 摄取覆盖 8% × 判读 78% ≈ 6~8%,与实测吻合。
- 还有两个伴生病:①**端点不公平**:5 个地址死盯 1 个(A ~27%),其余 4 个饿死(3~5%);②**u-lm2 判读精度崩**(误报从 82 一路涨到 568、精度掉到 30%)——这是 per-用户判读质量方差,和摄取瓶颈是两回事。

**要点:上一棒为 #4 改的"判读配额 / judge_headroom"是【判读】环——改错环了**(判读本就不是瓶颈),难怪没用。

### 证据(诊断)

### 修法方向

> **⚠️ 最重要 · 根本设计错误(用户 2026-07-07 强调"很严重"):禁按百分比/频率过滤,必须按内容研判。**
> 引擎那个"某取值在窗口里出现超 X% 就当常态、免疫/丢弃"的机制(`outside_normal_common_value_pct`),**按百分比/频率过滤这件事本身就是错的**——把 2% 调成 25% 还是同一个病(只换数字不治根),真事一旦频繁出现照样被当"太常见"整批扔。
> **正确做法=按内容研判**:系统应看【请求 + 响应的形态】(如"请求长这样、响应不是那样")→ 判定这一类是噪声还是真事 → 针对这一类**建一条内容过滤规则**(可临时生成、可学出来,复用 learn 车道)。**频率只能触发"去看看这一类到底是啥",绝不能直接当"扔掉"的理由。**
> **铁则:量大 ≠ 可以不研判**。事情多就按【类】研判(一类看一次、建规则复用),而不是按百分比盲扔。频率触发调查、内容决定去留;去留规则永远来自内容判断,不来自计数阈值。
> **落实**:①移除/停用一切"按百分比免疫丢弃"的路径(2%→25% 那个补丁不是终点);②改为"频率高的取值/形态 → 触发按内容(请求+响应)研判该类 → 判为噪声则建内容过滤规则(临时/学习),判为真事则照报";③规则要可见可审计(建了哪条、按什么内容判据、拦了多少),不静默。守铁律:判据是请求/响应的结构化形态与产物,不是自然语言关键词匹配。

下面几条是次要的摄取/端点配套(在"按内容研判"落地后仍适用):

1. **摄取跟上流**:pull / 摄取环必须能把速率追到 ≥ 流的产生速率(拉够批量 / 拉够频率 / 游标别空转),让 `funnelA` 覆盖趋近整条流,而不是卡在 ~8%。判据是结构量(funnelA vs 已产生量的差、backlog),守铁律。
2. **主修 · 端点公平**:多地址时轮询要公平(别把摄取预算全砸在一路上饿死其余),按结构量(各端点 pull 游标进度 / 待摄量)调度。
3. **保留(正确性加固,不是根治)**:窗口末尾有积压→判完再收口 / 不静默丢;每分钟判读有不被反压钳到 0 的下限——这两条对,留着,但不是 #4 的根(根在摄取)。
4. **u-lm2 精度崩**单列观察:若复现,查是判读提示 / 阈值问题还是纯模型方差;别为它牺牲召回。

### 验收

低速(~3 条 / 秒)长时盯守:摄取覆盖趋近 100% → **召回 ~100%、零丢失**;5 个端点召回均衡(不再死盯一路);高速流:召回明显抬升 + u-gm2 那种冷启动停摆不再出现。
