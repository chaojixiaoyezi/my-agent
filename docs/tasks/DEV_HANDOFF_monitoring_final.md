# 交接(最终收尾):盯守研判能力剩余问题清单 + 三轮复测证据

> 这是【领域无关】的通用数据研判能力问题,全程用中性视角,别往任何专业领域套。
> 前三轮的详细诊断见 `DEV_HANDOFF_monitoring_retest_recall.md`,本文是收尾总账 + 剩余问题。

## 一、三轮独立真机复测证据(去敏,只留指标)

| 轮次 | 引擎抬到率(surface) | 抓取率 | 报准 | 接管 churn | 头号瓶颈 |
|---|---|---|---|---|---|
| R1(基线) | ~40% | 32% | 47% | — | 引擎在模型看到前就丢真事 |
| R2 | 72% | 56% | 83% | respawn=3 | surface 漏 + 接管 spool 孤儿 |
| R3(本轮) | **92%** | 54% | 88% | 0~1 | **消费吞吐(spool 积压)** |

测法(每轮一致,可复现):5 个中性数据源的事件流、正常量、`since=0` 读存量、真/假都返回 200 类
状态、区别只在响应正文措辞、真事带某固定标识但该标识上几百比一是"看着像其实没生效"的迷惑项、
答案键在沙箱外(agent 够不着)。**每轮都换一批响应措辞防硬编码**(R2 一套、R3 又一套,连上一套的
词都不留);三轮报准都靠"换措辞后照样判对"坐实模型是真读语义、没背固定串。

**三轮进展一句话**:引擎"抬取/surface"这条主线已从 ~40% 修到 **92%**——R1/R2 的头号病根
(引擎在模型看到前丢真事)**基本解决**;报准从 47% 到 88%。但抓取率始终卡 ~54%,因为瓶颈
逐步从"引擎丢"转移到了"消费吞吐"。**下一棒该攻消费吞吐,不是再修 surface。**

## 二、剩余问题(按优先级)

### P1【头号】消费吞吐:抬得出来、消费不掉
surface 到 92% 了,但子代理判读/上报的速度**追不上抬取速度** → 已经 surface 的真事卡在 spool
缓冲区里没人消费。R3 实测:5 个已抬取的真事卡在 spool 未被消费,给了额外时间、还有多个 RUNNING
子代理也没补报;而且**有子代理 DONE / CANCELLED 停了,却把自己 spool 里的待判积压留着没清**。
- 这不是"候选丢了"(你上棒的 at-least-once 保证了不丢,不像 R2 变孤儿)——是**光不丢不够,
  得有人及时把它消费掉**。
- 修向:① 子代理停止(DONE / 收尾)前,**必须先把自己 spool 里的待判候选消费完**,或显式移交继任者;
  ② **"spool 还有待判积压"本身就是"未完成"的硬信号**,有积压时不许判 DONE;
  ③ 消费吞吐要跟得上抬取——抬取快了就该多派判读并发 / 提高每拍消费量 / 让抬取等消费(背压),
  别让 spool 单向只进不出。

### P2 宿主级进程重启后接管停摆
把整个服务进程重启(宿主级杀)后,重新派发的子代理**卡在 PENDING 长时间不恢复**、数据源游标
冻死、没人重新驱动它们(唤醒机制只驱动了一部分 owner / 任务,漏了在盯守的这个)。你上棒修的是
"同进程内换 lane 的接管"(那个验过好了),**没覆盖"整个进程重启后重新驱动在册子代理"**。
- 修向:进程重启后,正在盯守的 owner 名下**在册(PENDING / 未完成)的子代理要被唤醒机制重新
  驱动续跑**,不能只驱动一部分就不管了。

### P3 残留少量抬取漏(次要,P1 修完再量)
个别真事引擎仍没抬(多是刚冒出来还没轮到)。规模已很小,先修 P1——有些"没报"其实是 P1 的
积压未消费,不是真没抬;P1 修完再量真正剩下没抬的有几个,别对着虚高数字过度加抬取。

### P4 判读地板(不是 bug,别死磕)
把真事【一条一次】单独喂模型,判对约 **83%(15/18)**,对照迷惑项 2/2 正确不报。少数边界案例模型
判不稳(**非确定性**——同一条时而判成、时而判否)。**这不是管道 bug,是边界案例本身判读有方差**——
靠"存疑倾向于报"的召回优先策略兜就行(你已软化过一票否决,方向对);**别为它加固定规则、
别当 bug 死磕**(加了违反铁律、且换料就崩)。

### P5 长期(超本棒范围,记着别丢):学一次、长期复用
现在每次新来一种数据源都要现学判据。长期方向是把"喂几个样品学出来的判据"存成一份可复用资产、
按结构相似度检索命中——相似数据源学一次、几个月不忘、不重学。零件都有(学判据 / 相似度),
没拼成闭环。**本棒不用做,只是别让它丢了。**

## 三、自测(隔离环境 + 中性料 + 补两个场景)

- 中性料:接口返回 200 OK 但正文说没真生效(如 `{"result":"rolled_back"}` / 已超额丢弃 /
  未实际入账 / 命中缓存未执行)。5 个源、真事稀(约 1/100~1/1000)、真假只在正文措辞、`since=0` 读存量。
- **重点补两个场景**:
  - **消费压力**:让抬取量持续大于单个子代理的判读速度,验证 **spool 不单向堆积、真事最终都被
    消费上报**(而不是卡在缓冲区),且子代理停止前 spool 清空。
  - **进程重启**:盯守跑到中途把整个服务重启,验证**重启后在册子代理都被重新驱动续跑、零停摆**。
- 验到抓取率真上去(消费不积压 + 重启零停摆)再交回测试方独立复验。

## 四、守约

- 别碰测试方的 192.168.1.9 / 192.0.2.10(只读查看可以,严禁改动),自己另起隔离环境。
- 本地绿 ≠ 真机过,别自称"真机通过";真机由测试方独立复验,**会用又换一批措辞的料**——任何
  硬编码固定串的解法都会当场失灵。
- 铁律:去留 / 判据只用结构化信号(计数 / 状态 / 产物 / 请求响应的结构化形态)、禁自然语言关键词
  匹配;但当结构本身分不开真假时(区别只在正文措辞),不能用结构规则(含固定词黑名单)替模型
  做去留决定,必须把事递到模型手里判。

## 五、开发方回执(第四棒,P1/P2 已修,待测试方独立复验)

P1(消费吞吐)与 P2(进程重启停摆)已按上述修向完成机制层修复,详细根因与修复清单见
`evidence/monitoring_retest_recall/06_consumption_restart_fixes.md`。一句话:

- **P1**:①②子代理/主代理两条收口路都加了「spool 有未判完积压 → 不许体面收工」的闸
  (子代理不 ready 继续跑;主代理一次性打回,双出口不死锁);③「窗口走完但积压未清」的
  死岗现在照常补清账岗、排期自愈从 owner 级改 per-lane、终态 run 的盯守排期在账没清完前
  不再被调度器退休(修「每次 DONE 都把自己唤醒链埋了」的结构洞)——spool 不再单向只进不出,
  消费链断了必有人接,直到积压清零或显式 close。
- **P2**:磁盘发现口径加「在册未完成子代理 run / 未盯完 watch 路」两项事实(只有这两样的
  owner 重启后也会被周期重扫捞回、名下 supervision 照常跑);launching/running 启动残留
  加宿主硬死亡判活(pid/心跳/时效),supervision 回收时顺手清残留——重启后 PENDING 复活
  链不再被冻结记录挡死,游标随接管消费自然解冻。
- 隔离自测(未碰 .9/.10):handoff 三节的两个场景各建一台,均 PASS 且带修复前对照
  (消费压力:峰值积压 6~7× 口粮→最终归零、旧判定 0 建岗;重启:旧口径 0 捞回/旧判活
  0 复活 → 新链路全恢复)。零硬编码、零关键词判断,判读判据未动(P3/P4 按嘱未碰)。
