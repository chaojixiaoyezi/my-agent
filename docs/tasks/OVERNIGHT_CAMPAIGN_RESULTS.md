## 0. R4 复测 + 上线(盯守研判能力收尾棒)

- 开发方 R4(commit 49d1a09b)修 P1 消费吞吐 + P2 进程重启,单测 1214 过、隔离台+控制组坐实。
- **我独立真机复测(1.9,v3 第三套换措辞防作弊)**:报准 **100%**(v3 料照样判对=真读语义没硬编码)、
  引擎抬取 82%。**但抓取率仍 ~36%**:多源 surface 快过真 MiniMax 判读吞吐→已抬真事卡 spool 慢慢消费
  (不丢、但有限窗内到不了天花板);P2 进程重启后 **2/5 源恢复、3/5 仍卡**(比 R3 全卡好一半)。
- **判定**:R4 是净正向机制修复(候选不丢/停前不弃/重启部分复活),无正确性回归、无精度回归 →
  **已合 main(8776f5b4→49d1a09b)、推 origin、部署 1.10(网关+飞书 WS 正常)**。
- **遗留(头号)**:监控**消费吞吐天花板**——LLM 判读速度追不上多源 surface,是模型/规模层,非机制;
  P2 重启恢复只做到一半。跑间方差大(11–54%)也印证吞吐主导。

- **my-agent 产出**:分析报告(规模统计+类型分布+真正生效事件识别),**报出 19 起,19 起全对、

## 4b. 5 API 流监控(逐条汇报,记延迟)

**读法一:3 条/s 每源(=15/s 总)——监控硬崩(跑 36 分决定性停,止损)**
- 真事 26、抓到 **2**、瞎报 **115**、抓取率 **8%**;延迟中位 **~977 秒(16 分)**(n=2)。
- 瞎报集中在 C/E 两源(96/120),子代理疯狂 churn(16 状态 7 接管)。
- **判定**:15/s 超出 LLM 看守吞吐(经验容量 ~5–25/s),监控**过载崩溃**——非但延迟高,还
  狂报垃圾、真事几乎抓不到。继续跑 3h 只会烧 MiniMax 产垃圾(监控已崩、延迟样本也不增),
  故决定性停。

**读法二:3 条/s 总(=0.6/源)——即便低速率也报不出真事**
- 跑 26 分:真事 11、抓到 **0**、瞎报 4、延迟 **n=0**(没一条真事被报出)。
- 真事被 surface 进 spool 却因判读/消费太慢**报不出来**(R4 的老病:候选不丢但消费不掉),
  上报延迟实测 **>20~26 分甚至报不出**。

**结论**:监控的"逐条汇报延迟"由 **判读/消费吞吐** 决定,且在本轮真机上**很差**——低速率真事卡
spool 报不出(延迟极高)、高速率(15/s)直接过载崩。这与 R4 头号遗留(消费吞吐天花板)完全同源:
**R4 修好了"候选不丢"的机制,但没提判读速度,所以有限窗内真事仍报不出/延迟极高。** 这是下一棒
最该攻的(判读并发/更快模型/候选收窄)。

## 跨测试要点(不足/问题总账)

1. **终端应用 无头(--print)在本环境对实质任务不产出**——Test1/2 对照缺 终端应用 臂(小文件测试
   却成,是 headless 模式限制)。
2. **监控消费吞吐天花板**(头号)——LLM 判读速度 < 多源 surface 速率,recall 被压;R4 修了"不丢/续跑"
   机制但没提判读速度。治本靠更多判读并发/更快模型/更狠的候选收窄。
3. **P2 进程重启恢复只到一半**(2/5 源)。
4. **my-agent 编码完整度**不及 会话运行时(核心强、外围欠)。
5. **背景任务易被系统 kill**(并发多时)、**两测试机网络隔离**(数据经 Mac 中转)、**testbox 无 rsync/tar**
   ——运维摩擦,已用 scp+python 解包/减并发/单机同置绕过。
