## 1. 【头号 · 越修越差】B 摄取召回:真机端到端反而退步

### ① 上次修了啥
为治"结构预筛只筛出约 1/4 语义目标",加了三件套:**audit 抽检车道**(对预筛放过去的常态流按结构化规则抽样,让模型复判)+ **反馈学习**(模型确认一条"预筛漏的真目标"→ 把其结构特征反馈给预筛、以后自动抬同类)+ **自适应倾斜**(往预筛弱的源多抽)。**离线台测出 0%→68%**。

### ② 这次问题
真机 3 小时盯守(5 路流、~250 条/秒、真目标 ~1/3000、共 891 个):**"筛"这层确实抬得更多了,但端到端"逐条报出的真目标"反而崩了**——从上一版的 156 掉到 18-29,还冒了 1 个误报。

### ③ 证据(round2 vs round1,同 sim 同参)
| | round1(无 B) | round2(有 B) |
|---|---|---|
| funnel A 抬候选 | 175 | u-r1b **252**(更高 ✅) |
| **funnel B 逐条报出** | **156** | u-r1a 18 / u-r1b **29**(崩 ~6 倍 ❌) |
| 误报 | 0 | u-r1a **1** |
| 抽检/反馈车道 | 无 | audit_sample 4000+/用户、confirmed_target_similar 300+(反馈车道真活) |
- funnel B 增长速率:round2 比 round1 慢 4-6 倍(每 30 分钟只涨个位数-十几)。

### ④ 排除的变量(确认"不是这些")
- **不是 agent 个体方差**:round1 是"一好一坏"(一个 156、一个停摆);round2 是**两个用户都低**(18、29)→ 共性 = flood,不是个体差。
- **不是收割滞后**:收割游标全程跟得上源 seq(都在 ~31 万),harvester 没落后。
- **不是送达机制(§7)坏**:判读几乎 0 误报、findings 逐条落账正常——送达链是通的。
- **不是数据变难**:同一个 sim、同参数、同种子结构。
- → **就是 audit 抽检量太猛,把主代理判读吞吐淹了。**

### ⑤ 根因
**离线台只量了"筛"(funnel A),没建模"模型判读吞吐上限"。** 真机上 audit 每分钟抬出上千候选丢给模型,模型有限的判力被**随机抽检噪音(绝大多数非目标)占满**,真目标反而排不上队、报得更少。**"多抬 ≠ 多报"** —— 抬得再多,判不过来就是白抬,还挤掉了本该报的真目标。

### ⑥ 底座修法(通用 / 非限制)
1. **抽检率按"实际判读吞吐"动态封顶**:结构化观测主代理判读速率 / 候选队列积压,**抬进来的候选量绝不超过它判得完的**(积压高就自动降抽检率,判得快就升)。这是纯结构反馈调节,不写死具体数。
2. **反馈车道优先于随机 audit 车道占判力**:把有限判力**先给"像已确认真目标的"高价值候选**(confirmed_target_similar),随机 audit 只用剩余额度。别让随机噪音把判力占满。
3. **目标口径改对**:验收看的是 **funnel B(逐条报出真目标)真的上升**,而不是 funnel A(抬候选)上升——上次就是只盯了 funnel A 才误判"修好了"。

## 2. A2 耐力:机制在、但**从没触发**

### ① 上次修了啥
`coverage_incomplete_rework`:模型若**声明了功能清单 `coverage.targets`** 却没逐项做完 → 打回续做;并加了 guidance"大体量任务先立功能清单"。

### ② 这次问题
大体量建站任务,主代理**根本没声明功能清单**→ A2 的打回从没触发 → 白搭;代码量反而掉一半(round1 4692/5456 → round2 **1748/2279**),终端应用 反超(5048)。

### ③ 证据
两个用户的 `coverage.targets` 计数 = **0**,`[coverage-incomplete-rework]` 打回标记 = **0**(从没 fire)。

### ④ 排除的变量
- A2 机制本身单测过(能正确打回)——问题**不在机制,在入口**:它挂在"模型自觉先立清单"上,而**模型不稳定地立清单**(这次俩都没立)。
- 代码量下降本身是方差(见 §3),但 A2 因没触发**完全没起到兜底作用**。

### ⑤ 根因
**A2 的抓手("先声明清单")本身就是个不稳定的模型行为**——用一个不稳的行为去兜另一个不稳(耐力),等于没兜。

### ⑥ 底座修法(通用 / 非限制)
大体量构建任务**自动派生功能清单**:从任务需求里**结构化拆出待实现的功能项**(如按需求中列举的功能点/模块生成 coverage items),不靠模型自觉声明;然后 coverage-rework 就有抓手、逐项核对到位再收口。**仍非硬性行数限制**,只是"你要做的这些功能,做完没"。

## 3. A3 方差:分析类压住了、**代码/数据类仍"时好时坏"**

### ① 上次修了啥
关键步骤加**结构化自检 + 有界重试**,压"同任务时好时坏"。

### ② 这次问题
- **分析类:改善 ✅**——Test3 两个用户都覆盖 5/5(round1 有个只做 1/5)、深度接近、方差小了。
- **代码/数据类:没改善 ❌**——Test2 两轮代码量差 2-3 倍;Test4 大文件**一个用户全扫答 3/4、另一个 0 脚本直接空手**。

### ③ 证据
Test2:1748 vs (round1)4692;Test4:u-r4a 写 0 脚本、交付流 0 字(没干活),u-r4b 写脚本、答对 3/4(总额/最高类/异常账户对,漏了超阈值笔数)。

### ④ 根因
自检+重试的覆盖面**只惠及了分析类的"覆盖度"**(有没有把 N 个都分析),**没覆盖代码/数据类的"完成度/正确度"**(功能做全没 / 该算的算全没 / 有没有真动手)。

### ⑤ 底座修法(通用 / 非限制)
把自检+重试的适用面**扩到代码/数据类**,用结构化判据:
- 数据分析类:声明要回答的问题项都答了吗?该跑的全量扫真跑了吗(有无脚本/工具痕迹)?——没到位续做。
- 代码类:与 §2 的自动功能清单打通(功能项逐项做完没)。
- 目标:让"该做的做了吗"由**结构信号**判,不靠模型自觉。
