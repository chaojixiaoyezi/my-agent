# 能力包使用说明

这份说明讲怎么在 my-agent 里使用「能力包」：它是什么、怎么装、装好后 my-agent 怎么找到并使用、怎么自己做、安全边界在哪。界面细节以你实际看到的为准。

## 一、能力包是什么

能力包是一份**只含内容**的插件包：把一套方法、流程、模板和脚本整理成带版本的专业资料包，装好后 my-agent 在需要时能自己找到，并按包里的方法做事。它不包含可执行程序——不启动进程、不建运行环境，里面写的脚本只是文本资料，my-agent 要用时通过正常工具执行。

和几个相近概念的区别：

| 概念 | 是什么 | 和我的关系 |
| --- | --- | --- |
| MCP | 连接外部服务的协议 | 和 MCP 无关，能力包不连外部服务 |
| 插件 | 可装卸的命令、工具、面板等外部装备 | 插件是"装备"（可能带进程）；能力包只是"资料"，不装任何装备 |
| Skill | 可独立复用的单项方法 | Skill 是单个方法；能力包是一整套可版本化的方法集合 |
| 能力包 | 可独立发现、版本化和验收的专业能力集合 | 本说明的主角 |

适合装什么：任何"一套完整做法"都行——例如「从既有故事整理成可审阅的短剧结构」的方法集、一份「数据核对与报告」的流程加模板、一套「会议纪要整理」的规范加示例。不限定行业。

小例子：你有自己的一套写报告流程（一个方法说明 + 几个模板 + 一个核对脚本），把它打包成能力包装上；下次让 my-agent 写同类报告时，它会在需要时找到这份包，按里面的流程做。

## 二、怎么装、启用、停用、更新、回退、卸载

所有操作都通过 `/plugins` 命令（**TUI 终端与飞书等 IM 共用同一个插件服务；查看按当前用户权限，安装、配置、启停、更新和卸载仅管理员**）。在 IM 私聊中管理前，先通过已有的 `/admin` 验证管理员身份；群聊或正文里声称自己是管理员不会获得权限。命令形式：`/plugins install <本地包路径>` 这类，完整动作如下：

| 动作 | 做什么 | 注意 |
| --- | --- | --- |
| `/plugins install <包路径>` | 安装本地包 | 安装后**默认停用**，不会自动生效 |
| `/plugins enable <插件ID>` | 启用 | 启用时复验包内容和配置 |
| `/plugins disable <插件ID>` | 停用 | 停用后保留安装包，可再启用 |
| `/plugins update <插件ID> <新包路径>` | 更新到新版本 | 旧包先停用、验证并提交新包，然后显式重新启用 |
| 回退到旧版本 | 用**旧版本包**再走一次 update | 明确指定旧版本包，不会自动猜"上一版本" |
| `/plugins confirm <单号>` | 确认 my-agent 准备好的安装单 | 装上她自己做的包并启用；同一张单只执行一次，只有她最后给的那一行有效；联网和读写别的目录仍要你另外确认 |
| `/plugins revert <包名>` | 把 my-agent 做的包退回她做的上一版 | 先只预览会退到哪一版、会不会运行程序；照回执发带版本的那一行才执行，重发不会多退 |
| `/plugins remove <插件ID>` | 卸载 | 停用并卸载，**保留你的任务产物** |
| `/plugins configure <插件ID> --file <JSON>` | 保存停用包的配置 | 完整替换，不是打补丁 |
| `/plugins status <请求编号>` | 查询一次管理请求的结果 | 网络/后台请求不确定时用它查 |
| `/plugins list` / `info` / `help` | 查看 | 列出已安装、看说明、看动作参数 |

小例子：你拿到一个能力包文件 `report-pack.zip`，管理员在 TUI 或已绑定管理员的 IM 私聊里 `/plugins install report-pack.zip` → 看到安装成功但默认停用 → `/plugins enable report-pack` → 按回执核对启用结果。想换新版就 `/plugins update report-pack report-pack-v2.zip`；想退回旧版就拿旧包再 update 一次。路径是宿主机器上已有且获准访问的本地路径，不是 IM 附件自动下载地址。

插件包若带可执行文件或使用外部解释器，首次启用只给程序、文件摘要、解释器与风险预览，**不会启动程序**；用户本人核对后原样发送回执里的 `/plugins enable <插件ID> --confirm <确认码>`。包内容、平台或解释器变化后旧码失效。TUI 和 IM 使用同一确认规则；普通工具审批仍受现有权限和确认通道限制，纯文本 IM 不提供 TUI 本地插件面板。

注意：
- 更新不是无缝热升级：旧任务不会在停用后悄悄改用新版。
- 卸载只删安装记录，不会删你任务里已经生成的东西。
- `/plugins` 和 `/plugins#` 在 TUI 与已绑定管理员的 IM 私聊里都能用，回执是同一份纯文本。

### 能力包专用命令 `/plugins#`

能力包也可以不记插件命令，直接用 `/plugins#`（插件仍用 `/plugins@<插件ID>`，两者互不串）：

| 命令 | 做什么 | 注意 |
| --- | --- | --- |
| `/plugins#` | 列出全部能力包 | 写版本、启用状态、是不是 my-agent 自己做的；她做的会另起一行写她声明的来源与许可证（原文，宿主未核实） |
| `/plugins#<包名>` 或 `/plugins#<包名> 查看` | 看详情 | 写适用范围、关键词、带不带检查程序和可以用的管理命令 |
| `/plugins#<包名> 启用` / `停用` / `删除` | 启用、停用、卸载 | 和 `/plugins enable`、`disable`、`remove` 是同一件事，只有管理员能做 |
| `/plugins#<包名> 退回` | 看会退到她做的哪一版 | 只预览；照回执最后一行发 `/plugins#<包名> 退回 <版本摘要>` 才执行，重发不会多退 |
| `/plugins#<包名> 安装 <单号>` | 确认她准备好的安装单 | 照她给的那一行原样发；单子上的包名对不上会被拒 |

## 三、装好后 my-agent 怎么发现和使用

能力包启用后，my-agent 不是每个任务都翻一遍所有包，而是按任务自动找到相关的：

- **按任务推荐（默认开启）**：开关 `enable_capability_package_recommendations`（默认 `true`）。当轮任务和已启用且已授权的包相关时，my-agent 会看到这些包的摘要并决定是否按包里的方法做。"相关"指你的话里出现了包的名字或它声明的某个关键词（整个词出现才算；只撞上说明里的常用词不算），所以做包时关键词要写用户会说的短词，比如"短剧""分镜"。只展示摘要，不自动读正文、不额外调用模型。关闭后，推荐消失，但手动检索和显式读取仍然可用。
- **一次选择（默认关闭）**：开关 `enable_capability_package_selection`（默认 `false`）。开启后，每个新主任务开始前，my-agent 会用一次主模型从已授权的包里选一个（或空选），然后把选中包的入口作为参考资料带进任务。开启会**增加辅助模型用量、等待时间，并留下普通任务记录**；不开就用上面的按任务推荐。

小例子：默认设置下，你派一个新任务「按报告流程写一份周报」，my-agent 会看到相关的报告能力包摘要；如果包里方法合适，它会读入口和需要的模板照着做。关闭一次选择开关不影响这个流程。

### 装好后怎么读包里的资源

my-agent 通过 `skill_search` 这个检索工具读能力包，实际链路是：**读入口文档 → 在包里找模板/脚本 → 把脚本复制到工作区 → 运行**。分步说明：

1. **找包**：`skill_search(action=search, query=...)` 按任务需求检索；结果里每个包带 `package_id`，后面几步都要用它。任务推荐里出现的包摘要同样可以用。
2. **读入口文档**：`skill_search(action=get, package_id=<包ID>)` 读取包的入口文档（如 `CAPABILITY.md`），先看整套方法怎么用。注意：能力包不能用 `skill_id` 读，必须用 `package_id`。
3. **在包里找资源**：`skill_search(action=search, package_id=<包ID>, query=...)` 检索包内的模板/脚本；结果里的 `next_read` 可以原样作为下一步的参数。
4. **读具体资源**：`skill_search(action=get, package_id=<包ID>, resource_path=<包内相对路径>)`。包内资源**不是工作区文件**，不能用 `read_file`/`find_files` 去猜安装位置，必须用 `package_id + resource_path` 读。
5. **把脚本放进工作区**：需要运行时，把返回的完整 `source_ref` 原样传给 `write_file(source_ref=...)`，写到工作区里自己选的目标路径。不要手抄或改写脚本内容；这一步只是复制，不会执行资源。
6. **运行**：脚本只是文本资料，执行仍走你平时允许的命令工具，且只在你授权的范围内运行。

小例子：my-agent 找到「会议纪要整理」包 `meeting-notes-qa-pack` 后，先 `get` 读入口文档，再 `get` 拿 `scripts/summarize.py`，用 `write_file(source_ref=...)` 把脚本原样复制到工作区，然后 `run_command` 运行它核对纪要。

### 新任务才会用到新版本

- 一个任务**开始后**用到的包版本会被固定住：包停用、卸载或换了新版，正在进行/已开始的任务仍然用当初固定的版本，不会中途换包，也不会悄悄改用新版。
- 想用新版本的效果，就在**新任务**里重新开始（或让 my-agent 在新任务里重新读包）。
- 已固定的版本被停用/删除后，旧任务只会看到"这个包不可用"的提示，不会拿别的包顶替。

小例子：你在旧任务里用了报告包 v1，这时报告包升级到 v2 或暂时停用，旧任务继续按 v1 跑；下一个新任务才用 v2。

## 四、派子代理时怎么把包授权给它

主代理可以把能力包授权给子代理使用：

- 派工参数 `allowed_skills` 里填 `capability:<包ID>`，例如 `capability:report-workbench-a`。
- 批量派多个子代理时，可以逐项在 `item.allowed_skills` 里分别指定；没单独指定的项沿用整批的默认列表。
- **只在 goal 或输入材料里提到包名不算授权**，必须通过 `allowed_skills` 显式传入；子代理没拿到授权时，可以按正常能力申请流程向父级申请同一个包。
- 子代理沿授权读取的版本与主任务固定的是同一个版本，孙代理只继承父级的授权，不会自己扩大。

小例子：你让主代理"用报告包做一份周报，分一部分给子代理整理数据"，主代理派子代理时在 `allowed_skills` 里填 `capability:report-workbench-a`，子代理才能读报告包里的模板和脚本。

### 子代理没拿到授权时先申请，不要直接读包

没有包授权的子代理直接调 `skill_search` 读这个包会失败，错误码固定为 `SKILL_SNAPSHOT_UNAVAILABLE`（当前轮快照里没有这个包，读不到正文），恢复建议就是去申请能力。正确做法是走"能力申请 → 父级裁决"两步：

1. 子代理调 `capability_request` 提交申请，`requested_skills` 里填 `capability:<包ID>`（例如 `capability:report-workbench-a`）。注意：裸包名、包内资源路径都不能代替这个引用，必须写 `capability:` 前缀的包稳定 ID。
2. 父级用 `resolve_capability_requests` 裁决：`decision=grant` 批准，或 `decision=deny` 拒绝；两种都会带着结果唤醒子代理继续跑。批准后，子代理从下一个工作片开始带新权限，重新读包即可。

小例子：子代理整理数据时发现报告包不可用（`skill_search` 返回 `SKILL_SNAPSHOT_UNAVAILABLE`），于是调 `capability_request` 申请 `requested_skills=["capability:report-workbench-a"]`；主代理用 `resolve_capability_requests` 批准后，子代理续跑并成功读到包里的模板。

### 申请被拒会带确定错误码，不会记成"结果未知"

父级批准（grant）时会对申请做安全检查，越界或超范围的申请会**确定拒绝**，回执带错误码，不会再被记成"结果未知"：

- 申请的写目录（`write_roots`）全部落在任务工作区或主代理工作区之外（例如 `/etc/hosts`）→ `PATH_OUTSIDE_WORKSPACE`，未授权。
- 申请的工具、MCP 或 Skill 超出直属父级当前可用范围 → `MISSING_CAPABILITY`，未授权。
- 裁决过程中出现异常 → `TOOL_ERROR`。

被拒绝后子代理会收到明确的拒绝结果（含原因），按现有权限调整方案或交付能完成的部分即可，不需要继续空等授权。

小例子：子代理申请把结果写到 `/etc/hosts`，父级 grant 时回执直接是 `PATH_OUTSIDE_WORKSPACE` 拒绝；子代理看到原因后改写到自己的任务工作区，不再空等。

## 五、自己做一个能力包

项目自带了构建脚本 `scripts/build_capability_package.py`，把一份声明文件 + 一组资源文件打包成能力包 ZIP：

```bash
python3 scripts/build_capability_package.py \
  --declaration 声明.json \
  --files-root  资源目录 \
  --output      报告能力包.zip
```

**声明文件**（JSON）需要这些字段：

| 字段 | 写什么 |
| --- | --- |
| `plugin_id` | 包的唯一标识，例如 `report-workbench-a` |
| `version` | 版本号，例如 `1.0.0` |
| `summary` | 一句话说明这个包是做什么的 |
| `capability` | 包的描述、关键词、入口文档名（`description` / `keywords` / `entry_document`） |
| `files` | 要打进包的资源，每项只写一个 `path`（相对资源目录的路径） |
| `settings_schema` | 配置结构（不需要配置就写空对象 `{}`） |

注意：`capability.entry_document` 指向的入口文档**必须同时列在 `files` 里**，否则构建会失败（构建时校验入口文档属于已声明资源）。

**包的基本结构**：一个入口文档（如 `CAPABILITY.md`，说明整套方法）+ 若干模板/脚本/示例文件。构建时会为每个文件计算内容摘要、统一不带执行权限，然后打包；构建、安装、读取都不会执行包里的代码。

小例子：目录 `report-pack/` 里有 `CAPABILITY.md`（方法说明）、`templates/weekly.md`（模板）、`scripts/check.py`（核对脚本）；声明文件里 `files` 写这三项，`capability.entry_document` 写 `CAPABILITY.md`。跑上面的命令得到 `报告能力包.zip`，再用 `/plugins install` 安装。

## 六、宿主核验（包自带检查程序时，宿主替你跑）

有些能力包自带**检查程序**——一段小的核对脚本，用来判断交付物做得对不对。任务里固定住这种包时，宿主会自己跑这些检查，不靠 my-agent 说"我检查过了"。

- **写完就查**：my-agent 用写文件工具（`write_file`、`edit_file`、`apply_patch`）写出包要求的交付物后，宿主马上用包里**原版**的检查程序查一遍，把结论摘要附进工具回执；my-agent 看到问题可以接着改。
- **收尾再查**：一轮快结束时（my-agent 不再调工具、准备给答复时），宿主再统一查一遍：这轮写过/改过的交付物、任务开始时给你的输入原件有没有被就地改、该交的必需交付物有没有交。
- 检查程序只从"已安装、启用时确认过、按内容摘要钉住"的包里读原版；运行时在沙箱里跑——**断网**、交付物只读、只写临时目录。环境里没有可用沙箱就不跑，并说明原因。
- 结论以宿主为准：my-agent 自己声称"已验证"不算数；它也不能复制、改写或自己重写检查程序来代替。

小例子：你让 my-agent 用报告包做一份周报，它把 `output/weekly.json` 写进工作区。写出的这一刻，宿主就跑了报告包里的原版检查程序；这一轮结束时你会收到一句 `宿主检查（report-workbench-a 1.0.0，原版 scripts/check_report.py）：output/weekly.json 有效，警告 0 条。`——这是宿主自己跑出来的结论，不是 my-agent 的自我评价。

### 开关在哪、谁能改、什么时候生效

- 开关名：`capability_pack_host_verification_enabled`，写在能力配置里，**默认关闭**：

  ```yaml
  capability_pack_host_verification_enabled: false   # 默认；改成 true 并重启 Gateway 后才生效
  ```

- **只有你能改**：经 `/settings`（管理员）或直接改配置文件；my-agent 自己打不开。
- **改后重启 Gateway 生效**。关着的时候，上面这些检查一步都不会发生。
- 就算开关开着，包含检查程序的包在**启用时仍要单独确认一次**（先看到检查程序的身份、内容摘要、运行方式和参数，凭确认码启用）；确认通过才会用它来检查。

小例子：管理员在 `/settings` 里把 `capability_pack_host_verification_enabled` 打开并重启 Gateway；从下一轮开始，固定了带检查程序包的任务才会自动核验。没打开时，包照常能用，只是没有宿主核验。

### 打开前要满足的三个前提（已全部完成，随下一版发布上线）

打开这个开关等于允许宿主自动运行包里的检查程序，所以定了三条前提，都做到才算正式能力：

1. **核验账本受宿主只读保护**：检查记录（"核验账本"）放在宿主托管的地方，普通方式改不到。
2. **主代理和子代理都写不进账本**：不管主代理还是子代理、用文件工具还是命令，都只能读、写不进去。
3. **`/stop` 能打断检查程序**：你按 `/stop` 时，正在跑的检查程序也能被打断。

这三条现在的状态：**三条都已做完**，在集成分支 step17i 里，随下一版发布上线——宿主只读保护（be 的 H3）把账本所在目录设成对模型只读，块 4 的回归用例证明主代理和子代理、文件工具和命令都写不进去（原先“命令的工作目录和写根都在任务目录外时保护够不到本任务账本”的缺口已修，账本保护改成只认宿主记下的任务目录）。**第三条 `/stop` 打断**（块 6a）也接上了：按下 `/stop` 后宿主不再起新的检查程序，正在跑的那个先收到终止信号，宽限期（默认 2 秒）内没退就强制结束，被取消的回合不会因此返工。三条全部就绪；随下一版发布上线之前，这个开关仍只用于开发验证，不算正式功能。

小例子：你在任务中途按 `/stop`，希望马上停手。第 3 条前提说的就是这种时候——正在跑的检查程序也会一起停（块 6a 已接上）：按下去之后不再起新的检查，正在跑的那个先收到终止信号，通常很快退出，最多等一小段宽限期（默认 2 秒）就强制结束。

### 你会看到什么

一轮结束时，宿主会发一条提示告诉你检查结论，和普通回复分开展示：

- **TUI**：一条灰色系统行。
- **飞书等 IM**：以 `【提示】` 开头的几行，放在回复正文前面，中间空一行。

提示只讲三类事实（每类最多 4 条，太长会截断；下面用代码里的真实文案举例）：

1. **检查结果**：
   - 通过：`宿主检查（report-workbench-a 1.0.0，原版 scripts/check_report.py）：output/weekly.json 有效，警告 0 条。`
   - 有问题：`宿主检查（report-workbench-a 1.0.0，原版 scripts/check_report.py）：output/weekly.json 无效，错误 2 条（MISSING_SECTION、BAD_DATE），警告 1 条。`
   - 没查成：`宿主检查（report-workbench-a 1.0.0，原版 scripts/check_report.py）：output/weekly.json 未检查（verifier_timeout）。`
2. **输入原件被就地改了**（只对声明要保留原件的包）：`宿主检查：任务开始时的输入 data/source.csv 被就地改了（原件副本已保存）。`；没留到副本时，括号里是"没有原件副本"。
3. **必需交付物缺失或打不开**：`宿主检查：report-workbench-a 要求的交付物 weekly_report 没找到符合 output/** 的文件。`；写了但打不开时，末尾是"写出了但打不开"。换了文件名（不匹配包声明的路径模式）也归在这条里，提示会写明要求的模式，模型照它改名后重新收尾即可。

如果这一轮没有正常收尾（比如被中断），提示末尾会加一句：`本回合没有正常收尾，上面是写入时的检查结果。`

小例子：你看到 `【提示】宿主检查：任务开始时的输入 data/source.csv 被就地改了（原件副本已保存）。`，就知道 my-agent 直接改了你给的原文件——它应该把改动另存成新文件，而不是改原件；宿主已经把原件副本留好了。

### 检查不过会怎样：返工

检查出**错误**时，宿主不会直接判定任务失败，而是把结构化事实（哪个文件、哪个检查程序、几条错误、错误码和位置）发回给 my-agent 让它返工，改完再收尾：

- **交付物检查不过**：最多返工 1 次；只有"错误"才返工，"警告"不返工。
- **输入原件被就地改**：最多返工 1 次——先把原件恢复原样（提示里会给副本路径和 `cp` 命令），把改动另存成一个新文件，并在答复里写明新文件路径。
- **必需交付物缺失或打不开**：最多返工 2 次。
- 三类各自计数；同一轮里同时出现就合成一条提示，顺序是：输入原件 → 交付物存在 → 交付物检查。
- 如果这次用户只要审阅、不要交付物：my-agent 在答复里说明即可（返工提示里就是这么写的）。
- 返工后还有问题：照常结束，宿主提示照发，检查结论不会被藏起来。

小例子：my-agent 写出的 `output/weekly.json` 被检查程序报"缺 2 个字段"。宿主给 my-agent 一条返工提示（"宿主用钉住的能力包原版检查程序核验了本回合写出的交付物，下面这些仍有错误：…… 请按这些错误码和位置修正交付物，再结束本回合。"）。它改好后再收尾、再查一遍，通过就正常结束；改了还是不过，就带着"无效"的结论正常结束，你会从宿主提示里看到。

### 反复改不对时，写后检查会怎么节流

同一处交付物反复被查出错误时，为了不把时间都花在“每写一次查一次”上，宿主有两个规则：

- **错误尽量一次列全**：给 my-agent 的检查结论最多列 10 条错误（错误码和位置），错误更多时标明还有没列出的；回执里还会提示它把这次列出的问题在下一次写入里一起改完。
- **连续失败 6 次先暂停**：同一个交付物被同一个检查程序连续 6 次写后检查都报错后，宿主暂停对它的写后检查——后面每次写入不再当场跑检查程序（只记一笔“已暂停”），把核对留到这一轮收尾时统一做一次（收尾照常检查、照常返工）。中间只要通过一次就重新计数；别的交付物、收尾检查的结果都不算。

小例子：my-agent 改 `output/weekly.json` 连续 6 次都被检查程序报错（它每次只改一处）。第 7 次写入时，宿主不再当场跑检查，只记一笔；等这一轮收尾时再完整查一次——那次还有错，就照常给一次返工提示。

### 已知限制

- **一个工具都不调的回合查不到**：交付物检查只认"本回合写过/改过的文件"。如果 my-agent 一个工具都没调、直接把内容贴在答复里，宿主没有可查的文件，也就不会触发（这种情况在界面上一眼能看出来）。
- **只在沙箱里跑、断网**：检查程序在沙箱里执行，网络是断的；环境里没有可用沙箱时直接不跑（结论里写明原因），不会退化成裸跑。
- **位置脱敏的代价**：检查程序给的"位置"文字在转给 my-agent 前会先脱敏宿主路径；如果这段位置恰好看起来像本机路径，整条位置会被置成 `<redacted>`，具体位置就看不到了。比如检查程序报的位置是一段 JSON Pointer（如 `/tmp/0`），而本机根目录下正好存在 `/tmp` 这个目录，这条位置就会被整条隐去。

小例子：检查程序报 `location: /tmp/0`（指向它输出里 `tmp` 字段的第 0 项）；如果本机根目录下正好有 `/tmp`，my-agent 只看到 `<redacted>`，得自己按错误码去找位置。

## 七、安全边界

- 能力包和「插件」是两回事：能力包只含内容、不跑进程；会跑代码、能订阅事件或在工具前把关的是**插件**，用法见[插件与安全开关使用说明](PLUGIN_GUIDE.md)。
- **只按声明读取**：my-agent 只能读取包里明确声明的资源（入口文档和 `files` 里列出的成员），不能越界读别的文件；读取时要校验包身份、版本和内容摘要。
- **改动过的包会被拒绝**：每个资源都有内容摘要；包被改动、路径不对、或在停用/重装后拿旧引用读取，都会明确失败，不会静默换读新版或别的包。
- **包内代码不自动执行**：包里的脚本只是文本资料；读取不等于执行授权，真正执行脚本仍走你平时允许的命令工具，且只在你授权的范围内。
- **包里不含密钥**：包不接受账号、任务身份或凭据；打包时不要把自己的密钥、个人路径、对话内容放进去。
- **停用/卸载不删你的东西**：停用只是不再被发现和读取；卸载保留你的任务产物。已经进入对话历史的包内容无法撤回。

## 八、常见疑问

- **为什么装了包却没反应？** 安装后**默认停用**，先 `/plugins enable <包ID>` 启用；另外推荐开关要开着（默认开），并且是"新任务"才会按包做。
- **为什么旧任务还用旧版本？** 任务开始后版本被固定，换代/停用不影响已开始的任务；新任务才用新版本。
- **为什么 my-agent 说这个包不可用？** 包被停用、卸载或版本被换后，旧任务里的引用会标记为不可用，不会偷偷换成别的包。
- **IM 里能不能管能力包？** 可以发 `/plugins` 查看和查询；安装、启停、配置、更新、卸载只允许已验证的管理员。`/plugins@<插件ID> [动作]` 也走同一插件服务，按原业务权限裁决并回纯文本；被拒会带错误码。源码入口于 2026-10-01 接通，真实渠道收发仍需部署后验收。
- **子代理说 skill_search 报 SKILL_SNAPSHOT_UNAVAILABLE？** 说明它没拿到这个包的授权：要么父级派工时的 `allowed_skills` 没传 `capability:<包ID>`，要么它申请后还没被批准。让父级在派工参数里授权，或让子代理走 `capability_request` 申请、父级 `resolve_capability_requests` 批准后再读。
- **父级拒绝能力申请会怎样？** 确定拒绝并带错误码：写目录越界是 `PATH_OUTSIDE_WORKSPACE`，工具/Skill 超出父级是 `MISSING_CAPABILITY`，裁决异常是 `TOOL_ERROR`；不会记成"结果未知"。子代理按拒绝原因调整方案即可。
- **界面和我看到的不一样？** 以实际界面为准；这份说明按 2026-10-01 的 `/plugins` 动作和真实运行观察编写。

### 在本会话接着用已经读过的方法（第 2 步本地实现，待复核部署）

会话沿用以能力包为主，也支持普通 Skill：主会话成功打开后记在本会话，之后目录标“本会话在用”；接着做同类工作沿用原步骤，不相关的问题照常回答。
一次最多保留 5 个方法，每包记最近 8 份资料路径；压缩后的下一轮按原授权和预算带回入口及资料清单，每份资料给原样重读参数，不自动执行脚本。

- `/skills using`：看当前会话在用的能力包和 Skill，包附已读资料数；TUI 与 IM 走同一入口。
- `/skills using remove <名字>`：只去掉本会话的登记；不卸载、不停用、不改权限或任务版本。以后再次成功打开仍会重新登记。
- 管理员用 `/settings set conversation_method_carry_enabled false` 关闭，设为 `true` 再开启，改完立即生效。关闭时不记账、不带回、目录走旧提示，命令回“会话沿用已关闭”。
- 包停用、删除或旧任务的固定版本失效时不会借沿用读取；合法的新任务才使用当前版本。Skill 删除后也不带回。

上述为本地实现说明；真实 TUI/飞书和生产模型尚未验证，部署后的实际验收由集成者进行。

## 九、让 my-agent 自己学、自己装（learnpack）

你看到一个别的领域做得好的 agent（比如写短剧的、写小说的、做字幕翻译的），可以直接跟 my-agent 说"去学一下这个"。她会照内置技能 `learn-external-agent` 的流程做：

1. 读人家的方法、模板、检查清单，学习笔记存成任务工作区里的文件（你隔多久回来、中间重启过，她都能接着做）；
2. 核对许可证：只收 MIT、Apache、BSD 这类宽松许可证的；没写许可证或 GPL 这类的，她会先跟你说明，不收原文；
3. 先查有没有同领域的能力包，有就问你"并进已有的包，还是单独成包"；
4. 默认做成**能力包**（方法、模板、离线小工具）；要联网、要账号、要常驻服务的工具做成**插件**；你明说要内部技能才做内部技能；
5. 打包，然后按你的开关装上，或者把一行确认交给你。

### 两个开关（默认都关，只有管理员能改，改完马上生效）

| 开关 | 管什么 | 打开 | 关闭 |
| --- | --- | --- | --- |
| 能力包自动装 | 她做好的能力包直接装上 | `/settings set capability_pack_self_install_enabled true` | `/settings set capability_pack_self_install_enabled false` |
| 插件自动装 | 她造好的插件直接装上并启用；能力包里的检查程序也跟它走 | `/settings set plugin_self_install_enabled true` | `/settings set plugin_self_install_enabled false` |

- **开着**：她做好就自己装，装完告诉你装了什么（版本由宿主写在回执里）、怎么停用删除退回、怎么关掉自动装。
- **关着**：她做好先问你，给你一行确认（能力包是 `/plugins#<包名> 安装 <单号>`，插件是 `/plugins confirm <单号>`）。你把那一行原样发回去才装；隔多久发都有效，只执行一次。她后来又给同一个包出了新单，旧的那行就作废，免得装回旧版。
- 开关只管"谁来按安装"。装上以后能做什么照原来的权限规则：要联网、读写别的目录或不受限运行时，就算开关开着，她也会停下来把命令交给你确认。
- 她只自动装**她自己做的**包和插件；别处来的还是管理员用 `/plugins install` 装。别处装过的同名包，她不会顶替，会换个包名。
- 管理能力包用第二节的 `/plugins#` 命令；想回到她做的上一版发 `/plugins#<包名> 退回`（插件是 `/plugins revert <插件名>`），宿主先告诉你会退到哪一版，再给你一行带版本的命令，发了才真退。

### 学了同领域的第二个 agent：并进去还是单独成包

比如已经有短剧分场的包，又让她学一个短剧台词润色的 agent。她会先问你："并进已有的 drama-scenes（新增一个方向），还是单独成包？"

- **并进去**：她出一个新版本（比如 0.1.0 → 0.2.0），包里按方向分节，每个方向的来源和许可证分开写；`/plugins#drama-scenes 查看` 能看到两个来源。装不装照旧看开关：关着就给你一行确认。她打包时宿主会提醒她版本号没升、比装着的旧、或者旧方向的文件没带上，她改好再交给你。只能并进她自己做的包，别处装的同领域包只能单独成包。
- **单独成包**：换一个新包名，按正常流程做。
- **并错了**：发 `/plugins#drama-scenes 退回`，宿主先告诉你会退到哪一版，再发它给的那一行就回到合并前。

### 让她把这次的做法总结成内部技能

跟她说"把这次的做法总结一下记下来"。她会把那次的活连同那次用到的相关记忆，交给自学习流水线总结（同一套闸门、版本和回退）。记忆只帮她理解背景，你的偏好、身份这类个人信息按规则不会写进技能；之后删掉或改掉某条记忆，不会自动改已经学到的技能，技能里有不想要的内容用 `/skills learned remove <名称>` 删。边做边说的，这次活做完收尾时总结；已经做完再说的，总结这个会话里刚做完的那次活，她会告诉你总结的是哪一次（写出那次你的提问）。同一次活按你的要求只交一次，再说一遍她会告诉你已经交给总结了；工具用得多的复杂活本来也会自动总结一次，和你要求的那次各算各的。中间重启过会找不到刚才那次，她会照实说。结果用 `/skills learned show` 看，不想要用 `/skills learned remove <名称>` 删，改坏了用 `/skills learned revert <名称>` 退回。自学习开关（`enable_self_learning`）关着时她会如实告诉你。
