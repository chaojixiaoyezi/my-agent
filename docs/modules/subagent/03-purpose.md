# Subagent：初衷和想法

本轮 R06/R07 继续沿原 owner/任务/审批事实：后台主代理派发孩子后，自身正式工作目录要能正常读写，文件工具与 Shell/PTY/后台进程意见一致。父级能力裁决与用户对具体调用的批准各守原语义；无 TUI 的 IM 审批是本轮待接目标，不另建第二套授权账，见 [实施记录](../../tasks/IM_MONITOR_PERMISSIONS_IMPLEMENTATION.md)。

## 初心

让用户少说，但系统不偷懒。用户只说目标时，系统也要自动补上质量标准、证据要求、写入边界和最终收口，而不是把“完成没完成”交给某个 worker 自己判断。

## 服务谁

- 给普通用户：不用学习复杂派工术语，也能得到更稳的多步骤交付。
- 给父会话：有结构化计划、证据和检查清单，能判断 worker 产物是否可信。
- 给开发者和初学者：可以从 Skill、任务结构、测试记录里学习多代理系统怎样控制风险。

## 为什么这样设计

subagent 系统最怕的是“看起来忙，实际不可收口”。因此把收口权交给父级控制：

- worker 可以生产、检查、修复材料，但不能自封最终完成。
- Skill 描述可复用的方法，模型根据当前任务显式选择拆工方式，不固定某一批永久角色。
- 质量契约把“什么算好、什么不能交、必须检查什么”写成结构化信息。
- 最终收口清单在派工前生成，避免事后临时想起要检查什么。

## 不做什么

- 普通任务不进入第二套 workflow runtime；始终继续同一 thread 和 task。
- 第一版不让 worker 直接写最终 `DONE` / `VERIFIED`。
- 第一版不一次性沉淀所有成功样本，只先建立可追加的位置和格式。
